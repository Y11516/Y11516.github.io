SQLi-Labs Less-26

2026年9月28日 SQLi-Labs Web安全 SQL注入 空格/注释符过滤

一、题目信息

  • 题目名称：SQLi-Labs Less-26 (GET - Error based - All your SPACES and COMMENTS belong to us)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 关键字过滤绕过 / 空格与注释符过滤
  • 靶场链接：http://localhost:8081/Less-26/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是在极度苛刻的过滤条件下进行报错注入。页面提示 All your SPACES and COMMENTS belong to us，意味着后端过滤了空格、注释符（-- 和 #），并且在 Less-25 的基础上继续过滤了 and 和 or 关键字。攻击者必须寻找替代语法来重构 SQL 语句。

2. 怎么想（破题思路）

  • 空格被过滤，考虑使用括号 () 包裹子查询，或使用 URL 编码的换行符 %0a 替代空格。
  • 注释符被过滤，无法注释掉原 SQL 末尾的 ' LIMIT 0,1，需要采用手动闭合引号的方式（如 '1'='1）修补语法。
  • and 被过滤，改用 && 替代（在 URL 中需编码为 %26%26）。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：换行符和and被双重过滤导致语法错误

踩坑情况：尝试使用 URL 编码的换行符 %0a 替代空格，并夹带 and。URL：?id=1'%0aand%0aupdatexml(1,concat(0x7e,(select%0adatabase()),0x7e),1)%0aand%0a'1'='1。

失败响应：页面报出 SQL 语法错误 You have an error in your SQL syntax... near 'updatexml(...)'1'='1'。截图底部的 Hint 显示过滤后的结果为 1'updatexml(1,concat(0x7e,(selectdatabase()),0x7e),1)'1'='1。

原因分析：后端对 %0a（换行符）进行了统一清洗，直接将其删除了。同时，and 关键字也被匹配并移除，导致 1' 和 updatexml 粘连在一起，select 和 database() 也粘连在一起，SQL 语法彻底崩溃。

改进方式：放弃使用空格和 and。改用 %26%26（即 &&）作为逻辑连接符，因为它两端不需要空格，且不被黑名单匹配。对于函数与参数之间的粘连，利用括号自带的语法分隔作用，写成 select(database())。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

直接在浏览器地址栏输入：

http://localhost:8081/Less-26/?id=1'%26%26updatexml(1,concat(0x7e,(select(database())),0x7e),1)%26%26'1'='1

第二步：Payload 逐字解析

  • 1'：闭合后端 SQL 语句 WHERE id='$id' 中的单引号。
  • %26%26：URL 编码后的 &&，作为逻辑连接符，替代被过滤的 and，且无需空格分隔。
  • updatexml(1,concat(0x7e,(select(database())),0x7e),1)：报错注入核心函数。
    • updatexml()：MySQL 用于更新 XML 的函数，当第二个参数不符合 XPath 格式时，MySQL 会抛出错误并回显该字符串。
    • 1：第一个参数，XML 文档，这里任意填写。
    • concat(...)：拼接字符串。
    • 0x7e：波浪号 ~ 的十六进制表示，用作边界标识，方便在报错信息中定位数据。
    • (select(database()))：子查询，获取当前数据库名。这里用括号包裹 database() 是为了在没有空格的情况下，让 SQL 解析器正确识别 select 和 database() 的语法关系。
    • 1：第三个参数，新值，任意填写。
  • %26%26'1'='1：再次使用 && 连接，并手动闭合末尾的引号。因为注释符被过滤，原 SQL 末尾会有 ' LIMIT 0,1，通过 &&'1'='1 让 SQL 语法变为 WHERE id='1' && updatexml(...) && '1'='1' LIMIT 0,1，保持语法完整。

第三步：验证

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 代码审计与WAF绕过：在代码审计和 WAF 绕过领域，此关具有极高的参考价值。当防御方采取去除空白字符或特定 SQL 关键词的白名单机制时，攻击者往往可以利用 SQL 语法的灵活性（如使用 &&、||、内联注释、括号包裹等）来规避过滤。
  • 文本处理与逻辑错位：在跨领域的文本处理中，这种“替换和清洗”往往会导致原有逻辑的错位，从而产生新的漏洞点。比如某些正则表达式在替换时遗漏了边界条件。
  • 安全开发启示：依赖黑名单或字符串替换来防御注入是极其脆弱的，必须从代码层面（参数化查询）和服务器配置层面入手，杜绝 SQL 注入的可能。

三、名词大全与原理深度复盘

1. SQL注入

攻击者通过将恶意的 SQL 代码插入到应用程序的输入字段中，欺骗后端数据库执行非预期的命令。

2. 报错注入

利用数据库在执行错误查询时返回的详细错误信息，将想要查询的数据拼接到错误信息中带出。其回显长度通常有限制。

3. updatexml() 函数

MySQL 内置的 XML 处理函数。当第二个参数出现 XPath 语法错误时，会触发报错，是经典报错注入函数。

4. 十六进制编码（0x7e）

将字符转换成十六进制表示，常用于绕过对引号的过滤或特殊字符的转义。

5. URL 编码

将特殊字符转换为 % 加上两位十六进制数的形式，以便在 URL 中安全传输。

6. 逻辑短路

SQL 语句中，A && B 的执行逻辑是，如果 A 为假，则 B 不会被执行。在盲注中常用于条件判断。

7. 黑名单过滤

通过正则表达式匹配并删除或拦截特定的危险字符或关键词。其局限性在于无法穷举所有变体，容易被符号替代或编码绕过。

8. 闭合引号

当注释符无法使用时，攻击者通过构造 '1'='1 等语句，主动补全 SQL 语句末尾缺失的引号，防止语法错误。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-25 的区别：Less-25 过滤了 OR 和 AND，Less-26 在它的基础上进一步过滤了空格和注释符。Less-25 使用 %26%26 即可绕过；Less-26 必须在无空格且无法注释的情况下，使用括号 select(database()) 和手动闭合 &&'1'='1 来重构 Payload。
  • 与 Less-25a 的区别：Less-25a 是盲注，Less-26 是报错注入。

2. 这种题目的出现原因（为什么存在）

从计算机底层来看，SQL 解析器对空白字符（空格、换行、制表符）的处理逻辑是一致的。开发者认为，只要通过正则把空格和注释符全部删掉，攻击者就无法构建复杂的 SQL 语句，因此系统就是安全的。这种漏洞的根源在于“黑名单防御”的先天缺陷——开发者试图穷举所有危险特征，但攻击者总能找到未在名单中的替代符号或语法结构。在历史生活中，这类似于古代城门守卫只知道没收刀剑，但不知道敌人可以用长矛或弓箭，防御手段始终滞后于攻击手段。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，面对带有 WAF（Web 应用防火墙）的站点，SQLMap 等自动化工具常常因为 Payload 包含空格或注释符而被拦截。此时就需要编写自定义的 Tamper 脚本，将空格替换为 %0a 或 /**/，将 and 替换为 &&，以此来绕过 WAF 规则。

4. 如何抽象理解概念（大白话）

把题目比作一个“极其苛刻的检查站”：

  • 检查站宣布：禁止带“和（and）”字，禁止带“空白（空格）”，禁止带“橡皮擦（注释符）”。
  • 你原本写了一句“我吃苹果和香蕉”。检查员把“和”字没收了，把空格删了，变成“我吃苹果香蕉”。语法崩了。
  • 你换了一种写法：“我吃苹果&&香蕉”。检查员不认识 &&，放行了。末尾如果写不完整，你就自己画个句号（'1'='1），而不是用橡皮擦。这就是 Less-26 的核心逻辑：利用语法规则的变体来欺骗过滤机制。
