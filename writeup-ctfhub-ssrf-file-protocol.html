CTFHub SSRF - 伪协议读取文件

2026年9月22日 CTFHub Web安全 SSRF 伪协议

一、题目信息

  • 题目名称：伪协议读取文件（SSRF）
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / SSRF（服务端请求伪造） / 伪协议利用
  • 靶场链接：http://challenge-db2c13ddaab33f11.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 SSRF 漏洞配合 PHP 伪协议读取服务器本地文件。后端代码会请求用户传入的 URL。攻击者利用 file:// 协议直接读取服务器文件系统，或者利用 php://filter 协议读取文件并进行编码，从而绕过页面显示限制，获取 Flag。

2. 怎么想（破题思路）

  • 页面空白，参数为 ?url=_，表明存在 SSRF 漏洞。
  • 题目提示明确：“尝试去读取一下Web目录下的flag.php吧”。Web 目录通常位于 /var/www/html/。
  • 尝试使用 file:// 协议直接读取：?url=file:///var/www/html/flag.php。
  • 如果页面只显示乱码或 ???，**这绝代表没有回显**，立刻按 F12 查看网页源代码或 Elements 面板，Flag 很可能藏在代码里。
  • 如果直接读取真的完全空白，改用 php://filter 协议，使用 convert.base64-encode 过滤器，让文件内容以 Base64 编码形式输出，绕过解析并完美回显。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误以为环境损坏或页面空白是错误

踩坑情况：看到空白页面以为环境报错。

原因分析：SSRF 探测类题目初始参数为 _，页面无回显是正常现象，需要构造有效的协议去请求资源。

改进方式：主动构造目标 URL 并提交。

踩坑记录二：页面显示 ??? 或乱码，误以为读取失败

踩坑情况：使用 file:///var/www/html/flag.php 读取，页面显示 ???。

原因分析：文件内容中的 <?php 标签被浏览器当作不完整的 HTML 标签渲染，导致显示为问号，但后面的文本内容（如 Flag）仍存在于 HTML 结构中。

改进方式：遇到此情况立刻按 F12 或 Ctrl+U 查看网页源代码。

详细实操步骤（逐字解析）

第一步：尝试 file:// 协议读取

构造 URL：

http://challenge-db2c13ddaab33f11.sandbox.ctfhub.com:10800/?url=file:///var/www/html/flag.php

Payload 逐字解析：

  • ?url=：传递给服务器的参数。
  • file://：声明使用本地文件系统协议。
  • /var/www/html/flag.php：Web 服务器默认存放网站文件的绝对路径。

第二步：查看网页源代码提取 Flag

页面显示 ???，按 F12 查看 Elements（元素），发现：
<?php // Flag is ctfhub{2ea0499701f883bc5da538e0} ?>

成功提取 Flag。

第三步：备选方案（php://filter 协议）

如果 file:// 直接读取失败，构造 URL：

http://challenge-db2c13ddaab33f11.sandbox.ctfhub.com:10800/?url=php://filter/convert.base64-encode/resource=/var/www/html/flag.php

Payload 逐字解析：

  • php://filter：使用 PHP 的过滤器协议。
  • convert.base64-encode：调用转换过滤器，将读取到的文件内容进行 Base64 编码。
  • resource=：指定要读取的资源文件路径。
  • /var/www/html/flag.php：目标文件路径。

页面回显一长串 Base64 字符串，复制后去在线工具解码，得到 Flag。

4. 怎么迁移（跨领域联想）

  • php://filter 的进阶利用：除了读取文件，还可以使用 convert.iconv、string.strip_tags 等过滤器绕过 WAF 或构造反序列化链。
  • SSRF 读取云元数据：在云服务器上，利用 file:// 或 http:// 协议可以访问 http://169.254.169.254/ 获取云主机的临时 AK/SK 凭据。
  • 安全开发（SDL）：防御 SSRF 需要禁用不安全的协议（如 file://、gopher://），设置 URL 白名单，并限制服务器发起请求的权限。

三、名词大全与原理深度复盘

1. file:// 协议

一种标准的本地文件传输协议，格式通常为 file:///path/to/file。在 SSRF 漏洞中，攻击者可以利用它直接读取服务器上的敏感文件，绕过 HTTP 请求的网络限制。

2. 为什么页面显示 ??? 而源码里却有 Flag？

浏览器渲染和 HTML 源码是两回事。file:// 直接输出了原始 PHP 文件内容，浏览器看到 <?php 这样的不完整标签，无法正常渲染，显示为 ???。但后面的注释文本（包含了 Flag）依然存在于 DOM 树中，查看源代码即可发现。

3. php://filter 协议

PHP 独有的流过滤器协议，它允许在读取文件流之前对其进行处理，例如编码、解码、大小写转换等。在 SSRF 和文件包含漏洞中，常被用来读取 PHP 文件源码（因为直接读取会被 PHP 执行导致看不到源码）。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与“内网访问”的区别：“内网访问”是让服务器通过 HTTP 协议去请求内网的资源；本题是让服务器通过底层的 file:// 协议直接读取文件系统，绕过了网络层的限制。
  • 与“文件包含漏洞”的区别：文件包含是直接在本地执行代码；SSRF 伪协议读取是读取文件的内容。两者通常可组合使用（如 SSRF 配合 php://filter 拿到源码）。

2. 这种题目的出现原因

开发人员为了实现动态功能（如加载远程图片、抓取网页内容），使用 file_get_contents() 或 curl 等函数处理用户输入的 URL，但没有对协议进行限制（如只允许 http/https），也没有屏蔽内网地址。这属于典型的“功能设计超出安全边界”漏洞。

3. 这种应用在实际中如何体现？

在真实渗透测试中，SSRF 配合伪协议是获取服务器敏感信息的常规手段。攻击者不仅用于读取文件，还常利用 gopher:// 协议攻击内网的 Redis、MySQL 等服务，实现从 SSRF 到 RCE 的升级。

4. 如何抽象理解概念（大白话理解）

把服务器比作一个传令兵：

  • 内网访问（http://127.0.0.1）：你让传令兵去“隔壁房间”（内网）拿一份文件。
  • 伪协议读取（file://）：你告诉传令兵：“不要去隔壁了，直接把经理抽屉里的文件（本地文件系统）拿出来。”传令兵不知道这会违规，于是直接打开抽屉把文件递给了你。
  • F12 查看源码：传令兵拿回来的是一份用暗号写的文件，肉眼看着像乱码（???），但你拿放大镜（F12）仔细一看，里面其实写着清晰的 Flag。
