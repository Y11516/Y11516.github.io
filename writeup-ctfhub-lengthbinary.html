LengthBinary - CTFHub Misc Writeup

2026年9月17日 CTFHub Misc 流量分析 ICMP隐蔽通道

这是我第一次接触“Misc”（杂项）大类的流量分析题。从 Mac 无法打开文件，到手动解码出现乱码，再到用 tshark 命令行完美破局，这篇 Writeup 记录了完整的排错过程。

一、什么是 Misc 与流量分析？

  • Misc（杂项）： CTF 中的“杂物间”，包含流量分析、隐写术、数字取证等无法归入 Web/Pwn/Reverse/Crypto 的题目。
  • 流量分析： 类似于网络监控录像回放。在 Web 攻击里，我们主动发请求；在这里，我们要分析已经抓到的数据包（pcap 文件），从底层网络协议中寻找蛛丝马迹。

二、题目原理：什么是“ICMP 隐蔽通道”？

题目提示： ping 包的大小有些奇怪。

原理剖析： 正常的 Ping 包数据大小是固定的（通常是 32 或 64 字节）。题目名为 LengthBinary（长度二进制），意思是把数据包的“长度”当作二进制位来传递信息。

我们将帧长度为 74 的包记为 0，帧长度为 106 的包记为 1。每 8 个 0/1 组成一个二进制串，转换为 ASCII 字符，即可还原 Flag。

三、解题过程与踩坑全记录

1. 踩坑一：Mac 打不开 pcap 文件

下载附件解压后，双击 .pcap 文件，Mac 提示“未设定用来打开文稿的应用程序”。

解决： 去官网下载并安装 Wireshark（全球最强大的网络协议分析器）。

2. 踩坑二：被 Data 里的 4d 迷惑

在 Wireshark 中看到 Data (32 bytes) 里的内容全是 4d 4d 4d...（ASCII 码中的 'M'）。一开始误以为这是密码。

原因分析： 这只是 ICMP 协议用来填充数据包长度的随机内容，真正的线索不在内容里，而在数据包的长度（Length 列）。

3. 踩坑三：手动提取导致乱码

我把请求包的长度手动复制到 Python 列表里进行解码，结果得到了乱码 có。

原因分析： Wireshark 中请求包（74/106）和回复包（74/106）是交替出现的。手动复制极易混入回复包，导致二进制 0/1 错位。

4. 成功破局：使用 tshark 命令行

在终端中，使用 Wireshark 自带的 tshark 命令行工具，直接过滤请求包并自动转换：

/Applications/Wireshark.app/Contents/MacOS/tshark -r icmp_len_binary.pcap -Y "icmp.type==8" -T fields -e frame.len | awk '{if($1==74) printf "0"; else if($1==106) printf "1";}' | perl -lpe '$_=pack("B*",$_)'

终端直接打印出了完整的 Flag！ctfhub{04efed1e05}

四、知识点总结与防御思考

💡 隐蔽通道（Covert Channel）： 攻击者利用网络协议中的某些字段（如数据包大小、时间间隔）来传递数据，以绕过安全检测。

💡 tshark 命令行的强大： 在处理纯数据提取类题目时，图形界面容易陷入视觉疲劳，命令行工具往往能一键搞定。

💡 防御手段： 网络监控设备（IDS/IPS）可以检测异常的 ICMP 包大小或时间间隔，及时阻断隐蔽通道外泄数据。

做一道题，就要往自己脑子里装点东西。
