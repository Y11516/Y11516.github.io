SQLi-Labs Less-29

2026年9月28日 SQLi-Labs Web安全 SQL注入 HTTP参数污染

一、题目信息

  • 题目名称：SQLi-Labs Less-29 (GET - Error Based - IMPIDENCE MISMATCH - Having a WAF in front of web application)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / HTTP参数污染 (HPP) / WAF绕过
  • 靶场链接：http://localhost:8081/Less-29/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是HTTP 参数污染（HPP）导致的 WAF 绕过。题目环境模拟了生产环境中的 WAF 架构：WAF 位于最前端，负责过滤恶意请求，后端是 PHP 应用。如果 WAF 和 PHP 在解析同名 GET 参数时逻辑不一致（比如 WAF 只检查第一个参数，而 PHP 取最后一个参数），攻击者就可以利用这种“阻抗失配”绕过防御。

2. 怎么想（破题思路）

  • 页面提示“This Site Protected by World's Best Firewall”，意味着前面有 WAF 拦截。
  • 尝试直接输入 Payload，WAF 可能会拦截。但如果发送两个同名参数：?id=1&id=恶意Payload。
  • WAF 解析：看到第一个 id=1，判断安全，放行。
  • 后端 PHP 解析：默认取最后一个参数，即 id=恶意Payload，执行了注入语句。
  • 利用这个差异，成功绕过 WAF，注入生效。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：URL 编码未处理导致注入失败

踩坑情况：在地址栏直接敲入带有空格和单引号的 Payload，浏览器报错或 URL 被截断。

原因分析：URL 中不能直接包含空格和单引号，必须进行 URL 编码。

改进方式：将空格编码为 %20，单引号编码为 %27，注释符编码为 --%20-。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入以下 URL：

http://localhost:8081/Less-29/?id=1&id=1%27%20and%20%20updatexml(1,concat(0x7e,(select%20database()),0x7e),1)--%20-

第二步：Payload 逐字解析

  • ?id=1：第一个参数，用于欺骗 WAF，让 WAF 认为请求是安全的。
  • &id=1%27%20and%20%20updatexml(...)：第二个参数，真正的注入 Payload。由于 PHP 取最后一个 id，它将执行该语句。
  • %27：URL 编码后的单引号，闭合原 SQL。
  • %20：URL 编码后的空格。
  • updatexml(1,concat(0x7e,(select%20database()),0x7e),1)：报错注入核心函数，获取数据库名。
  • --%20-：注释符，注释掉原 SQL 末尾的引号。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 代码审计与 WAF 绕过：在真实渗透中，HPP 不仅用于 SQL 注入，也常用于绕过 XSS 过滤器、CSRF 保护等。例如，发送多个同名的 role 参数，前端校验第一个（认为你是普通用户），后端取值最后一个（导致越权）。
  • 架构设计中的阻抗失配：HPP 的根源在于 WAF 和 APP 解析 HTTP 协议的逻辑不同。这警示架构师：安全设备必须和后端应用采用一致的解析标准，否则就会出现安全漏洞。
  • 安全开发启示：依赖 WAF 来防御注入是极其脆弱的。必须在代码层面使用参数化查询（Prepared Statements）。

三、名词大全与原理深度复盘

1. HTTP 参数污染 (HPP)

指攻击者向 HTTP 请求中注入多个同名的参数，导致不同的 Web 组件（如 WAF、PHP、Java）在解析这些参数时，取值逻辑不一致，从而引发安全漏洞。

2. WAF (Web Application Firewall)

Web 应用防火墙，部署在 Web 服务器前，用于过滤恶意请求。本例中 WAF 没有正确解析重复的参数。

3. IMPIDENCE MISMATCH (阻抗失配)

在网络安全中，指安全设备（WAF）与受保护的应用（APP）对同一个请求的解析结果不一致。如 WAF 看到的是无害参数，APP 看到的是恶意参数。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-28 的区别：Less-28 是后端代码过滤了关键字和空格，属于“内部防御”。Less-29 是部署了 WAF，属于“外部防御”，需要我们利用协议解析差异来绕过。
  • 与 Less-20/21 的区别：Less-20/21 注入点在 Cookie/Referer，Less-29 是 GET 参数注入。

2. 这种题目的出现原因（为什么存在）

现代 Web 架构通常由 WAF、负载均衡器、Web 服务器和应用程序组成。不同的组件对 HTTP 协议的实现细节有微小差异。例如，PHP 会取最后一个重复参数，而某些 Java 框架取第一个。攻击者利用这种差异，就能让 WAF 看到的“安全内容”与后端执行的“恶意内容”分离，从而绕过防御。这类似于现实生活中，巡逻兵只检查了卡车表面，但卡车暗格里藏了违禁品。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，如果发现目标使用了 WAF，渗透测试人员常尝试 HPP 绕过。比如在参数中混入 %00 或重复参数。防御方应确保 WAF 和后端应用对参数的处理逻辑一致。

4. 如何抽象理解概念（大白话）

把靶场比作一个“双关卡检查站”：

  • 第一道关卡是 WAF 检查员。第二道关卡是后端 PHP 检查员。
  • 你提交了一张表格，上面写着“第一行：我的名字是张三（安全）。第二行：我的名字是李四（炸弹）”。
  • 第一道关卡只看第一行，觉得安全，放行了。
  • 第二道关卡只看最后一行，把炸弹带了进去。这就是 Less-29 的 HPP 原理。
