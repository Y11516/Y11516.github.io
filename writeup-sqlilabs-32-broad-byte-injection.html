SQLi-Labs Less-32

2026年9月28日 SQLi-Labs Web安全 SQL注入 宽字节注入

一、题目信息

  • 题目名称：SQLi-Labs Less-32 (GET - Bypass custom filter adding slashes to dangerous chars)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 宽字节注入 / 转义绕过
  • 靶场链接：http://localhost:8081/Less-32/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是宽字节注入绕过 addslashes() 转义。后端使用 addslashes() 对单引号进行转义，导致常规注入失效。由于数据库使用 GBK 编码，攻击者可以通过在单引号前插入 %df，使 %df 和反斜杠 %5c 组合成一个合法的 GBK 汉字，从而“吃掉”反斜杠，让单引号成功逃逸。

2. 怎么想（破题思路）

  • 直接使用 ?id=1'，页面提示被转义，注入失败。
  • 观察 Hint：输入的字符串被转义，并在底层变成了十六进制。
  • 利用 GBK 编码特性：发送 ?id=1%df'，后端转义后变成 1%df%5c%27，在 GBK 下 %df%5c 被解析为汉字，单引号 %27 逃逸。
  • 拼接报错注入 Payload，直接获取数据库名。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：直接使用单引号被转义

踩坑情况：输入 ?id=1'，页面没有报错，也没有注入成功。

原因分析：后端使用 addslashes() 将单引号转义为了 \'（即 %5c%27），导致单引号无法闭合 SQL 语句。

改进方式：在单引号前插入 %df，利用 GBK 编码将 %df%5c 组合成一个汉字，从而吃掉转义符。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-32/?id=1%df'%20and%20updatexml(1,concat(0x7e,(select%20database()),0x7e),1)--%20-

第二步：Payload 逐字解析

  • 1%df'：核心宽字节 Payload。%df 和转义后的 %5c 合成汉字，单引号逃逸。
  • %20：URL 编码的空格。
  • and updatexml(...)：报错注入，获取当前数据库名。
  • --%20-：注释符，阻止后续 SQL 执行。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 字符集与编码安全：宽字节注入的根源是“字符集不一致”。如果数据库配置为 GBK，而 PHP 未正确处理转义，就会产生漏洞。这警示我们，跨语言、跨组件的编码问题往往是安全漏洞的温床。
  • 转义函数的局限性：addslashes() 仅对特定字符加反斜杠。在 GBK 等多字节编码下，这种单字节转义机制会被“吃掉”，防御瞬间失效。
  • 安全开发启示：使用参数化查询（Prepared Statements）时，数据库和驱动会自动处理所有转义，彻底杜绝宽字节注入。

三、名词大全与原理深度复盘

1. 宽字节注入 (Broad Byte Injection)

利用数据库字符集（如 GBK）将两个单字节“拼”成一个多字节汉字的特性，让转义符 \（%5c）被吃掉，从而让后续的危险字符逃逸。

2. addslashes() 函数

PHP 中用于转义单引号、双引号、反斜杠等特殊字符的函数。但其单字节转义机制在多字节编码环境下存在缺陷。

3. GBK 编码

中文编码标准之一。其字符使用两个字节表示，首字节范围是 0x81-0xFE，尾字节范围是 0x40-0xFE。%df 是合法的首字节。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-31 的区别：Less-31 是 WAF + 盲注，Less-32 是后端转义 + 宽字节注入，是底层编码层面的攻击。

2. 这种题目的出现原因（为什么存在）

开发者知道要用 addslashes() 防御 SQL 注入，但忽略了数据库字符集的特性。当 PHP 和 MySQL 连接使用了 GBK 编码时，单字节转义就会被多字节解析“吃掉”。这反映了“安全防御不能只看代码层，还要看底层配置”的问题。

3. 这种应用在实际中如何体现？

在实战中，宽字节注入常见于使用 GBK 编码的国产 CMS（如 DedeCMS、Discuz）中。防御方必须统一使用 UTF-8 编码，或者强制使用参数化查询。

4. 如何抽象理解概念（大白话）

把靶场比作一个“检查站”：

  • 安检员（addslashes）看到单引号（炸弹），会在前面加一个锁（反斜杠 \）。
  • 但你把炸弹写成了“%df'”。
  • 安检员加锁后变成“%df\ '”。
  • 但翻译官（GBK 解码）看到“%df\”，以为它们是一个汉字，直接把锁吃掉了。于是炸弹又漏了出来。
