SQLi-Labs Less-27a

2026年9月28日 SQLi-Labs Web安全 SQL注入 时间盲注 / 过滤绕过

一、题目信息

  • 题目名称：SQLi-Labs Less-27a (GET - Blind Based - All your UNION & SELECT Belong to us - Double Quotes)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 时间盲注 / UNION 与 SELECT 过滤绕过 / 双引号闭合
  • 靶场链接：http://localhost:8081/Less-27a/（本地环境）
  • 涉及工具：Chrome浏览器 (F12 开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是在盲注场景下绕过对 UNION 和 SELECT 关键字过滤。Less-27a 是 Less-27 的盲注变体： 1. 无任何报错回显，唯一反馈是响应时间（时间盲注）。 2. 过滤了 union、select、and、or 以及空格和注释符。 3. 闭合方式是双引号 "。

2. 怎么想（破题思路）

  • 首先确认闭合符是双引号 "，而非单引号。
  • 过滤了 and，改用 &&（URL 编码为 %26%26）替代。
  • 过滤了空格，使用 URL 编码的空格 %20 替代。
  • 过滤了注释符，使用手动闭合的方式（如 "1"="1）替代。
  • 由于过滤了 select，我们直接调用 sleep(3) 无需子查询，验证时间盲注是否生效。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：盲目套用 Less-27 的单引号闭合导致失败

踩坑情况：使用 1' && sleep(3) && '1'='1 测试，页面返回 SQL 语法错误。

原因分析：Less-27 是单引号 ' 闭合，Less-27a 是双引号 " 闭合。这涉及到源码中 SQL 语句的构造逻辑差异。

改进方式：将 Payload 中的单引号全部替换为双引号。

踩坑记录二：未使用 F12 验证时间盲注

踩坑情况：页面没有任何变化，误以为注入失败。

原因分析：盲注的特性就是页面内容不变。时间盲注只能通过观察页面加载时间判断。

改进方式：打开 F12 的 Network 面板，勾选 Disable cache，查看请求的 Time 列。耗时超过 3 秒即证明注入成功。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-27a/?id=1"%20%26%26%20sleep(3)%20%26%26%20"1"="1

第二步：Payload 逐字解析

  • 1"：闭合原 SQL 中的双引号。
  • %20：URL 编码后的空格。
  • %26%26：URL 编码后的 &&，替代被过滤的 and。
  • sleep(3)：核心时间函数，令数据库停顿 3 秒。
  • %20%26%26%20"1"="1：再次使用空格和 && 连接，并手动闭合末尾的双引号，保证 SQL 语法完整。

第三步：验证结果

页面无变化，但 F12 的 Network 面板中，该请求的耗时显示为 3.03 s，证明时间盲注成功。

4. 怎么迁移（跨领域联想）

  • 真实渗透与 WAF 绕过：在实战中，面对 WAF 拦截 AND 或 OR 时，渗透测试人员会优先尝试 &&、||、%26%26、%7C%7C 等变体。防御方应使用参数化查询，或使用 WAF 的正则优化来匹配这些替代符。
  • 盲注的效率与脚本自动化：盲注是实际渗透中效率最低但最隐蔽的手段。通常需要编写 Python 脚本进行自动化，否则手工注入成百上千次会耗费大量时间。
  • 安全开发启示：依赖黑名单和字符串替换来防御注入极其脆弱。必须从代码层面（参数化查询）和服务器配置层面入手，才能根治 SQL 注入。

三、名词大全与原理深度复盘

1. 时间盲注 (Time-Based Blind SQL Injection)

当页面没有回显位，且过滤了报错信息时，攻击者通过构造 if(条件, sleep(N), 0) 来制造延迟。如果条件成立，页面响应时间会显著增加。

2. 双引号闭合

SQL 语句的字符串值由双引号（"）包裹，Payload 必须与之匹配，以正确闭合字符串。

3. 关键字过滤绕过 (Obfuscation)

后端过滤了关键字和符号，攻击者使用替代符（&&, ||）、编码（URL编码）或等效语法来绕过拦截。

4. 逻辑短路

在 SQL 中，A && B 如果 A 为假，B 不会被执行；A || B 如果 A 为真，B 不会被执行。MySQL 优化器会主动利用这种特性加速查询。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-27 的区别：Less-27 是报错注入（有回显，单引号闭合），Less-27a 是时间盲注（无回显，双引号闭合）。
  • 与 Less-26a 的区别：Less-26a 过滤了空格和注释符，但未过滤 UNION 和 SELECT。Less-27a 在它们的基础上进一步过滤了关键字。

2. 这种题目的出现原因（为什么存在）

从计算机底层来看，SQL 解析器对空白字符和关键字有严格的处理规则。开发者认为，通过黑名单过滤这些特征就能高枕无忧。然而，SQL 语法具有极高的灵活性，攻击者总能找到等效的替代语法。这警示我们：黑名单防御永远无法穷举所有攻击手法。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，遇到带有 WAF 的站点，SQLMap 常因 Payload 包含关键字或空格而被拦截。此时需要编写自定义的 Tamper 脚本，将空格替换为 %0a 或 /**/，将 and 替换为 &&，以此来绕过 WAF 规则。

4. 如何抽象理解概念（大白话）

把题目比作一个“极其苛刻的检查站”：

  • 检查站宣布：禁止带“和（and）”字，禁止带“空白（空格）”，禁止带“橡皮擦（注释符）”。
  • 你原本写了一句“我吃苹果和香蕉”。检查员把“和”字没收了，把空格删了，变成“我吃苹果香蕉”。语法崩了。
  • 你换了一种写法：“我吃苹果&&香蕉”。检查员不认识 &&，放行了。末尾如果写不完整，你就自己画个句号（'1'='1），而不是用橡皮擦。这就是 Less-27a 的核心逻辑：利用语法规则的变体来欺骗过滤机制，同时靠时间差来传递信息。
