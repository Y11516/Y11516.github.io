SQLi-Labs Less-64

2026年10月2日 SQLi-Labs Web安全 SQL注入 挑战模式 / 时间盲注 (130次)

一、题目信息

  • 题目名称：SQLi-Labs Less-64 (GET - challenge - Blind - 130 queries allowed - variation 3)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 挑战模式 / 时间盲注 / 双右括号闭合 / 限制尝试次数
  • 靶场链接：http://localhost:8081/Less-64/（本地环境）
  • 涉及工具：Chrome浏览器、VS Code、Python3 (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是在限制 130 次尝试的极端条件下，完成基于时间盲注的数据提取。Less-64 无法使用 UNION 联合查询，且页面没有回显差异，闭合方式为双右括号 ))。必须通过构造 SLEEP() 延迟函数来推断数据，并利用 Python 脚本自动化爆破。

2. 怎么想（破题思路）

  • Less-64 是 Less-63 的变体（Variation 3），核心逻辑完全一致，只是闭合方式变了。
  • Less-63 使用的是单引号 '，Less-64 去掉单引号，使用双右括号 )) 闭合。
  • 无需重写脚本，只需要复制 Less-63 的脚本，修改 url 和 闭合符号 即可。
  • 再次强调：不携带 Cookie 发起请求，可完全绕过 130 次的限制。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误用单引号闭合导致脚本失效

踩坑情况：直接复制 Less-63 的 Payload ?id=1' AND IF(1=1, SLEEP(3), 0)-- -，页面无延迟。

原因分析：Less-64 源码为 id=(($id))，没有引号。多出来的单引号导致 SQL 语法错误，SLEEP 无法执行。

改进方式：去掉单引号，将 Payload 修正为 ?id=1)) AND IF(1=1, SLEEP(3), 0)-- -，页面成功延迟 3 秒。

详细实操步骤（Payload逐字解释）

第一步：验证时间盲注可行性（手动测试）

?id=1)) AND IF(1=1, SLEEP(3), 0)-- -

逐个字符解释：

  • ?id=1))：闭合原有的两个右括号。
  • AND：逻辑与操作符。
  • IF(1=1, SLEEP(3), 0)：如果 1=1 为真，执行 SLEEP(3) 延迟3秒。
  • -- -：注释掉后面的 SQL 语句。

成功响应：页面卡顿约3秒后返回。失败响应：页面立即返回，无延迟。

第二步：修改 Less-63 的 Python 脚本

修改以下两处代码，并删除硬编码的表名：

url = "http://localhost:8081/Less-64/"
full_url = url + "?id=1)) AND " + payload + "-- -"

将主程序中的 table_name = "..." 删除，让脚本自动执行获取表名的逻辑。

4. 怎么迁移（跨领域联想）

  • 网络协议排错：时间盲注非常像网络工程中的 Ping 命令。当你无法直接查看目标服务器的内部状态（无回显）时，通过发送特定数据包并测量往返时间（延迟），来判断目标是否在线或条件是否成立。
  • 自动化测试中的重试机制：脚本中加入了 for _ in range(3) 的重试机制，这种“容忍网络抖动”的设计思想，在分布式系统和微服务架构中非常常见，用于提高系统的鲁棒性。

三、名词大全与原理深度复盘

1. 双右括号闭合 (Double Parentheses Closure)

SQL 注入中常见的一种数字型闭合方式。后端代码如 SELECT * FROM users WHERE id=(($id))，用户输入 1)) 时，两个右括号提前闭合，使得后续的恶意 SQL 语句得以执行。

2. 二分法 (Binary Search)

在盲注中，将 ASCII 码范围（32-126）不断折半，每次请求可以排除一半的可能性。例如先猜 >79，如果为真，再猜 >102，将每个字符的爆破次数从最多94次减少到约7次。

3. information_schema

MySQL 自带的系统数据库，存储了关于数据库自身的信息，包括所有数据库名、表名、列名等。它是 SQL 注入中获取元数据的核心入口。

4. SUBSTR() / ASCII() / IF() / SLEEP()

SUBSTR(str, pos, len) 截取字符串；ASCII(char) 转化为整数值；IF(cond, true_val, false_val) 条件判断；SLEEP(n) 延迟函数。四者组合是实现时间盲注的核心工具箱。

5. 无 Cookie 绕过限制

Less-64 尝试次数限制基于 Cookie 的会话跟踪。Python 脚本在 requests.get() 时不携带 Cookie 字段，服务器每次都会将其视为一个全新的会话，从而完全绕过 130 次的尝试限制。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-63 的区别：Less-63 是单引号闭合 '，Less-64 是双右括号闭合 ))。这是 Sqli-labs 为了训练攻击者对闭合方式敏感度而设计的变体。
  • 与 Less-59/60 的区别：Less-59/60 是双查询报错注入（依赖回显），限制5次。Less-64 是时间盲注（无回显），限制130次，需要脚本自动化。

2. 这种题目的出现原因（为什么存在）

这种漏洞存在的根本原因在于代码层直接拼接 SQL 语句，且没有使用预编译（Prepared Statements）。开发者将用户输入的 id 直接拼接在 SQL 查询后，导致攻击者可以闭合括号并执行恶意 SQL。

从计算机底层来说，SQL 解析器在解析语句时，无法区分哪些是开发者写的 SQL 代码，哪些是用户传入的数据。当用户输入 1)) AND SLEEP(3)-- - 时，解析器会将其当作合法的 SQL 语法执行。这在历史上类似于早期 PHP/ASP 应用中广泛存在的 SQL 注入漏洞，著名的如 2011 年索尼 PlayStation Network 被黑事件，攻击者正是利用了未过滤的 SQL 查询参数，窃取了上亿用户的数据。

3. 这种的应用

时间盲注在实战中应用广泛。当遇到带有 WAF 的站点，或者后端代码封装极好、没有任何报错和回显时，联合查询和报错注入都会失效。此时，时间盲注是唯一能有效提取数据的手段。在渗透测试中，常配合 SQLMap 的 --time-sec 参数或自定义 Python 脚本使用，用于评估数据库安全风险。

4. 如何抽象理解概念（大白话）

把时间盲注比作“蒙眼猜数字”：

  • 你被蒙住眼睛，面前有一个黑盒子，里面藏着一串密码。
  • 你无法看到密码，也无法听到盒子里的声音（无回显）。
  • 但你可以向盒子里投币。如果你投的币符合某个条件，盒子会“卡顿3秒”才吐出来（时间延迟）。
  • 你利用“二分法”，先问“密码第一个字母的ASCII码大于100吗？”，盒子卡顿了3秒，说明大于100；再问“大于113吗？”，盒子没卡顿，说明在100到113之间。
  • 如此反复，最终把密码完整猜出来。这就是时间盲注的底层逻辑。

做一道题，就要往自己脑子里装点东西。
