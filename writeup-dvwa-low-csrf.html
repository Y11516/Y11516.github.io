DVWA-Low-跨站请求伪造 (CSRF)

2026年10月2日 DVWA Web安全 CSRF 跨站请求伪造

一、题目信息

  • 题目名称：DVWA Cross Site Request Forgery (CSRF) (Low)
  • 题目平台：DVWA (本地 Docker / 灵境靶场)
  • 题目类型：Web安全 / 逻辑漏洞 / 跨站请求伪造
  • 靶场链接：http://192.168.242.80/vulnerabilities/csrf/
  • 涉及工具：Google Chrome 浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是跨站请求伪造（CSRF）。攻击者利用受害者已登录的合法会话（Cookie），构造一个恶意请求（如修改密码、转账），诱导受害者点击。由于浏览器会自动携带 Cookie，服务器会误以为这是受害者本人的操作，从而执行恶意指令。

2. 怎么想（破题思路）

  • 正常修改密码，发现请求是 GET 型，且参数（新密码、确认密码）直接暴露在 URL 中。
  • 后端没有验证“旧密码”，也没有 CSRF Token。
  • 构造一个包含上述参数的恶意 URL（或 HTML 页面），诱导已登录的受害者访问。
  • 受害者访问后，密码被成功篡改，攻击者用新密码登录。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误以为 CSRF 需要攻击服务器

踩坑情况：试图用 SQL 注入或命令注入的思路去攻击 DVWA 的 CSRF 关卡，发现无从下手。

原因分析：CSRF 是“借刀杀人”，攻击的是“已登录的用户”，而不是服务器本身。服务器并没有漏洞，漏洞在于浏览器和服务器之间的信任机制被滥用。

改进方式：转变思路。你需要模拟受害者，先登录，然后在另一个标签页访问恶意链接。

踩坑记录二：忘记了原密码，无法重新登录

踩坑情况：成功用恶意链接修改了密码，但忘记了改成了什么，导致无法再登录 DVWA。

原因分析：CSRF 直接修改了数据库中的密码，没有回显。

改进方式：点击左侧菜单的 Setup / Reset DB，一键重置数据库，即可恢复所有数据。

详细实操步骤（Payload逐字解释）

第一步：获取合法请求的格式

正常输入 123456 修改密码，观察地址栏，URL 如下：

http://192.168.242.80/vulnerabilities/csrf/?password_new=123456&password_conf=123456&Change=Change

第二步：构造恶意链接

将 URL 中的密码参数修改为攻击者想要的值（例如 hacked）：

http://192.168.242.80/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change

第三步：模拟受害者触发

保持 DVWA 登录状态，新开标签页访问上述恶意 URL。页面回显 Password Changed.。

退出登录，使用 admin / hacked 尝试登录，成功即通关。

4. 怎么迁移（跨领域联想）

  • 网络钓鱼中的“一键转账”：攻击者伪造一个“领取红包”的链接，实际背后是银行转账接口。受害者点击后，银行卡里的钱就被转走。
  • 社交平台的“自动点赞/发帖”：如果你在登录微博时，点击了某个带有 CSRF 漏洞的第三方页面，你可能在不知情的情况下，自动发布了一条广告微博。

三、名词大全与原理深度复盘

1. CSRF (Cross-Site Request Forgery)

跨站请求伪造。攻击者诱导已登录的用户在不知情的情况下，向目标网站发送非预期的请求。CSRF 不窃取数据，而是伪造操作。

2. 同源策略 (Same-Origin Policy)

浏览器的安全机制。它限制了来自不同源的脚本对当前页面的读取权限，但**允许**发送跨站请求（比如 `` 标签的 `src` 可以请求任何网站）。CSRF 正是利用了同源策略对“发送请求”的宽容。

3. CSRF Token

一种防御 CSRF 的机制。服务器在页面中嵌入一个随机生成的 Token，每次提交请求都必须携带该 Token。由于攻击者无法预测这个随机值，也无法从跨站页面中读取它，因此无法构造有效的恶意请求。

4. 旧密码验证

修改密码时，强制用户输入原密码。这是最有效的 CSRF 防御手段之一，因为攻击者无法知道用户的旧密码。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 的区别：XSS 是“窃取用户的敏感数据（如 Cookie）”，而 CSRF 是“伪造用户的操作”。XSS 需要注入恶意脚本，CSRF 不需要。
  • 与 SQL 注入的区别：SQL 注入是攻击服务器上的数据库，CSRF 是攻击浏览器的信任机制。

2. 这种题目的出现原因（为什么存在）

漏洞存在的根本原因在于Web 应用没有对用户的“操作意图”进行二次验证。开发者默认只要请求携带了正确的 Cookie，就是用户本人发起的。这在早期的 Web 开发中非常普遍。

从历史角度看，这类似于 2007 年 Gmail 曾爆出的 CSRF 漏洞，攻击者可以构造恶意页面，只要 Gmail 用户登录着，就会自动转发邮件或更改设置。

3. 这种的应用

在护网演练中，CSRF 常用于攻击后台管理员。攻击者通过 XSS 漏洞或社工手段，让管理员在后台执行添加管理员账号、修改密码等操作，从而控制整个系统。

4. 如何抽象理解概念（大白话）

把 CSRF 比作“冒充老板签字”：

  • 你在一家公司上班，你的工牌（Cookie）可以打开公司的大门。
  • 攻击者捡到了你的工牌，或者趁你工牌挂在脖子上时，拿来刷了一下门禁，并在签字本上签了字。
  • 门卫（服务器）只认工牌和笔迹，不会问你“这是你本人签的吗？”
  • 于是，攻击者成功以你的名义做了事情。这就是 CSRF。

做一道题，就要往自己脑子里装点东西。
