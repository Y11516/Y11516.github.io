SQLi-Labs Less-46

2026年9月29日 SQLi-Labs Web安全 SQL注入 ORDER BY 报错注入

一、题目信息

  • 题目名称：SQLi-Labs Less-46 (GET - Error based - ORDER BY CLAUSE)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / ORDER BY 注入 / 报错注入
  • 靶场链接：http://localhost:8081/Less-46/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是ORDER BY 子句中的报错注入。这是 SQLi-Labs 中一个全新的注入维度。之前的关卡参数都跟在 WHERE id = $id 后面，而这一关的参数跟在 ORDER BY $sort 后面。因为在 ORDER BY 后面不能使用 UNION SELECT，也不能使用 AND 1=1 进行布尔判断，所以我们要利用 MySQL 函数（如 updatexml）触发报错回显。

2. 怎么想（破题思路）

  • 页面提示 "Please input parameter as SORT with numeric value"，说明参数是 sort，且用于排序。
  • 尝试输入 ?sort=1，页面按默认排序；输入 ?sort=1 desc，页面逆序排列，证明注入点存在。
  • 尝试拼接 updatexml() 函数，看是否能触发报错。
  • 构造 Payload：?sort=updatexml(1,concat(0x7e,(select database()),0x7e),1)。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：空格被识别为排序参数的一部分

踩坑情况：直接输入 ?sort=updatexml(1,concat(0x7e,(select database()),0x7e),1)，页面没有反应或报错。

原因分析：如果 Payload 中包含空格，可能被后端误认为是 ORDER BY id DESC 中的分隔符，导致语法错误。此外，浏览器会自动将空格转义。

改进方式：在 URL 中手动将空格替换为 %20，并用括号包裹函数调用，确保语法严密。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-46/?sort=updatexml(1,concat(0x7e,(select%20database()),0x7e),1)

第二步：Payload 逐字解析

  • ?sort=：将参数传递给 ORDER BY。
  • updatexml(...)：报错注入的核心函数。当第二个参数不符合 XPath 语法时，MySQL 会抛出错误信息。
  • 0x7e：波浪号 ~ 的十六进制编码，用作边界标识。
  • select%20database()：子查询获取当前数据库名。这里的 %20 是空格的 URL 编码。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 应用场景联想：ORDER BY 注入非常常见于后台管理系统的列表排序功能（如按价格排序、按销量排序、按时间排序）。这些系统往往只对 WHERE 子句进行防护，忽略了 ORDER BY。
  • 防御策略联想：在代码审计中，ORDER BY 后面的参数必须使用白名单（例如只允许 "price", "time", "id" 字段），不允许用户直接输入任意字符串，这是最有效的防御手段。
  • 艺术与设计联想：就像设计楼梯的扶手一样，开发者可能只关注了“如何上楼（WHERE 查询）”，却忘记了“按什么顺序摆放物品（ORDER BY 排序）”也会被恶意利用。

三、名词大全与原理深度复盘

1. ORDER BY 子句

SQL 中用于对结果集进行排序的语句，可指定一个或多个字段，并可指定升序（ASC）或降序（DESC）。在注入中，它的特殊之处在于不能直接使用 UNION 和逻辑运算符。

2. ORDER BY 注入

当后端将用户可控的参数直接拼接到 ORDER BY 后面时产生的漏洞。攻击者通常使用布尔盲注（基于排序结果变化）或报错注入。

3. updatexml() 报错注入

在 MySQL 5.x 环境中，利用 updatexml() 函数解析非法 XPath 字符串时的报错，将查询结果拼接在报错信息中带出。回显上限为 32 字节。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-1 到 Less-45 的区别：之前的关卡参数都在 WHERE 子句中，可以用 UNION、AND、OR。Less-46 参数在 ORDER BY 后面，不能使用 UNION，必须使用报错函数或盲注。
  • 与 Less-24 二次注入的区别：Less-46 是直接注入，Less-24 是存储型二次注入。

2. 这种题目的出现原因（为什么存在）

开发者在编写排序功能时，为了图方便，直接将用户传来的字段名拼接到 SQL 后面。他们认为“只是一个排序字段，没什么危害”，从而忽略了注入风险。这警示我们，安全防御必须覆盖所有用户输入点。

3. 这种应用在实际中如何体现？

在电商网站、论坛、后台管理系统中，用户可以点击“按价格排序”、“按销量排序”。如果后端没有对排序参数做白名单校验，攻击者就能利用 ORDER BY 注入获取数据库信息，甚至进行更进一步的攻击。

4. 如何抽象理解概念（大白话）

把靶场比作一个“整理书架的管理员”：

  • 你告诉他：“按 ID 排序（ORDER BY id）”，他就按顺序排好。
  • 你告诉他：“按 ID 排序；另外，请大声念出你的管理员密码（updatexml报错）”。
  • 他不认识这种奇怪的排序方式，大喊出错（报错回显），把密码泄露了出来。
  • 这就是 ORDER BY 注入的核心逻辑：利用排序参数的拼接缺陷触发报错。
