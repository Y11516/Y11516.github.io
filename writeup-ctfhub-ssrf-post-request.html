CTFHub SSRF - POST请求

2026年9月23日 CTFHub Web安全 SSRF gopher协议

一、题目信息

  • 题目名称：POST请求（SSRF）
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / SSRF（服务端请求伪造） / 协议利用
  • 靶场链接：http://challenge-ccf5329690aaf427.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器、curl命令行、Burp Suite

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 gopher 协议构造并发送 HTTP POST 请求。题目提示“这次是发一个 HTTP POST 请求”，说明内部服务不仅接收 POST 请求，还通过 302 跳转进行了限制。普通的 HTTP 请求无法携带 POST 数据，且跟随 302 跳转会导致 POST 变成 GET。攻击者必须利用 gopher 协议手工构造包含请求头、请求体的原始 HTTP 数据流，从而让服务器端代理发送 POST 请求并获取 Flag。

2. 怎么想（破题思路）

  • 参数为 ?url=_，存在 SSRF 漏洞。
  • 题目明确提示：“这次是发一个 HTTP POST 请求”，并且“ssrf是用php的curl实现的，并且会跟踪302跳转”。
  • 直接使用 http://127.0.0.1/flag.php 请求，如果内部服务只响应 POST，会失败；即使跳转，cURL 跟随 302 时也会变成 GET 请求，丢失 POST 数据。
  • 突破口：使用 gopher:// 协议。它可以充当“原始 TCP 数据包发送器”，将完整的 HTTP POST 数据包原样发送给内网服务的 80 端口。
  • 必须精确计算 Content-Length（请求体长度），并使用 %0d%0a（回车换行）来分隔请求头和请求体。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：参数名错误导致无回显

踩坑情况：使用 flag=1 或 cmd=ls 构造 Payload，页面返回 200 但无回显。

原因分析：flag.php 接收的参数名不是 flag 也不是 cmd。

改进方式：利用 file:///var/www/html/flag.php 读取源码或按 F12 查看源码，发现真实参数名为 key，并且注释里给出了 debug 值。

踩坑记录二：浏览器地址栏自动二次编码

踩坑情况：直接在浏览器地址栏输入 gopher Payload，页面返回空白或乱码。

原因分析：浏览器会对 URL 中的 % 进行二次转义（例如把 %0d 变成 %250d），导致 gopher 协议发送给内部服务的 HTTP 数据包格式损坏。

改进方式：必须使用 curl 命令行或 Burp Suite Repeater（重放器） 发送请求，这两者都不会对 URL 进行二次编码。如果必须用浏览器，则需使用双重编码（把 % 换成 %25）。

踩坑记录三：环境在最后时刻过期

踩坑情况：执行命令后终端返回 Content-Length: 0 或显示“环境已销毁”。

原因分析：环境倒计时归零，服务器关闭。

改进方式：拿到 Flag 后必须秒提交。如果环境过期，立刻回 CTFHub 面板重新开启，再执行一次相同的 Payload 即可。

详细实操步骤（使用 curl 命令发送）

第一步：获取新的 key 值

浏览器访问 ?url=http://127.0.0.1/flag.php，按 Ctrl+U 查看源码，找到 <!-- Debug: key=xxxxxxxx... -->。假设拿到的 key 是 c79b0d610dc8c785377d233e812360a2。

第二步：构造并执行 gopher Payload

在终端中执行以下命令：

curl -i "http://challenge-ccf5329690aaf427.sandbox.ctfhub.com:10800/?url=gopher://127.0.0.1:80/_POST%20/flag.php%20HTTP/1.1%0d%0aHost:%20127.0.0.1%0d%0aContent-Type:%20application/x-www-form-urlencoded%0d%0aContent-Length:%2036%0d%0a%0d%0akey=c79b0d610dc8c785377d233e812360a2"

Payload 逐字深度解析：

  • gopher://127.0.0.1:80/：声明使用 gopher 协议，发送数据到本机 80 端口。
  • _：gopher 协议的占位符，后面紧跟要发送的原始 TCP 数据。
  • POST%20/flag.php%20HTTP/1.1%0d%0a：构造 HTTP 请求行（%20 是空格，%0d%0a 是回车换行）。
  • Host:%20127.0.0.1%0d%0a：构造 Host 请求头。
  • Content-Type:%20application/x-www-form-urlencoded%0d%0a：声明 POST 请求体格式。
  • Content-Length:%2036%0d%0a：声明请求体长度为 36 字节（即 key=+32位密钥 的总长度）。
  • %0d%0a：空行，用于分隔 HTTP 请求头和请求体（必须有！）。
  • key=c79b0d610dc8c785377d233e812360a2：POST 的请求体数据。

第三步：获取并提交 Flag

执行成功后，终端会直接回显 Flag：ctfhub{bb440f28ece6c13485bfc6e3}，立刻提交。

4. 怎么迁移（跨领域联想）

  • SSRF 打内网 Redis 未授权：利用 gopher 协议可以构造 Redis 的命令行数据流，写入 Webshell 或定时任务，实现 RCE。
  • SSRF 打 MySQL：利用 gopher 协议构造 MySQL 的握手和查询数据包，进行内网数据库攻击。
  • 安全开发（SDL）：防御 SSRF 必须限制协议为 http/https，并禁止服务器访问内网 IP。不能因为“只是获取内容”就放松对用户输入 URL 的校验。

三、名词大全与原理深度复盘

1. gopher 协议

Gopher 是一种早期的互联网协议，在 SSRF 漏洞中因其“可以发送任意 TCP 数据流”的特性而变成“万能协议”。攻击者利用它构造原始的 HTTP 请求包，从而打破 HTTP 协议的一些限制（如不能发 POST、跟随 302 跳转后变 GET 等）。

2. HTTP POST 请求的原始结构

一个标准的 POST 请求由四部分组成：请求行（Request Line）、请求头（Headers）、空行（CRLF）、请求体（Body）。其中空行（%0d%0a）是至关重要的分隔符。Content-Length 必须严格等于请求体的字节长度，否则服务器会截断请求。

3. 浏览器与终端对 URL 编码的差异

浏览器为了用户友好性，会自动进行 URL 解码和编码（二次编码），导致 gopher Payload 损坏；而 curl 或 Burp 会原样发送 URL 编码后的数据。这也反映了渗透测试中“工具选择”的重要性。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与“内网访问”的区别：“内网访问”只是简单的 GET 请求；本题要求构造完整的 POST 请求，且需要处理 302 跳转带来的数据丢失问题。
  • 与“伪协议读取文件”的区别：伪协议利用 file:// 直接读文件；本题利用 gopher:// 发送网络数据包，属于网络层的攻击。

2. 这种题目的出现原因

开发人员在实现 SSRF 功能时，没有限制用户输入的协议和 IP。虽然编写了 cURL 代码，但在处理 302 跳转或限制 POST 请求时存在逻辑漏洞。这本质上是“网络协议特性滥用”导致的安全边界突破。

3. 这种应用在实际中如何体现？

在红蓝对抗中，SSRF 配合 gopher 协议是打点内网服务的“核武器”。攻击者常利用它攻击 Redis、MySQL、FastCGI 等服务，快速获取服务器权限，是内网渗透的经典手段。

4. 如何抽象理解概念（大白话理解）

把服务器比作一个传令兵：

  • 普通 SSRF：你让传令兵去隔壁房间“看一眼”有没有文件（GET 请求），但门卫规定必须“递进去”一张纸条才给回应（POST 请求）。
  • gopher 协议：传令兵不懂怎么递纸条。于是你亲手写好了一封完整的信（包含信封、格式、内容），装进了一个叫“gopher”的万能信封里递给他。
  • 执行与结果：传令兵把万能信封原封不动地给了门卫。门卫拆开信封，看到了标准格式的信件，成功把 Flag 交给了传令兵。
