game1 - Bugku WEB Writeup

2026年9月13日 | WEB | 抓包改包 / 签名伪造

这道题名为“game1”，分类为 WEB。进入页面后是一个打砖块游戏，游戏结束后会显示分数。题目要求获取 Flag，不能靠玩游戏，而是要通过伪造分数来骗过服务器。

一、题目信息

  • 题目名称：game1
  • 题目平台：Bugku CTF
  • 题目类型：WEB / 抓包改包 / 参数签名伪造
  • 涉及工具：浏览器开发者工具（F12）、Mac 终端（curl）

二、解题过程（详细步骤）

1. 抓包分析：定位分数提交接口

打开游戏并按下 F12，切换到 Network（网络）面板。点击“再来一次”并故意输掉游戏。在请求列表中发现了关键请求：score.php?score=100&ip=xxx&sign=zMMTAw==。

分析参数发现，score 是分数，sign 是分数的 Base64 编码（zMMTAw== 解码后为 100）。服务器通过验证 sign 来确认分数未被篡改。

2. 伪造满分签名

在控制台（Console）中，使用前端暴露的 Base64 函数计算满分（100000分）的签名：

Base64.encode('100000')

得到签名串：zMMTAwMDAw==。

3. 使用 curl 构造请求获取 Flag

在 Mac 终端中，使用 curl 命令伪造一个包含满分和正确签名的请求，发送给服务器：

curl "http://160.202.254.160:10508/score.php?score=100000&sign=zMMTAwMDAw=="

服务器接收到伪造的高分及合法签名后，返回了包含 Flag 的响应。

最终 Flag： flag{b1cdcd5d50dd1ba0bf3faca7c0229718}

三、原理深度剖析（为什么伪造请求能成功？）

核心概念：客户端不可信原则

这道题完美演示了 Web 安全中一个致命漏洞：服务器盲目信任了前端（浏览器）提交的数据。

  1. 前端负责计算分数和签名：游戏在浏览器中运行，分数由前端 JS 计算，签名也是前端通过公开的 Base64 算法生成的。
  2. 前端代码是透明的：我们在控制台里可以直接调用 Base64.encode()，这意味着我们掌握了“伪造数据”的钥匙。
  3. 服务器只验证签名的合法性：服务器收到请求后，只检查了 sign 是否和 score 匹配（即验证 Base64 解码后是不是这个分数），却无法判断这个分数是不是玩家真正玩出来的。

通俗比喻：这就像学生自己批改试卷，然后告诉老师“我考了100分，这是我的证明”。因为证明的算法（Base64）是公开的，学生完全可以自己伪造“考了100000分”的证明。老师只看证明对不对，却不去核对试卷，结果就被骗了。

防御方法：服务器端应该使用带有密钥的哈希算法（如 HMAC-SHA256）进行签名，或者在服务器端独立校验游戏逻辑，不能依赖前端提交的分数和签名。

四、知识点总结（核心复习素材）

  • 1. 客户端不可信原则：任何在浏览器中运行的数据（包括分数、签名）都可能被篡改。安全校验必须在后端进行。
  • 2. 抓包与改包：使用 F12 的 Network 面板抓取关键请求，分析其参数结构，是 Web 渗透测试的基础技能。
  • 3. 签名绕过：当服务器使用前端生成的签名（如 Base64）验证数据完整性时，攻击者可以在前端计算出合法签名，进而伪造高权限请求（如满分）。防御方法是使用后端密钥进行 HMAC 等强签名。
