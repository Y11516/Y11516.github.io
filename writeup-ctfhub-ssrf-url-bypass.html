CTFHub SSRF - URL Bypass

2026年9月23日 CTFHub Web安全 SSRF URL解析绕过

一、题目信息

  • 题目名称：SSRF - URL Bypass
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / SSRF（服务端请求伪造） / 白名单绕过
  • 靶场链接：http://challenge-15db4b10b9a7bd40.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是URL 解析绕过。后端代码对用户传入的 URL 参数做了白名单校验，强制要求必须以 http://notfound.ctfhub.com 开头。但由于 URL 协议标准（RFC 3986）中 @ 符号的特殊性，攻击者可以利用它构造出“校验时看起来合法，但实际请求目标是内网”的 URL，从而绕过白名单限制，成功 SSRF 请求到 127.0.0.1/flag.php。

2. 怎么想（破题思路）

  • 访问页面，提示“请求的URL中必须包含 http://notfound.ctfhub.com，来尝试利用URL的一些特殊地方绕过这个限制吧”。
  • 如果直接请求 ?url=http://127.0.0.1/flag.php，会被后端代码检测到“不以 notfound.ctfhub.com 开头”而直接拦截报错。
  • 突破口：URL 结构允许包含认证信息（用户名:密码），并用 @ 符号与真实主机分隔。后端代码如果用 strpos() 校验字符串前缀，就会把 http://notfound.ctfhub.com 当成合法前缀放行。
  • 而底层网络请求库（如 cURL）在真正发起请求时，会解析 @ 后面的 127.0.0.1 作为真实目标。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：直接请求 127.0.0.1 被拦截

踩坑情况：尝试输入 ?url=http://127.0.0.1/flag.php，页面报错 url must startwith "http://notfound.ctfhub.com"。

原因分析：后端代码执行了类似 if (strpos($_GET['url'], 'http://notfound.ctfhub.com') !== 0) 的前缀校验，直接拒绝了不符合要求的 URL。

改进方式：利用 @ 符号构造 URL，既满足前缀校验，又让 cURL 请求 127.0.0.1。

详细实操步骤（逐字解析）

在浏览器地址栏输入以下 Payload：

http://challenge-15db4b10b9a7bd40.sandbox.ctfhub.com:10800/?url=http://notfound.ctfhub.com@127.0.0.1/flag.php

Payload 逐字深度解析：

  • ?url=：后端接收的参数名。
  • http://：声明协议。
  • notfound.ctfhub.com：伪造的认证信息。后端代码看到它，认为前缀合法，予以放行。
  • @：URL 中的分隔符。前面是用户名（或认证信息），后面是真实请求的主机。
  • 127.0.0.1：真实请求的主机（本地回环地址）。底层 cURL 会忽略 @ 前面的内容，直接请求它。
  • /flag.php：真实请求的文件路径。

页面直接回显明文 ctfhub{547dc4c1f56f01f5ea1b38f7}，提交即可通关。

4. 怎么迁移（跨领域联想）

  • 绕过云厂商白名单：在云安全场景中，如果云函数或WAF只允许请求特定域名的URL，攻击者可以利用 @ 符号构造恶意 URL，绕过域名白名单，进而访问内网元数据（如 169.254.169.254）。
  • 钓鱼链接伪装：在实际网络钓鱼中，攻击者常使用 http://trusted-bank.com@evil.com/ 这种链接，诱导用户点击。用户粗略一看以为要去正规银行，实际上浏览器会跳转到 evil.com。
  • 安全开发（SDL）：防御 SSRF 绝不能仅靠字符串匹配校验。必须使用 URL 解析库（如 PHP 的 parse_url()）提取真实的 Host，并对其做黑名单或白名单校验。同时需禁用不安全的协议（如 file、gopher）。

三、名词大全与原理深度复盘

1. URL 标准结构（RFC 3986）

一个标准的 URL 格式为：scheme://user:password@host:port/path?query#fragment。本题正是利用了 user:password@ 这一部分。当后端使用字符串前缀匹配时，看到 http://notfound.ctfhub.com 就放行，而忽略了后面还有 @127.0.0.1 这个真实的主机地址。

2. 白名单机制与解析差异

白名单机制（只允许特定域名）本身是安全的，但“校验逻辑”与“执行逻辑”必须使用同一套解析标准。后端代码用“字符串”校验，而底层 cURL 用“协议标准”解析，两者之间的差异就是漏洞的温床。

3. 为什么 @ 后面的内容才是真实目标？

在 URL 规范中，@ 前面的部分是认证信息。HTTP 基本认证允许 http://user:pass@host/。cURL 等库会将其剥离并用于身份验证，而实际连接的 host 是 @ 后面的部分。这正是本题能成功绕过的根本原因。

四、题目思考

1. 这跟前面的 SSRF 题有什么区别？

  • 与“内网访问”的区别：“内网访问”直接请求 127.0.0.1 即可，没有前端限制；本题增加了白名单校验，需要绕过。
  • 与“伪协议读取文件”的区别：伪协议利用的是 file:// 等底层协议；本题利用的是 URL 字符串解析的差异，属于逻辑层面的绕过。
  • 与“POST请求”的区别：POST请求用 gopher:// 构造复杂的数据包；本题只需要巧妙地修改 URL 的结构，属于“四两拨千斤”的绕过。

2. 这种题目的出现原因

这类漏洞源于开发人员的安全意识不到位。他们知道要防 SSRF，于是写了白名单校验，但错误地使用了字符串匹配（strpos）而非标准 URL 解析（parse_url）。这本质上是“安全校验逻辑存在缺陷”，防御方与攻击方在协议解析标准上存在认知偏差。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，SSRF 是突破边界进入内网的核心入口。攻击者常利用 @、#、? 等 URL 特殊字符，配合 302 重定向、DNS 重绑定等技术，绕过企业的 WAF 和 URL 白名单，进而攻击内网的 Redis、MySQL 或云元数据服务。

4. 如何抽象理解概念（大白话理解）

把服务器比作大楼的安检员：

  • 白名单校验（前台安检）：安检员（后端代码）只看你纸条上开头写的是不是“内部人员”（notfound.ctfhub.com）。
  • 攻击者构造：你在纸条上写：“内部人员：去机密档案室”。安检员一看：“哟，开头是内部人员，放行。”
  • 底层请求（实际执行）：真正的跑腿小哥（cURL）拿到纸条，按照纸条上的格式，只认冒号后的地址：“去机密档案室”。于是他直接绕过了安检，去机密档案室取回了 Flag。
  • 结论：安检员只看了“用户名”就放行，却没检查“真实目的地”。
