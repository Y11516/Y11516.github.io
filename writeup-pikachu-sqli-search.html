一、题目信息

  • 题目名称：SQL-Inject 搜索型注入
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 搜索型 / GET 方式
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_search.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是搜索型 SQL 注入。与普通的字符型注入不同，搜索型注入的后端 SQL 语句通常使用 LIKE 关键字进行模糊匹配，代码形态类似 select * from users where username like '%$input%'。攻击者不仅要闭合单引号，还必须处理变量前后的 % 通配符，才能成功注入恶意逻辑并拖取全表数据。

2. 怎么想（破题思路）

页面提示“如果记不住用户名，输入用户名的一部分搜索的试试看？”。解题思路如下：

  • 首先进行正常搜索，输入 vince，确认接口可正常匹配数据。
  • 在搜索词后添加英文单引号 vince%'，观察是否引发数据库语法报错，以此确认闭合点。
  • 构造能够同时闭合 % 和 ' 的通用 Payload：%' or 1=1 #，使查询条件恒为真。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：闭合测试时的语法报错引发恐慌

踩坑情况：在输入框输入 vince%' 并提交，页面直接返回了红色的 MySQL 语法错误提示。

原因分析：后端代码被拼接为 like '%vince%''。多出来的单引号破坏了 SQL 语法结构，从而触发报错。这属于正常现象，是漏洞存在的直接证据。

改进方式：理解报错是注入测试的第一步。构造 Payload 时，必须使用注释符将原代码末尾多余的引号注释掉，从而恢复语法的完整性。

踩坑记录二：未处理通配符导致注入失败

踩坑情况：尝试直接使用字符型注入的 Payload ' or 1=1 #，可能无法成功获取全表数据，或者 SQL 语法报错。

原因分析：搜索型注入的代码结构为 like '%输入%'。输入开头的单引号无法闭合前面的 %，导致 Payload 无法生效。

改进方式：Payload 必须以 % 开头，即 %' or 1=1 #，这样才能正确闭合前面的通配符和单引号，构成逻辑完整的注入语句。

终极解法：利用通配符与逻辑绕过

在输入框中提交以下 Payload：

%' or 1=1 #

代码逐个符号深度解析：

  • %：SQL 通配符，匹配任意字符。用于替换原代码中的模糊匹配前缀。
  • '：单引号。用于闭合原 SQL 语句中的左单引号。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。使得查询条件变为 like '%%' or 1=1。因为 1=1 恒为真，数据库会忽略原有搜索词限制，返回所有用户数据。
  • #：MySQL 注释符。用于将原代码末尾剩余的 %' 注释掉，保证 SQL 语句语法的完整性。

提交后，页面成功回显了 7 条用户数据（vince、allen、kobe、grady、kevin、lucy、lili），证明注入攻击成功。

4. 怎么迁移（跨领域联想）

  • 模糊查询应用场景的安全测试：在电商平台的商品搜索、后台管理系统的用户检索、日志查询等功能中，大量使用了 SQL 的 LIKE 语句。这类搜索框是 SQL 注入的高发区，渗透测试时需重点关注。
  • 代码审计：审计代码时，搜索关键字 like 并结合字符串拼接（如 "%" . $_GET['keyword'] . "%"）的写法，应直接判定为存在 SQL 注入风险。这是最典型的白盒审计特征之一。
  • WAF 绕过：当 WAF 拦截了 or 1=1 时，可以尝试使用 union select 联合查询，或者内联注释 /**/、大小写混淆等方式绕过规则拦截，从而继续渗透。

三、名词大全与原理深度复盘

1. 搜索型注入与字符型注入的区别

字符型注入的 SQL 结构是 username = '$input'；搜索型注入的 SQL 结构是 username like '%$input%'。搜索型注入多了一层 % 通配符的包裹。这要求攻击者在 Payload 开头加上 % 以及 '（即 %'），才能完成闭合。

2. LIKE 通配符的底层逻辑

在 SQL 中，% 代表零个或多个字符。系统在执行 like '%%' 时，意味着匹配所有字符串（即匹配全表）。攻击者正是利用了这一点，将原本精确匹配的查询，利用逻辑漏洞转化为全表扫描。

3. 为什么需要 # 注释符？

后端代码拼接后，多余的 %' 留在语句末尾，如果不注释掉，数据库会将其视为非法字符并报错。使用 # 可以截断后续代码，使 SQL 语句在执行到此处时逻辑完整、语法正确。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与字符型注入相比：字符型注入只需闭合单引号 '；搜索型注入必须同时闭合 % 和 '，且末尾的 %' 必须一并处理。构造难度略微提升。
  • 与数字型注入相比：数字型不需要任何引号闭合，直接拼接逻辑即可；搜索型需要精确掌握当前 SQL 语句的形态，才能构造出语法正确的攻击载荷。

2. 这种题目的出现原因（为什么存在）

这类漏洞源于开发人员在实现搜索功能时，直接将用户输入的搜索词与 % 通配符进行字符串拼接，并交给数据库执行。缺乏对引号等特殊字符的过滤（或转义），使得攻击者能够轻松闭合原有的 SQL 结构，执行任意查询逻辑。

3. 这种应用在实际中如何体现？

在实际的安全事件中，搜索型注入常被用于批量获取网站的注册用户信息、订单信息等敏感数据。如果攻击者配合联合查询，甚至可以直接读取数据库中的管理员账号密码，为后续拿下服务器权限铺平道路。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个图书馆的管理员：

  • 正常搜索：你说“我找名字里包含 vince 的书”（后端 SQL 为 like '%vince%'）。管理员把所有包含这个关键词的书拿给你。
  • 搜索型注入：你狡猾地说：“我找名字里包含 % 的书（也就是全部），或者把所有书都给我（or 1=1），后面的话当我没说（#）”。管理员没理解你语句里的逻辑陷阱，直接把整个图书馆所有的书都搬了出来。
