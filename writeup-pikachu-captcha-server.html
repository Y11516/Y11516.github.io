验证码绕过(on server) - Pikachu 靶场 Writeup

2026年9月17日 Pikachu 靶场 Web安全 暴力破解 验证码绕过

这是我做完 Pikachu 第一关后的第二关。第一关没有验证码，我顺利地用 Python 完成了爆破。但这一关加入了图形验证码，而且 Burp Suite 在本地环境死活抓不到包。本篇 Writeup 记录了我从 Burp 抓包失败，到转战 F12 Network 面板过滤流量，最终成功登录的心路历程。

一、题目分析

  • 靶场路径：暴力破解 -> 验证码绕过(on server)
  • 页面现状：多了一个图形验证码输入框，并在后台有对应的验证逻辑。
  • 题目意图：考察是否理解“服务端验证码”的逻辑缺陷（即验证码在验证后未及时销毁，导致可复用）。

二、核心原理：验证码为什么能绕过？

逻辑缺陷： 在后台代码中，服务器把验证码存到了 Session 里。如果你第一次输入了正确的验证码，点击登录，验证码会被校验为“正确”。但是，服务器并没有立刻清空 Session 里的验证码。

攻击思路： 我们只需要在浏览器里输入一次正确的验证码，然后抓取这个请求，在 Burp 里反复重放（把密码替换成不同的字典），服务器会一直认为验证码是正确的，从而允许我们持续进行密码爆破。

深度拓展：为什么验证码在验证后必须及时销毁？

在验证码机制中，“验证后立即销毁”是一条铁律。如果验证码在验证后（无论成功还是失败）没有被及时销毁，就会引发极其严重的安全问题。结合本关的实战，原因主要有以下四点：

原因一：防止“重放攻击”（Replay Attack）—— 最致命的原因

假设服务器生成了一个验证码 1234，攻击者输入 1234，服务器验证通过（或密码错误但验证码通过），但没有销毁这个 1234。

攻击者操作： 攻击者抓包，保留着 1234 这个参数，然后把用户名改为 admin，密码参数改为字典里的各种密码，不断发送请求。

结果： 因为 1234 一直没有失效，服务器会认为每一次请求都是合法的。验证码形同虚设，攻击者顺利完成了自动化爆破。

原因二：彻底阻断自动化脚本（防爆破）

验证码的设计初衷就是为了区分“人”和“机器”。如果能复用，攻击者只需要手动输入一次验证码，或者用 OCR（光学字符识别）工具识别一次，之后就可以利用脚本无限次发送登录请求。及时销毁意味着每一次尝试登录，都必须获取一个新的验证码并重新识别，这极大地增加了攻击者的时间成本和计算成本。

原因三：防止并发/多线程绕过（逻辑漏洞）

在一些存在并发漏洞的代码中，攻击者可以利用“时间差”进行攻击（这也是 CTF 中常考的“条件竞争”）。如果验证码在验证后不立即销毁，攻击者可以开启多个线程（比如 50 个并发），同时拿着同一个正确的验证码 1234 去尝试 50 个不同的密码。服务器在极短的时间内处理这些请求时，可能还没来得及销毁验证码，导致这 50 次请求全部被判定为“验证码正确”，从而实现了并发爆破。

原因四：会话状态管理与资源泄露

验证码通常是存在服务器的 Session 或 Redis 缓存里的。如果不及时销毁，这些无效的验证码会占用服务器内存。如果验证码没有设置合理的过期时间，随着用户访问量的增加，会导致服务器资源被耗尽（类似于 DDoS 攻击中的资源耗尽）。

💡 开发者的正确做法： 在代码逻辑中，无论比对结果是成功还是失败，必须第一时间删除 Session 中的验证码（unset($_SESSION['captcha']) 或 Redis 的 DEL 操作），然后再判断密码是否正确。

三、解题过程（详细步骤与踩坑记录）

1. 踩坑：Burp Suite 抓不到本地 Pikachu 包

我按照教程配置了 Burp 代理，但 HTTP history 里全是百度和搜狗的流量，没有 Pikachu。

原因分析： 1. 浏览器默认绕过 localhost 的代理；2. Pikachu 和 Burp 端口冲突（都在 8080）；3. Intercept 开启导致请求被卡住。即便更换了 IP 也未能成功。

2. 破局：使用浏览器 F12 面板精准抓包

放弃 Burp，直接使用浏览器自带的开发者工具：

  • 按 F12 打开开发者工具，切换到 Network（网络）面板。
  • 勾选 Preserve log（保留日志）。
  • 在页面输入 admin / 123456 和正确验证码，点击 Login。
  • 在 Network 列表里，发现请求多达 25 个（包括 CSS、JS、图片）。这是正常现象，F12 会记录页面加载的所有资源。
  • 点击 Fetch/XHR 过滤器，或者直接搜索 bf_server.php，精准定位到了核心的 POST 请求。
  • 查看该请求的 Payload，确认了参数格式为 username=admin&password=123456&captcha=sj801v&submit=Login。

🔍 为什么偏偏搜 bf_server.php？

因为 bf_server.php 就是后端处理登录的“大脑”。

  1. 当你点击 Login 按钮时，前端 HTML 代码里的 <form> 标签其实已经写好了要把数据发给谁。你可以去 Elements 面板看看那个表单，代码大概率是 <form action="bf_server.php" method="POST">。
  2. bf_server.php 这个文件负责接收用户名、密码和验证码，去数据库里比对，然后告诉你“登录成功”或者“失败”。
  3. 其他的 css、js 只是用来给页面化妆和做特效的，跟破解毫无关系。

所以，搜索 bf_server.php 是为了“精准狙击”，直接过滤掉所有无关的图片和样式，直击要害。

🎯 为什么也可以用 Fetch/XHR 过滤器？

这也是一个非常专业的小技巧：

  • 现代网页加载数据，通常用的是 XHR（XMLHttpRequest）或 Fetch 技术（这叫 Ajax 异步加载）。
  • 点击 Fetch/XHR 过滤器，浏览器就会只显示动态请求，直接把那些死板的图片、CSS 文件统统隐藏。
  • 因为登录往往是一个动态的 POST 请求，所以点击这个过滤器，那个核心的 bf_server.php 就会立刻现形，不用你再手动去搜了。

拓展思考：为什么在真实护网中，红队更喜欢看 JS 文件？

截图里说的“搜 bf_server.php 是为了精准狙击、过滤干扰”，这在 CTF 这种纯手工搭建的简单靶场里是绝对正确的。因为靶场只有一个简单的表单，后端逻辑就是核心考点。

但是，为什么在真实的护网（HW）中，黑客和红队却经常像“寻宝”一样去翻看、甚至扒取 JS 文件呢？因为现代 Web 架构发生了巨大的变化，JS 文件在实战中已经成了信息泄露的重灾区和突破口。以下是护网中必须看 JS 的核心原因：

  1. 前后端分离架构的普及： 现在的企业级系统很少像 CTF 靶场那样用 PHP 直接渲染页面了，绝大多数是“前后端分离”（如 Vue、React 框架）。后端（PHP/Java/Go）只负责提供 API 接口和业务逻辑；前端（JS）负责页面展示、路由跳转以及与后端 API 交互。在前后端分离架构下，你抓 HTML 页面什么有用的信息都看不到，所有的业务逻辑、请求路径、参数格式，全都在打包压缩后的 app.js 或 chunk.js 里。不看 JS，你连后端的 API 接口在哪都不知道，更别提测试漏洞了。
  2. JS 文件是“敏感信息泄露”的宝库： 开发人员为了方便调试或者由于疏忽，经常会把极其敏感的信息硬编码（写死）在 JS 文件里。在护网的信息收集阶段，从 JS 中提取敏感信息是必备操作：
    • 未授权的 API 接口：发现隐藏的后台管理接口、测试接口、文件上传接口。
    • 硬编码的密钥：如云服务的 AccessKey、SecretKey、数据库连接密码、JWT 签名密钥。
    • 内网 IP 或域名：帮助攻击者进行内网横向移动或寻找边缘资产。
    • 测试账号密码：开发留下的测试账号（如 test/test123）。
  3. 挖掘前端逻辑漏洞： 有些系统为了减轻服务器压力，把部分校验逻辑放在了前端（JS）里。比如：输入框限制只能输入数字、金额计算逻辑、或者隐藏的“超级管理员”按钮（通过 display: none 隐藏）。攻击者在看 JS 时，能直接发现这些逻辑，从而通过修改 HTTP 请求包（绕过 JS 验证）或直接调用特定接口来实现越权、0元购等攻击。
  4. 寻找 WAF 绕过的线索： 护网中经常遇到各种 WAF（Web 应用防火墙）。有时候，后端接口被 WAF 保护得死死的，但静态的 JS 文件通常是放行的（因为 WAF 默认 JS 是静态资源）。攻击者通过阅读 JS，了解后端期望的数据格式，从而构造出能绕过 WAF 的畸形 Payload。
  5. 源码泄露与前端源码审计： 有时候开发在打包部署时，没有关闭 Source Map（xxx.js.map 文件）。攻击者下载 .map 文件，就能直接还原出开发写的原始源代码（可能包含大量注释、敏感接口和未加密的变量名）。

3. 验证码复用逻辑的完美体现

我手动输入了正确的验证码，页面显示 login success。这证明了服务端的逻辑漏洞：验证码一旦验证成功，只要 Session 未过期，就可以被重复使用。如果这是真实的攻击场景，攻击者只需抓取一次正确的验证码，然后编写脚本复用这个验证码，即可完成密码爆破。

💡 你的“顿悟”时刻：如何自动化利用这个漏洞？

当你手动输入一次正确的验证码，成功进入后，如果你再去 Network 里看请求，你会发现：

  • 原本的验证码参数 captcha=sj801v 被你抓下来了。
  • 既然后端不销毁它，你只要写一个 Python 脚本，把 username=admin&password=123456&captcha=sj801v 里的 password 换成字典里的密码，疯狂往 bf_server.php 发 POST 请求。
  • 只要验证码不刷新，服务器就一直认这个号，你的脚本就能无限次尝试密码，这就是“验证码复用漏洞”的可怕之处。

通过这个思路，你将之前学到的 Python 脚本知识（如 requests.post）与本次的验证码抓包结合起来，就能写出一个绕过验证码的自动化爆破脚本。

四、知识点总结与防御思考

💡 F12 Network 面板的过滤： 现代网页请求极其庞杂。学会使用 Fetch/XHR 过滤器，或者按 Doc 类型过滤，是安全从业者高效分析请求的基本功。

💡 防御手段： 1. 验证码使用一次后立即失效（无论登录成功还是失败）；2. 限制单个 Session 或 IP 的尝试频率；3. 采用更复杂的验证码（如滑动拼图、reCAPTCHA）。

做一道题，就要往自己脑子里装点东西。
