RCE-Labs Level 28 - 通配符 ? 绕过 WAF

2026年10月5日 RCE-Labs WAF绕过 Shell语法 网络基础

一、题目信息

  • 1.题目名称：RCE-Labs Level 28 (通配符 ? 代替单字符)
  • 2.题目平台：RCE-Labs 靶场 (灵境平台部署)
  • 3.题目类型：Web安全 / 远程代码执行 (RCE) / WAF 绕过 / Shell 语法
  • 4.靶场链接：http://靶机IP:8080/less-28/
  • 5.涉及工具：浏览器

二、解题步骤

1. 分析题目考什么

这一关的源码里，黑名单再次升级，几乎封禁了前面学过的所有命令：cat|tac|head|tail|more|less|nl|sort|uniq|od|xxd|hexdump|base32|base64|strings|grep|file|find|cp|mv|ping|curl|echo|wget|nc|ncat|sed。弹窗提示“利用通配符 ？ 来模糊匹配单个字符”。这标志着我们正式进入 Shell 语法层面的 WAF 绕过。

2. 怎么想（破题思路与踩坑记录）

踩坑记录一：命令全被拉黑，无命令可用

尝试 Payload：尝试直接使用 ?cmd=cat /flag、?cmd=sed -n '1p' /flag 等常规命令。

失败响应：页面无任何回显（命令被 WAF 拦截）。

原因分析：WAF 的正则 #/cat|sed|.../# 匹配到了完整的命令关键字，直接丢弃了请求。

改进方式：既然 WAF 通过匹配完整的字符串拦截，那么我们只要打破字符串的连续性即可。利用 Shell 的通配符 ?。

3. 怎么解（详细步骤与逐字翻译）

源码核心逻辑

$pattern = '/cat|tac|head|tail|more|less|nl|sort|uniq|od|xxd|hexdump|base32|base64|strings|grep|file|find|cp|mv|ping|curl|echo|wget|nc|ncat|sed/';
if(!preg_match($pattern,$cmd)){
    system($cmd);
}

最终成功 Payload 与逐字解析

?cmd=/???/c?t /flag

成功响应：页面直接回显明文 flag{TEST_Dynamic_FLAG}。

命令逐字解析：

  • /???/c?t：? 是 Shell 通配符，代表任意单个字符。Shell 在执行前，会自动到系统目录下查找匹配的文件。它发现 /bin/cat 符合这个模式（??? 匹配 bin，c?t 匹配 cat），于是把它替换成了 /bin/cat。
  • /flag：要读取的目标文件。
  • 绕过原理：WAF 检测到的字符串是 /???/c?t，它里面并不包含连续完整的 cat 字符串（WAF 只看字符序列，不懂 Shell 替换），于是放行。而 Shell 收到指令后，先进行“通配符展开”，再执行真正的 /bin/cat。

4. 怎么迁移（跨学科与跨领域联想）

  • 真实渗透中的免杀：在真实的护网中，WAF 会拦截大量包含明文命令的请求。红队人员经常利用通配符（?、*）、拼接（c'a't）、变量（$a$b）等方式来绕过基于文本特征的 WAF。
  • 系统运维中的模糊匹配：运维人员经常使用 rm -rf /tmp/??? 来删除临时目录下的特定文件，或者用 ls /etc/*.conf 批量查看配置文件，这体现了 Shell 通配符强大的自动化能力。

三、名词大全与原理深度复盘

1. 通配符 ? 与 Shell 扩展 (Globbing)

在 Shell 中，? 表示匹配任意单个字符，* 表示匹配任意多个字符。当 Shell 解析命令时，如果发现参数包含通配符，它会去文件系统中寻找匹配的文件名，这个过程叫 Globbing（通配符扩展）。这意味着：命令还没执行，参数就已经在内存中被替换成了真实路径。 WAF 是在 HTTP 层检测文本，它无法感知 Shell 层的这个替换动作，这就是绕过成功的根本原因。

2. WAF 与 防火墙 的区别

  • 防火墙（Firewall）：工作在网络层和传输层，主要负责控制 IP 和端口的进出。它会拦截非标准端口的 TCP 连接（如 9002），这就是反弹 Shell 容易失败的原因。
  • WAF（Web 应用防火墙）：工作在应用层，专门检查 HTTP 请求的内容。它维护一个黑名单字典，包含 cat、sed 等敏感词。它只看“请求长什么样”，不看“命令执行后会变成什么”。

3. 核心网络基础与护网认知（陌生人也能看懂版）

  • 外网（公网/互联网）：拥有全球唯一的门牌号（公网 IP，如 8.8.8.8），任何人任何车都能开到你家门口。
  • 内网（局域网）：门牌号是“小区内部编号”（如 192.168.1.19），只有小区内部的人才能互相找到。外面的人想找你，必须经过小区保安（路由器/NAT）允许并做地址转换。
  • 完全隔离的内网：小区不仅不让外面的人进，甚至把大门用砖头砌死了（物理隔离）。这种环境下，反弹 Shell 和重定向写入 100% 都会失效。
  • HTTP 是公网吗？这是一个经典的误解！HTTP 不是网络，它是语言（协议）。就像“普通话”不是某个地方，而是一种交流方式。无论你是在访问内网的 OA 系统（http://192.168.1.100），还是访问百度官网（http://baidu.com），都是在用 HTTP 这个“语言”说话。所以，HTTP 既可以跑在内网，也可以跑在外网。
  • 操作系统与网络的关系：电脑操作系统是管理网络硬件的“交通警察”。你的网卡是公路，操作系统负责定义 IP 地址、网关，并内置防火墙（如 iptables）。当你监听 80 端口成功、9002 端口失败时，根本原因就是操作系统或 Docker 的虚拟网卡策略，只放行了 80 端口的出站，拦截了 9002 端口。
  • 护网是在攻击内网吗？简单来说，护网是一场“攻城战”：第一阶段是“外网打点”（攻打城门），寻找对外门户的漏洞；第二阶段是“内网渗透”（巷战与横向移动），拿下边界服务器后，以它为跳板，在内网里提权、抓密码、扫描其他机器；第三阶段是“拿下靶标”（直捣黄龙），控制核心数据库或域控。所以，内网渗透绝对是护网中最核心、最残酷、决定胜负的主战场。

四、题目思考

1. 这跟前面关卡的区别

前面关卡（Level 1-27）的绕过，更多是在“替换命令”或者“转换编码”。而 Level 28 首次触及了 Shell 的语法层。从“我该用什么命令”，进化到了“我该怎么写命令，WAF 才看不懂”。这是真正的 WAF 绕过思维的转变。

2. 这种题目的出现原因（底层逻辑与历史原因）

WAF 为了防御 RCE，会维护一个庞大的“危险命令黑名单”。但 Shell 的语法极其灵活（支持通配符、变量、拼接等），导致 WAF 的“关键字匹配”天然存在盲区。只要请求文本不包含被拉黑的字样，WAF 就无法拦截。这就是基于黑名单的防护体系必然存在的漏洞。

3. 这种漏洞在实际中的应用

在护网和红队行动中，遇到 WAF 是家常便饭。利用通配符、变量替换（如 $IFS）、编码（Base64）等手段绕过关键字拦截，是渗透测试人员的基本功。同时，防守方也据此推出了“语义分析”型的高级 WAF，不仅看关键字，还会还原命令执行后的真实意图。

4. 如何抽象理解概念（大白话）

把 WAF 比作考场门口的安检员，他手里拿着一张黑名单，上面写着“不准带写着‘刀’字的东西”。你如果直接把刀带进去，会被没收。于是你想了个办法：你带了一把“水果切切乐”，安检员看不懂这是什么（WAF 没拦截），但监考老师（Shell）一看，哦，这就是把刀，于是他帮你组装好，把水果切了（执行 /bin/cat）。这就是通配符绕过的本质。

5. 他的本质

本质是利用 Shell 解析器的“预处理”特性，将恶意命令的构建过程从“文本层面”推迟到“运行时层面”，从而绕过了应用层防火墙对静态文本的检测。

6. 如果我是出题人或者攻击者我会怎么防守或者破解

  • 防守方（蓝队）：单纯的字符串黑名单已经过时。需要部署具备“语义分析”能力的 WAF，或者直接在系统层面禁用危险函数（如 PHP 的 disable_functions），并严格限制 Web 进程的用户权限（如使用 open_basedir 限制文件访问）。
  • 破解方（红队）：如果通配符 ? 也被拦截，可以尝试变量拼接（如 a=c;b=at;$a$b /flag）、利用环境变量（如 $PATH 截取）、或者使用 base64 解码后通过管道执行（如 echo Y2F0IC9mbGFn | base64 -d | bash）。
