一、题目信息

  • 题目名称：Unsafe Fileupload (MIME type)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 文件上传漏洞 / 服务端 MIME 类型校验绕过
  • 靶场链接：http://localhost:8080/vul/unsafeupload/servercheck.php
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12 Console）

二、解题步骤

1. 分析题目考什么

本题的核心考点是服务端 MIME 类型校验绕过。与客户端校验不同，后端服务器在接收到上传文件时，会检查 HTTP 请求头中的 Content-Type（MIME 类型）。如果该类型不属于图片格式（如 image/jpeg、image/png），服务器会拒绝上传。攻击者需要通过抓包改包，将 PHP 木马的 MIME 类型伪装成图片格式，从而绕过校验。

2. 怎么想（破题思路）

页面提示“这里只允许上传图片，不要乱搞！”。解题思路如下：

  • 准备一个恶意的 PHP 文件（如 shell.php）。
  • 尝试直接上传，观察响应，确认服务器是否对 MIME 类型进行了校验。
  • 使用 F12 或 Burp Suite 抓取上传请求，修改请求体中的 Content-Type 为 image/jpeg，从而欺骗服务器认为上传的是合法图片。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：直接上传 PHP 木马被服务端拦截

踩坑情况：直接上传 shell.php，浏览器没有弹窗，但页面提示“上传失败”或显示后端报错信息。

原因分析：因为请求包中文件对应的 Content-Type 为 application/x-php，不符合服务器要求的图片类型。

改进方式：必须拦截请求，将 Content-Type 修改为 image/jpeg（或 image/png、image/gif）。

踩坑记录二：利用 F12 复制 as fetch 后手动修改导致文件丢失

踩坑情况：尝试在 F12 Network 面板通过“Copy as fetch”修改 multipart 请求体，虽然改了文件名，但上传上去的文件为空，无法执行。

原因分析：“Copy as fetch”默认只复制文本形式的请求体，丢失了上传文件真实的二进制数据。如果只改文本，服务器收到的只是一个空字符串。

改进方式：必须使用专业的抓包工具 Burp Suite，或者使用 Console 中的 FormData 配合 Blob 重新构造带有二进制数据的请求。

终极解法：利用 Console 伪造 MIME 类型上传

第一步：准备木马

新建 shell.php，写入内容：<?php phpinfo(); ?>。

第二步：在网页上选中该文件

在页面点击“选择文件”，选中 shell.php（页面可能弹窗或报错，忽略即可）。

第三步：在 Console 中执行终极 Payload

var input = document.querySelector('input[type="file"]');
var file = input.files[0];
var blob = new Blob([file], { type: 'image/jpeg' });
var fd = new FormData();
fd.append('uploadfile', blob, 'shell.php');
fetch('/vul/unsafeupload/servercheck.php', {
    method: 'POST',
    body: fd
}).then(res => res.text()).then(text => console.log(text));

代码逐个符号深度解析：

  • document.querySelector('input[type="file"]')：利用 CSS 选择器，精准定位页面上的文件选择框。
  • input.files[0]：获取用户选中的第一个文件对象（即我们的 PHP 木马）。
  • new Blob([file], { type: 'image/jpeg' })：核心突破点。Blob 是二进制大对象，这段代码将原本的 PHP 文件包装成一个新的二进制对象，并强行将其 type 属性设置为 image/jpeg。
  • new FormData()：创建一个表单数据对象，用于模拟 multipart/form-data 请求。
  • fd.append('uploadfile', blob, 'shell.php')：将伪装后的 Blob 添加到表单中。第一个参数是后端接收的参数名，第二个是文件对象，第三个是重命名后的文件名（保留 .php 后缀）。
  • fetch('/vul/unsafeupload/servercheck.php', { method: 'POST', body: fd })：发送伪造后的 POST 请求。

请求发送后，后端检查到 Content-Type 为 image/jpeg 便放行，但保存下来的文件后缀依然是 shell.php，成功绕过 MIME 校验。访问路径，成功弹出 phpinfo 页面。

4. 怎么迁移（跨领域联想）

  • Burp Suite 抓包改包：除了用 JS 脚本，另一种更通用的绕过方法是将文件改为 shell.jpg，在 Burp Suite 中拦截上传请求，将文件名改回 shell.php，同时将对应段的 Content-Type 修改为 image/jpeg，放行即可。
  • 代码审计与安全开发：本题证明了只信任客户端请求头中的 MIME 类型是极其危险的。真实开发中，必须通过读取文件内容的“魔数”（Magic Number）或使用 getimagesize() 函数来验证文件的真实类型。
  • 黑帽攻击链：在真实渗透中，拿到 WebShell 只是第一步。攻击者会立即利用 WebShell 进行提权、留下后门、探测内网拓扑，进而控制整个内网域环境。

三、名词大全与原理深度复盘

1. MIME 类型（Multipurpose Internet Mail Extensions）

MIME 类型是一种标准，用来表示文档、文件或字节流的性质和格式。在 HTTP 请求中，Content-Type 头部使用 MIME 类型来描述发送的数据。例如，JPEG 图片的 MIME 类型是 image/jpeg。

2. 服务端校验（Server-side Validation）

在服务器端执行的校验，发生在数据到达后端之后。虽然比客户端校验更安全，但如果校验逻辑本身存在缺陷（如仅信任 HTTP 头中的 MIME 类型），同样可以被攻击者绕过。

3. 为什么修改 MIME 类型能绕过？

因为 HTTP 请求是明文且由客户端构造的。攻击者完全可以控制请求头中的每一个字段。服务端读取 Content-Type 时，如果仅将其作为判断依据，而不去解析文件真实的二进制内容，就会被伪造的 MIME 类型所欺骗。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 client check 相比：client check 是前端 JS 校验，利用 F12 修改 DOM 即可绕过；MIME type 是服务端校验，必须通过抓包改包或构造 Blob 来绕过，绕过难度提升了一个层级。
  • 与后续 getimagesize 相比：MIME type 校验只看 HTTP 头；getimagesize 校验会读取文件的二进制头（魔数），检测是否为真正的图片格式，因此后续关卡需要制作“图片马”来绕过。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在编写后端代码时，误以为 HTTP 请求头中的 Content-Type 是浏览器自动生成且不可篡改的。但实际上，攻击者可以轻易通过代理工具（如 Burp Suite）修改任意请求头。开发人员未考虑到这一点，导致校验形同虚设。

3. 这种应用在实际中如何体现？

在实际的 Web 安全渗透中，文件上传漏洞是获取服务器权限最直接的方式。一旦发现，攻击者往往能直接 GetShell，进而控制服务器。在现代企业安全防护中，文件上传接口通常会被 Web 应用防火墙（WAF）重点监控，拦截恶意的文件后缀和内容。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个需要检查行李的机场安检：

  • 正常操作：你带了一个行李箱（文件），上面贴了“衣服”的标签（MIME 类型），安检员看一眼标签就放行了。
  • MIME 类型绕过：你带了一把刀（PHP 木马），但你在行李箱上贴了一个“衣服”的标签（修改 Content-Type 为 image/jpeg）。安检员只看标签不看内容，以为你带的是衣服，就放你进去了。这就是 MIME 类型校验的致命缺陷——只看标签，不查实质。
