CSRF(post) - Pikachu Writeup

2026年9月19日 Pikachu Web安全 CSRF

一、题目信息

  • 题目名称：CSRF(post) login / 修改个人信息
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站请求伪造（CSRF） / POST型篡改
  • 靶场链接：http://localhost:8080/vul/csrf/csrfpost/csrf_post_login.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是POST 型 CSRF（跨站请求伪造）。与 GET 型不同，POST 请求的参数不在 URL 中，而是在 HTTP 请求体（Body）里。攻击者无法通过简单的超链接直接触发攻击，必须构造一个包含隐藏字段的 HTML 表单，并利用 JavaScript 自动提交该表单。本题考察的是解题者能否提取 POST 请求体参数，并构造恶意页面实现静默篡改。

2. 怎么想（破题思路）

题目提示账号密码为 vince / 123456。解题思路如下：

  • 必须先用浏览器正常登录，获取服务端下发的 Cookie（身份凭证）。
  • 进入修改个人信息页面，打开 F12 的 Network 面板，提交一次正常修改，抓取 POST 请求的 Payload（请求体数据）。
  • 构造一个隐藏的 HTML 表单，表单的 action 指向该修改接口，method 为 POST，并填入恶意参数（如篡改邮箱为 hacker@evil.com）。
  • 利用 JavaScript 实现页面加载时自动提交表单，实现无感知攻击。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：用 GET 请求代替 POST 请求导致登录失败

踩坑情况：直接在浏览器地址栏构造 ?username=admin&password=123456 试图登录，页面提示“登录失败,请重新登录”。

原因分析：本题的登录接口 csrf_post_login.php 是 POST 接口，无法通过 GET 方式（地址栏参数）进行身份验证。此外，admin 并不是靶场定义的有效账号。

改进方式：必须回到页面输入框，在 Username 和 Password 中填入 vince / 123456，鼠标点击 Login 按钮进行正常登录。

踩坑记录二：本地 HTML 文件被现代浏览器 SameSite 策略拦截

踩坑情况：在本地新建 csrf_poc.html 文件并双击打开，表单自动提交后，回到靶场刷新，发现邮箱未改变。

原因分析：本地文件以 file:// 协议加载，而靶场在 http://127.0.0.1，两者属于不同的源。现代浏览器为了防止 CSRF，默认将 Cookie 的 SameSite 属性设置为 Lax，导致从本地文件发起的跨域 POST 请求不会携带靶场的身份 Cookie。

改进方式：为了绕过浏览器的同源策略和 SameSite 限制，改为在靶场页面的 F12 Console 中直接执行 JavaScript 代码，让请求从 http://127.0.0.1 这个源发出，从而自动携带 Cookie。

踩坑记录三：JS 属性覆盖导致 form.submit is not a function 报错

踩坑情况：在 Console 中执行包含 form.submit() 的自动化脚本时，控制台报出红色错误：Uncaught TypeError: form.submit is not a function。

原因分析：这是 JavaScript 中一个经典的属性覆盖陷阱。由于定义的参数中有 submit: "submit"，脚本会创建一个名为 submit 的输入框并附加到表单上。在 DOM 中，表单的子元素如果与表单的 API 方法同名，会覆盖原有的方法。因此，form.submit 此时代表的是那个输入框，而不再是一个函数。

改进方式：放弃使用 form.submit()，改用原型链调用：HTMLFormElement.prototype.submit.call(form)。这种方法强制指向最原始的表单 submit 方法，无视属性覆盖。

终极解法：利用 JavaScript 自动提交恶意表单

在已登录的靶场页面 F12 Console 中执行以下代码：

var form = document.createElement("form");
form.action = "http://127.0.0.1:8080/vul/csrf/csrfpost/csrf_post_edit.php";
form.method = "POST";

var params = {
    sex: "boy",
    phonenum: "110",
    email: "hacker@evil.com",
    add: "hacker",
    submit: "submit"
};

for (var key in params) {
    var input = document.createElement("input");
    input.type = "hidden";
    input.name = key;
    input.value = params[key];
    form.appendChild(input);
}

document.body.appendChild(form);
HTMLFormElement.prototype.submit.call(form);

代码逐个符号深度解析：

  • document.createElement("form")：在内存中动态创建一个 HTML 表单标签。
  • form.action = "..."：指定表单提交的目标 URL，这里是靶场修改信息的 PHP 接口。
  • form.method = "POST"：指定表单提交方式为 POST。
  • for (var key in params)：遍历定义好的参数对象（如 key 为 email，value 为 hacker@evil.com）。
  • input.type = "hidden"：将输入框隐藏，保证攻击悄无声息，用户在页面上看不到任何变化。
  • form.appendChild(input)：将创建的隐藏字段挂载到表单中，模拟真实表单。
  • document.body.appendChild(form)：将表单挂载到页面 DOM 树中，使浏览器可以识别并提交它。
  • HTMLFormElement.prototype.submit.call(form)：绕过属性覆盖，强制使用浏览器原生的 submit 方法提交表单。

执行完毕后，目标页面被静默刷新，邮箱被成功篡改为 hacker@evil.com。

4. 怎么迁移（跨领域联想）

  • 网络钓鱼实战：攻击者会将包含自动提交表单的 JS 脚本伪装成“点击领取奖品”或“查看照片”的网页。受害者点击链接并处于登录状态时，就会不知不觉地触发转账、修改密码等 CSRF 攻击。
  • Web 防御体系：要防御 POST 型 CSRF，必须在后端使用 CSRF Token（随机校验码）。前端页面每次加载时生成一个唯一 Token，提交时携带并校验，攻击者无法预测该 Token，这是目前主流的防御手段。
  • 现代浏览器的 SameSite Cookie：正因为 CSRF 攻击的泛滥，现代浏览器默认开启了 SameSite 防护。这也是本地 HTML 文件无法攻击成功的原因。理解这个机制，对于日常开发 Web 应用、配置 Cookie 属性极其重要。

三、名词大全与原理深度复盘

1. POST 型 CSRF 与 GET 型 CSRF 的区别

GET 请求将参数暴露在 URL 中，攻击者可以直接利用 <img> 或 <script> 标签发起请求。POST 请求将参数放在 HTTP 请求体（Body）中，这意味着无法通过简单的链接直接触发。攻击者必须构造一个完整的表单页面，并借助 JavaScript 实现自动提交，利用难度稍高。

2. SameSite Cookie 属性

SameSite 是 HTTP Cookie 的一个属性，用于控制跨站请求是否携带 Cookie。其值可以是 Strict、Lax、None。现代浏览器默认值为 Lax，这意味着通过 POST 方式发起的跨域请求不会携带 Cookie，这直接拦截了大部分 CSRF 攻击。

3. JavaScript 原型链与属性覆盖

在 JavaScript DOM 中，表单元素的子元素如果使用了与表单内置方法同名的 name 属性，则子元素会直接覆盖该方法的引用。例如，一个名叫 submit 的输入框会覆盖 form.submit 方法。理解这一点是解决“为什么浏览器会报错 is not a function”的关键。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 CSRF(get) 相比：GET 型攻击只需要一个 URL 就能触发，而 POST 型攻击需要攻击者提供包含完整 HTML/JS 代码的恶意站点，且需绕过浏览器同源策略。后者的利用门槛更高，但隐蔽性也更强。
  • 与 XSS 相比：XSS 是攻击者窃取了用户的浏览器执行权，可以无限制地操作页面；CSRF 是攻击者借用用户的身份发起请求，无法读取服务器返回的数据（盲打），破坏性往往局限于增删改数据。

2. 这种题目的出现原因（为什么存在）

这类题目出现的原因，是因为很多早期网站开发框架未能很好地分离“请求机制”和“身份验证”。开发人员假设所有 POST 请求都是用户本人通过页面交互发出的，从未想过攻击者可以在域外伪造 POST 请求，从而导致了这类漏洞。

3. 这种应用在实际中如何体现？

在实际的护网行动或渗透测试中，安全人员如果发现后台管理系统的删除用户、修改密码等接口未设置 CSRF Token 校验，会尝试构建恶意页面进行测试。如果攻击成功，将可能导致数据库被篡改、核心业务被破坏等严重后果。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个严格的保安：

  • POST 型 CSRF：保安认为 GET 请求太随意（谁都能往信箱里扔纸条），所以规定修改业务必须“面对面把信封递给我”（POST 请求）。
  • 攻击者的对策：攻击者无法通过发送一个链接来触发 POST，所以他在你家门口放了一个“自动邮筒”（恶意网页）。你只要路过看一眼（打开恶意网页），邮筒就会立刻自动把一封伪造的信件递给保安。保安看了一眼你的脸（Cookie），就收下信件办理了业务。
  • SameSite 策略：保安后来发现这样不行，于是规定：只有在公司内部（同源）递过来的信封才有效，外部来的邮筒信件一律拒收。这就是为什么我们的本地文件失效，必须在 Console 里执行的原因。
