CSRF(get) - Pikachu Writeup

2026年9月19日 Pikachu Web安全 CSRF

一、题目信息

  • 题目名称：CSRF(get) login / 修改个人信息
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站请求伪造（CSRF） / GET型篡改
  • 靶场链接：http://localhost:8080/vul/csrf/csrfget/csrf_get.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是GET 型 CSRF（跨站请求伪造）。CSRF 攻击的本质是攻击者利用受害者在目标网站上已登录的合法身份（如浏览器自动携带的 Cookie），诱导受害者点击一个精心构造的恶意链接或提交恶意表单，从而在受害者不知情的情况下执行非预期的操作。本题考察的是解题者能否提取 GET 请求的参数，伪造 URL 并成功篡改数据。

2. 怎么想（破题思路）

题目提示了用户名（如 vince），密码为 123456。解题思路如下：

  • 首先必须正常登录，获取合法的身份凭证（Cookie）。
  • 进入修改个人信息页面，观察提交操作。若提交后浏览器地址栏的参数发生变化（包含 ?sex=...&phonenum=...&email=...），则说明该操作是 GET 请求。
  • 将修改操作的参数（尤其是邮箱参数）替换为攻击者预设的恶意数据，构造完整的恶意 URL。
  • 在登录状态下直接访问该 URL，服务器会将请求视为用户本人的主动修改，从而实现 CSRF 攻击。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：不知道如何构造攻击向量

踩坑情况：登录后直接点击“修改个人信息”，页面显示空白表单，即使修改并提交，也只是普通的功能操作，未体现攻击流程。

原因分析：未理解 CSRF 的利用需要提取操作逻辑并伪造。空白表单是服务器返回的模板，并非攻击的执行代码。

改进方式：必须在空白表单中随便填写内容并提交，从地址栏中获取真实的请求 URL（包含所有参数）。然后再对这个 URL 进行参数替换（如修改邮箱）。

终极解法：构造恶意 URL 并触发

第一步：正常提交获取参数。在修改信息页面填写内容，点击 submit 按钮，浏览器地址栏将变为：

http://localhost:8080/vul/csrf/csrfget/csrf_get_edit.php?sex=boy&phonenum=12345&email=test%40123.com&add=test&submit=submit

第二步：伪造攻击 URL。将 URL 中的邮箱参数篡改为 hacker@evil.com（URL 编码后为 hacker%40evil.com）：

http://localhost:8080/vul/csrf/csrfget/csrf_get_edit.php?sex=boy&phonenum=12345&email=hacker%40evil.com&add=test&submit=submit

代码逐个符号深度解析：

  • csrf_get_edit.php：目标接口地址，负责处理用户信息的修改逻辑。
  • ?：URL 中用于分隔路径和查询字符串的符号。
  • sex=boy&phonenum=12345&add=test&submit=submit：原有参数。其中 & 符号用于连接不同的参数键值对，= 连接键和值。
  • email=：目标篡改参数。将其从 test%40123.com 修改为 hacker%40evil.com。%40 是 @ 符号的 URL 编码，浏览器解析后等同于 hacker@evil.com。

第三步：触发攻击。在保持登录状态（Cookie 未过期）的情况下，直接在浏览器地址栏粘贴刚刚构造的恶意 URL 并回车。由于服务器缺乏 Token 校验机制，它直接根据 URL 参数将用户邮箱修改为了 hacker@evil.com，证明 CSRF 攻击成功。

4. 怎么迁移（跨领域联想）

  • 网络钓鱼攻击（Phishing）：实际场景中，攻击者会将恶意 URL 伪装在图片、短链接或邮件里。只要用户处于登录状态，点击链接就会触发 CSRF，攻击者可以修改密码、添加管理员账号或转账。
  • 社交工程与蠕虫传播：著名的“新浪微博 CSRF 蠕虫”事件，就是利用 CSRF 漏洞让受害者在不知情的情况下发送带有攻击链接的微博，导致病毒式传播。
  • Web 安全防御体系：要防御 CSRF，不能只依赖前端的防范。必须在后端引入随机生成的 Token 进行校验，或者校验 HTTP 请求的 Referer 头。这是后续学习 CSRF Token 和 SameSite Cookie 属性的前提。

三、名词大全与原理深度复盘

1. CSRF（跨站请求伪造）

Cross-Site Request Forgery，是一种 Web 攻击方式。它利用的是“浏览器对目标网站的信任”。攻击者不窃取用户的 Cookie，而是利用用户登录后浏览器自动携带 Cookie 的特性，伪造用户的身份去发起请求。

2. 为什么 GET 请求容易引发 CSRF？

GET 请求的参数全部在 URL 中。攻击者可以非常容易地构造一个 <img src="恶意URL"> 或 <a href="恶意URL"> 标签，当用户打开页面时，浏览器会自动去加载这个 src 或 href，从而自动发起 GET 请求，实现攻击。而 POST 请求需要构造表单或 JS 提交，门槛略高。

3. Cookie 与 Session 机制

用户登录成功后，服务器会下发一个 Cookie 保存在浏览器中。之后用户每次访问该网站，浏览器都会自动带上此 Cookie。CSRF 的攻击基础正是建立在这个自动携带的凭证之上，服务器无法分辨这是用户本人发起的请求，还是伪造的请求。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 相比：XSS 利用的是“用户对网站的信任”，本质是执行了攻击者的 JavaScript 代码；CSRF 利用的是“网站对用户浏览器的信任”，本质是借用用户的身份发起正常请求，不需要注入 JavaScript。
  • 与其它 Web 漏洞相比：SQL 注入等是利用服务端代码逻辑漏洞，而 CSRF 是客户端和服务端交互机制上的漏洞（缺少请求来源验证）。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在设计修改、删除、转账等敏感操作接口时，使用了无状态的 GET 请求，并且没有加入任何随机校验参数（Token）。只要用户处于登录状态，任何第三方网站都可以构造链接诱导用户点击，从而触发这些敏感操作。

3. 这种应用在实际中如何体现？

在实际的渗透测试中，安全工程师会测试所有增删改的操作。如果发现请求参数中缺乏 Token，且修改操作可以通过 GET 直接触发，就会尝试构造 HTML 页面（<img src="http://target/delete_user?id=123">）进行验证。如果攻击者成功，便可实现“一键删库”或“无感转账”。

4. 如何抽象理解概念（大白话理解）

如果把银行转账比作拿号排队：

  • 正常操作：你拿着身份证（Cookie）去柜台填写转账单，柜员核对后办理。
  • CSRF 攻击：攻击者写了一张“转账给黑客”的纸条（恶意 URL），揉成团扔给你。你因为好奇把纸条打开看了看（点击了链接），结果纸条上粘着你的身份证（浏览器自动携带 Cookie），ATM 机立刻执行了转账。
  • 防御思路：怎么防止？柜员在办理时必须问你一句：“你今天的暗号是什么？”（CSRF Token 校验），答不出来就不办理。
