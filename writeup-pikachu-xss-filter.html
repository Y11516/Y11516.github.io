一、题目信息

  • 题目名称：XSS之过滤（黑名单绕过）
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 反射型 / 过滤绕过
  • 靶场链接：http://localhost:8080/vul/xss/xss_01.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是反射型 XSS 的黑名单过滤绕过。服务器端为了防御 XSS，通常会编写一段过滤代码（黑名单）来拦截常见的恶意标签或函数。本题考察的是解题者能否利用 HTML 语言特性或语法差异，绕过这种不严谨的黑名单机制，从而使 Payload 成功执行。

2. 怎么想（破题思路）

页面提示“有些内容被过滤了，试试看怎么绕过？”。解题思路是逐步递进的：

  • 先输入最标准的 Payload（如 <script>alert(1)</script>），观察页面回显，确认过滤规则是什么。
  • 如果页面将 script 关键字强制删除或替换为空，尝试使用 HTML 标签不区分大小写的特性（如 <ScRiPt>）进行绕过。
  • 如果依然被过滤，彻底放弃 script 标签，改用其他可以触发脚本执行的内置事件标签（如 <img> 的 onerror 事件）。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：直接提交标准 Payload 被拦截

踩坑情况：在输入框直接提交 <script>alert(1)</script>，页面没有弹窗，且回显内容中 <script> 标签消失了。

原因分析：服务器使用了类似 preg_replace('/<script>/i', '', $input) 的黑名单函数，直接清除了标签。但黑名单过滤往往不严谨。

改进方式：利用 HTML 大小写不敏感的特性，绕过只匹配小写的正则表达式。

终极解法：大小写混淆绕过

在输入框中输入以下 Payload：

<ScRiPt>alert(1)</ScRiPt>

代码逐个符号深度解析：

  • <ScRiPt>：把标签改成大小写混合。因为 HTML 解析标签是忽略大小写的，浏览器会把它当作 <script> 来执行。但如果服务端的黑名单只拦截小写的 <script>，这就完美绕过了防御。
  • alert(1)：JavaScript 的内置弹窗函数，参数为数字 1。
  • </ScRiPt>：标签闭合。

提交后，URL 显示为 ?message=<ScRiPt>alert%281%29<%2FScRiPt>&submit=submit#，浏览器成功弹出了“1”的对话框，证明绕过成功。

4. 怎么迁移（跨领域联想）

  • WAF（Web应用防火墙）绕过：在真实的渗透测试中，防火墙往往使用复杂的正则表达式。学习这种大小写混淆、标签替换、编码转换（如 HTML 实体编码、Unicode 编码）的思维，是绕过企业级 WAF 的基础。
  • SQL 注入的过滤绕过：与 XSS 过滤思路一致，SQL 注入也常常面临关键字（如 select、union）被拦截的情况，攻击者会使用大小写混合（SeLeCt）、内联注释（/*!select*/）等方式进行绕过。
  • 代码审计：在设计安全防御方案时，应避免使用黑名单过滤。因为黑名单总会存在遗漏，应采用白名单原则或 HTML 实体编码（如 htmlspecialchars）进行彻底防御。

三、名词大全与原理深度复盘

1. 黑名单过滤（Blacklist Filtering）

一种防御机制，即明确列出不允许出现的字符或字符串（例如禁止 <script> 标签）。由于其需要穷举所有可能的攻击向量，很难做到全面覆盖，因此在实际安全开发中通常不被推荐。

2. HTML 大小写不敏感特性

HTML 标签和属性名是不区分大小写的。也就是说，<SCRIPT>、<script> 和 <ScRiPt> 对于浏览器来说完全一样。如果服务器的正则只匹配小写，就可以用混合大小写绕过。

3. 事件驱动执行 (Event-driven Execution)

除了 <script> 标签能执行 JS 代码外，HTML 的许多事件属性（如 onerror、onload、onclick）都可以绑定并执行 JS 代码。这些事件属性往往不在 WAF 的黑名单中，是绕过过滤的利器。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型 XSS（基础）相比：基础反射型是“直给”，没有任何防御；本题在服务端引入了安全检查代码（过滤机制），攻击者需要先分析防御规则，再构造特殊 Payload 进行对抗。
  • 与存储型 XSS 相比：过滤机制属于服务端逻辑，存储型也可以通过类似手段绕过过滤存入数据库。本质上，这是攻防对抗中“防御策略”与“绕过策略”的博弈。

2. 这种题目的出现原因（为什么存在）

这类题目的出现，是因为许多初级开发者为了防御 XSS，常常会直接使用字符串替换函数（如将 <script> 替换为空字符串）。这种防御过于脆弱，忽视了 HTML 语法的灵活性（大小写、不同标签、编码等），导致简单的防御被轻易绕过。

3. 这种应用在实际中如何体现？

在实际的安全演练（红蓝对抗）中，攻击者面对的大多是带有防护设备（如 WAF）的目标。发现输入被拦截后，攻击者会针对拦截规则进行 fuzz 测试（模糊测试），尝试变异 Payload，直到找到能够穿透过滤器的写法，这也是“WAF Bypass”的重要应用场景。

4. 如何抽象理解概念（大白话理解）

如果把网站比作一个夜总会：

  • XSS 攻击：就像你带了一把枪（恶意代码）想进夜总会。
  • 过滤机制：门卫有一份黑名单，上面写着“不许带枪（不许带 <script>）”，看到这个词就直接没收。
  • 绕过：你换了一种方式，把枪拆成零件放在包里（使用 <ScRiPt> 变体标签）。门卫检查黑名单，没发现“枪”这个字，就放你进去了。但进去之后，你把零件组装起来，依然完成了攻击。

做一道题，就要往自己脑子里装点东西。
