Length - CTFHub MISC Writeup

2026年9月19日 CTFHub MISC 流量分析 协议长度隐写

一、题目信息

  • 题目名称：Length（题目描述提示：ping 包的大小有些奇怪）
  • 题目平台：CTFHub
  • 题目类型：MISC / 流量分析 / 协议字段隐写 / 数值转ASCII
  • 靶场链接：CTFHub - 技能树 - 流量分析 - Length
  • 涉及工具：Wireshark、终端 (Terminal)、tshark、awk

二、解题步骤

1. 分析题目考什么

本题的核心考点是网络流量分析与协议字段隐写。与以往将数据藏于 Payload（载荷内容）中的隐写不同，本题将信息隐藏在了 ICMP 协议头部的 Data Length（数据长度） 字段中。这考察了解题者对协议结构的深度理解，以及对数值型数据与 ASCII 码之间转换的敏感度。

2. 怎么想（破题思路）

拿到附件 icmp_len.pcap 后，题目提示“ping 包的大小有些奇怪”。这直接引导我们关注 Ping 包的长度属性。

  • 在 Wireshark 中过滤 icmp，发现所有包的 Info 列长度显示一致（如 106 字节），但如果仔细看 IPv4 头部或 ICMP 头部的 Data 字段长度，会发现其数值在变化。
  • 排查规律：将变化的长度数值提取出来（例如 99, 116, 102...），如果将其对应 ASCII 码表，恰好可以拼出英文单词（如 ctf）。这证实了长度值就是 Flag 字符的 ASCII 码。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：常规字符串搜索失效

踩坑情况：直接使用 strings icmp_len.pcap | grep -i "ctfhub" 或 Wireshark 的 String 搜索，均无法找到任何有效明文。

原因分析：因为 Flag 信息并不是以字符串的形式存放在文件中的。它被转换成了十进制的数字（例如字符 c 对应十进制数值 99），存储在协议的长度字段里。strings 命令只能提取文本，不能将数字自动映射为字符。

改进方式：必须使用能提取协议字段的工具（如 tshark 的 -e data.len），并通过脚本或命令行工具进行数值到 ASCII 的转换。

终极解法：使用 tshark 配合 awk 转换 ASCII

在终端执行以下命令，提取长度并自动转换为字符：

tshark -r icmp_len.pcap -Y "icmp.type == 8" -T fields -e data.len | awk '{printf "%c", $1}'

代码逐个符号深度解析：

  • tshark：Wireshark 的命令行版本，用于解析和分析 pcap 文件。
  • -r icmp_len.pcap：-r 代表 Read，指定读取名为 icmp_len.pcap 的流量包文件。
  • -Y "icmp.type == 8"：-Y 代表 Display Filter。此处过滤出 icmp.type == 8，即 Echo (ping) request 请求包（通常包含隐写数据）。
  • -T fields：-T 代表 Output Format，fields 表示仅输出指定的字段内容，而非完整的数据包信息。
  • -e data.len：-e 代表 Extract Field，提取 data.len（ICMP 载荷的长度）字段，输出结果为十进制的数字序列。
  • |（管道符）：将前一个命令的输出作为后一个命令的输入。
  • awk '{printf "%c", $1}'：awk 是文本处理工具。printf 是格式化输出命令。%c 是格式控制符，表示将对应的参数按 ASCII 字符输出。$1 代表当前行的第一个字段（即数字长度）。这一步将十进制长度数值直接转换成了对应的 ASCII 字符。

最终在终端输出连续的字母，提取到的 Flag 为：ctfhub{acb659f023}。

踩坑记录二：ASCII 转换乱码与偏移量调整

踩坑情况：执行上述命令后，若输出的全是乱码，可能是由于提取的字段包含了 ICMP 头部大小（通常 8 字节）或 IP 头部大小（通常 20 字节）。

原因分析：Data.len 在不同工具或协议中可能指的是“纯数据长度”或“包含头部的总长度”。如果包含头部，转换出的 ASCII 将是不可见字符或标点符号。

改进方式：若遇到乱码，可尝试在 awk 命令中减掉相应的偏移量，例如：awk '{printf "%c", $1 - 8}' 或 awk '{printf "%c", $1 - 20}'，直到输出可读的英文大写或小写字母。

4. 怎么迁移（跨领域联想）

  • 高级持续性威胁（APT）检测：攻击者常用这种“数值转字符”的方式，将窃取的数据（如系统信息、密码）转换成 IP 包的 TTL 值、TCP 的序列号（SEQ）、ACK 号等字段外发，从而绕过防火墙的深度包检测（DPI）。
  • 时序隐写（Timing Channel）：将信息隐藏在数据包发送的时间间隔中（例如间隔 100ms 代表 0，200ms 代表 1），这也是同类思想（利用协议元数据而非载荷）的延伸，属于侧信道分析。
  • 恶意软件逆向分析：在分析木马样本时，如果发现其在发包时频繁修改包头中看似不重要的数值，这可能就是其与 C2 服务器通信的隐蔽信道，需要提取序列号等数值进行数学解码。

三、名词大全与原理深度复盘

1. ICMP 协议头部结构

ICMP 报文包含 8 字节的头部（类型、代码、校验和、标识符、序列号）以及变长的数据部分。正常情况下，Ping 命令发送的数据部分长度固定（如 Windows 默认 32 字节，Linux 默认 56 字节），用于测试网络连通性。本题中，出题人将数据部分的长度（Length）作为了隐写载体。

2. 数值隐写与 ASCII 编码

计算机中所有字符都有对应的数字编码（ASCII 码）。例如大写字母 A 对应十进制 65，小写字母 a 对应 97，字符 { 对应 123。这种隐写方式将字符转换成数字，存放在协议的数值型字段（如长度、ID、序列号）中。这不需要占用额外的数据载荷空间，极其隐蔽，如果只查看 Payload 内容根本无法察觉。

3. 为什么协议长度字段可以被滥用？

网络通信中，包头字段（如长度、校验和、ID）通常被网络设备用于路由、分片和重组，防火墙和入侵检测系统（IDS）通常不会对这些元数据（Metadata）进行深度语义检测，因为它们只关心值是否合法（如长度是否超过 MTU）。因此，修改长度值在一定范围内（如 20-200）是“合法的”，这给了攻击者利用数值编码信息的空间，形成了隐蔽信道。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 ICMP 数据隐写（上一题）相比：上一题是载荷隐写，把 Flag 藏在 Payload 的字节里，用 4d 填充干扰；本题是协议字段隐写（Length），完全不碰 Payload 内容，而是改变数据包的数据长度。考察方向从“数据剥离”转向了“数值转码”。
  • 与 Redis / MongoDB 流量相比：Redis 和 MongoDB 属于应用层协议分析，Flag 明文或结构化地存在于通信数据中，重在“看懂协议”；Length 题目属于网络层（IP/ICMP）元数据隐写，重在“看破伪装”，需要转换思维去分析数值规律。

2. 这种题目的出现原因（为什么存在）

这类题目源于真实的网络攻防对抗。在高度管控的网络环境中，出口流量会被严格审查（DPI）。如果攻击者把数据放在 Payload 里，很容易被特征匹配查杀。因此，攻击者开始研究“隐蔽信道”（Covert Channel），利用协议头部的合法字段（如包长度、TTL、IP ID、TCP 窗口大小）来夹带私货。CTF 出题人通过这种题目，让选手体会攻击者的思路，从而在今后的防守中能注意到这些不起眼的异常流量。

3. 这种应用在实际中如何体现？

在现实的安全运维与应急响应中，安全分析师会使用 NetFlow、Zeek 等工具监控网络流量。如果发现某台主机的 ICMP 包长度分布异常（例如大量非标准长度，且长度数值在 90-130 之间波动），这就极可能是木马在利用长度字段外发 ASCII 编码的数据。高级的流量清洗设备现在也会对 ICMP 的包长分布进行基线学习，一旦偏离基线即产生告警。

4. 如何抽象理解概念（大白话理解）

如果把网络传输比喻成寄快递：

  • 载荷隐写（上一题）：把纸条（Flag）藏在箱子底部的废纸堆里，箱子本身大小是固定的。
  • 长度隐写（本题）：不写任何纸条，而是通过改变箱子的尺寸来传递信息。比如 99cm 的箱子代表字母 c，116cm 的箱子代表字母 t。外人看着只是一堆不同尺寸的箱子，但收件人只需要测量箱子尺寸，查一下尺码表（ASCII 表），就能拼出完整的信息。这就叫“此处无声胜有声”，信息藏在物理属性而非内容里。
