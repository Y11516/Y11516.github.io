DVWA-Low-存储型XSS (XSS Stored)

2026年10月2日 DVWA Web安全 XSS 持久化攻击

一、题目信息

  • 题目名称：DVWA XSS (Stored) (Low)
  • 题目平台：DVWA (本地 Docker / 灵境靶场)
  • 题目类型：Web安全 / 跨站脚本攻击 / 存储型 XSS
  • 靶场链接：http://192.168.242.80/vulnerabilities/xss_s/
  • 涉及工具：Google Chrome 浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是存储型 XSS（Stored Cross-Site Scripting）。与反射型不同，恶意代码被存入数据库（留言板），当任何用户访问包含该留言的页面时，恶意代码都会被执行。这是一种“持久化”的攻击，危害极大。

2. 怎么想（破题思路）

  • 页面是一个留言板，包含 Name 和 Message 两个输入框。
  • 提交一条普通留言，页面将其存入数据库并回显。
  • 尝试在 Message 中输入 JavaScript 代码，提交后观察是否执行。
  • 如果执行，说明留言板未对输入进行过滤，且渲染时直接执行了脚本。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：Chrome 浏览器拦截了脚本弹窗

踩坑情况：在输入框中输入 <script>alert(1)</script> 并提交后，页面没有弹窗，或者页面直接卡住。

原因分析：现代浏览器（特别是 Chrome）内置了 XSS 审计器。当它在页面中检测到明显的 <script> 标签时，会出于安全考虑直接拦截其执行。

改进方式：换一个不需要 <script> 标签的 Payload。使用 <img src=x onerror=alert(1)>，利用图片加载失败的事件来触发弹窗，这种形式通常不会被浏览器拦截。

详细实操步骤（Payload逐字解释）

第一步：提交恶意留言

在 Message 输入框中输入：<script>alert('Stored XSS')</script>，然后点击 Sign Guestbook。

响应结果：页面刷新后，留言板中出现了你的留言，并立即弹出一个警告框，内容为 Stored XSS。

第二步：验证“持久化”特性

按 F5 刷新页面，弹窗会再次出现。这说明恶意脚本已经存储在数据库中，只要页面被加载，脚本就会被执行。

第三步：备用 Payload（绕过 Chrome 拦截）

如果 <script> 失效，使用以下 Payload：

<img src=x onerror=alert(1)>

解释：

  • <img>：图片标签。
  • src=x：指定一个不存在的图片地址。
  • onerror=alert(1)：当图片加载失败时，执行 alert(1) 弹窗。

4. 怎么迁移（跨领域联想）

  • 论坛蠕虫：2005 年著名的 MySpace Samy 蠕虫，就是利用了存储型 XSS。Samy 在个人资料中插入了一段 JavaScript，任何查看他资料的人都会自动添加他为好友，并复制这段代码到自己的资料中，导致蠕虫在短时间内感染了上百万用户。
  • 钓鱼攻击：攻击者可以在电商平台的商品评价中，插入一段伪造登录框的 JavaScript，诱导其他用户输入账号密码，从而窃取凭证。

三、名词大全与原理深度复盘

1. 存储型 XSS

恶意代码被永久存储在目标服务器上（如数据库、文件系统），当其他用户访问该页面时，恶意代码被执行。这是三种 XSS 类型中危害最大的一种。

2. 反射型 XSS 与存储型 XSS 的区别

  • 反射型：恶意代码在 URL 中，需要诱导用户点击特定链接。一次触发，影响单个用户。
  • 存储型：恶意代码在数据库中，所有访问该页面的用户都会触发。持久化，影响大量用户。

3. 持久化攻击 (Persistent Attack)

攻击者的恶意载荷被保存在服务器上，持续对后续访问者造成影响。存储型 XSS 是典型的持久化攻击。

4. HTML 实体编码 (HTML Entity Encoding)

防御 XSS 的核心手段。将特殊字符（如 <、>、&、"）转换为对应的 HTML 实体，使浏览器将其视为纯文本而非代码。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型 XSS 的区别：反射型需要诱导用户点击链接，存储型不需要。存储型只需要用户访问页面，脚本就会自动执行。
  • 与 SQL 注入的区别：SQL 注入攻击的是数据库引擎，存储型 XSS 是利用数据库作为“弹药的储存库”，最终攻击的是浏览器端的用户。

2. 这种题目的出现原因（为什么存在）

漏洞存在的根本原因在于开发者直接将用户输入存入数据库，并在读取时未经 HTML 实体编码直接输出到页面。这是 Web 开发中“信任用户输入”的典型反面教材。

这在早期的社交平台、论坛、博客系统中非常普遍，导致了大量的 XSS 蠕虫攻击。

3. 这种的应用

在护网攻防演练中，存储型 XSS 是攻击后台管理员的主要手段。攻击者将恶意脚本嵌入到用户反馈、留言板等管理员会查看的地方，一旦管理员访问，攻击者就能获取管理员的 Cookie，进而接管后台。

4. 如何抽象理解概念（大白话）

把存储型 XSS 比作“公共饮水机投毒”：

  • 正常情况：你往饮水机里加了一块糖（正常留言），每个喝到水的人都尝到了甜味。
  • 恶意情况：你在饮水机里投了毒（恶意脚本），每个来喝水的人都会中毒。存放毒药的饮水机就是服务器的数据库，所有喝水的用户就是受害者。这就是存储型 XSS——不需要特定的人去投毒，只要他去“喝水”就会中招。
