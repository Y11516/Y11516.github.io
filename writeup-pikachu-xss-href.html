XSS之href输出 - Pikachu Writeup

2026年9月19日 Pikachu Web安全 XSS

一、题目信息

  • 题目名称：XSS之href输出
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 反射型 / 属性注入
  • 靶场链接：http://localhost:8080/vul/xss/xss_href.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是HTML 属性中的 XSS（Attribute Injection）。页面提示“a标签里面的href属性”，说明用户输入被直接拼接到了 <a href="用户输入"> 中。本题考察的是解题者能否理解：当输出点在标签属性内时，即使不能创建新的 HTML 标签，依然可以利用 URI 伪协议（javascript:）来执行 JS 代码。

2. 怎么想（破题思路）

结合页面提示，解题思路如下：

  • 页面提示“a标签里面的href属性”，意味着输出上下文被限制在链接的属性中。
  • 不能使用 <script> 标签，考虑使用 javascript: 伪协议。
  • 输入伪协议 Payload 后，页面必定会生成一个可点击的超链接。需要手动点击该链接，JavaScript 才会执行。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：仅输入 Payload 未点击超链接

踩坑情况：在输入框中提交了 javascript:alert(1)，页面显示“你的输入已经被记录”，但没有任何弹窗。

原因分析：与之前自动执行的 <script> 或 onerror 不同，属性中的 javascript: 只是定义了一个链接目标，它只有在被点击时才会触发执行。

改进方式：提交 Payload 后，必须用鼠标点击页面上生成的蓝色超链接，才能触发 XSS。

踩坑记录二：过滤规则不明确

踩坑情况：如果直接输入 javascript:alert(1) 点击无反应，可能是服务器对关键字进行了大小写过滤。

原因分析：服务器可能使用了黑名单或正则匹配，拦截了全小写的 javascript 协议。

改进方式：利用 HTML 对协议大小写不敏感的特性，尝试输入 JaVaScRiPt:alert(1) 或 " onclick="alert(1) 进行闭合绕过。

终极解法：利用 Javascript 伪协议

在输入框中输入以下 Payload：

javascript:alert(1)

代码逐个符号深度解析：

  • javascript:：这是一个 URI 伪协议。javascript 是协议名，: 是协议标识符。与 http:// 不同，它告诉浏览器将后面的内容作为 JavaScript 代码执行。
  • alert(1)：JavaScript 的内置弹窗函数，参数 1 代表在弹窗中显示的内容。

点击 submit 按钮后，点击页面上生成的超链接，成功弹窗。

4. 怎么迁移（跨领域联想）

  • 网络钓鱼攻击（Phishing）：在邮件或聊天软件中，攻击者经常发送看似正常的链接，但实际上 href 属性链接到 javascript: 恶意代码或伪装成正规网站的钓鱼页面。掌握此原理有助于识别和防范钓鱼攻击。
  • WAF（Web应用防火墙）绕过：如果目标环境使用了防火墙，可能会拦截 javascript 关键字。此时需要掌握 HTML 实体编码（如 javascript:）或使用 data URI（如 data:text/html;base64,...）等更高级的绕过手法。
  • 前端框架安全：现代前端框架（如 Vue、React）在绑定 :href 时，如果未做安全过滤，同样存在此类漏洞。这是前端开发中必须规避的安全隐患。

三、名词大全与原理深度复盘

1. HTML 属性注入

当用户输入被输出到 HTML 标签的属性值中时，被称为属性注入。开发者往往只过滤了尖括号以防止新标签创建，却忽略了属性自身也可能被利用（如 href 指向伪协议、src 指向恶意资源、on事件绑定 JS）。

2. href 属性与 URI 协议

href（Hypertext Reference）是用于指定链接目标的属性。通常接受 http:、https: 等协议。但浏览器也支持 javascript:、data:、vbscript: 等非标准协议，这为 XSS 提供了可乘之机。

3. 为什么点击链接才执行？

伪协议本身只是一段文本，类似于导航地址。浏览器只有在用户触发导航动作（如鼠标点击）时，才会去解析并执行它。因此，javascript: 协议的攻击需要用户配合（点击），这也是攻击者常将其伪装成“点击查看详情”等文案来诱导用户点击的原因。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS之htmlspecialchars 相比：上一题是因为 htmlspecialchars 本身没有对 javascript: 协议做拦截，导致使用了伪协议。本题同样存在未验证协议（白名单）的问题。但上一题是开发者主动加了过滤函数（但没做全），本题则是开发者直接未做协议过滤。
  • 与反射型 XSS（基础）相比：基础反射型是直接输出在 HTML 标签之间，可以随意创建标签。属性注入型被限制在属性内，攻击面更窄，需要更精细的 Payload 构造。

2. 这种题目的出现原因（为什么存在）

这种题目的出现，是因为很多开发者在输出 URL 类数据时，没有对协议进行“白名单校验”。开发者的思维盲区是：认为只要防住了尖括号，就安全了。但他们忽略了 href 这个属性本身是可以承载 JS 执行入口的。

3. 这种应用在实际中如何体现？

在实际的渗透测试中，如果发现某个页面将用户输入回显在 <a href="..."> 或 <iframe src="..."> 中，测试人员会立刻尝试插入 javascript:alert(1) 或 data:text/html;base64,PHNjcmlwdD5hbGVydCgxKTwvc2NyaXB0Pg==（Base64 编码的 HTML/JS）进行利用。这是前端安全测试的基础套路之一。

4. 如何抽象理解概念（大白话理解）

如果把网站比作一个公司：

  • 输出在标签之间（标准反射型）：你有权在公司的公告栏（HTML 标签之间）上贴海报。你可以直接贴一张写着“请拨打 110”的海报（<script>），路人扫一眼就会执行。
  • 输出在标签属性内（href注入）：你没有权力贴海报，只能在前台放一张“专线联系卡”（超链接）。卡片背面写着“你拨打电话时请拨打这个号码”（javascript:）。
  • 为什么需要点击：路人如果不拿起来这张卡片拨打（点击），号码就不会生效。一旦拨打（点击），就会触发后果（弹窗）。
