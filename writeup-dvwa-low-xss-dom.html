DVWA-Low-DOM型XSS (XSS DOM)

2026年10月2日 DVWA Web安全 XSS 前端安全

一、题目信息

  • 题目名称：DVWA XSS (DOM) (Low)
  • 题目平台：DVWA (本地 Docker / 灵境靶场)
  • 题目类型：Web安全 / 跨站脚本攻击 / DOM 型 XSS
  • 靶场链接：http://192.168.242.80/vulnerabilities/xss_d/
  • 涉及工具：Google Chrome 浏览器 (F12 开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是DOM 型 XSS（Document Object Model Cross-Site Scripting）。与前几关不同，这关的漏洞完全发生在**客户端（浏览器）**。服务器端并未执行任何注入，而是前端 JavaScript 代码从 URL 中提取了 default 参数，并将其不安全地写入到了页面的 DOM 结构中，导致恶意脚本被执行。

2. 怎么想（破题思路）

  • 选择一种语言（如 English），点击 Select，观察 URL 变成了 ?default=English。
  • 推测前端 JavaScript 代码直接读取了 URL 中的 default 参数。
  • 尝试在 URL 中注入一段 JavaScript 代码（如 <script>alert(1)</script>）。
  • 由于是客户端渲染，服务器和 WAF 根本看不到这段脚本，因此能够顺利执行。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：Chrome 拦截了脚本弹窗

踩坑情况：在 URL 中输入 ?default=<script>alert(1)</script>，回车后页面没有弹窗。

原因分析：Chrome 浏览器内置了 XSS 审计器，当它在 URL 中发现明显的 <script> 标签时，会出于安全考虑直接拦截。

改进方式：换一个不需要 <script> 标签的 Payload。使用 <img src=x onerror=alert(1)>，利用图片加载失败的事件来触发弹窗，这种形式通常不会被浏览器拦截。

详细实操步骤（Payload逐字解释）

第一步：观察参数注入点

在下拉框选择 English，点击 Select。观察地址栏：.../xss_d/?default=English。

第二步：构造 Payload 并注入

直接在地址栏将 English 替换为：

<script>alert('DOM-XSS')</script>

响应结果：如果浏览器未拦截，会弹出弹窗，内容为 DOM-XSS。

第三步：备用 Payload（绕过 Chrome 拦截）

如果 <script> 失效，使用以下 Payload：

<img src=x onerror=alert(1)>

解释：

  • <img>：图片标签。
  • src=x：指定一个不存在的图片地址。
  • onerror=alert(1)：当图片加载失败时，执行 alert(1) 弹窗。

4. 怎么迁移（跨领域联想）

  • 现代前端框架的隐患：在使用 React、Vue 等现代框架时，如果开发者错误地使用了 dangerouslySetInnerHTML（React）或 v-html（Vue），同样会导致 DOM 型 XSS。这种漏洞在单页应用（SPA）中非常常见。
  • 路由劫持：很多 SPA 应用使用 URL 的 hash（#）来做前端路由，如 example.com/#/profile。如果不对 hash 做过滤，攻击者可以构造 example.com/#/<script>...</script> 来实现 XSS。

三、名词大全与原理深度复盘

1. DOM (Document Object Model)

文档对象模型。它是 HTML 和 XML 文档的编程接口。浏览器会将网页解析为一个树形结构，JavaScript 可以通过操作 DOM 来动态修改页面的内容、结构和样式。

2. DOM 型 XSS

一种 XSS 漏洞。它的恶意数据不经过服务器端，而是通过 URL 或本地存储进入前端，被 JavaScript 直接提取并写入 DOM，导致代码执行。传统的服务器端 WAF 很难检测这种漏洞。

3. 反射型 XSS 与 DOM 型 XSS 的区别

  • 反射型 XSS：恶意代码被发送到服务器，服务器将代码“反射”回浏览器执行。请求中会包含恶意代码。
  • DOM 型 XSS：恶意代码不经过服务器，服务器返回的 HTML 中根本没有这段代码。是浏览器端的 JavaScript 自己执行了它。

4. onerror 事件

HTML 标签的事件属性。当资源（如图片、脚本）加载失败时触发。在 XSS 中常被用来替代 <script> 标签执行 JavaScript。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型 XSS 的区别：反射型 XSS 需要服务器将恶意代码拼接到 HTML 中返回。DOM 型 XSS 完全在客户端发生，服务器只返回了静态的 JS 代码，是 JS 代码自己“读取”并“执行”了恶意参数。
  • 与命令注入的区别：命令注入执行的是系统命令（危害服务器），DOM XSS 执行的是浏览器脚本（危害其他用户）。

2. 这种题目的出现原因（为什么存在）

漏洞存在的根本原因在于前端 JavaScript 开发不规范。开发者直接使用了类似 document.write() 或 innerHTML 的方法，将 URL 中的用户输入（如 ?default=）直接写入页面，而没有进行 HTML 实体编码（比如把 < 转换为 &lt;）。

这在早期的 Web 2.0 时代（大量使用 AJAX 和前端路由）非常普遍，即使现代框架也偶有发生。

3. 这种的应用

在护网中，DOM 型 XSS 常被用来窃取用户的 Cookie（document.cookie），进而实现会话劫持。攻击者会把恶意链接发给管理员，管理员点击后，攻击者就能拿到管理员的 Cookie，登录后台。

4. 如何抽象理解概念（大白话）

把 DOM 型 XSS 比作“传声筒”：

  • 正常情况：你对着传声筒说“你好”，传声筒原样传出去。
  • 恶意情况：你对着传声筒说“去帮我打开金库”，如果传声筒不加处理，它就会把这句指令传给机器人，机器人真的去打开金库了。这个“传声筒”就是前端不安全的 JavaScript 代码。
