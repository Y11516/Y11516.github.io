Pikachu 敏感信息泄露 - I can see your ABC

2026年9月24日 Pikachu Web安全 敏感信息泄露 抓包分析

一、题目信息

  • 题目名称：敏感信息泄露 - I can see your ABC
  • 题目平台：Pikachu 漏洞练习平台（本地 Docker 环境）
  • 题目类型：Web安全 / 信息收集 / 敏感信息泄露
  • 靶场链接：http://localhost:8080/vul/infoleak/findabc.php（本地环境）
  • 涉及工具：Chrome浏览器、开发者工具（F12 Network面板）、Docker

二、解题步骤

1. 分析题目考什么

本题的核心考点是敏感信息泄露与网络抓包分析。页面包含一个登录框，提示“找找看，很多地方都漏点了...”。攻击者需要利用浏览器的开发者工具（Network 面板）抓取登录过程中产生的 HTTP 请求，分析请求头（Headers）中的 Cookie 信息，从中发现被明文或弱哈希泄露的用户名和密码。

2. 怎么想（破题思路）

  • 页面是一个登录框，尝试使用弱口令（admin/123456）登录，提示“账号密码错误”。
  • 题目提示“很多地方都漏点了”，可能指向 Cookie、隐藏源码或备份文件。
  • 利用 F12 的 Network（网络）面板，抓取登录成功后的请求包。
  • 重点检查“请求头（Request Headers）”中的 Cookie 字段，看看服务器是否把账号密码直接塞进了 Cookie。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：本地镜像缺失文件导致无法扫描

踩坑情况：尝试用 Python 脚本扫描 abc.php.bak、.zip 等备份文件，全部返回 404。

原因分析：通过进入 Docker 容器内部查看 /var/www/html/vul/infoleak/，发现本地精简版镜像中只包含 abc.php、findabc.php 和 infoleak.php，官方原版的 abcdl.php 缺失了。

改进方式：不要死磕缺失的文件，转向抓包分析登录流程。

踩坑记录二：Docker 环境崩溃（数据库连接失败）

踩坑情况：重新拉起镜像后，页面报错“数据库连接失败，请检查config.inc.php配置文件”。

原因分析：镜像内的 MySQL 服务未随容器自动启动。

改进方式：通过 docker exec 进入容器，执行 service mysql start 手动启动数据库服务。

踩坑记录三：Network 面板抓不到请求

踩坑情况：打开 F12 Network 面板，一片空白，或者被输入了 test 过滤条件导致看不到请求。

原因分析：Network 面板只能记录你打开它“之后”发生的请求。页面加载完了再打开，历史请求不会被记录。

改进方式：清空过滤框，勾选 Keep log，并按下 Cmd + R 刷新页面，重新触发请求。

详细实操步骤（抓包分析）

第一步：登录并跳转

访问 http://localhost:8080/vul/infoleak/findabc.php，输入用户名 lucy，密码 123456（或使用万能密码 admin' OR 1=1 #），点击 Login。

登录成功后，页面会跳转到包含王小波《黄金时代》引文的 abc.php 页面。

第二步：抓包与查看 Cookie

按下 F12 打开开发者工具，切换到 Network（网络）面板。清空搜索框，勾选 Keep log。

按 Cmd + R 刷新页面。在左侧列表中找到 abc.php 请求，点击它。

在右侧面板中，点击 标头（Headers），向下滚动找到 请求标头（Request Headers）中的 Cookie 字段：

Cookie: abc[uname]=lucy; abc[pw]=e10adc3949ba59abbe56e057f20f883e; PHPSESSID=...

第三步：解密与信息泄露分析

我们看到了明文用户名 lucy 和加密密码 e10adc3949ba59abbe56e057f20f883e。这个密码是 MD5 哈希值。

将 e10adc3949ba59abbe56e057f20f883e 放入在线 MD5 解密工具中，即可解密为：123456。这就是敏感信息泄露的直接证据。

4. 怎么迁移（跨领域联想）

  • 真实渗透中的信息收集：在实战中，查看 Cookie 是基础操作。很多开发者为了方便，会把用户名、角色（如 admin=true）甚至密码直接写在 Cookie 里。攻击者只需修改 Cookie 就能实现越权或直接获取账号。
  • Nginx 配置错误漏洞：别人解题时用到的“Nginx 中间件”技巧，是指如果 Nginx 配置不当，会把 .php 源码当作文本文件直接返回给浏览器。这在真实场景中常导致数据库配置文件（如 config.php.bak）泄露。
  • CSRF 防御缺失：缺乏 CSRF Token 防护时，攻击者可以伪造请求，结合上述漏洞，直接在后端触发敏感文件的读取。

三、名词大全与原理深度复盘

1. Cookie 与敏感信息泄露

Cookie 是服务器存储在用户浏览器上的一小块数据，用于保持会话状态。如果服务器把明文密码或可逆向的哈希（如 MD5）写在 Cookie 里，那么任何能够访问该用户浏览器（或抓包）的人都能获取到凭证，这就是典型的敏感信息泄露。

2. Nginx 中间件解析错误

Nginx 作为 Web 服务器，通常会将 .php 文件交给 PHP 引擎处理。但如果配置里错误地把 .php 匹配成了静态文件（例如 location ~* \.php$ { ... } 写错），浏览器请求时就会直接下载该文件的源码。

3. CSRF（跨站请求伪造）与防御缺失

正常情况下，表单提交应携带一个随机生成的 CSRF Token。如果缺少 Token 校验，攻击者可以伪造一个 HTML 页面，让管理员在不知情的情况下提交表单，从而执行恶意操作。这也是别人能在前端成功请求到 abcdl.php 的原因之一。

4. MD5 哈希

MD5 是一种广泛使用的密码散列函数。虽然它是单向的，但由于彩虹表的存在，弱密码（如 123456）的 MD5 值很容易被反向查出。在这里，`e10adc...` 就是 `123456` 的 MD5 值。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 CTFHub 信息泄露的区别：CTFHub 更侧重于备份文件下载（.git、.bak）和目录遍历，是静态文件的泄露。而本题是动态数据（登录凭证）在网络传输过程中的泄露，要求必须通过抓包来发现。
  • 与 SQL 注入的区别：SQL 注入是攻击数据库获取数据；本题是服务器主动把数据塞进了 Cookie 发给了客户端，属于“送上门”的信息泄露。

2. 这种题目的出现原因

这类漏洞源于开发者的“图方便”。为了在多个页面间传递用户的登录状态，开发者可能直接把用户名和密码塞进了 Cookie，而不是使用安全的 Session ID。此外，本地 Nginx 配置错误也是由于部署时缺乏标准化的安全配置导致的。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，攻击者一旦拿到 WebShell 或通过 XSS 拿到用户的 Cookie，就能直接登录受害者账号。如果 Cookie 里包含明文密码，攻击者甚至可以直接登录受害者的其他系统（撞库）。企业防御必须在 Cookie 中使用 HttpOnly 和 Secure 标志，且绝对禁止在客户端存储明文密码。

4. 如何抽象理解概念（大白话理解）

把服务器比作一家酒店的前台：

  • 正常情况：你登记入住后，前台给你一张房卡（Session ID），上面只有房间号，没有你的身份证号。
  • 信息泄露（本题）：前台偷懒，给你的房卡背面直接写上了你的名字和房间密码（Cookie 里的账号密码）。
  • 抓包（F12 Network）：其他住客（攻击者）只要多看一眼你的房卡（抓包），就能直接拿到你的名字和密码，去前台开你的房间。

做一道题，就要往自己脑子里装点东西。
