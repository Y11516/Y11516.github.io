Token防爆破 - Pikachu 靶场 Writeup

2026年9月17日 Pikachu 靶场 Web安全 暴力破解 动态Token

这是 Pikachu 暴力破解模块的最后一关（第四关）。前三关我摸清了验证码的套路，但这一关服务器引入了动态的 Token，导致普通的 Burp Suite 重放攻击完全失效。本篇 Writeup 记录了我从“不知道这道题在干什么”，到理解“动态抓票”逻辑，并最终用 Python 脚本成功爆破的全过程。

一、这道题在考什么？跟前面有什么不一样？

1. 与前三关的核心差异

  • 第一关（无验证码）： 纯裸奔。Burp 无脑重放即可。
  • 第二关（Server端验证码）： 验证码验证后不销毁，可以复用同一个验证码疯狂发请求。
  • 第三关（Client端验证码）： 验证逻辑在前端 JS，直接删掉或禁用 JS 即可绕过。
  • 第四关（Token防爆破）： 服务器每次动态生成一个 Token 隐藏在 HTML 里。用一次就立刻作废。这意味着：你无法用 Burp Suite 拦截一次请求然后无限重放。

2. 考点是什么？

考察你是否能用脚本模拟人类的“动态行为”。人类登录流程是：打开网页（拿 Token） -> 输入账号密码 -> 提交。脚本也必须模拟这个流程：每次试密码前，都先去“领一张新票”，再带着新票去提交。

二、灵魂拷问：为什么不直接把 Token 写进去？

原因： 因为 Token 是“一次性门票”。如果你在脚本里写死 token = '753...'，第一次提交密码后，这个 Token 就被服务器作废了。你尝试第二个密码时，服务器会说“你的票过期了”，连密码都懒得验证，直接把你踢出去。因此，必须在 for 循环的每一次，都重新去抓一张新票。

三、陌生名词解释（新手必读）

  • Token： 服务器发放的一次性“通行证”。用来防止 CSRF 和重放攻击。用一次就失效。
  • Session： 保持会话。在 Python 里用 requests.Session()。如果用普通的 requests.get()，你抓到的 Token 可能和后续提交请求的 Cookie 对不上号（因为不是同一个会话）。使用 Session，就像浏览器一样，自动帮我们带上 Cookie，确保领票和提交是同一人。
  • 正则表达式（Regex）： 用 re.search() 从一大堆 HTML 文本中，精准匹配并抠出我们需要的 Token 值。
  • Python 字典： data = {"key": "value"}。注意里面是冒号，不是等号。变量需要在字典外面定义好。

四、踩坑全记录（每一步为什么错，要注意什么）

1. 坑一：代理没关，请求被拦截

现象： 脚本一直报“找不到 Token”。

原因： 我为了抓包，开着 Burp Suite 代理。Python 发请求时被 Burp 拦截，返回的是 Burp 的错误页面，里面没有 Pikachu 的 Token。

注意： 写脚本跑自动化时，务必关闭浏览器代理插件，或去 Mac 系统设置里关闭 HTTP/HTTPS 代理。

2. 坑二：URL 路径错误（404）

现象： 报错 404 Not Found，说找不到 /pikachu/vul/...。

原因： 不同 Docker 镜像的目录结构不同。我的环境源码直接挂在根目录，不需要 /pikachu/ 这一层。

注意： 写脚本前，务必先在浏览器打开该页面，直接复制浏览器地址栏里的完整 URL。以浏览器地址为准，不要瞎猜。

3. 坑三：Python 语法错误（SyntaxError）

现象： 报错 SyntaxError: invalid syntax。

原因： 我把 username = "pikachu" 直接写进了 data = {} 大括号里。字典里面必须是键值对。

注意： 变量要在字典外面定义，字典里面用冒号 "username": username 传值。

4. 坑四：如何动态抓取 Token

浏览器里 F12 -> Console 输入 document.querySelector('[name=token]').value 确实能拿到 Token，但在 Python 里我们需要模拟这个过程。使用了 re.search(r'name="token" value="([^"]+)"', r_get.text) 自动提取。

五、最终成功的 Python 脚本

import requests
import re

# ⚠️【注意】浏览器地址复制过来，不要加 /pikachu/
url = "http://localhost:8080/vul/burteforce/bf_token.php"

username = "pikachu"
passwords = ["000000", "123456", "password", "admin888", "root"]

# 使用 Session 保持会话
session = requests.Session()

print("开始带 Token 的暴力破解...")

for pwd in passwords:
    # 1. 每试一个密码，先领一张新票
    r_get = session.get(url, timeout=5)
    token_match = re.search(r'name="token" value="([^"]+)"', r_get.text)
    if not token_match:
        print("❌ 找不到 Token！")
        break
    token = token_match.group(1)
    
    # 2. 带着账号、密码和新票去提交
    data = {"username": username, "password": pwd, "token": token, "submit": "Login"}
    r_post = session.post(url, data=data, timeout=5)
    
    # 3. 判断成功
    if "login success" in r_post.text:
        print(f"\n🎉 爆破成功！密码是: {pwd}")
        break
    else:
        print(f"尝试: {username}:{pwd} -> 失败")

六、成功验证与结果

运行脚本后，终端打印出了：🎉 爆破成功！密码是: 000000。页面跳转返回了 <title>Get the pikachu</title>，证明我们成功绕过了 Token 的防护，完成了 Pikachu 暴力破解模块的全部通关！

七、拓展：Python 字典构造与 Web 实战逻辑

为什么这么构造？

在 Python 中，这种 data = {"key": "value"} 的构造方式叫做字典（Dictionary）。

为什么是冒号 : 和花括号 {}？

你可以把 Python 字典想象成一本真正的《新华字典》或者通讯录。

  • key（键）： 你要查的字（比如“安”），或者你要找的人（比如“张三”）。
  • value（值）： 这个字的解释，或者这个人的电话号码（比如“123456”）。

在 Python 的语法里：

  • {} （花括号）代表这是一个“集合/字典”。
  • : （冒号）代表“映射关系”，左边是名字，右边是内容。
  • , （逗号）用来隔开多组数据。

为什么不能用等号 =？

因为在 Python 中，= 是赋值。如果你写成 {"username" = "admin"}，Python 会报错（SyntaxError），因为它以为你要把 "admin" 赋值给一个字符串 "username"，字符串是常量，不能被赋值。

用 : 的意思是：“在这个字典里，username 对应的值是 admin”。

对比一下这两种写法：

  • 赋值（在外面）： a = 1 （把 1 赋值给变量 a）
  • 字典（在里面）： data = {"a": 1} （创建一个字典，里面包含了一个映射：a 对应 1）

为什么打 Web 必须这么构造？（实战意义）

在你在做 CTF 或者写爬虫脚本时，通常使用的是 requests 库。当你向靶场（服务器）发送账号、密码或者 Token 时，网络传输实际上是一堆类似 username=admin&password=123 的字符串。

requests 库非常聪明，它允许你直接把一个 Python 字典传进去，它会自动帮你转换成服务器认识的格式。

场景 A：提交表单（POST 数据）

import requests
# 构造字典
data = {
    "username": "admin",
    "password": "123456",
    "token": "abcd"
}
# 发送请求，requests 会自动把字典变成 username=admin&password=123456...
response = requests.post("http://xxx.com/login", data=data)

场景 B：发送 JSON 数据（现代前后端分离 API）

现在的接口通常要求发送 JSON 格式。由于 JSON 本身的语法和 Python 字典几乎一模一样，所以直接把字典丢进去，requests 就能完美转换：

response = requests.post("http://xxx.com/api/login", json=data)

场景 C：修改 HTTP 请求头（Headers）

# 伪装成浏览器
headers = {
    "User-Agent": "Mozilla/5.0 (Macintosh...)",
    "Cookie": "sessionid=123456"
}
requests.get(url, headers=headers)

八、防御思考

💡 Token 防御的局限性： Token 可以防止简单的重放攻击，但无法防止攻击者用脚本动态抓取。应对方法：加入频率限制（Rate Limiting）、限制同一 IP/Session 的失败次数、使用滑动验证码或复杂的人机验证。

九、深度剖析：Token 防爆破的核心机制与黑客破解思路

Token 防爆破的核心是什么？

1. 绝对的一次性（防重放攻击 Replay Attack）

这是最核心的一点。服务器发出的每一个 Token 都是一次性的。

  • 正常流程：你打开登录页 -> 服务器发给你一个 Token A -> 你用 Token A + 密码去请求登录 -> 服务器验证通过，并立刻销毁 Token A。
  • 防爆破原理：如果黑客想跑字典爆破密码，他第一次用 Token A 跑了一个密码，不管对不对，Token A 都失效了。他如果想试第二个密码，就必须重新去获取一个新的 Token B。
  • 结果：黑客无法一次性发几万个请求，因为后续的请求都会因为 Token 无效被拒绝。这就强行拖慢了爆破速度。

2. 强绑定机制（防伪造和并发）

Token 不能是随机乱码，它必须在服务端和特定的用户会话（Session）、时间或者特定表单绑定。

  • 绑定 Session：这也是为什么你截图里提到要用 requests.Session()。如果你不用 Session，你请求登录页拿到了 Token，但当你发爆破请求时没有带上之前的 Cookie，服务器发现这个 Token 和当前会话（Session）对不上，直接拦截。这也是所谓的“领票人和提交人必须是同一人”。
  • 防并发（条件竞争）：如果服务器有逻辑漏洞（比如只验证 Token 是否正确，但代码执行到最后才去销毁），攻击者可以用多线程在几毫秒内，用同一个 Token 并发发送 50 个不同的密码。如果服务器处理不及，50 个全部验证成功。好的 Token 机制必须在验证的第一步就把它锁死。

3. 不可预测性

Token 必须足够长、足够随机（通常使用 UUID 或加密安全的随机数生成器）。

  • 如果 Token 是按时间戳递增的，或者有规律（比如 MD5(用户名+日期)），攻击者就可以绕过前端，自己伪造一个有效的 Token，直接让防御失效。

实战中，黑客是如何“绕过”或“破解” Token 防爆破的？

理解了核心，在护网或者打 CTF 时，如果你遇到了 Token 防御，你可以从这几个方向去思考怎么突破：

  1. 找“不销毁”的逻辑漏洞： 你发现你用同一个 Token 发包，服务器依然一直返回“密码错误”而不是“Token失效”，说明它没有做到“用完即焚”，直接拿字典继续跑。
  2. 利用并发（条件竞争）： 这是打 Token 防爆破的经典大招。开启几十个线程，同时拿着一个合法 Token 请求不同的密码。只要服务器还没销毁 Token，总有几个请求能成功验证。
  3. 自动获取 Token（自动化脚本）： 你之前学的 requests.Session() 就是为了这个。写个循环：发 GET 请求 -> 正则提取页面里最新的 Token -> 发送 POST 爆破请求 -> 循环往复。
    • 虽然每次都要先获取 Token，但这只是增加了一点网络延迟。如果你有 100 万条密码，这种方式依然能把系统打穿（所以真实系统还会配合 IP 频率限制和验证码）。
  4. 找 Token 泄露： 如果 Token 不是通过服务端生成的，而是用 JS 在前端生成的（或者把生成逻辑写在 JS 里），攻击者可以直接看 JS 源码，本地伪造合法 Token。
  5. 前端可控： 如果 JS 把 Token 放在了 Cookie 里，而你发现服务端根本不校验 Cookie 里的 Token，那你直接删掉 Token 参数去爆破即可。

总结： Token 防爆破的本质，就是把“连续的无状态攻击”，强行变成了“必须交互、有状态、且按次收费”的阻断机制。
