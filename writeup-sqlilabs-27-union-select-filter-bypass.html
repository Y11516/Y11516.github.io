SQLi-Labs Less-27

2026年9月28日 SQLi-Labs Web安全 SQL注入 UNION/SELECT 过滤绕过

一、题目信息

  • 题目名称：SQLi-Labs Less-27 (GET - Error Based - All your UNION & SELECT Belong to us - String - Single quote)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 关键字过滤绕过
  • 靶场链接：http://localhost:8081/Less-27/（本地环境）
  • 涉及工具：Chrome浏览器、F12开发者工具、URL编码

二、解题步骤

1. 分析题目考什么

本题的核心考点是绕过对 UNION 和 SELECT 关键字的过滤。页面提示“All your UNION & SELECT belong to us”，且闭合方式为单引号 '。攻击者必须寻找替代语法，或通过大小写、双写、内联注释等方式绕过关键字拦截，最终实现报错注入。

2. 怎么想（破题思路）

  • 输入 ?id=1'，页面报出 SQL 语法错误，确认注入点及单引号闭合方式。
  • 尝试常规报错注入 updatexml，发现关键字 select 被过滤，页面提示被清洗为 1'。
  • 尝试大小写混合（SeLeCt），失败。源码使用 preg_replace 并带有 i 修饰符，忽略大小写。
  • 尝试双写（seleselectct），依然失败，因为 updatexml、and 及空格也一并被过滤，导致语句崩塌。
  • 终极思路：既然 select 被过滤，我们直接使用 database() 函数获取库名，因为该操作不需要 select 关键字！同时使用 &&（%26%26）替代 and 以绕过空格过滤，并用 '1'='1 替代注释符。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：大小写混合被过滤

踩坑情况：使用 SeLeCt 混写绕过，页面依然报错，Hint 显示只剩下 1'。

原因分析：源码中使用了 preg_replace('/select/i', '', $id)，正则表达式带有 i 修饰符，意味着不区分大小写。

改进方式：放弃大小写绕过，思考替代语法或完全不使用该关键字。

踩坑记录二：双写绕过及内联注释失败

踩坑情况：使用 seleselectct 双写，或 /*!50000SELECT*/ 内联注释，依然报语法错误。

原因分析：靶场在题目中已提示过滤了 COMMENTS，意味着 /**/ 被过滤。双写失败可能是因为 updatexml、and 及空格也被一并过滤，导致整条语句崩塌。

改进方式：改用不含 select 的报错注入 Payload。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入以下 URL（使用不含 select 的报错注入）：

http://localhost:8081/Less-27/?id=1'%26%26updatexml(1,concat(0x7e,(database()),0x7e),1)%26%26'1'='1

第二步：Payload 逐字解析

  • 1'：闭合原 SQL 语句中的单引号。
  • %26%26：URL 编码后的 &&（逻辑与），完美替代被过滤的 and，且不需要空格。
  • updatexml(1,concat(0x7e,(database()),0x7e),1)：核心报错注入函数。由于直接调用 database() 而不使用 select，完美避开了关键字过滤。
  • %26%26'1'='1：再次使用 && 连接并手动闭合末尾引号，防止语法错误。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 代码审计的必要性：靶场提供的 ?source=1 是学习代码审计的最佳入口。在真实环境中，通过查看泄露的源码（如 Git 泄露、备份文件），可以迅速定位过滤逻辑，从而精准构造 Payload。
  • PHP 正则替换的局限性：preg_replace 如果不写好边界条件，依然会被绕过。例如，如果只替换一次，可以使用双写。如果完全不使用关键字，则无法被替换。安全防御不能依赖字符串替换。
  • 安全开发启示：使用参数化查询（Prepared Statements）是防御 SQL 注入的唯一终极方案。

三、名词大全与原理深度复盘

1. 代码审计 (Code Audit)

通过阅读程序源码来分析其逻辑、寻找安全漏洞的过程。SQLi-Labs 通过 ?source=1 提供了源码查看功能，帮助学习者理解过滤逻辑。

2. 关键字过滤与替代语法

后端使用正则过滤危险关键字（如 select、union、and）。攻击者可以通过大小写混合、双写、内联注释、或完全改变语法结构（如不使用 select 而使用 database()）来绕过。

3. 报错注入 (Error-Based)

利用数据库执行错误时抛出的信息，将想要查询的数据通过非法格式（如调用 updatexml）拼接在错误信息中带出。是高效的数据回显方式。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-26 的区别：Less-26 过滤空格和注释符，Less-27 过滤了 UNION 和 SELECT 关键字。Less-27 的过滤重点在“关键字”，Less-26 在“空白字符和注释”。
  • 与 Less-20/21 的区别：Less-20/21 注入点在 Cookie 或 Referer，Less-27 是 GET 参数注入。

2. 这种题目的出现原因（为什么存在）

开发者在编写代码时，为了防御 SQL 注入，会去搜集攻击者常用的关键字（如 select、union），然后写正则去替换它们。但这种“黑名单”防御存在先天缺陷——攻击者完全可以通过大小写、双写、或者换个函数（如用 database() 替代 select database()）来绕过。这种漏洞源于对攻击手段的认知不全面。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，遇到带有 WAF 的站点，SQLMap 等自动化工具常因 Payload 包含关键字而被拦截。此时需要编写自定义的 Tamper 脚本，对 Payload 进行变形处理。防御方应使用参数化查询，而非字符串替换。

4. 如何抽象理解概念（大白话）

把靶场比作一个“严格的语法老师”：

  • Less-27 的老师宣布：禁止使用“寻找（SELECT）”和“合并（UNION）”这两个词。
  • 你原本想说：“请帮我寻找苹果。”老师直接把“寻找”划掉，句子变成了“请帮我苹果”，语法崩溃。
  • 你换了一种说法：“请给我苹果（database()）”。老师没禁止“给我”，你成功拿到了苹果。这就是 Less-27 的核心逻辑：绕开被禁的词汇，用同义或替代语法表达需求。

做一道题，就要往自己脑子里装点东西。
