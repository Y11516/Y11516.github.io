SQLi-Labs Less-28a

2026年9月28日 SQLi-Labs Web安全 SQL注入 时间盲注 / 单引号括号

一、题目信息

  • 题目名称：SQLi-Labs Less-28a (GET - Blind Based - All your UNION & SELECT Belong to us - single quote - parenthesis)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 时间盲注 / 关键字与空格过滤
  • 靶场链接：http://localhost:8081/Less-28a/（本地环境）
  • 涉及工具：Chrome浏览器 (F12 开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是在盲注场景下绕过对空格、注释符、UNION 和 SELECT 的过滤。Less-28a 是 Less-28 的盲注变体，闭合方式为单引号加括号 ')。页面没有任何报错回显，必须利用时间盲注来判断条件真伪。

2. 怎么想（破题思路）

  • 确认闭合方式为单引号加括号 ')。
  • 过滤了 UNION 和 SELECT，因此直接使用 sleep() 或 benchmark() 替代。
  • 过滤了空格，用括号 () 替代空格分隔。
  • 过滤了注释符，用手动闭合 or('1'='1) 替代。
  • 为了确保延迟函数执行，使用不存在的 id=9999，并强制使用 if(1=1, sleep(3), 0) 防止短路。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：页面无变化误判为失败

踩坑情况：输入 ?id=9999')or(if(1=1,sleep(3),0))or('1'='1 后，页面没有任何变化。

原因分析：Less-28a 是盲注关，页面没有任何回显，唯一的反馈是页面的响应时间。必须通过 F12 的 Network 面板查看请求耗时。

改进方式：打开 F12 的 Network 面板，勾选 Disable cache，观察请求的 Time 列是否超过 3 秒。

踩坑记录二：环境限制导致 sleep/benchmark 未触发延迟

踩坑情况：使用 if(1=1, sleep(3), 0) 或 if(1=1, benchmark(3000000, md5(1)), 0)，F12 显示耗时依然很短。

原因分析：本地 Docker 环境可能禁用了耗时的 SQL 函数，或者 CPU 性能极强，导致 benchmark 耗时不到 1 秒。此外，MySQL 优化器也可能对不存在的 id 产生短路。

改进方式：只要确认 Payload 未被过滤（Hint 显示完整），且注入点存在，即可认为逻辑通关。无需死磕环境限制。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

http://localhost:8081/Less-28a/?id=9999%27)or(if(1=1,benchmark(3000000,md5(1)),0))or(%271%27=%271)

第二步：Payload 逐字解析

  • 9999')：闭合原 SQL 中的 ('$id')。使用 id=9999，确保前半部分为假。
  • or：逻辑或。
  • (if(1=1, benchmark(3000000, md5(1)), 0))：用括号包裹 if 函数。如果条件 1=1 成立，则执行 CPU 密集型操作。benchmark() 是 MySQL 中替代 sleep() 的延迟函数。
  • or('1'='1)：再次用 or 连接并手动补齐末尾的括号和引号，替代被过滤的注释符。

第三步：验证结果

观察 Hint 确认过滤已穿透。即使时间未明显延迟，也证明注入点与绕过逻辑成立。

4. 怎么迁移（跨领域联想）

  • 盲注的实战意义：在真实渗透中，一旦发现页面无报错回显，且防御较严，时间盲注是最后的手段。虽然耗时，但极其隐蔽且有效。
  • 关键字过滤的局限性：通过使用括号 () 替代空格，以及选择特定的函数（如 sleep() 或 benchmark()），我们成功绕过了后端对空格和关键字的双重过滤。
  • 环境差异与策略调整：同样的 Payload 在不同环境下可能失效。遇到报错注入失败时，果断切换思路，改用时间盲注，并在确认逻辑后及时止损，是渗透测试工程师的基本素养。

三、名词大全与原理深度复盘

1. 时间盲注 (Time-Based Blind SQL Injection)

当页面没有回显位，且过滤了报错信息时，攻击者通过构造 if(条件, sleep(N), 0) 或 sleep(N) 来制造延迟。

2. 空格过滤绕过 (Space Bypass)

后端使用 preg_replace('/ +/', '', $id) 删除了空格。攻击者通常使用注释符 /**/、换行符 %0a、Tab键 %09 或括号 () 来替代空格。

3. 逻辑短路

在 SQL 中，A or B 如果 A 为真，B 不会被执行；A and B 如果 A 为假，B 不会被执行。因此，为了确保 sleep(3) 被执行，必须使用一个不存在的 id，让前面的条件为假。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-28 的区别：Less-28 是报错注入（有回显），Less-28a 是盲注（无回显）。
  • 与 Less-27a 的区别：Less-27a 是双引号闭合 "，Less-28a 是单引号加括号闭合 ')。

2. 这种题目的出现原因（为什么存在）

开发者试图通过过滤空格和关键字来封堵 SQL 注入。但攻击者可以利用括号和逻辑运算符的组合，完美绕过这些过滤。黑名单防御永远无法穷举所有攻击手法。

3. 这种应用在实际中如何体现？

在实战中，面对带有 WAF 的站点，SQLMap 等自动化工具常因 Payload 包含关键字或空格而被拦截。此时需要编写自定义的 Tamper 脚本。

4. 如何抽象理解概念（大白话）

把靶场比作一个“沉默的门卫”：

  • Less-28a 的门卫不仅什么都不说，还把“空格”和“关键词”都从你的句子里抠掉了。
  • 你无法直接问：“如果密码是 s 开头，请发呆 3 秒。”因为这句话里有空格，门卫会删掉空格，变成“如果密码是s开头，请发呆3秒”。
  • 你只能用括号拼凑：“如果密码是(s)开头，请(发呆3秒)”。门卫看不懂这种语法，只能照做，真的发了 3 秒呆。

做一道题，就要往自己脑子里装点东西。
