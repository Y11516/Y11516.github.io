2026年9月19日 Pikachu Web安全 SQL注入

一、题目信息

  • 题目名称：SQL-Inject delete注入
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 数据删除 / DELETE语句注入
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_del.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 DELETE 语句的 SQL 注入进行破坏性数据删除。与查询（SELECT）和更新（UPDATE）不同，DELETE 语句一旦被成功注入，会导致数据永久丢失。后端代码通常使用 delete from message where id = $id 的拼接形式，攻击者可通过逻辑注入（如 or 1=1）绕过原有的 ID 限制，从而清空整个数据表。

2. 怎么想（破题思路）

页面提示“我是一个不正经的留言板”。解题思路如下：

  • 在留言板中提交一条留言，触发“删除”功能。
  • 由于点击删除按钮时前端可能未正确刷新地址栏，需通过 F12 或手动构造 URL，观察删除操作传递的参数（如 id=1）。
  • 直接修改 URL 中的参数为 id=1 or 1=1，触发全表删除逻辑，使留言列表清空。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：点击删除按钮浏览器地址栏无变化

踩坑情况：在留言列表点击“删除”按钮，页面没有反应，地址栏也没有发生跳转。

原因分析：该靶场的前端代码可能使用了 JavaScript 事件或 AJAX 请求，未直接通过 href 属性跳转；或者是前端代码存在缺陷导致点击无响应。

改进方式：放弃依赖前端按钮，通过审查页面源码或直接手动构造请求 URL。根据后端接口命名规律，直接访问 http://localhost:8080/vul/sqli/sqli_del.php?id=1，手工触发删除逻辑。

踩坑记录二：手动构造 URL 后未使用注入语句

踩坑情况：手动访问 sqli_del.php?id=1 仅能删除特定的那条留言，未体现漏洞利用效果。

原因分析：正常的 ID 传参只能删除特定记录。要证明漏洞存在，必须使用逻辑运算符打破原有的 ID 限制。

改进方式：构造逻辑注入 Payload：id=1 or 1=1。这将使 SQL 条件恒为真，从而删除表中所有留言。

终极解法：利用逻辑注入清空数据表

在浏览器地址栏直接输入以下 URL 并回车：

http://localhost:8080/vul/sqli/sqli_del.php?id=1 or 1=1

代码逐个符号深度解析：

  • id=1：正常的查询参数，指向第一条留言。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。此时后端执行的 SQL 语句变为：delete from message where id = 1 or 1=1。由于 1=1 恒为真，where 条件对每一行数据都成立，数据库将删除整个 message 表的所有记录。

提交后，留言列表瞬间变空，证明 delete 注入攻击成功，完成了数据库清空破坏。

4. 怎么迁移（跨领域联想）

  • 业务逻辑安全：在真实开发中，执行删除操作绝不应使用 GET 请求，且必须校验当前用户是否有权删除目标数据（水平权限校验）。仅靠前端点击按钮的交互，不能作为安全依据。
  • 代码审计：在代码审计中，所有执行 DELETE 和 UPDATE 且未使用参数化查询的代码，都是高危审计点。特别是未验证 where 条件直接拼接的代码，极易导致全表误删。
  • WAF 绕过：在实战中，若 WAF 拦截了 or 1=1，可尝试使用 or true、or 'a'='a'、内联注释 /*!or*/ 或大小写混淆等方式进行绕过。

三、名词大全与原理深度复盘

1. DELETE 注入与 SELECT / UPDATE 注入的区别

SELECT 注入用于“读取”数据，攻击者试图窃取敏感信息；UPDATE 注入用于“篡改”数据，攻击者试图修改密码或权限；DELETE 注入用于“删除”数据，攻击者意图破坏业务完整性。DELETE 注入的破坏力最直接，一旦得手，往往造成无法挽回的数据丢失。

2. 为什么 DELETE 注入无法回显数据？

DELETE 语句执行后没有查询结果集，因此无法使用联合查询（union select）来提取数据。攻击者常使用布尔盲注（依据页面变化判断）或时间盲注（sleep()）来盲猜数据，或者直接利用逻辑漏洞进行破坏性操作。

3. GET 请求执行删除操作的安全隐患

如果将删除接口设计为 GET 请求（如 ?id=1），不仅容易遭受 CSRF 攻击（通过诱导点击链接删除数据），还会导致浏览器历史记录、服务器访问日志、代理缓存中留存大量敏感的操作 URL。规范的做法是使用 POST 请求，并配合 CSRF Token 校验。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 INSERT/UPDATE 注入相比：前者是修改或增加数据，对数据完整性产生局部影响；后者是直接清空数据表，属于毁灭性破坏。
  • 与字符型/数字型注入相比：字符型与数字型重在“获取查询结果”，DELETE 注入重在“触发删除动作”，攻击目的和验证方式截然不同。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在实现删除功能时，使用了字符串拼接构造 SQL 语句，并且没有对用户传入的 ID 进行强类型转换或安全过滤。同时，将修改数据的敏感操作暴露为 GET 请求，进一步降低了攻击门槛。

3. 这种应用在实际中如何体现？

在真实的安全事件中，DELETE 注入常被恶意攻击者用来清空用户的订单记录、文章数据、注册信息等，甚至直接删库跑路，给企业造成巨大的经济损失。这也是为什么“删库跑路”在安全圈是一个非常著名的梗（如著名的微盟删库事件）。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个图书馆的管理员：

  • 正常操作：你说“把编号为 1 的那本书扔掉”（delete from books where id = 1）。管理员照做，只扔掉了一本。
  • 攻击操作：你说“把编号为 1 的那本书扔掉，或者把图书馆里所有的书都扔掉”（delete from books where id = 1 or 1=1）。管理员听完，把整个图书馆的书全扔了。这就是 DELETE 注入的可怕之处——逻辑漏洞导致全库毁灭。
