SQL字符型注入 - CTFHub Web 入门 Writeup

2026年9月17日 CTFHub Web安全 SQL注入 字符型注入

这是我做的第二道 SQL 注入题。相比上一道整数型注入，这道“字符型注入”让我彻底搞懂了 SQL 注入的本质。这篇 Writeup 记录了我从“为什么要加 #”、“为什么不能直接问它要 flag”这两个灵魂拷问出发，最终成功“指挥”后台数据库拿到 Flag 的完整过程。

一、核心心法：把后台想象成一个“只听字面意思的傻子”

后台服务器是一个极其死板的“傻子”。你输入 1，它就去数据库找 1 号新闻；你输入 1' union select 1, flag from flag #，它依然当成“数据”去拼 SQL 语句。

SQL 注入的本质：就是利用这个傻子的死板，让原本应该被当成“数据”的输入，被后台当成了“指令”去执行。我们不仅是在“拿密码”，我们是在“劫持服务器的大脑”，让它去执行我们指定的查询。

二、灵魂拷问与解答（为什么这么执行？）

❓ 问题 1：为什么必须加 # ？

后台代码写死了：WHERE id = '$id'（它会把我们输入的内容用单引号夹起来）。

  • 不加 # 的情况：输入 1' union select 1, flag from flag。拼进去变成 WHERE id = '1' union select 1, flag from flag'。你看最后，**多出来一个单引号**！数据库直接报错：“你这引号都没闭合！”（这也是页面空白的原因）。
  • 加了 # 之后：输入 1' union select 1, flag from flag #。拼进去变成 WHERE id = '1' union select 1, flag from flag #'。# 在 SQL 里代表注释。它告诉数据库：“从我 # 后面的东西，全部视为废话，不要管它！”
  • 结论：# 是一把剪刀，专门用来剪掉后面那个讨厌的、闭合不上的单引号。

❓ 问题 2：为什么不能直接让他给我 flag？

因为服务器听不懂人话，它只认死理。后台代码规定死了：SELECT * FROM news WHERE id='$id'。它根本不知道什么叫 flag 表，也不知道什么叫“给我 Flag”。如果你直接输入 flag，它会去 news 表里找一个 id 叫 flag 的新闻，当然什么都查不到。

黑客的解法：利用 union select（联合查询），强行把另一条完全不同的 SQL 语句“拼接”到了后面。相当于告诉傻子：“你刚才查 id=-1 没查到对吧？没关系，别查那个了。现在执行我给你的新命令：去 flag 表里，把 flag 列的内容给我显示出来！”

三、具体怎么“指挥”？（解题步骤）

1. 骗过门卫（测试闭合方式）

输入：1' #。1' 闭合前面的引号，# 注释掉后面的引号。页面正常回显，说明我们成功骗过了后台，让 SQL 语句合法了。

2. 抢过话筒（确定字段数与回显位）

输入：1' order by 2 #，页面正常；输入 1' order by 3 # 报错，说明这张表有 2 列。

输入：-1' union select 1, 2 #。使用 -1' 让前面的查询落空，页面被迫显示我们注入的 1, 2。页面显示 ID: 1, Data: 2，说明第 2 列是“话筒”（回显位）。

3. 下达指令（顺藤摸瓜拿数据）

既然话筒在第 2 列，我们就把查询语句塞在第 2 列：

  • 查库名：-1' union select 1, database() #
  • 查表名：-1' union select 1, group_concat(table_name) from information_schema.tables where table_schema=database() #（查出表名 flag）
  • 查列名：-1' union select 1, group_concat(column_name) from information_schema.columns where table_name='flag' #（查出列名 flag）

4. 终极收割（拿到 Flag）

最终 Payload：-1' union select 1, flag from flag #

页面直接回显了最终的 Flag！

最终 Flag： ctfhub{8c03f589535f2f3b03918d9e}

四、踩坑记录与防御思考

💡 注释符的坑：一开始在地址栏用 --+ 注释，但服务器直接把它转义成了字面加号，导致闭合失败。改用 #（URL 编码为 %23）后成功。这说明实战中要注意不同数据库对注释符的解析差异。

💡 防御思考：怎么防止被“指挥”？这需要用到参数化查询（Prepared Statements）。它把“指令”和“数据”彻底隔离，哪怕黑客输入了恶意指令，数据库也只会把它当作普通文本处理，SQL注入彻底失效。
