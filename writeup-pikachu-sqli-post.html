SQL-Inject 数字型注入(POST) - Pikachu Writeup

2026年9月19日 Pikachu Web安全 SQL注入

一、题目信息

  • 题目名称：SQL-Inject 数字型注入(post)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 数字型 / POST 方式
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_id.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是POST 方式的数字型 SQL 注入。数字型注入的特点是，后端 SQL 语句中参数没有被引号包裹（如 select * from users where id = 1），因此攻击者不需要闭合引号，只需利用逻辑运算符（如 or 1=1）就能篡改 SQL 语义，绕过原有查询条件，拖取全表数据。

2. 怎么想（破题思路）

页面提供了一个下拉框（User ID）和“查询”按钮。解题思路如下：

  • 因为接口是 POST 请求，参数隐藏在 HTTP 请求体中，无法直接在浏览器地址栏拼接参数（GET 方式）来触发。
  • 必须使用 F12 的 Network 面板抓取请求格式，或者使用 Console 面板直接构造 POST 请求。
  • 尝试将 id 参数篡改为 1 or 1=1，观察服务器返回的 HTML 页面中是否包含所有用户的数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：直接在 URL 拼接参数导致无响应

踩坑情况：尝试在浏览器地址栏手动拼接 ?id=1 or 1=1（GET 方式），页面没有任何变化，依然停留在当前用户信息界面。

原因分析：后端代码使用 $_POST['id'] 接收参数，不会解析 URL 中的 GET 参数。因此直接在地址栏修改参数无效。

改进方式：改用 F12 Console 发送 POST 请求，将注入代码放入 `body` 中。

踩坑记录二：靶场环境异常导致无法回显数据（关键踩坑）

踩坑情况：通过 Console 发送 POST 请求后，状态码返回 200 OK，但页面源码中搜索不到任何用户数据（如 allen、kobe）。同时，Network 面板中多次出现 sqli_post.php 404 Not Found。

原因分析：本地 Docker 镜像打包不完整，导致 SQL 注入模块的核心文件缺失或逻辑损坏。虽然请求返回了 200，但后端并未真正执行 SQL 查询，而是返回了默认页面，导致无法回显数据。

改进方式：面对损坏的靶场环境，不必强行死磕。应转而梳理攻击逻辑与原理，模拟正常环境下的注入过程。如果在真实渗透中遇到类似接口 404 或逻辑异常，可以通过目录扫描（如 dirsearch）寻找其他可用的接口，或者利用 Burp Suite 抓包分析响应内容是否符合预期。

终极解法（理论）：利用 SQL 逻辑漏洞篡改查询

在假设环境正常的情况下，我们会在 POST 请求体中提交以下 Payload：

id=1 or 1=1&submit=1

代码逐个符号深度解析：

  • id=1：正常的查询参数。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。这使得 SQL 查询语句变成 select * from users where id = 1 or 1=1。由于 1=1 永远成立，数据库会忽略 id=1 的限制，返回表中所有用户的数据。
  • &submit=1：模拟点击提交按钮。

由于环境限制，我们未能亲眼看到返回结果，但理解了其底层漏洞利用逻辑，这在安全学习中同样至关重要。

4. 怎么迁移（跨领域联想）

  • 高级 SQL 注入（联合查询与盲注）：当页面不直接回显数据时，可以学习使用 union select 联合查询，或者使用布尔盲注（and 1=1 / and 1=2）、时间盲注（sleep(5)）来提取信息。
  • 代码审计与安全开发：这道题揭示了“拼接字符串构建 SQL 语句”的致命缺陷。在实际开发中，必须使用参数化查询（预编译语句，如 PDO 或 PreparedStatement）来分离代码与数据，这是防御 SQL 注入的根本手段。
  • WAF（Web应用防火墙）绕过：在实战中，SQL 注入往往面临 WAF 拦截。攻击者会利用大小写混淆、内联注释（/*!select*/）、URL 编码等技巧绕过过滤。理解基础注入原理是学习绕过的前提。

三、名词大全与原理深度复盘

1. 数字型注入与字符型注入的区别

数字型注入时，后端 SQL 为 id = $id，注入时无需闭合引号，直接用 or 1=1 即可；而字符型注入时，SQL 为 id = '$id'，攻击者需要先闭合单引号 ' or 1=1 --，才能注入逻辑。

2. POST 请求与 GET 请求的渗透测试差异

GET 请求参数在 URL 中，方便直接篡改和分享；POST 请求参数在 HTTP Body 中，相对隐蔽，且不容易被浏览器历史记录和代理缓存记录。测试 POST 注入必须依赖 Burp Suite 或浏览器开发者工具（F12）。

3. 为什么 or 1=1 能拖库？

SQL 引擎在执行 where id = 1 or 1=1 时，会先计算逻辑表达式的值。由于 1=1 为 True，整个 or 表达式恒为 True，这意味着表中的每一行数据都满足条件，从而绕过了原本只查询 id 为 1 的限制。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 相比：XSS 攻击的是浏览器端，用户是受害者；SQL 注入攻击的是服务器端的数据库，网站本身是受害者。
  • 与 CSRF 相比：CSRF 是借用用户的身份做合法操作；SQL 注入是直接构造非法查询语句，突破数据库的权限限制。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发人员为了实现功能，直接使用了字符串拼接的方式构造 SQL 查询语句（如 "select * from users where id = " . $_POST['id']）。这使得用户输入的数据被当成了 SQL 代码的一部分执行，从而引发了注入漏洞。

3. 这种应用在实际中如何体现？

在实际的安全事件中，SQL 注入常被用来“脱库”（窃取整个数据库的账号密码）、篡改网页内容、甚至获取服务器最高权限（通过 into outfile 写入 Webshell）。是 Web 安全中危害最大的漏洞之一。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个仓库管理员：

  • 正常查询：你拿着提货单说：“我取第 1 号货架上的东西”（id=1）。管理员照做。
  • SQL 注入：你狡猾地说：“我取第 1 号货架上的东西，**或者把整个仓库都给我**”（id=1 or 1=1）。管理员听不懂逻辑陷阱，直接把整个仓库的货都搬给了你。这就是 SQL 注入的威力。

做一道题，就要往自己脑子里装点东西。
