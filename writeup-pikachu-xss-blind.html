XSS之盲打 - Pikachu Writeup

2026年9月19日 Pikachu Web安全 XSS

一、题目信息

  • 题目名称：XSS之盲打
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 存储型 XSS 变种
  • 靶场链接：http://localhost:8080/vul/xss/xssblind.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是存储型 XSS 的一个特殊分支——盲打（Blind XSS）。与普通的反射型 XSS 不同，盲打的 Payload 会先被服务器存入数据库，但不会在当前提交的页面立刻执行或显示。只有当网站管理员在后台管理系统中查看这些提交的数据时，恶意代码才会在管理员的浏览器中触发执行。

2. 怎么想（破题思路）

盲打的核心是“打给管理员看”。因此，解题的必经之路是：

  • 在前台（提交页面）植入带有 JavaScript 执行能力的 Payload。
  • 找到管理员查看该数据的后台页面（管理员登录地址通常隐藏在 URL 路径中，或通过靶场提示获取）。
  • 模拟管理员身份访问后台，触发 Payload。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：提交后未立刻弹窗，误以为失败

踩坑情况：在输入框中提交了 <script>alert('xss')</script> 后，当前页面没有反应，只提示“谢谢参与，阁下的看法我们已经收到！”。

原因分析：盲打 XSS 的 Payload 是存储在服务端的数据库中的。当前提交页面只负责写入数据库，不负责在前台渲染执行 Payload。

改进方式：提交成功后，必须去后台管理系统查看提交的内容。如果不知后台地址，可点击提示按钮获取，或查看 URL 规律。

踩坑记录二：后台地址拼写错误导致 404

踩坑情况：将 URL 误拼为 localhost:8080/xssblind/admin_login.php，导致浏览器报错 ERR_FILE_NOT_FOUND。

原因分析：漏掉了原有的路径层级。原本的 URL 是 http://localhost:8080/vul/xss/xssblind.php，所以后台地址应当在此基础上拼接，需要保留 /vul/xss/ 前缀。

改进方式：面对 404 报错，第一反应应该检查地址栏路径是否完整。正确的后台地址应为：http://localhost:8080/vul/xss/xssblind/admin.php（或 admin_login.php）。

终极解法：构造盲打 Payload 并触发

在“看法”文本框中输入以下 Payload：

<script>alert('xss')</script>

代码逐个符号深度解析：

  • < 和 >：HTML标签的定界符，告诉浏览器这是一个标签。
  • script：脚本标签，浏览器会解析并执行里面的 JavaScript 代码。
  • alert('xss')：JavaScript 内置函数，用于弹出警告框。当管理员打开后台页面时，这段代码就会被执行，弹出包含 'xss' 文本的对话框。
  • </script>：脚本标签闭合，标示代码结束。

点击提交按钮后，页面提示成功。接下来，在浏览器地址栏输入：

http://localhost:8080/vul/xss/xssblind/admin.php

打开该后台页面时，如果 Payload 写入了数据库并被成功读取，浏览器将直接弹出 xss 弹窗，证明盲打攻击成功。此题目没有设置特定的 Flag 字符串，弹窗成功即为通关。

4. 怎么迁移（跨领域联想）

  • 实际渗透测试中的 OOB（带外）攻击：在真实的黑盒渗透测试中，盲打的 Payload 常常配合 XSS 平台（如 XSSer.me 或 Ceye.io）使用。Payload 执行后会自动将管理员 Cookie 发送到攻击者搭建的外网服务器，实现会话劫持，这属于典型的带外（Out-of-Band）数据外带手法。
  • Web 漏洞挖掘的延伸：除了 XSS 盲打，还有 SQL 注入盲注、XXE 盲打等。其核心思想高度一致：提交恶意代码后，通过观察后端系统或外网服务器上的响应来间接判断漏洞是否存在以及利用成功与否。

三、名词大全与原理深度复盘

1. 盲打（Blind XSS）

盲打 XSS 是存储型 XSS 的一种特殊形式。攻击者无法直接观察到 Payload 在前端的执行情况，只能寄希望于后台管理员查看时触发。这种攻击通常发生在反馈、留言、举报等交互功能中。

2. 为什么盲打需要后台触发？

因为盲打的 Payload 是存储在服务端的数据库中的。只有当具有查看该数据权限的用户（通常是管理员）通过前端页面渲染这些数据时，浏览器才会解析并执行攻击者插入的恶意 JavaScript 代码。这是攻击者利用管理员的浏览器作为“替罪羊”来执行恶意操作的一种手段。

3. 为什么在实际攻击中盲打危害更大？

盲打攻击获取的是“管理员权限”的浏览器执行环境。如果攻击成功，攻击者可以利用管理员的 Session 直接进入后台，甚至通过后台的富文本编辑器或文件上传功能获取服务器权限（GetShell）。因此，盲打 XSS 经常被列为高危漏洞。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型 XSS 相比：反射型是输入即回显，需要诱导受害者点击构造好的 URL 触发；盲打是输入后存入数据库，无需诱导，在管理员日常后台审核时自动触发，属于“被动触发”型持久化漏洞。
  • 与普通存储型 XSS 相比：普通存储型 XSS 在留言板前台就能看到，其他用户访问前台就会触发；盲打 XSS 的触发点在前台看不到，必须进入后台管理界面才能触发，攻击路径更隐蔽。

2. 这种题目的出现原因（为什么存在）

这种题目的出现，是因为 Web 开发中往往对“后台管理系统”的安全性过于自信，认为后台只有管理员能访问，所以对从前台提交过来的数据没有做严格的过滤和转义（如未使用 htmlspecialchars 进行实体编码）。但实际上，数据流是从前台流向后台的，这种“跨边界”的数据流正好被攻击者利用来攻击管理员。

3. 这种应用在实际中如何体现？

在实际的安全演练（红蓝对抗）中，攻击者会在所有可输入的地方（如反馈、举报、简历投递、评论）插入 XSS 盲打 Payload。当管理员在后台审核这些数据时，Payload 被执行，悄悄将管理员的 Cookie 发送到攻击者控制的服务器，攻击者利用获取的 Cookie 直接登录后台系统，完成权限提升。

4. 如何抽象理解概念（大白话理解）

如果把网站比作一个公司：

  • 前台：是公司的大厅，接待客户（普通用户）。
  • 后台：是公司的经理办公室，闲人免进（管理员）。
  • 盲打 XSS：就像一个匿名客户在前台的意见箱里塞了一封“带毒”的信（恶意代码）。前台人员看完信没事（前台不触发），但经理在办公室里拆开这封信阅读时，信件突然喷出墨汁弄瞎了经理的眼睛（在管理员的浏览器里执行了恶意代码）。攻击者通过这种方式，偷偷获取了只有经理才能看到的机密（如 Cookie）。
