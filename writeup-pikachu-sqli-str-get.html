一、题目信息

  • 题目名称：SQL-Inject 字符型注入(get)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 字符型 / GET 方式
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_str.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是GET 方式的字符型 SQL 注入。与数字型不同，字符型注入的后端 SQL 语句中，参数被单引号包裹（如 select * from users where username = 'vince'）。因此，攻击者需要先使用单引号闭合原本的引号，才能插入恶意的 SQL 逻辑（如 or 1=1），最后使用注释符（# 或 -- ）注释掉原本的闭合引号，保证语法正确。

2. 怎么想（破题思路）

页面提示“what's your username?”。右上角提示“变量类型为字符型”。解题思路如下：

  • 首先输入一个存在的用户名（如 vince），确认接口可正常回显数据。
  • 在用户名后加一个英文单引号 vince'，观察是否引发数据库报错。如果报错，说明单引号成功闭合，漏洞存在。
  • 构造能绕过逻辑判断的 Payload：' or 1=1 #，使 SQL 条件恒为真，从而拖取全表用户数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：输入单引号导致页面报错，误以为操作失败

踩坑情况：在输入框中输入 vince'，点击查询后，页面直接弹出一行红色 SQL 报错代码，没有任何数据回显，初学阶段容易误以为破坏了靶场导致无法继续。

原因分析：这恰恰是漏洞存在的证明。后端 SQL 变为 username = 'vince''，多余的单引号导致数据库语法解析失败，因此报出 You have an error in your SQL syntax 错误。

改进方式：充分理解“报错即漏洞特征”。正确构造闭合语句（如 ' or 1=1 #），同时利用注释符注释掉多余引号，即可使语法恢复平衡并绕过原有逻辑。

踩坑记录二：注释符使用不当导致语句截断

踩坑情况：在输入 ' or 1=1 # 时，如果井号后面没有加空格，或者使用 -- 时没有在末尾加空格，可能导致注释失败。

原因分析：MySQL 中的 # 和 -- 都是注释符，但使用 -- 时必须在后面紧跟一个空格，否则会被当作减号运算符解析。

改进方式：严格遵循 Payload 语法：' or 1=1 #（# 前自带一个空格以防万一），或使用 ' or 1=1 -- （-- 后必须紧跟一个空格）。

终极解法：利用单引号闭合与逻辑绕过

最终在输入框中提交以下 Payload：

' or 1=1 #

代码逐个符号深度解析：

  • '：单引号。用来闭合后端 SQL 语句中原有的前引号（例如 username = '）。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。这使得 SQL 查询条件变成 username = '' or 1=1。由于 1=1 永远成立，整个 or 表达式为真，数据库忽略了 username 限制，返回表中所有用户的数据。
  • #：MySQL 中的注释符。用来注释掉 SQL 语句末尾原本存在的闭合单引号（'），保证语句语法完整不报错。

提交后，页面成功回显所有用户信息（vince、allen、kobe、grady、kevin、lucy、lili），证明注入攻击成功。

4. 怎么迁移（跨领域联想）

  • 高级 SQL 注入（联合查询 union select）：在拖取全表数据后，可以进一步使用联合查询获取数据库名、表名和字段名。例如 ' union select 1,database() #，逐步扩大战果。
  • 代码审计与安全开发：这道题揭示了“拼接字符串构建 SQL 语句”的致命缺陷。在实际开发中，必须使用参数化查询（预编译语句，如 PDO 或 PreparedStatement）来分离代码与数据，这是防御 SQL 注入的根本手段。
  • WAF（Web应用防火墙）绕过：在实战中，SQL 注入往往面临 WAF 拦截。攻击者会利用大小写混淆（Or）、内联注释（/*!or*/）、URL 编码等技巧绕过过滤。理解基础注入原理是学习绕过的前提。

三、名词大全与原理深度复盘

1. 字符型注入与数字型注入的区别

数字型注入时，后端 SQL 为 id = $id，注入时无需闭合引号，直接用 or 1=1 即可；而字符型注入时，SQL 为 id = '$id'，攻击者需要先闭合单引号 ' or 1=1 #，才能注入逻辑。单引号是字符型注入的核心突破口。

2. GET 请求与 POST 请求的渗透测试差异

GET 请求参数在 URL 中，方便直接篡改和分享；POST 请求参数在 HTTP Body 中，相对隐蔽，且不容易被浏览器历史记录和代理缓存记录。测试 POST 注入必须依赖 Burp Suite 或浏览器开发者工具（F12）。

3. 为什么 # 可以注释掉后面多余的单引号？

在 MySQL 中，# 表示从该符号开始，直到行尾的所有内容都被视为注释，数据库引擎会忽略这部分内容。因此，原本后端代码中用于闭合的最后一个单引号被跳过，从而避免了语法错误。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与数字型注入相比：数字型不需要闭合引号，直接注入逻辑条件即可；字符型必须闭合单引号，且必须使用注释符处理多余的单引号，Payload 构造更加精细。
  • 与 XSS 相比：XSS 攻击的是浏览器端，用户是受害者；SQL 注入攻击的是服务器端的数据库，网站本身是受害者。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发人员为了实现功能，直接使用了字符串拼接的方式构造 SQL 查询语句（如 "select * from users where username = '" . $_GET['name'] . "'"）。这使得用户输入的数据被当成了 SQL 代码的一部分执行，从而引发了注入漏洞。

3. 这种应用在实际中如何体现？

在实际的安全事件中，SQL 注入常被用来“脱库”（窃取整个数据库的账号密码）、篡改网页内容、甚至获取服务器最高权限（通过 into outfile 写入 Webshell）。是 Web 安全中危害最大的漏洞之一。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个仓库管理员：

  • 正常查询：你拿着提货单说：“我取用户名是 vince 的包裹”（username = 'vince'）。管理员去对应货架找。
  • 字符型 SQL 注入：你狡猾地说：“我取用户名是 '' 的包裹，**或者把整个仓库都给我**”（username = '' or 1=1），并顺带把提货单后半截撕掉（# 注释符）。管理员看不懂逻辑陷阱，直接把整个仓库的货都搬给了你。这就是字符型注入的威力，核心在于用单引号打破原有的规则边界。
