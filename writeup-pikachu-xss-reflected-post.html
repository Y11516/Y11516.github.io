反射型XSS(POST) - Pikachu 靶场 Writeup

2026年9月17日 Pikachu 靶场 Web安全 XSS POST请求

这是我 XSS 模块的第二关。与上一关的 GET 型完全不同，POST 型 XSS 的数据不在 URL 里，不能直接在地址栏拼参数。本篇 Writeup 记录了我如何在这个充满障眼法的页面里，成功找到注入点并让浏览器弹窗。

一、GET 与 POST 型 XSS 的核心区别

  • GET 型： 参数在 URL 里（?name=xxx），可以直接通过地址栏拼 URL 传参。
  • POST 型： 参数在请求体（Request Body）里，浏览器地址栏不可见，必须通过表单提交或抓包改包来修改参数。

二、解题过程（从困惑到顿悟）

1. 踩坑：靶场的“障眼法”

进入页面后，页面并没有直接展示输入框，而是先弹出了“你已经登陆成功,退出登录”和科比的照片。我一度以为目标完成了，但页面上又出现了一个“Which NBA player do you like?”的输入框和一个 submit 按钮。

解析： 这是靶场故意设计的模拟场景，让你有代入感。真正的漏洞就藏在这个用来测试 XSS 的输入框中。千万不要被前面的提示忽悠了！

2. 尝试直接输入 Payload

在输入框里输入：<script>alert('xss')</script>，点击 submit。

浏览器立刻弹出了写着 xss 的警告框。就是这么简单！

3. 万能备用方案：Burp Suite 抓包改包

如果输入框有长度限制，或者服务器过滤了 <script> 标签，我们就用 POST 型的标准解法：

  • 开启 Burp 代理，在页面输入正常的 kobe，点击 submit。
  • 在 Burp 里拦截这个 POST 请求。
  • 把请求体里的 kobe 改成 <img src=x onerror=alert('xss')>。
  • 放行请求，浏览器弹窗。

三、知识点总结与防御思考

💡 POST 型 XSS 的本质： 服务器对 POST 请求的 Body 参数没有进行过滤和转义，直接将用户输入拼接到了 HTML 页面中。

💡 核心绕过手段： 遇到前端限制时，尝试使用 Burp Suite 抓包改包，因为抓包是在浏览器和服务器之间“截胡”，可以随意修改请求体内容。

💡 防御： 后端必须对用户提交的所有输入进行严格的过滤和 HTML 实体编码输出（转义 < 为 &lt;）。

做一道题，就要往自己脑子里装点东西。
