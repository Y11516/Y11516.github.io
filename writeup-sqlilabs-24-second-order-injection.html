SQLi-Labs Less-24

2026年9月28日 SQLi-Labs Web安全 SQL注入 二次注入

一、题目信息

  • 题目名称：SQLi-Labs Less-24 (POST - Second Order Injections *Real treat* - Stored Injections)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 二次注入 / 存储型注入
  • 靶场链接：http://localhost:8081/Less-24/（本地环境）
  • 涉及工具：Chrome浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是二次注入（Second Order Injection）。与之前的直接注入不同，二次注入分两步触发：
第一步（存储阶段）：攻击者将恶意 Payload 存入数据库（如注册一个恶意用户名 hacker'#）。此时后端会转义单引号，直接注入失败。
第二步（触发阶段）：当程序再次从数据库读取该数据（如修改密码），且未再次过滤直接拼接到新的 SQL 语句时，漏洞爆发。

2. 怎么想（破题思路）

  • 在登录页发现存在“注册”和“修改密码”功能。
  • 注册恶意用户名 hacker'#，密码 123456。
  • 登录该账号，进入“修改密码”页面。
  • 后端执行 SQL 时，会通过用户名拼接，因为 # 的作用，SQL 语句变成了修改 admin 用户的密码。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：修改密码页面触发 failed.php

踩坑情况：在修改密码页面点击 Reset 后，跳转到 failed.php，显示“BUG OFF YOU SILLY DUMB HACKER”。

原因分析：修改密码时，后端会先校验 Current Password。如果未填写或与注册时的密码不一致，校验就会失败；另外，# 字符在 HTTP 传输中可能被转义为 %23，导致它无法起到注释作用，从而找不到 hacker 用户。

改进方式：注册新账号时使用 hacker'#，登录后修改密码时，必须在 Current Password 栏严格填入注册时的密码 123456，并确保密码框全部正确填写。

详细实操步骤（Payload逐字解释）

第一步：注册恶意账号

点击页面底部的 New User click here?：

  • 用户名：hacker'#
  • 密码：123456

第二步：登录恶意账号

  • 用户名：hacker'#
  • 密码：123456

第三步：触发二次注入

在修改密码页面填入：

  • Current Password: 123456（必须填写正确）
  • New Password: 123456
  • Retype Password: 123456

点击 Reset。此时后端执行了以下 SQL：

UPDATE users SET password='123456' WHERE username='hacker'#' AND password='123456'

因为 # 的作用，后面的 AND password='123456' 被注释掉了。实际执行的是：

UPDATE users SET password='123456' WHERE username='hacker'

注意：由于用户名是 hacker'#，拼接后实际变成了 UPDATE ... WHERE username='hacker'#'...。在 MySQL 中，# 是注释符，这意味着整个 SQL 变成了修改用户名为 hacker 的记录（如果注册时被转义，实际上数据库里存的是 hacker\'#，而在 UPDATE 时单引号被还原，# 生效注释掉了后面的密码验证）。

稍等，如果数据库里存的是 hacker'#，那么 UPDATE 语句为 UPDATE users SET password='123456' WHERE username='hacker'#'，# 注释掉尾部的引号，实际执行修改的是用户名为 hacker 的记录。等等，我们要修改 admin 的密码！

正确的逻辑是：我们需要让 UPDATE 语句变成 UPDATE users SET password='123456' WHERE username='admin'#。为了让前端传入的 admin 作为用户名，我们注册的恶意用户应该是以 admin 开头的，比如 admin'#。这样在 UPDATE 时，SQL 语句为 UPDATE users SET password='123456' WHERE username='admin'#'，成功注释掉后面的检查，从而修改了 admin 的密码！

（修正说明：如果在第一步注册时用户名填写的是 admin'#，那么数据库里存的就是 admin'#。当你在登录状态修改密码时，后端拼出的 SQL 就是 UPDATE users SET password='123456' WHERE username='admin'#'，刚好完美注释，修改了 admin 的密码！）

第四步：验证成果

点击 Logout 退出，用新密码 admin / 123456 登录，成功。

4. 怎么迁移（跨领域联想）

  • 信任边界与数据流：二次注入深刻体现了“不要相信从数据库中取出的数据”这一原则。开发者常认为数据存进去时已经过验证，取出来时就“安全”了，这种思维盲区极其危险。
  • 存储型 XSS 的同理：二次注入的原理与“存储型 XSS”如出一辙——都是将恶意载荷存入数据库，待管理员或其他程序读取时触发。这说明漏洞的触发点往往不在输入点，而在输出点。
  • 真实场景的防御：防御二次注入的核心是使用参数化查询（Prepared Statements），确保所有 SQL 操作都严格区分代码与数据。

三、名词大全与原理深度复盘

1. 二次注入 (Second Order Injection)

指恶意载荷首先被存入数据库（或文件系统），在后续的业务逻辑中，程序再次读取该载荷并拼接到 SQL 语句中执行时触发的注入漏洞。其利用过程分为存储和触发两个阶段。

2. 存储型注入 (Stored Injection)

二次注入的另一种称呼。强调注入载荷被持久化保存，可能在后端的定时任务、管理员后台等场景中触发，危害范围更大。

3. 参数化查询 (Prepared Statements)

通过占位符（如 ? 或 :name）将 SQL 代码与用户输入严格分离，从根本上杜绝 SQL 注入。是防御所有 SQL 注入漏洞（包括二次注入）的终极方案。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-11~23 的区别：之前的关卡都是“输入即触发”，前端提交 Payload，后端立刻执行。Less-24 是“先存入，后触发”，输入和触发点在不同的页面，防御机制和利用难度都更高。
  • 与 Less-20/21 的区别：Less-20/21 是 Cookie 注入（传输层注入），Less-24 是数据库持久化注入。

2. 这种题目的出现原因（为什么存在）

开发者通常会在用户输入的第一个入口（如注册）进行严格过滤，但由于思维惯性，当从数据库读取数据去执行 UPDATE、SELECT 等操作时，往往会忽略二次过滤。这是典型的“信任边界”失控问题。

3. 这种应用在实际中如何体现？

在实战中，二次注入常出现在具有“用户中心”、“密码找回”、“后台审核”功能的系统中。比如：攻击者将 Payload 隐藏在用户名中，管理员在后台审核用户时触发了 SQL 注入。防御方必须统一使用参数化查询，或对所有从数据库取出的变量再次进行安全处理。

4. 如何抽象理解概念（大白话）

把靶场比作一个“档案管理员”：

  • Less-24 的档案管理员在门口收资料时，会把所有“炸弹代码”都锁进档案柜（安全存入数据库）。
  • 但当他去档案柜里拿资料时，他认为这是自己人存进去的“安全资料”，于是毫无防备地照着念（直接拼接到 UPDATE 语句）。
  • 结果，档案柜里那颗炸弹被触发了。
