SQL-Inject 宽字节注入 - Pikachu Writeup

2026年9月19日 Pikachu Web安全 SQL注入

一、题目信息

  • 题目名称：SQL-Inject 宽字节注入
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 编码绕过 / GET方式
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_widebyte.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、终端（Terminal）、curl 命令

二、解题步骤

1. 分析题目考什么

本题的核心考点是宽字节注入（Wide Byte Injection）。在很多Web应用中，开发者会使用 addslashes() 或 mysql_real_escape_string() 等函数对用户输入的单引号进行转义（在单引号前加上反斜杠 \）。但如果数据库使用了 GBK 等多字节编码，攻击者可以通过构造特定的高位字节（如 %df），与转义符 %5c 组合成一个合法的汉字，从而“吃掉”反斜杠，使单引号成功逃逸。

2. 怎么想（破题思路）

页面是一个普通的用户名查询框。解题思路如下：

  • 尝试输入 kobe'，如果页面没有报错，而是显示“不存在”，说明单引号被转义了（变成了 kobe\'）。
  • 既然单引号被转义，我们需要在单引号前面加上一个特殊的高位字节（如 %df），这样 %df%5c 会被 GBK 编码解析为一个汉字，反斜杠失效。
  • 因为浏览器输入框会自动将 % 转义为 %25，所以必须在地址栏或使用终端进行 URL 编码注入。
  • 构造最终的 Payload：kobe%df%27 or 1=1 %23，使 SQL 逻辑恒为真，拖取全表数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：终端 zsh 报错 no matches found

踩坑情况：在 Mac 终端（zsh）直接粘贴带有 ? 和 & 的长 URL，终端报错 zsh: no matches found: http://...。

原因分析：zsh 会把问号 ? 和 & 识别为通配符或特殊控制字符，导致解析失败。

改进方式：在使用 curl 时，URL 需要用单引号或双引号包裹，如 curl "http://..."，或者使用 --data-urlencode 配合短 URL 进行 POST 请求。

踩坑记录二：终端报错 quote> 卡死

踩坑情况：复制过长命令时，终端没有执行，而是出现 quote> 提示符，无法继续输入。

原因分析：命令的引号没有完全闭合，终端在等待用户输入剩余的闭合引号。

改进方式：按 Ctrl + C 强行终止当前命令，然后使用干净、简洁的 curl 命令，或直接使用 F12 复制 Copy as cURL (bash) 后替换数据体中的 name 参数。

踩坑记录三：本地 Docker 环境未触发回显

踩坑情况：执行宽字节注入命令后，终端未抓取到 uid 或其他用户信息。

原因分析：部分 Pikachu Docker 镜像在打包时默认使用 UTF-8 字符集，MySQL 未正确配置 GBK，导致 %df 无法吃掉 %5c，宽字节注入漏洞实际上处于不可利用状态。

改进方式：了解环境差异带来的影响，不钻牛角尖。在真实渗透中遇到编码不匹配的环境，应转用参数化查询漏洞（如之前的题）或其他注入点，或者利用十六进制编码绕过。

终极解法（理论）：利用 %df 吃掉转义符

在地址栏或利用终端执行以下 Payload：

http://localhost:8080/vul/sqli/sqli_widebyte.php?name=kobe%df%27%20or%201=1%20%23&submit=%E6%9F%A5%E8%AF%A2

代码逐个符号深度解析：

  • name=：参数名。
  • kobe：正常用户名前缀，用于闭合原有的字符串。
  • %df：高位字节。用于与后端的反斜杠 %5c 结合成 GBK 汉字。
  • %27：URL 编码的单引号，逃逸出来闭合 SQL 语句。
  • %20：URL 编码的空格。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。
  • %23：URL 编码的井号 #，用于注释掉 SQL 语句末尾多余的代码。
  • submit=：提交按钮的参数名。
  • %E6%9F%A5%E8%AF%A2：“查询”二字的 URL 编码。

由于本地环境字符集配置问题，未能回显数据，但完全掌握了其编码绕过的底层逻辑。

4. 怎么迁移（跨领域联想）

  • WAF 绕过（Web应用防火墙）：宽字节注入是绕过 WAF 的一种思路。当 WAF 使用正则匹配单引号进行拦截时，将单引号编码为 %df%27 可以欺骗部分 WAF，绕过其规则库。
  • 代码审计：在审计代码时，如果发现使用了 addslashes() 并且没有使用 mysql_set_charset('utf8') 指定字符集，应直接判定存在宽字节注入风险。
  • 跨国应用与编码兼容：在进行国际化的网站开发时，必须严格统一前端、后端、数据库连接、数据库存储的字符集为 UTF-8，避免因字符集不一致引发的各类安全漏洞和乱码问题。

三、名词大全与原理深度复盘

1. 宽字节注入（Wide Byte Injection）

利用多字节编码（如 GBK）的特性，通过提交高位字节与原本的转义符号（如 \）组合成新的合法字符，从而绕过转义函数，使单引号逃逸。这是数据库字符集设置错误导致的一种安全漏洞。

2. GBK 编码原理

GBK 是双字节编码。一个汉字占用两个字节：第一个字节（高位字节）的范围是 0x81-0xFE，第二个字节（低位字节）的范围是 0x40-0xFE。反斜杠 \ 的十六进制是 0x5c，正好落在低位字节范围内。因此，当攻击者输入 %df 时，后端拼接为 %df%5c，这被 GBK 解析为一个合法的汉字（如“運”），反斜杠被吃掉了。

3. 为什么必须用终端或抓包？

浏览器的表单输入框会自动对 % 进行 URL 编码（将 % 编码为 %25），导致 %df 被破坏。要发送未经二次编码的恶意字节，必须绕过表单，直接通过修改 URL（地址栏）或使用 Burp Suite / curl 等工具修改请求体。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与普通字符型注入相比：字符型注入是直接通过输入单引号闭合；宽字节注入是在单引号被转义的情况下，利用编码漏洞绕过转义函数，使单引号重新生效。
  • 与盲注相比：盲注是解决“不回显”的问题；宽字节注入是解决“单引号被过滤/转义”的问题。两者的攻击侧重点和利用场景完全不同。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者使用了 addslashes() 进行防御，但后端数据库连接层默认使用了 GBK 等多字节编码（例如未执行 SET NAMES 'utf8' 或 mysql_set_charset('utf8')）。防御机制没有配合正确的字符集，导致转义字符被编码“吃掉”，防御形同虚设。

3. 这种应用在实际中如何体现？

在实际的安全测试中，如果目标网站使用了中文，且数据库编码陈旧（如 GBK），测试人员会尝试提交 %df%27。如果页面报出 SQL 语法错误，说明宽字节注入成功，这是一个极具破坏力的漏洞，常被用来绕过 WAF 的通用防护规则。

4. 如何抽象理解概念（大白话理解）

如果把转义函数比作一个负责检查单引号的保安：

  • 正常防御：保安看到单引号，就在它前面插一个盾牌 \，让它无法生效。
  • 宽字节注入：你拿出一张符纸 %df，贴在了保安的盾牌上。由于符纸和盾牌拼在一起变成一个汉字（合法的魔法），保安就以为盾牌消失了，单引号顺利过关。这就是利用编码特性进行“越狱”的核心逻辑。
