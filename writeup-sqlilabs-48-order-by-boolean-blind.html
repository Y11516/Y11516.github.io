SQLi-Labs Less-48

2026年9月29日 SQLi-Labs Web安全 SQL注入 ORDER BY 布尔盲注

一、题目信息

  • 题目名称：SQLi-Labs Less-48 (GET - Error based - Blind - Numeric - ORDER BY CLAUSE)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / ORDER BY 注入 / 布尔盲注
  • 靶场链接：http://localhost:8081/Less-48/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是ORDER BY 子句中的布尔盲注。Less-48 是 Less-46 的盲注变体，没有报错回显，且闭合方式为数字型（Numeric，无需引号闭合）。攻击者必须使用 if(条件, 字段A, 字段B) 来改变排序结果，通过观察页面数据排列的顺序来判断条件真伪。

2. 怎么想（破题思路）

  • 页面提示 "Please input parameter as SORT with numeric value"，说明是数字型注入。
  • 因为没有任何报错回显（Blind），不能使用 updatexml 或 extractvalue。
  • 构造布尔盲注 Payload：?sort=if(1=1,id,username)，观察页面是否按 ID 排序。
  • 输入 ?sort=if(1=2,id,username)，观察页面是否按 USERNAME 排序。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：尝试堆叠注入导致页面空白

踩坑情况：尝试使用 ?sort=1; update users set password='123456' where username='Dumb';-- - 进行堆叠注入，页面没有报错，但返回了空白的 Welcome Dhakkan 页面（无用户列表）。

原因分析：在 ORDER BY 子句中，使用 1; 结束排序后，直接拼接 update 语句违背了 MySQL 的解析规则（或者环境未开启 mysqli_multi_query 的解析支持），导致整个 SQL 查询崩溃，没有数据返回。

改进方式：本关标签是 Blind，核心是使用布尔盲注而非堆叠注入。通过 if 语句改变排序字段来验证逻辑即可通关。

详细实操步骤（Payload逐字解释）

第一步：布尔盲注真值测试

在浏览器地址栏输入以下 URL：

http://localhost:8081/Less-48/?sort=if(1=1,id,username)

预期结果：页面按 ID 排序（1, 10, 11, 12...）。

第二步：布尔盲注假值测试

http://localhost:8081/Less-48/?sort=if(1=2,id,username)

预期结果：页面按 USERNAME 排序（admin, admin'#, admin1...）。

第三步：Payload 逐字解析

  • if(1=1, id, username)：这是一个条件判断函数。如果 1=1 成立（真），则使用 id 字段进行排序；如果不成立（假），则使用 username 字段排序。
  • sort=：将 Payload 传递给参数 sort，该参数最终会被拼接到 SQL 的 ORDER BY 后面。

第四步：如何真正脱库？

如果为了脱库，可以将 1=1 替换为猜解数据库的 Payload，如：?sort=if(substr(database(),1,1)='s', id, username)。如果页面按 ID 排序，则说明数据库名的第一个字母是 's'。

4. 怎么迁移（跨领域联想）

  • 应用场景联想：ORDER BY 注入常见于电商系统或后台管理系统的“排序”按钮。用户在点击“按价格排序”、“按销量排序”时，底层就是在执行 ORDER BY 子句。
  • 防御策略联想：对于 ORDER BY 后面的参数，绝对不能接受用户直接输入的字符串。必须使用**白名单**机制（如只允许 "price", "time", "id"），或强制转换为数字类型。
  • 安全开发启示：使用参数化查询（Prepared Statements）是防御 SQL 注入的终极方案。

三、名词大全与原理深度复盘

1. 布尔盲注 (Boolean-Based Blind SQL Injection)

当页面没有回显位时，攻击者通过构造返回真或假的 SQL 条件，观察页面内容或状态是否变化（如排序字段变化、页面内容不同等），从而推断数据库信息。

2. ORDER BY 子句

SQL 中用于对结果集进行排序的语句，可指定一个或多个字段。在注入中，它的特殊之处在于不能直接使用 UNION 和逻辑运算符。

3. 优化器短路

当数据库可以通过索引快速返回结果时，查询优化器会跳过不必要的函数执行（如 sleep()），导致盲注延迟失效。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-46 的区别：Less-46 是报错注入（有回显），Less-48 是布尔盲注（无回显）。
  • 与 Less-47 的区别：Less-47 是 POST 请求，Less-48 是 GET 请求。

2. 这种题目的出现原因（为什么存在）

开发者在编写排序功能时，为了图方便，直接将用户传来的字段名拼接到 SQL 后面，并且没有对参数进行白名单校验。他们认为“只是一个排序字段，没什么危害”，从而忽略了注入风险。

3. 这种应用在实际中如何体现？

在电商网站、论坛、后台管理系统中，用户可以点击“按价格排序”、“按销量排序”。如果后端没有对排序参数做白名单校验，攻击者就能利用 ORDER BY 注入获取数据库信息。

4. 如何抽象理解概念（大白话）

把靶场比作一个“整理书架的管理员”：

  • 你告诉他：“按 ID 排序（ORDER BY id）”，他就按顺序排好。
  • 你问他：“如果 1=1 成立，就按 ID 排；否则按名字排”。
  • 他按 ID 排了，你就知道 1=1 成立。你换成 1=2，他按名字排了，你就知道 1=2 不成立。
  • 这就是布尔盲注的核心：利用状态变化来推断真相。

做一道题，就要往自己脑子里装点东西。
