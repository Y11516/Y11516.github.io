XSS之js输出 - Pikachu Writeup

2026年9月19日 Pikachu Web安全 XSS

一、题目信息

  • 题目名称：XSS之js输出
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 反射型 / JavaScript 上下文注入
  • 靶场链接：http://localhost:8080/vul/xss/xss_js.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是输出上下文决定攻击方式（Context-Dependent XSS）。当用户输入被输出在 HTML 标签之间、标签属性内、URL 中或 JavaScript 代码块中时，攻击的 Payload 构造方式截然不同。本题考察的是解题者能否识别出输入处于 <script> 标签内部，并利用 JavaScript 语法特性（如引号闭合、表达式执行）来注入代码。

2. 怎么想（破题思路）

页面提示“输入被动态的生成到了 javascript 中，如何是好。输入 tmac 试试-_ -”。解题思路如下：

  • 输入提示中的 tmac，页面回显显示在页面上，说明输入被正常处理。
  • 尝试输入常规 HTML 标签 Payload（如 <script>alert(1)</script>），页面无弹窗。原因在于，此时的输出上下文是 JavaScript 字符串（例如 var player = '用户输入';），HTML 标签在 JS 字符串中会被当作纯文本，不会触发解析执行。
  • 既然处于 JS 字符串中，就需要闭合原有的单引号，跳出字符串限制，然后注入 JS 代码，并处理后续代码以保证语法正确。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：常规 Payload 在 JS 上下文中失效

踩坑情况：在输入框中提交 <script>alert(1)</script>，页面没有任何弹窗，也没有报错。

原因分析：后端 PHP 代码可能通过 echo 输出了类似 var player = '<script>alert(1)</script>'; 的代码。对于浏览器来说，这是一段字符串赋值，HTML 标签仅仅作为字符串的内容存在，不会被解析为 DOM 节点。

改进方式：必须打破字符串的闭合边界。使用单引号（或双引号）闭合原本的字符串变量，然后插入 JS 代码。

踩坑记录二：闭合不完整导致语法错误

踩坑情况：尝试输入 tmac' 提交，页面直接变成空白或报错。

原因分析：输入 tmac' 后，最终 JS 代码变成 var player = 'tmac'';，单引号不配对，导致严重的 JavaScript 语法错误，整个脚本终止执行。

改进方式：在闭合前一个字符串的同时，必须构造有效的 JS 语法结构。

终极解法：利用运算符执行表达式

在输入框中输入以下 Payload：

tmac'-alert(1)-'

代码逐个符号深度解析：

  • tmac：普通字符串前缀，用来定位和验证注入位置。
  • '：单引号闭合。用来闭合后端代码中的起始单引号（如 var player = '），使接下来的代码成为独立的 JS 语句。
  • -：减号运算符。在 JavaScript 中，减法运算符会触发类型转换。它是一个二元运算符，左侧是字符串 tmac，右侧是函数执行结果。
  • alert(1)：JavaScript 的内置弹窗函数，作为表达式被求值，触发弹窗。
  • -：减号运算符。用于与后面的空字符串组成完整的表达式，确保语法结构闭合。
  • '：单引号闭合。闭合新构造的字符串，使整段注入的 JS 代码在语法上保持平衡，避免破坏其后代码的执行。

提交后，后端拼接出的最终代码为：var player = 'tmac'-alert(1)-'';。浏览器解析该代码时，会先执行 alert(1)，成功弹窗。

4. 怎么迁移（跨领域联想）

  • 前端代码审计与安全开发：在进行前端开发时，如果需要将后端数据传递给 JavaScript，绝不能直接拼接字符串。必须使用 JSON.stringify() 对数据进行序列化处理，或者使用 data-* 属性传递，再由 JS 读取，从而从根本上避免上下文注入。
  • WAF（Web应用防火墙）绕过：在真实渗透中，如果 WAF 拦截了 <script> 和 onerror 等 HTML 关键字，攻击者会尝试识别是否存在 JS 上下文注入点，利用 JS 语法本身的特性（如使用 Unicode 编码、拼接函数、反引号模板字符串等）来绕过 WAF 的规则。
  • 客户端 JSONP 劫持与 XSSI：JSONP（JSON with Padding）接口如果未做好安全防御，攻击者可以通过构造恶意页面，利用 JS 上下文注入读取用户的敏感 JSON 数据。

三、名词大全与原理深度复盘

1. 输出上下文 (Output Context)

指用户输入最终在 HTML 页面中所处的环境。常见的上下文包括：HTML 标签间、HTML 属性内、URL 参数中、JavaScript 代码内、CSS 代码内。不同的上下文需要不同的转义策略（如 HTML 实体编码、JS 十六进制转义、URL 编码等）。很多 XSS 漏洞的根源在于开发者使用了错误的转义策略，或者根本没有转义。

2. JavaScript 表达式与运算符优先级

在 JavaScript 中，alert(1) 是一个函数调用表达式。当它参与算术运算（如 -）时，由于运算符优先级的存在，JS 引擎会优先执行函数调用，将返回值（undefined）参与减法运算（导致结果为 NaN）。我们正是利用了这一语言特性，在不依赖分号的情况下，触发了函数执行。

3. 为什么 JS 上下文不能直接注入 HTML 标签？

HTML 解析和 JavaScript 解析是浏览器中两个独立的阶段。当 HTML 解析器遇到 <script> 标签时，它会将标签内的内容全部交给 JavaScript 引擎去解析。此时，HTML 引擎处于等待状态。在 JavaScript 引擎看来，<script> 只不过是一串由普通字符组成的字符串，并不具备执行 HTML 的能力。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS之htmlspecialchars 相比：上一题是在 HTML 标签属性中，可以使用伪协议或闭合标签属性；本题是在 JavaScript 代码中，无法使用 javascript: 伪协议，需要绕过的是 JS 字符串的边界。
  • 与 XSS之href输出 相比：两者都属于特定上下文的注入，但 href 处于 HTML 属性内，需要用户点击才能触发；而 js 输出处于脚本执行环境中，只要页面加载解析到该段脚本，就会自动执行，无需用户交互。

2. 这种题目的出现原因（为什么存在）

这种题目的出现，是因为开发者在混合编写 PHP/HTML/JavaScript 时，缺乏对上下文的感知。为了图方便，开发者经常直接使用 var a = '<?php echo $_GET['x']; ?>'; 这样的代码。这使得用户输入直接进入了 JS 代码的语法层，即使做了 HTML 实体编码，也无法阻止单引号逃逸和 JS 语法注入。

3. 这种应用在实际中如何体现？

在真实的渗透测试和漏洞挖掘中，如果发现页面参数被传递到了 JavaScript 的变量中（如通过查看网页源码，搜索“var config =”、“var user =”等关键字），测试人员会立刻尝试闭合单引号、双引号或反引号，注入 alert(1)、console.log(1) 等 Payload 来验证。这是前端 JS 注入最直接的测试手法。

4. 如何抽象理解概念（大白话理解）

如果把浏览器解析页面比作翻译文件：

  • HTML 上下文（如标签间）：属于“HTML 语种”区域。你只需要用 HTML 语法说“把这句话加粗”（<b>），浏览器就会照做。
  • JavaScript 上下文（本题）：属于“JavaScript 语种”区域。你如果在这里说 HTML 语（<script>），JS 翻译官听不懂，只会把它当成一段普通的文字记录下来。
  • 闭合注入：要想在这个区域搞破坏，你必须用 JS 语种的语法来说话。你输入的单引号 ' 就好比告诉 JS 翻译官：“刚才那句话到此为止，现在听我的新指令”，然后用 -alert(1)- 写下一句 JS 命令。
