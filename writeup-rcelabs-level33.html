一、题目信息

  • 1.题目名称：RCE-Labs Level 33 (多命令执行逻辑 ||)
  • 2.题目平台：RCE-Labs 靶场 (灵境平台部署)
  • 3.题目类型：Web安全 / 远程代码执行 (RCE) / 命令拼接 / 源码审计
  • 4.靶场链接：http://靶机IP:8080/less-33/
  • 5.涉及工具：浏览器

二、解题步骤

1. 分析题目考什么

源码中依然存在强制拼接 $cmd = "ls " . $cmd;。弹窗提示“使用逻辑或 || 分隔符，在第一个命令失败时执行第二个命令”。核心考点是利用 Shell 的逻辑或符号截断系统预置命令，并在前一条失败时执行 Payload。

血泪踩坑记录：工具惯性、盲猜源码与 Nginx 400 的致命陷阱

错误尝试：受前几关“变态WAF”的思维惯性影响，我盲目推荐使用 Burp Suite 发送复杂的 Payload（如 printf 写马、$a$b 变量拼接），试图绕过不存在的防御。

失败响应：全部返回 400 Bad Request（Nginx 直接拒收）。

根本原因：

  • 没仔细看源码：这道题的正则规则只有 $pattern = '/;|&/';，它只拦截了分号和逻辑与！cat 和管道符 |、逻辑或 || 根本没有被拉黑。
  • Nginx 的拦截：Nginx 极其讨厌 URL 中的 $、()、%3B、%27 等符号，只要带了这些，Nginx 直接返回 400，请求根本到不了 PHP。

改进与成功：停止盲目猜测，直接看源码。既然只拦截 ; 和 &，我们直接在浏览器里用 || 即可。用最简单的 | cat /flag 或 /nonexistent || cat /flag 直接通关。**不要陷入“复杂绕过”的思维定势，回归最简单的源码审计。**

2. 怎么解（详细步骤与逐字翻译）

源码核心逻辑

$cmd = $_GET['cmd'] ?? '...';
$cmd = "ls " . $cmd;
$pattern = '/;|&/';
if(!preg_match($pattern,$cmd)){
    system($cmd);
}

最终成功 Payload 与逐字解析

方案一：利用 || 使 ls 失败后执行（符合题意）

?cmd=%2Fnonexistent%20%7C%7C%20cat%20%2Fflag

命令逐字解析：

  • %2Fnonexistent：/nonexistent。这是一个不存在的路径，用来使前一条命令失败。
  • %20：空格。
  • %7C%7C：逻辑或 ||。前一条命令失败才执行后一条。
  • cat %2Fflag：cat /flag。
  • 最终效果：拼接后执行 ls /nonexistent || cat /flag。因为 /nonexistent 不存在，ls 失败返回非0状态码，|| 检测到失败，于是执行后面的 cat /flag，成功回显。

方案二：直接用管道符（最简单）

?cmd=%7Ccat%20%2Fflag

逐字解析：%7C 是 |。拼接后变成 ls |cat /flag。ls 输出为空，管道将空输入传给 cat，cat 顺便读取了 /flag 并回显。

3. 怎么迁移（跨学科与跨领域联想）

  • 真实渗透中的源码审计：永远不要依赖直觉去猜防护规则。拿到目标系统，第一件事永远是看它的源码或报错信息。这能让你少走无数弯路。
  • Nginx 与 WAF 的边界：在真实的护网中，Nginx 返回 400 Bad Request 往往意味着请求格式非法（特殊字符太多），而 WAF 拦截通常会返回 403 或自定义的拦截页面。根据返回码判断“是谁在拦你”，是渗透测试的基本功。

三、名词大全与原理深度复盘

1. 命令分隔符家族深度对比（大白话版）

  • ;（分号）：顺序执行。不管前一条死活，后一条一定执行。
  • &&（逻辑与）：前一条成功，才执行后一条。
  • ||（逻辑或）：前一条失败，才执行后一条。
  • |（管道）：把前一条的输出，作为后一条的输入。

本题中，源码只拦截了 ; 和 &，所以 | 和 || 都是通关的钥匙。推荐使用 |，因为它不需要前一条命令成功或失败，直接传递数据。

2. 为什么 Nginx 会报 400 Bad Request？

Nginx 是严谨的 HTTP 服务器，遵循 RFC 标准。如果 URL 中包含了未编码的 $、(、)、%3B、%27 等“危险字符”，Nginx 会认为这是非法请求，直接切断连接，返回 400。这就是为什么越复杂的 Payload 越容易失败的原因。

3. WAF 与 防火墙 的区别

  • 防火墙（Firewall）：工作在网络层和传输层，主要负责控制 IP 和端口的进出。它会拦截非标准端口的 TCP 连接（如 9002），这就是反弹 Shell 容易失败的原因。
  • WAF（Web 应用防火墙）：工作在应用层，专门检查 HTTP 请求的内容。它维护一个黑名单字典，包含 cat、sed 等敏感词。它只看“请求长什么样”，不看“命令执行后会变成什么”。

4. 核心网络基础与护网认知（陌生人也能看懂版）

  • 外网（公网/互联网）：拥有全球唯一的门牌号（公网 IP，如 8.8.8.8），任何人任何车都能开到你家门口。
  • 内网（局域网）：门牌号是“小区内部编号”（如 192.168.1.19），只有小区内部的人才能互相找到。外面的人想找你，必须经过小区保安（路由器/NAT）允许并做地址转换。
  • 完全隔离的内网：小区不仅不让外面的人进，甚至把大门用砖头砌死了（物理隔离）。这种环境下，反弹 Shell 和重定向写入 100% 都会失效。
  • HTTP 是公网吗？这是一个经典的误解！HTTP 不是网络，它是语言（协议）。无论访问内网 OA 还是百度官网，用的都是 HTTP 语言。
  • 操作系统与网络的关系：电脑操作系统是管理网络硬件的“交通警察”。你监听 80 端口成功、9002 端口失败，根本原因就是操作系统或 Docker 的虚拟网卡策略，只放行了 80 端口的出站，拦截了 9002 端口。
  • 护网是在攻击内网吗？护网是一场“攻城战”：第一阶段是“外网打点”（攻打城门），寻找对外门户的漏洞；第二阶段是“内网渗透”（巷战与横向移动），以边界服务器为跳板在内网提权、抓密码；第三阶段是“拿下靶标”（直捣黄龙），控制核心数据库或域控。内网渗透是决定胜负的主战场。

四、题目思考

1. 这跟前面关卡的区别

Level 31 考的是 ;（分号），Level 32 考的是 &&（逻辑与），Level 33 考的是 ||（逻辑或）。四个连接符（还包括 |）的区别是这几关的核心。这也提醒我们：不要被前期的经验固化思维，每到一个新环境，一定要重新侦察。

2. 这种题目的出现原因（底层逻辑与历史原因）

在 Web 开发中，开发者常常在不经意间将用户输入与系统命令拼接（如 ls ）。如果过滤不严，攻击者就可以利用 Shell 的分隔符来截断原本的命令。这类题目正是模拟开发者修补漏洞时的“漏网之鱼”。

3. 这种漏洞在实际中的应用

在护网和红队行动中，遇到 WAF 是家常便饭。利用分隔符、通配符、变量替换等手段绕过关键字拦截，是渗透测试人员的基本功。但同时，要懂得分析 400、403、500 等状态码的差异，判断是 Nginx、WAF 还是后端代码在拦你。

4. 如何抽象理解概念（大白话）

把读取文件比作“考试传递答案”。监考老师（开发者）强行在你面前放了一块“请保持安静”的牌子（ls ）。你不能用分号（;）或者逻辑与（&&），因为它们被拦截了。于是你用了一个“逻辑或”（||），你先故意说一句废话（/nonexistent），监考老师皱眉头（前一条失败了），于是你赶紧说“我要交卷”，他（Shell）听到了你的真实意图，帮你把卷子（flag）收上去了。

5. 他的本质

本质是利用 Shell 的命令分隔符，截断应用层强制拼接的上下文，将原本的“参数”提升为“独立的命令”，从而执行恶意 Payload。

6. 如果我是出题人或者攻击者我会怎么防守或者破解

  • 防守方（蓝队）：不要使用字符串拼接来构造系统命令！应使用编程语言提供的安全 API（如 PHP 的 escapeshellarg），或者直接使用白名单限制用户输入。同时，WAF 应拦截 ;、|、&、||、&& 等所有命令分隔符。
  • 破解方（红队）：如果所有分隔符都被拦截，尝试使用换行符 %0A。如果写文件也被拦截，考虑利用语言特性（如 PHP 的 include 包含文件，或利用已上传的木马）来实现读取。
