RCE-Labs Level 37 - 绕过空格 $IFS

2026年10月5日 RCE-Labs 空格绕过 变量替换

一、题目信息

  • 1.题目名称：RCE-Labs Level 37 (绕过空格 $IFS)
  • 2.题目平台：RCE-Labs 靶场 (灵境平台部署)
  • 3.题目类型：Web安全 / 远程代码执行 (RCE) / 空格绕过 / 变量替换
  • 4.靶场链接：http://靶机IP:8080/less-37/
  • 5.涉及工具：浏览器

二、解题步骤

1. 分析题目考什么

源码中正则变为 $pattern = '/\x20|\x09/';。此时 WAF 同时拦截了 ASCII 空格（\x20）和 Tab 键（\x09）。弹窗提示“尝试用环境变量 $IFS 代替空格”。核心考点是利用 Shell 的变量替换机制，绕过对特定空白字符的黑名单过滤。

踩坑记录：Tab 被拦截，Nginx 400 陷阱

尝试 Payload：延续上一关的思路，尝试 ?cmd=cat%09/flag 或直接拼 URL。

失败响应：页面空白（WAF 拦截了 `%09`），或者浏览器返回 400 Bad Request（Nginx 拦截了 `%09`）。

根本原因：WAF 的正则增加了 `\x09`（Tab），旧方法失效；Nginx 有时也会对 `%09` 等控制字符报 400。

改进与成功：使用 ${IFS} 变量替换。由于它是由普通字母组成的变量名，WAF 的正则无法匹配空格或 Tab，直接放行。

2. 怎么解（详细步骤与逐字翻译）

源码核心逻辑

$cmd = $_GET['cmd'] ?? '...';
$pattern = '/\x20|\x09/';
if(!preg_match($pattern,$cmd)){
    system($cmd);
}

最终成功 Payload 与逐字解析

?cmd=cat%24%7BIFS%7D%2Fflag

成功响应：页面直接回显明文 flag{TEST_Dynamic_FLAG}。

命令逐字解析：

  • cat：读取文件的命令。
  • %24：$ 符号。
  • %7B：{ 左花括号。
  • IFS：Shell 内部的环境变量（Internal Field Separator），默认包含空格、Tab、换行符。
  • %7D：} 右花括号。用花括号界定变量边界，防止后面紧跟的 / 被误解析为变量名的一部分。
  • %2Fflag：/flag。
  • 最终效果：Shell 在执行前，将 ${IFS} 替换为空格，命令变成 cat /flag，成功读取并回显。

3. 怎么迁移（跨学科与跨领域联想）

  • 真实渗透中的空格绕过：在护网中，WAF 常常拦截空格。红队经常使用 ${IFS}、%09、<、{} 等替代方案，让命令继续执行。理解 Shell 变量替换的优先级，是绕过这类防御的关键。
  • 系统运维中的变量替换：写 Shell 脚本时，${IFS} 常用于需要处理包含空格的文件名时，起到安全分隔的作用，防止参数被错误拆分。

三、名词大全与原理深度复盘

1. IFS 环境变量深度解析

IFS（Internal Field Separator）是 Shell 的内置环境变量。它的作用是定义 Shell 在解析命令时，用哪些字符来分隔单词。默认值通常为： \t\n（空格、Tab、换行符）。

  • 替换时机：Shell 在词法分析阶段，会先进行变量替换，再根据 IFS 进行分词。因此 ${IFS} 会先被替换成空格，然后空格再起作用。
  • 为什么用 ${IFS} 而不是 $IFS？因为 $IFS/flag 会被 Shell 解析为变量名 IFS/flag（变量名中不能有斜杠，但解析器可能会先尝试吃掉斜杠），导致替换失败。加花括号 {} 明确界定了变量名的范围，是最安全的写法。

2. 空格替代方案大全

  • %09：Tab 键。WAF 会拦截 \x09。
  • ${IFS}：Shell 内置变量。WAF 无法拦截变量名。
  • <：重定向符。如 cat，不需要空格分隔。
  • {}：大括号扩展。如 {cat,/flag}，Shell 会展开为 cat /flag。

3. WAF 与 防火墙 的区别

  • 防火墙（Firewall）：工作在网络层和传输层，主要负责控制 IP 和端口的进出。它会拦截非标准端口的 TCP 连接（如 9002），这就是反弹 Shell 容易失败的原因。
  • WAF（Web 应用防火墙）：工作在应用层，专门检查 HTTP 请求的内容。它维护一个黑名单字典，包含 cat、sed、空格等敏感词。它只看“请求长什么样”，不看“命令执行后会变成什么”。

4. 核心网络基础与护网认知（陌生人也能看懂版）

  • 外网（公网/互联网）：拥有全球唯一的门牌号（公网 IP，如 8.8.8.8），任何人任何车都能开到你家门口。
  • 内网（局域网）：门牌号是“小区内部编号”（如 192.168.1.19），只有小区内部的人才能互相找到。外面的人想找你，必须经过小区保安（路由器/NAT）允许并做地址转换。
  • 完全隔离的内网：小区不仅不让外面的人进，甚至把大门用砖头砌死了（物理隔离）。这种环境下，反弹 Shell 和重定向写入 100% 都会失效。
  • HTTP 是公网吗？这是一个经典的误解！HTTP 不是网络，它是语言（协议）。无论访问内网 OA 还是百度官网，用的都是 HTTP 语言。
  • 操作系统与网络的关系：电脑操作系统是管理网络硬件的“交通警察”。你监听 80 端口成功、9002 端口失败，根本原因就是操作系统或 Docker 的虚拟网卡策略，只放行了 80 端口的出站，拦截了 9002 端口。
  • 护网是在攻击内网吗？护网是一场“攻城战”：第一阶段是“外网打点”（攻打城门），寻找对外门户的漏洞；第二阶段是“内网渗透”（巷战与横向移动），以边界服务器为跳板在内网提权、抓密码；第三阶段是“拿下靶标”（直捣黄龙），控制核心数据库或域控。内网渗透是决定胜负的主战场。

四、题目思考

1. 这跟前面关卡的区别

Level 36 利用 Tab 绕过空格，Level 37 利用 ${IFS} 变量替换绕过空格。这提醒我们：不要被前期的经验固化思维，每到一个新环境，一定要重新侦察源码。同时，Shell 的变量替换机制是绕过 WAF 的天然利器。

2. 这种题目的出现原因（底层逻辑与历史原因）

在 Web 开发中，开发者常常将用户输入与系统命令拼接。为了防御，WAF 会尝试拦截空格。但 Shell 对空白字符的宽容度极高，且有 IFS 等内置变量，使得这种防御形同虚设。

3. 这种漏洞在实际中的应用

在护网和红队行动中，遇到 WAF 拦截空格是家常便饭。利用 ${IFS}、%09、< 等手段绕过空格拦截，是渗透测试人员的基本功。同时，防守方也据此推出了“语义分析”型的高级 WAF，不仅看关键字，还会还原命令执行后的真实意图。

4. 如何抽象理解概念（大白话）

把读取文件比作“考试传递答案”。监考老师（开发者）说：“不准用逗号”。于是你把逗号换成了句号或者感叹号。老师（WAF）没看懂，但读者（Shell）完全理解你的意思。

5. 他的本质

本质是利用 Shell 词法解析器对变量替换的支持，将恶意命令的构建过程从“文本层面”推迟到“运行时层面”，从而绕过应用层防火墙对特定字符（空格）的黑名单匹配。

6. 如果我是出题人或者攻击者我会怎么防守或者破解

  • 防守方（蓝队）：不要使用字符串拼接来构造系统命令！应使用编程语言提供的安全 API（如 PHP 的 escapeshellarg），或者直接使用白名单限制用户输入。同时，WAF 应拦截 Tab、换行符、$IFS、{} 等所有可能替代空格的字符。
  • 破解方（红队）：如果 ${IFS} 被拦截，尝试使用 $IFS（Level 38）、{}（Level 39）或者直接使用重定向符 <（如 cat）。
