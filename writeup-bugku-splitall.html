split_all - Bugku MISC Writeup

2026年9月13日 Bugku CTF MISC 文件头欺骗 图像拆分与重组 Mac 终端 Python 实战

这道题名为“split_all”，分类为 MISC。附件是一个名为 file.png 的图片。双击打开时，Mac 系统直接报错“文件已损坏”。这是一道极其经典的“文件头伪装 + GIF 拆帧重组”题，也是我在 Mac 终端上用 Python 连续踩坑四次才通关的实战记录。这篇 Writeup 会把每一行代码、每一次报错、每一次修改、以及背后的底层逻辑，全部毫无保留地记录下来。

二、解题过程（详细步骤与四轮代码踩坑记录）

1. 现象：文件损坏，打不开

我把 file.png 下载到 Mac 桌面，双击用“预览”打开，弹窗报错：“未能打开文件‘file.png’。它可能已损坏，或者可能使用了‘预览’无法识别的文件格式。”

逻辑分析：Mac 的“预览”软件不仅看后缀名，还会校验文件内部的二进制结构。如果扩展名是 PNG，内部数据不是真正的 PNG，它就会报错。这说明文件被伪装了。

2. 终端侦察：查真实身份

在终端输入以下两条命令进行侦察：

cd ~/Desktop
xxd "file.png" | head -20
strings "file.png" | grep -i "gif"

命令解释：

  • xxd：将文件转换成十六进制（0-9，A-F）查看。我们看到了文件开头是 89 50 4E 47，这是 PNG 的“魔术数字”。
  • strings：提取文件中的可打印字符。grep -i "gif" 用于过滤包含“gif”的行。我们发现里面藏着 GIF89a 的特征。

结论：这是一张伪装成 PNG 的 GIF 文件。出题人把真正的 GIF 头（47 49 46 38 39 61）藏在文件中间了。我们需要把它切出来。

3. 踩坑第一轮：文件名错误

第一次写代码（错误）：

with open('flag1.png', 'rb') as f:
    data = f.read()
start = data.find(b'\x47\x49\x46\x38\x39\x61')
if start != -1:
    with open('real.gif', 'wb') as f:
        f.write(data[start:])
print("提取成功！")

终端报错： FileNotFoundError: [Errno 2] No such file or directory: 'flag1.png'

原因与修改： 我习惯性写了上一题的文件名 flag1.png，实际文件叫 file.png。把第一行的文件名改成 'file.png'。

4. 踩坑第二轮：缺失完整文件头

第二次写代码（错误）： 修正文件名后运行，终端提示“未找到 GIF 文件头”。

原因与修改： 出题人把 GIF 完整头 47 49 46 38 39 61 截断了，只留下了 38 39 61（即 89a）。我们需要搜索残缺特征，并在前面强行补全“GIF”。

第三次写代码（补全版）：

with open('file.png', 'rb') as f:
    data = f.read()

pos = data.find(b'\x38\x39\x61')
if pos != -1:
    gif_data = b'\x47\x49\x46' + data[pos:]
    with open('real.gif', 'wb') as f:
        f.write(gif_data)
print("补全并提取成功！")

结果： 桌面生成了 real.gif。打开一看，它是一根极其细长的黄色竖线！这完美呼应了题目名“split_all”，出题人把一张大图切成了几百份竖条，藏在 GIF 的每一帧里。

5. 踩坑第三轮：脚本没创建，终端找不到文件

我直接运行 python3 split_gif.py，终端报错 No such file or directory。

原因与修改： 我们只是构思了脚本，还没在电脑上创建它！我用终端自带的 cat 命令在终端内直接创建文件：

cat > split_gif.py << 'EOF'
from PIL import Image, ImageSequence

img = Image.open('real.gif')
frames = [frame.convert('RGB') for frame in ImageSequence.Iterator(img)]

for i, frame in enumerate(frames):
    frame.save(f"frame_{i:03d}.png")
print(f"提取成功！共保存了 {len(frames)} 张竖条图片。")
EOF

代码解释：

  • cat > split_gif.py << 'EOF'：这是 Shell 的重定向命令。意思是“把下面输入的内容全部写入到 split_gif.py 这个文件里，直到遇到单词 EOF 为止”。
  • from PIL import Image, ImageSequence：引入 Python 最强大的图像处理库 Pillow。
  • Image.open('real.gif')：打开我们刚提取的 GIF 文件。
  • ImageSequence.Iterator(img)：GIF 动图是由多帧组成的。这个函数是一个“迭代器”，它会像翻书一样，把每一帧按顺序拿出来。
  • frame.convert('RGB')：把每一帧转换为 RGB 颜色模式。
  • for i, frame in enumerate(frames)：循环遍历每一帧。`i` 是索引（0, 1, 2...）。
  • frame.save(...)：把每帧保存成 `frame_001.png` 这样带编号的文件，保证拼图时能按顺序排好。

运行后，桌面瞬间出现几百张竖条 png。

6. 踩坑第四轮：拼接脚本同样未创建

运行 python3 merge_images.py 依然报错找不到文件。同样用 cat 创建拼接脚本：

cat > merge_images.py << 'EOF'
from PIL import Image
import os

files = sorted([f for f in os.listdir('.') if f.startswith('frame_') and f.endswith('.png')])
images = [Image.open(f) for f in files]

total_width = sum(img.width for img in images)
max_height = max(img.height for img in images)

merged_img = Image.new('RGB', (total_width, max_height))

x_offset = 0
for img in images:
    merged_img.paste(img, (x_offset, 0))
    x_offset += img.width

merged_img.save("final_result.png")
print("拼接成功！已保存为 final_result.png")
EOF

代码解释：

  • os.listdir('.')：列出当前目录（桌面）下的所有文件。
  • startswith('frame_')：只过滤出以 frame_ 开头的文件，避开其他无关图片。
  • sorted()：按文件名排序，保证 `frame_001`、`frame_002` 的顺序是正确的。
  • Image.new('RGB', (total_width, max_height))：创建一张全新的、巨大的空白画布。宽度是所有小图宽度之和，高度取小图的最大高度。
  • merged_img.paste(img, (x_offset, 0))：把小图依次贴到画布上。`x_offset` 是横向偏移量。
  • x_offset += img.width：每贴完一张，横向偏移量加上这张图的宽度，这样下一张图就会紧挨着它右边。

7. 成功获取 Flag

在终端输入：

python3 merge_images.py
open final_result.png

Mac 自动弹出了拼接完整的图片，Flag 清晰地显示在上面！

最终 Flag： flag{9f019c27eca746beb9c297cd70bf93ca}

三、深度名词解释与底层逻辑复盘

1. 什么是“文件头伪装”？

计算机通过文件的“魔术数字”来识别真实类型。比如 PNG 是 89 50 4E 47，GIF 是 47 49 46。出题人故意把扩展名写成 .png，文件头也改成 PNG，但实际数据是 GIF。这就是经典的“文件头欺骗”。

2. 什么是“魔术数字”（Magic Number）？

文件开头的一串固定字节，用来标识文件的真实类型。它是二进制分析中最核心的破案线索。

3. 什么是 Pillow 库？

Python 中最强大的图像处理库（PIL）。它可以读取、拆分、裁剪、拼接图像。我们用它完成了 GIF 拆帧和图片拼接。

4. 什么是 GIF 帧？

GIF 动图是由多张静态图片（帧）快速切换形成的。出题人把一张大图切成了数百份竖条，存放在 GIF 的每一帧里。

5. 什么是终端里的“cat > 文件”和“EOF”？

cat 是连接文件的工具。> 是重定向符号，表示“把左边的输出写到右边的文件里”。<< 'EOF' 是一种特殊的输入方式，表示“我接下来输入的内容，全部当做文件内容，直到我输入一个叫 EOF 的词结束”。

四、这道题到底在考察什么？我在终端干什么？

1. 考察点：这道题综合考察了 MISC 的四大能力：

  • 文件结构分析能力：识别出伪装的 PNG 文件。
  • 二进制操作能力：用 xxd 和 strings 探查文件底层。
  • Python 自动化能力：用代码搞定数百张图片的拆分和拼接，而不是傻傻用手拼图。
  • 环境生存能力：在 Mac 上没有 Windows 工具（如 010 Editor、随波逐流）时，如何用系统自带的终端 + Python 解决问题。

2. 我在终端到底在干什么？

终端不仅仅是一个黑框框，它是你直接控制电脑的“驾驶舱”。你敲下的每一行命令，都是在向操作系统下达精确的指令：

  • cd ~/Desktop：告诉系统“请把我的工作目录切换到桌面”。
  • xxd "file.png"：告诉系统“请把这个文件当成二进制数据流，帮我翻译成十六进制给我看”。
  • python3 extract_gif.py：告诉系统“请启动 Python 解释器，然后逐行执行我写好的那些代码”。
  • open final_result.png：告诉系统“请调用默认的图片查看器，把这个图片弹出来给我看”。

五、代码修改全记录与底层逻辑（为什么改了几次）

回顾这道题，代码经历了四次实质性的修改。这不是因为笨，而是因为真实的 CTF 就是不断遇到报错、定位问题、修改逻辑的过程：

  1. 第一次修改（文件名错误）： 把 flag1.png 改成 file.png。因为文件名写错了，Python 找不到要操作的目标。
  2. 第二次修改（文件头残缺）： 搜索完整 GIF 头失败，改为搜索残缺的 38 39 61 并强制补全 47 49 46。因为出题人故意把文件头切碎了，必须要在代码逻辑里“缝”上。
  3. 第三次修改（脚本缺失）： 用 cat > 命令在终端创建脚本。因为我们虽然想好了代码，但还没有创建那个具体的 .py 文件。
  4. 第四次修改（拼接脚本缺失）： 再次用 cat > 创建拼接脚本。因为拼接是另一个独立的功能，必须写另一个脚本来完成。

背后的逻辑： 编程不是一次写对，而是“发现现象 -> 判断原因 -> 修改代码 -> 验证结果”的循环。你的每一次修改，都在让代码更贴近真实的物理世界（即文件结构）。
