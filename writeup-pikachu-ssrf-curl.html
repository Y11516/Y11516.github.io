SSRF(curl) - Pikachu Writeup

2026年9月20日 Pikachu Web安全 SSRF

一、题目信息

  • 题目名称：SSRF(curl)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 服务端请求伪造（SSRF） / 内网探测与文件读取
  • 靶场链接：http://localhost:8080/vul/ssrf/ssrf_curl.php
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是服务端请求伪造（SSRF）。后端提供了一个“读诗”的功能，但具体读哪首诗是由用户传入的 URL 参数决定的。如果后端没有对 URL 进行严格的协议白名单校验和 IP 限制，攻击者就可以利用该接口，让服务器去请求内网服务（如 127.0.0.1）或读取本地文件（如 file:///etc/passwd），从而窃取敏感信息或探测内网架构。

2. 怎么想（破题思路）

页面只有一行字“累了吧,来读一首诗吧”。解题思路如下：

  • 点击“读诗”链接，发现浏览器直接报 404 Not Found（地址栏显示多了一个 /vul/）。
  • 判断为前端代码存在硬编码 Bug，无法正常触发请求。
  • 绕过前端，直接手动构造请求。根据后端接口命名规律，猜测参数名为 url。
  • 构造 ?url=http://127.0.0.1/vul/ssrf/ssrf_info/info1.php，让服务器请求自身的内网服务。
  • 进一步利用 file:// 协议读取系统敏感文件。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：点击前端“读诗”按钮触发 404 Not Found

踩坑情况：点击页面上的“累了吧,来读一首诗吧”链接，浏览器直接跳转到一个 404 页面，地址栏显示 http://localhost:8080/vul/vul/ssrf/ssrf_info/info1.php。

原因分析：前端 HTML 代码在拼接跳转链接时，路径写错了，多写了一个 /vul/ 前缀，导致请求到了不存在的路径。

改进方式：放弃点击该按钮，直接在浏览器地址栏手动构造正确的 URL。SSRF 的核心是“让服务器去请求 URL”，因此只要我们能控制参数，前端报错不影响我们发送 Payload。

踩坑记录二：直接在浏览器访问内部文件路径

踩坑情况：在地址栏直接输入 http://localhost:8080/vul/ssrf/ssrf_info/info1.php，试图直接访问内网服务。

原因分析：直接访问是客户端（浏览器）发起请求，而不是服务端（Pikachu 服务器）发起。我们需要让服务器作为“代理”去请求，才能证明 SSRF 漏洞存在。

改进方式：必须将内部地址作为参数，传给 SSRF 漏洞接口：ssrf_curl.php?url=http://127.0.0.1/vul/ssrf/ssrf_info/info1.php。

终极解法：利用 SSRF 读取系统文件

在浏览器地址栏输入以下 URL：

http://localhost:8080/vul/ssrf/ssrf_curl.php?url=file:///etc/passwd

代码逐个符号深度解析：

  • ssrf_curl.php?：触发 SSRF 漏洞的后端接口。
  • url=：后端用于接收请求地址的参数名。
  • file:///：核心突破点。这是一个本地文件传输协议，告诉服务器不要去请求 HTTP 网页，而是直接读取本机文件。三个斜杠表示文件系统的根目录。
  • etc/passwd：目标文件的路径，用于读取 Linux 系统的用户列表。

由于后端使用了 curl 发起请求，且未禁用 file 协议，服务器成功读取了本机的 passwd 文件并回显在页面上，证明 SSRF 漏洞利用成功。

4. 怎么迁移（跨领域联想）

  • 内网服务探测（Intranet Scanning）：攻击者可以利用 SSRF 扫描内网主机的端口（如 http://192.168.1.1:6379），探测内网未授权的 Redis、MySQL 等服务，进而实施横向攻击。
  • 云环境元数据读取（Cloud Metadata）：在 AWS、阿里云等云服务器上，通常存在一个元数据接口（如 http://169.254.169.254/latest/meta-data/）。一旦 SSRF 可以利用该接口，攻击者就能窃取服务器的临时凭证，从而接管云资源。
  • Gopher 协议利用：除了 file 和 http，SSRF 还可以利用 gopher:// 协议构造任意 TCP 数据流，直接攻击内网的 Redis、MySQL 等服务，实现从 SSRF 到 RCE 的跨越。

三、名词大全与原理深度复盘

1. 服务端请求伪造（SSRF）

一种 Web 安全漏洞，攻击者通过构造恶意参数，让 Web 应用服务器去发起网络请求。由于服务器通常具有访问内网的权限，SSRF 常常被用来突破防火墙，探测和攻击内网系统。

2. SSRF 与 CSRF 的区别

SSRF 是“服务器”发起请求，攻击目标是内网；CSRF 是“用户的浏览器”发起请求，攻击目标是 Web 应用本身。SSRF 的请求来源是服务器，因此不受同源策略限制，能访问内网。

3. curl 与 file 协议

curl 是一个利用 URL 语法在命令行下工作的文件传输工具，支持多种协议（HTTP、HTTPS、FTP、FILE 等）。如果后端使用 curl 且未指定 --proto 限制协议，攻击者就可以利用 file:// 读取本地文件，或利用 dict:// 探测端口。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 URL 重定向相比：URL 重定向是服务器让“浏览器”跳转；SSRF 是服务器“自己”去请求。前者是客户端行为，后者是服务端行为。
  • 与文件包含相比：文件包含是将文件包含进 PHP 代码并执行；SSRF 是发起网络请求或读取文件内容并回显，不涉及代码执行。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在实现 Webhook、图片下载、在线翻译、文章抓取等功能时，为了灵活，直接让用户传入 URL，而没有对目标地址进行严格的白名单校验或内网 IP 过滤。同时，后端使用的 curl 组件默认支持多种危险协议，进一步放大了危害。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，SSRF 是内网渗透的重要突破口。攻击者可以通过 SSRF 探测内网存活主机、服务版本，甚至利用 Gopher 协议打穿内网的 Redis 数据库，直接获取服务器权限。在企业安全中，SSRF 通常被列为高危漏洞。

4. 如何抽象理解概念（大白话理解）

如果把 Web 服务器比作一个公司前台：

  • 正常功能：你告诉前台“帮我取一下百度官网的资料”。前台（服务器）去外网取了资料给你。
  • SSRF 漏洞：你告诉前台“帮我取一下财务室保险柜里的密码本”（file:///etc/passwd 或 http://127.0.0.1/...）。前台没有核实这个地址是否属于公司内部机密，真的跑去财务室把密码本拿给你看。这就是 SSRF 的可怕之处——利用服务器的信任，窃取内网的机密。
