SQLi-Labs Less-19

2026年9月28日 SQLi-Labs Web安全 SQL注入 Header注入

一、题目信息

  • 题目名称：SQLi-Labs Less-19 (POST - Header Injection - Referer field - Error based)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / HTTP头部注入 / Referer注入
  • 靶场链接：http://localhost:8081/Less-19/（本地环境）
  • 涉及工具：Python (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是HTTP 头部中的 Referer 字段注入。与 Less-18 的 User-Agent 注入原理完全一致，后端在登录成功后，会将 Referer 字段插入数据库，形成 INSERT 语句注入。由于只有登录成功才会触发 INSERT，因此必须先获取正确的账号密码。

2. 怎么想（破题思路）

  • 在浏览器使用 admin/admin 尝试登录，确认登录成功并回显了 Referer 信息。
  • 使用 Python 脚本发送 POST 请求，在 HTTP Header 的 Referer 中构造 Payload。
  • 尝试报错注入（updatexml）和时间盲注（sleep）。
  • 受限于本地环境（MySQL 8 移除 updatexml，且 sleep 被禁用），漏洞无法成功利用。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：本地环境彻底阉割了漏洞利用条件

踩坑情况：使用 Python 脚本发送注入 Payload 后，无论怎么修改闭合符（%23、-- -），服务器响应始终在 0.01 秒左右，无报错回显。

原因分析： 1. 本地环境为 MySQL 8.0+，官方已彻底移除 updatexml 和 extractvalue 函数，导致报错注入无法回显数据。 2. 本地 PHP 配置禁用了 sleep() 函数或限制了最大执行时间，导致时间盲注无法触发延迟。 3. 部分环境会对 Referer 头部进行 WAF 过滤，导致 Payload 无法拼接进 SQL 语句。

改进方式：在真实环境中，如果遇到这种环境限制，建议直接跳过该关。如果是为了学习原理，可以尝试使用 Docker 搭建一个包含 MySQL 5.x 的旧版环境。

源码逻辑逐行解析

后端核心逻辑如下（基于通用标准版）：

1.  $referer = $_SERVER['HTTP_REFERER']; // 获取 Referer 头
2.  $sql = "INSERT INTO referers (referer) VALUES ('$referer')"; // 拼接 SQL
3.  mysqli_query($conn, $sql); // 执行
4.  echo "Your Referer is: " . $referer; // 回显

漏洞点详解：

  • 第1行：后端没有对 Referer 进行过滤，直接获取。
  • 第2行：将用户可控的 Referer 直接拼接到 INSERT 语句中。
  • 攻击逻辑：构造 Referer: ' or updatexml(...)-- ，使得 INSERT 语句在语法解析时触发报错。

4. 怎么迁移（跨领域联想）

  • HTTP 头部注入：不仅是 Referer，User-Agent、X-Forwarded-For 等头部若被拼接进 SQL 语句，同样会引发注入。这是代码审计中容易被忽略的盲区。
  • 环境差异与漏洞可利用性：同一个漏洞在不同版本的语言和数据库环境下，可利用性天差地别。MySQL 8 移除报错函数，PHP 8 禁用危险函数，都是现代安全对抗的体现。
  • 实战策略：面对环境限制，灵活判断并跳过，不在无法复现的漏洞上浪费时间，是渗透测试工程师的基本素养。

三、名词大全与原理深度复盘

1. Referer 头部

HTTP 请求头的一部分，用于告诉服务器请求是从哪个页面链接过来的。它常常被用于统计、防盗链，也常被后端记录到数据库。

2. INSERT 注入

当后端执行 INSERT 语句将用户输入插入数据库时，如果未过滤，攻击者可以通过闭合单引号来构造恶意 SQL，触发报错或盲注。

3. 函数移除与版本更新

MySQL 8 移除了 updatexml 和 extractvalue，体现了官方对安全漏洞的修复，同时也倒逼渗透测试人员使用更隐蔽的盲注或联合注入手法。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-18 的区别：Less-18 注入的是 User-Agent，Less-19 注入的是 Referer。两者注入原理完全相同，只是 HTTP 头部字段不同。
  • 与 Less-11~17 的区别：Less-11~17 的注入点在表单输入框，Less-18/19 转移到了 HTTP 头部。

2. 这种题目的出现原因（为什么存在）

后端开发者认为 HTTP 头部是“用户代理”或“来源页”，属于系统级别的信息，不会想到攻击者能随意篡改它们。但实际上 HTTP 头部完全由客户端控制，这种盲目的信任导致了漏洞。

3. 这种应用在实际中如何体现？

在实战中，如果发现一个接口使用了 User-Agent 或 Referer 进行日志记录，且后端没有过滤，就极有可能存在头部注入。但现代 WAF 通常会对头部进行严格的格式校验，利用难度增加。

4. 如何抽象理解概念（大白话）

把靶场比作一个“笔记簿”：

  • Less-19 的笔记簿上有一栏叫“来源”（Referer）。
  • 你把“来源”一栏填上：“来自百度，并且把笔记簿炸了”。
  • 管理员照着抄（拼接 SQL），结果笔记簿真的炸了（报错注入）。
  • 但如果管理员带了“防爆盾”（MySQL 8 + WAF），你就炸不成了。

做一道题，就要往自己脑子里装点东西。
