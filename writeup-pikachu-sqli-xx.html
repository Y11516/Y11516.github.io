一、题目信息

  • 题目名称：SQL-Inject xx型注入
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 括号包裹型 / GET方式
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_x.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是被括号和引号同时包裹的 SQL 注入。与常规字符型注入不同，后端的 SQL 语句不仅用单引号包裹了变量，还在外层加了圆括号，形如 select * from users where username = ('$input')。攻击者必须同时闭合圆括号和单引号 ')，才能跳出限制并注入恶意 SQL 逻辑。

2. 怎么想（破题思路）

页面提供基本的用户名查询功能。解题思路如下：

  • 先输入 vince，确认页面正常回显。
  • 尝试单引号闭合，输入 vince'，报错。再尝试同时闭合括号与引号，输入 vince')，页面再次报错，确认闭合点。
  • 构造完整的绕过语句：') or 1=1 #，使查询条件恒为真，从而拖取全表数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：仅闭合单引号导致失败

踩坑情况：直接使用上一关字符型注入的 Payload ' or 1=1 #，发现无法成功获取全表数据。

原因分析：后端语句结构为 username = ('$input')。只闭合单引号，括号仍在包裹，无法打破原有的结构限制，导致注入逻辑失效。

改进方式：必须先闭合圆括号，再闭合单引号，即使用 ') 作为 Payload 开头。

踩坑记录二：语法报错恐慌症

踩坑情况：输入 vince') 时页面出现红色 SQL 报错，误以为搞坏了环境。

原因分析：报错 You have an error in your SQL syntax 恰恰是漏洞存在的证明。多出的符号（')）破坏了 SQL 语法，说明成功闭合了原有结构。

改进方式：保持冷静，将报错视为“注入测试的成功反馈”，然后基于闭合点构造完整的逻辑绕过语句。

终极解法：括号与引号双闭合注入

在输入框中提交以下 Payload：

') or 1=1 #

代码逐个符号深度解析：

  • '：单引号，闭合原 SQL 语句中的左单引号。
  • )：右圆括号，闭合原 SQL 语句中的左圆括号（如 username = ('...）。
  • or：SQL 逻辑运算符“或”。
  • 1=1：恒真条件。使得查询条件变为 username = ('') or 1=1，由于 1=1 恒为真，数据库忽略原有查询条件，返回所有用户数据。
  • #：MySQL 注释符。用来注释掉原代码末尾多余的 ')，保证 SQL 语句语法的完整性。

提交后，页面成功回显所有 7 条用户数据（vince、allen、kobe、grady、kevin、lucy、lili），证明 xx 型注入攻击成功。

4. 怎么迁移（跨领域联想）

  • 代码审计：审计 SQL 注入漏洞时，除了关注 select 和字符串拼接，还要留意开发者是否在变量外添加了括号等特殊符号。代码形态可能千变万化，但闭合与逻辑绕过的本质不变。
  • WAF 绕过实战：在真实环境中，目标可能把 ') or 1=1 # 也加入了黑名单。此时可以尝试使用 ') or '1'='1' #、大小写混淆 ') Or 1=1 #，或使用 union select 联合查询来绕过防御。
  • 高级注入（盲注）：当页面不直接回显数据时，无论闭合方式多复杂，都可以使用布尔盲注（') and 1=1 # 与 ') and 1=2 # 对比页面差异）或时间盲注（') and sleep(5) #）来提取信息。

三、名词大全与原理深度复盘

1. xx型注入与字符型注入的区别

字符型注入的 SQL 结构是 username = '$input'，只需闭合单引号；xx型注入的 SQL 结构是 username = ('$input')，必须同时闭合圆括号和单引号 ')。本质上是开发人员为了某种语法需求（如优先级控制、特定框架写法）添加了额外的包裹层，但这并不能防御 SQL 注入。

2. 为什么需要同时闭合括号和引号？

在 SQL 语法中，括号用于改变运算优先级和分组。攻击者输入的 Payload 必须满足 SQL 语法树的要求。如果只闭合单引号，SQL 引擎仍然处于括号嵌套的环境中，无法跳出逻辑限制；只有将括号也闭合，才能让 or 1=1 处于与整个条件平等的逻辑层级上，从而发挥效果。

3. 注释符在复杂闭合中的作用

当 Payload 成功地闭合了前面的括号和引号后，原代码末尾残余的闭合符号（如 ')）会再次引发语法错误。注释符 # 的作用就是“截断”代码，让 SQL 引擎在解析到此处时停止，从而忽略后方的残余符号，保持语句的完整和合法性。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与数字型注入相比：数字型不需要闭合任何符号，直接拼接逻辑；xx型则需要精准识别并闭合括号和引号的双重包裹。
  • 与字符型注入相比：字符型仅需处理单引号，xx型多了一层括号，Payload 多了一个符号，对闭合点的精准度要求更高。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发人员在编写 SQL 查询时，常常会为了满足业务逻辑（如分组、提高可读性、配合某些 ORM 框架）而在变量外层加入括号。但他们依然使用了字符串拼接的方式构造 SQL，导致用户输入的数据可以打破括号限制，引发注入漏洞。

3. 这种应用在实际中如何体现？

在实际的渗透测试中，SQL 注入的闭合方式千变万化。除了 ')，还可能遇到 ))、"、%' 等多种组合。掌握扎实的闭合与逻辑绕过原理，才能在面对复杂代码时快速构造出正确的 Payload，从而窃取数据库中的管理员密码或敏感信息。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个快递分拣员：

  • 正常查询：你拿着单号说“取 1 号包裹”（username = 'vince'）。
  • 字符型注入：你用单引号切断了原有单号，加上自己的指令：“取空单号，或者把整个仓库都给我”（' or 1=1 #）。
  • xx型注入：快递员这次把你的指令放在了一个“安全箱”里（括号 ('$input')）。你不仅需要切断单引号，还需要把安全箱也撕开（') or 1=1 #），才能把指令传递给分拣员。只要撕开层层伪装，就能拿到所有的包裹。
