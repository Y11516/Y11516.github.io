SQLi-Labs Less-36

2026年9月29日 SQLi-Labs Web安全 SQL注入 宽字节注入

一、题目信息

  • 题目名称：SQLi-Labs Less-36 (GET - Bypass MySQL_real_escape_string)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 宽字节注入 / 高级转义绕过
  • 靶场链接：http://localhost:8081/Less-36/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是宽字节注入绕过 mysql_real_escape_string() 函数。该函数是 PHP 中比 addslashes() 更强大的转义函数，它会根据数据库连接的字符集来转义危险字符。然而，如果数据库连接被设置为 GBK 编码，攻击者仍可利用 %df 和转义符 %5c 组合成汉字，从而“吃掉”转义符，完成注入。

2. 怎么想（破题思路）

  • 直接使用 ?id=1'，页面提示被转义，注入失败。
  • 观察 Hint：输入的字符串被转义，并在底层变成了十六进制。
  • 利用 GBK 编码特性：发送 ?id=1%df'，后端转义后变成 1%df%5c%27，在 GBK 下 %df%5c 被解析为汉字，单引号 %27 逃逸。
  • 拼接报错注入 Payload，直接获取数据库名。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：mysql_real_escape_string 的欺骗性

踩坑情况：认为 mysql_real_escape_string() 比 addslashes() 安全，因为官方文档说它会考虑字符集，因此可能无法绕过。

原因分析：如果 PHP 脚本没有显式调用 mysql_set_charset('gbk') 或 SET NAMES 'gbk'，PHP 不知道该使用 GBK 进行转义，它默认还是会使用 latin1 或 UTF-8 处理。但 SQL 查询传递到 MySQL 时，MySQL 会根据数据库配置的字符集（如 GBK）进行解析。这种“PHP 端转义”与“MySQL 端解析”的字符集不一致，导致了宽字节注入。

改进方式：需要在 PHP 端也强制声明使用正确的字符集（如 UTF-8），同时使用参数化查询。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-36/?id=1%df'%20and%20updatexml(1,concat(0x7e,(select%20database()),0x7e),1)--%20-

第二步：Payload 逐字解析

  • 1%df'：核心宽字节 Payload。%df 和转义后的 %5c 合成汉字，单引号逃逸。
  • %20：URL 编码的空格。
  • and updatexml(...)：报错注入，获取当前数据库名。
  • --%20-：注释符，阻止后续 SQL 执行。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。同时 Hint 底部的 Hex 显示 31df5c27，完美印证了宽字节。

4. 怎么迁移（跨领域联想）

  • 字符集与编码安全：宽字节注入的根源是“字符集不一致”。这警示我们，跨语言、跨组件的编码问题往往是安全漏洞的温床。在现代系统中，如果 PHP 和 MySQL 的连接字符集不匹配，依然会面临这类风险。
  • 转义函数的局限性：addslashes() 仅对特定字符加反斜杠。在 GBK 等多字节编码下，这种单字节转义机制会被“吃掉”，防御瞬间失效。这告诉我们，不要试图用黑名单来防御注入。
  • 安全开发启示：使用参数化查询（Prepared Statements）时，数据库和驱动会自动处理所有转义，彻底杜绝宽字节注入。

三、名词大全与原理深度复盘

1. 宽字节注入 (Broad Byte Injection)

利用数据库字符集（如 GBK）将两个单字节“拼”成一个多字节汉字的特性，让转义符 \（%5c）被吃掉，从而让后续的危险字符逃逸。

2. mysql_real_escape_string() 函数

PHP 中用于转义 SQL 语句中特殊字符的函数。它会根据当前连接的字符集来转义，比 addslashes() 安全，但如果连接字符集设置不当（如未设置 GBK），仍会被宽字节注入绕过。

3. 字符集不一致 (Character Set Mismatch)

指 PHP 端在转义时使用的字符集与 MySQL 端解析 SQL 时使用的字符集不同。这是宽字节注入的核心成因。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-32/33/34 的区别：Less-32 使用的是自定义过滤函数（如 check_addslashes()），Less-33 使用 addslashes()，Less-36 使用的是 mysql_real_escape_string()。三者的绕过方式完全相同，都是利用 GBK 宽字节，只是防御函数名不同。

2. 这种题目的出现原因（为什么存在）

开发者知道要用 addslashes() 防御 SQL 注入，但忽略了数据库字符集的特性。当 PHP 和 MySQL 连接使用了 GBK 编码时，单字节转义就会被多字节解析“吃掉”。这反映了“安全防御不能只看代码层，还要看底层配置”的问题。

3. 这种应用在实际中如何体现？

在实战中，宽字节注入常见于使用 GBK 编码的国产 CMS（如 DedeCMS、Discuz）中。防御方必须统一使用 UTF-8 编码，或者强制使用参数化查询。

4. 如何抽象理解概念（大白话）

把靶场比作一个“检查站”：

  • 安检员（mysql_real_escape_string）看到单引号（炸弹），会在前面加一个锁（反斜杠 \）。
  • 但你把炸弹写成了“%df'”。
  • 安检员加锁后变成“%df\ '”。
  • 但翻译官（GBK 解码）看到“%df\”，以为它们是一个汉字，直接把锁吃掉了。于是炸弹又漏了出来。
