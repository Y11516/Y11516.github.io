一、题目信息

  • 靶场链接：http://靶机IP:8080/less-14/

二、解题步骤

1. 分析题目考什么

黑名单封禁了 base32，但开发者再次遗漏了 base64。这关考察的是数据编码格式的识别、Base64 与 Base32 的区别，以及利用编码转换进行 WAF 绕过的基本思路。

2. 怎么解（详细步骤与输出解析）

源码核心逻辑

$pattern = '/cat|tac|head|tail|more|less|nl|sort|uniq|od|xxd|hexdump|base32/';
if(!preg_match($pattern,$cmd)){
    system($cmd);
}

最终成功 Payload 与解码流程

使用 base64 命令对文件进行编码：

?cmd=base64 /flag

回显内容：页面输出一长串包含大小写字母、数字以及 +、/、= 的 Base64 字符串（例如：ZmxhZ3tURVNUX0R5bmFtaWNfRkxBR30=）。

解码方法：

  1. 复制页面的 Base64 字符串。
  2. 打开 CyberChef (https://gchq.github.io/CyberChef/) 或任何在线 Base64 解码器。
  3. 选择 From Base64 操作。
  4. 粘贴字符串，即可还原出明文 flag{TEST_Dynamic_FLAG}。

踩坑记录：误用 Base32 解码器

情况：如果直接将 Base64 的字符串放进上一关的 Base32 解码器，会解码失败或得到乱码。

原因：Base64 的字符集是 A-Z, a-z, 0-9, +, / 加上等号填充；而 Base32 只有 A-Z, 2-7。二者的字符集完全不同，切分位数（6位 vs 5位）也不同。

改进方式：看到包含大小写字母和 +、/ 的字符串，优先尝试 Base64 解码。

3. 怎么迁移（跨学科与跨领域联想）

  • 电子邮件传输：Base64 诞生于早期的电子邮件系统（MIME 协议）。因为 SMTP 协议最初只支持 7 位的 ASCII 字符，无法直接传输图片、附件等二进制数据，所以需要 Base64 将二进制数据编码成纯 ASCII 文本进行传输，接收方再解码还原。
  • Web 开发与数据传输：在现代 Web 开发中，Base64 被大量用于将小图片直接嵌入 HTML/CSS（Data URI 形式），以减少 HTTP 请求；在 JWT（JSON Web Token）中，Header 和 Payload 也都是用 Base64 编码的。

三、名词大全与原理深度复盘

1. Base64 的底层原理

Base64 将二进制数据按 6 位（bit） 一组进行切分。因为 6 位二进制可以表示 0-63 共 64 个数值，正好映射到 64 个可打印字符（A-Z 是 0-25，a-z 是 26-51，0-9 是 52-61，+ 是 62，/ 是 63）。编码后的数据量比原数据膨胀约 33%。

2. Base64 vs Base32

  • Base64：每 6 位一组，字符集包含大小写，编码效率高，体积膨胀率 33%。
  • Base32：每 5 位一组，字符集仅大写字母和数字，不区分大小写，体积膨胀率约 60%。
  • 应用场景：Base64 更节省带宽，Base32 更适用于对大小写不敏感的存储环境（如域名、文件名）。

3. 黑名单的“打地鼠”效应

开发者封禁了 Base32，却忘了 Base64，这是黑名单防御常见的漏洞。编码方式成百上千（Base16, Base32, Base64, Base85, URL编码, Unicode等），开发者根本无法穷举完，只能被动挨打。

四、题目思考

1. 这跟前面关卡的区别

Level 13 引入了 Base32，而 Level 14 换成了 Base64。这就像是给你一套工具，让你在实战中体会到：面对“不能直接读取内容”的限制，编码转换（Encoding）是一种极其有效的绕过手段。你不需要真正读取明文，只需要拿到编码后的乱码，回本地解码即可。

2. 如何抽象理解概念（大白话）

把读取文件比作寄信。cat 是直接给你看原件；od 是把原件拆解成数字坐标；而 base64 则是把信件内容翻译成另一套完全不同的字母表（比如把所有字都转成二进制后再重新分组）。你收到翻译稿后，只要对照翻译字典（解码器），就能完美还原出原文。这是一种既保护了传输过程，又让你能绕过检查拿到情报的绝佳方案。
