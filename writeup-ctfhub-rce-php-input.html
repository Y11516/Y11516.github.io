CTFHub RCE - php://input

2026年9月22日 CTFHub Web安全 RCE 伪协议

一、题目信息

  • 题目名称：php://input
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / RCE（远程代码执行） / 文件包含 / PHP 伪协议利用
  • 靶场链接：http://challenge-5a2595f74203a483.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Burp Suite 抓包工具、curl 命令行工具

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 php://input 伪协议绕过文件包含限制，实现任意代码执行。后端代码对用户传入的 file 参数做了前缀限制，必须以 php:// 开头。由于服务器没有预置现成的木马文件，攻击者需要利用 PHP 的输入流功能，通过 POST 请求体传递恶意 PHP 代码，利用 include 包含并执行该输入流，从而获得服务器控制权。

2. 怎么想（破题思路）

  • 页面提示“我没有 Shell，如何获取 Flag？”，说明不能像上一题那样直接包含服务器上现成的 shell 文件。
  • 源码限制 substr($_GET["file"], 0, 6) === "php://"，强制要求参数前缀，这排除了常规的本地文件包含（LFI）。
  • 题目名称直接给出了破局点：php://input。
  • php://input 能够读取 POST 请求的原始数据（Body）。当它被 include 时，Body 中的数据会被 PHP 引擎当作“虚拟文件”内容来执行。
  • 思路确认：构造一个 POST 请求，URL 带上 ?file=php://input，请求体写入 PHP 代码。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：Burp Suite 构造 POST 请求报 400 Bad Request

踩坑情况：在 Burp Suite 的 Repeater 模块中，构造了 POST /?file=php://input HTTP/1.1，下一行紧跟 Host: ...，再下一行直接写 Payload <?php system('ls /'); ?>，点击 Send 后服务器返回 400 Bad Request。

原因分析：HTTP 协议规范要求：请求行与请求头之间、请求头与请求体之间，必须有一个空行。在 Burp 中直接顶格写 Payload，服务器会将 Payload 误认为是新的请求头（Header），导致解析失败。

改进方式：在请求头的最后一行（如 Connection: close）之后，按回车键产生一个空行，再在空行下方写 Payload。或者，直接放弃 Burp，改用系统自带的 curl 命令行工具（更加快捷，不易产生格式错误）。

详细实操步骤（使用 curl 命令行）

第一步：验证环境条件

点击页面里的 phpinfo 链接，搜索 allow_url_include，确认其值为 On。如果为 Off，则无法使用该伪协议。

第二步：发送 POST 请求执行命令

打开终端，运行以下命令查看根目录文件：

curl -X POST "http://challenge-5a2595f74203a483.sandbox.ctfhub.com:10800/?file=php://input" --data ""

命令逐字深度解析：

  • curl：命令行 HTTP 请求客户端工具。
  • -X POST：指定请求方法为 POST。
  • "URL/?file=php://input"：目标地址，file 参数指向 php://input 伪协议。
  • --data "Payload"：将 Payload 作为 HTTP 请求体（Body）发送。这里的 Payload 会被 php://input 接收。
  • <?php：PHP 脚本起始标记。
  • system：执行外部系统命令并输出结果的内置函数。
  • ('ls /')：参数为 ls /，即列出根目录下的文件。
  • ; 和 ?>：PHP 语句结束和脚本结束标记。

第三步：读取 Flag

发现根目录下有 flag_23285，直接将命令修改为读取该文件：

curl -X POST "http://challenge-5a2595f74203a483.sandbox.ctfhub.com:10800/?file=php://input" --data ""

页面回显明文 ctfhub{f1f8538413dcdc608715b280}，提交即可通关。

4. 怎么迁移（跨领域联想）

  • php://filter 伪协议（源码读取）：当遇到 LFI 且无法 RCE 时，可以使用 php://filter/convert.base64-encode/resource=index.php 读取源码。这能帮助发现更多隐藏漏洞。
  • data:// 伪协议（代码执行）：如果 allow_url_include 为 On，且 php://input 被拦截，可以使用 data://text/plain;base64,PD9waHAgcGhwaW5mbygpOyA/Pg== 将 Payload 做 Base64 编码后直接包含执行。
  • WAF 绕过实战：在真实渗透中，WAF 常拦截 URL 中的敏感字符（如 system、flag）。使用 php://input 可以把这些敏感字符藏在 POST 请求体中，避开 WAF 对 URL 的检测机制。

三、名词大全与原理深度复盘

1. php://input 伪协议

PHP 提供的一个输入流，用于读取 POST 请求的原始数据。它不依赖 php.ini 中的 allow_url_fopen 配置，但依赖 allow_url_include 才能被 include 包含。由于它能动态接收客户端数据，因此常被用于无文件落地攻击。

2. allow_url_include 配置项

PHP 的核心安全配置。如果设置为 On，则 include/require 等函数允许包含 URL 形式的文件（包括 php://input、data://、http:// 等）。该选项默认为 Off。CTF 环境中为了考察伪协议利用，通常设为 On。

3. 为什么 include php://input 会触发代码执行？

PHP 引擎在处理 include 语句时，如果发现包含的文件是 php://input，会将 POST 请求的原始数据视作一个“虚拟文件”来读取。读取到的内容（即我们发送的 Payload）会被当作 PHP 代码解析，从而绕过了文件系统的限制，实现了从 HTTP 请求体到代码执行的跨越。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与本地文件包含（LFI）的区别：上一题（文件包含）服务器提供了 shell.txt 作为靶子，是“借刀杀人”；本题服务器没有任何现成脚本，需要利用输入流“无中生有”。
  • 与 eval 执行的区别：eval() 是直接将字符串作为代码执行；本题是通过 include 加载输入流，用输入流来执行代码。
  • 与文件上传的区别：文件上传是将代码物理写入服务器磁盘；php://input 则是将代码放入内存中直接执行，完全不留文件落地痕迹，隐蔽性更高。

2. 这种题目的出现原因

这类漏洞源于开发人员功能设计时的权衡疏忽。为了实现动态加载模板或插件，开发者直接将用户可控的参数传入 include，仅做了简单的前缀过滤。但 PHP 内置的伪协议功能过于强大，且服务器配置（allow_url_include=On）不当，导致攻击者可以通过输入流直接注入并执行代码。

3. 这种应用在实际中如何体现？

在真实渗透测试和红蓝对抗中，php://input 是绕过 WAF 和实现无文件落地的核心技术之一。攻击者常在目标存在文件包含漏洞时，利用它直接向服务器发送 C2（命令控制）载荷，实现隐蔽的 RCE。企业防御需确保 allow_url_include=Off，并对文件包含参数进行白名单限制。

4. 如何抽象理解概念（大白话理解）

把服务器比作一个餐厅：

  • 普通文件包含（LFI）：你对服务员说：“把厨房里那份菜（本地文件）端上来。”
  • 限制条件（只能以 php:// 开头）：经理规定：“想点菜，前缀必须是‘特制套餐’。”
  • php://input 伪协议：你点了一份“特制套餐”，并同时递给服务员一张纸条（POST 请求体），纸条上写着“去厨房拿 Flag”。
  • 执行与结果：服务员（PHP 解析器）接过纸条，发现这是一张指令，于是直接照做了。你没有在厨房存放任何武器（文件），但仅凭这张纸条，就拿到了想要的东西。这就是输入流攻击的精髓。

做一道题，就要往自己脑子里装点东西。
