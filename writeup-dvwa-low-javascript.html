DVWA-Low-JavaScript攻击 (JavaScript Attacks)

2026年10月2日 DVWA Web安全 前端安全 客户端验证绕过

一、题目信息

  • 题目名称：DVWA JavaScript Attacks (Low)
  • 题目平台：DVWA (本地 Docker / 灵境靶场)
  • 题目类型：Web安全 / 客户端验证绕过 / 前端安全
  • 靶场链接：http://192.168.242.80/vulnerabilities/javascript/
  • 涉及工具：Google Chrome 浏览器 (F12 开发者工具)、Burp Suite

二、解题步骤

1. 分析题目考什么

本题的核心考点是客户端（前端）验证绕过。页面要求提交单词 success，但输入框默认被锁定为 ChangeMe。这通常是因为前端 JavaScript 代码在提交前对输入内容进行了校验或替换。由于校验逻辑在客户端（浏览器）执行，攻击者可以通过修改 DOM 或拦截 HTTP 请求来轻松绕过。

2. 怎么想（破题思路）

  • 观察输入框，发现默认值为 ChangeMe，且直接提交无法通过。
  • 按 F12 查看网页源码，发现前端 JS 会在提交前修改输入框的值，或校验其是否等于 success。
  • 既然校验在浏览器端，我们完全掌控浏览器。可以通过 F12 控制台直接修改 DOM 的值，或者用 Burp Suite 抓包修改请求体，绕过前端验证。

3. 怎么解（详细步骤与踩坑记录）

详细实操步骤（Payload逐字解释）

方法一：修改 DOM（最快，推荐）

按 F12 打开开发者工具，点击 Console（控制台）标签，输入：

document.getElementsByName("phrase")[0].value = "success";

解释：

  • document.getElementsByName("phrase")：找到所有 name 属性为 phrase 的 HTML 元素（即当前输入框）。
  • [0]：取第一个元素。
  • .value = "success"：强行把它的值改为 success。

然后点击页面上的 Submit，页面回显 Well done!，通关成功。

方法二：Burp Suite 抓包绕过

输入框保持默认的 ChangeMe，点击 Submit，用 Burp 拦截请求。

将请求体中的 phrase=ChangeMe 修改为 phrase=success，并删除或修改 token 参数，放行请求，也能通关。

4. 怎么迁移（跨领域联想）

  • 电商价格篡改：很多电商网站在前端页面用 JavaScript 计算商品价格，如果攻击者修改前端 DOM 中的价格字段，再提交订单，可能以极低价格购买商品。这是一种典型的客户端验证绕过。
  • 游戏作弊：网页游戏的生命值、金币数往往由前端 JS 控制，玩家可以通过 F12 修改这些数值，这就是客户端逻辑漏洞的体现。

三、名词大全与原理深度复盘

1. 客户端验证 (Client-side Validation)

在用户的浏览器中执行的验证逻辑（通常用 JavaScript）。它只能用于提升用户体验（如提示格式错误），绝不能作为安全边界。因为用户完全掌控浏览器，可以随意修改。

2. DOM (Document Object Model)

文档对象模型。浏览器将 HTML 解析成树形结构，JavaScript 可以通过 DOM API 动态修改页面内容、属性和样式。

3. Token

在 Web 应用中，Token 通常指服务器下发的随机令牌。如果服务端下发 Token，并要求提交时必须携带且不可预测，就能有效防止 CSRF 和重放攻击。但如果 Token 的校验逻辑只在前端，或者 Token 可由前端计算，就形同虚设。

4. Burp Suite 抓包绕过

通过代理拦截 HTTP 请求，在请求到达服务器之前修改其内容。这是绕过客户端验证最直接的手段。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 的区别：XSS 是攻击者往页面注入脚本，攻击其他用户。而本关是攻击者修改自己浏览器里的脚本或 DOM，来欺骗服务器。前者是“注入”，后者是“篡改”。
  • 与命令注入的区别：命令注入发生在服务器端（执行系统命令），本关发生在客户端（浏览器修改）。

2. 这种题目的出现原因（为什么存在）

漏洞存在的根本原因在于开发者盲目信任客户端提交的数据。他们误以为前端 JS 的校验能拦住攻击者，却忽略了攻击者可以完全不经过前端页面，直接用脚本或 Burp Suite 伪造请求。

在 Web 开发的历史中，很多早期系统只做前端校验，导致了大量的逻辑越权、支付篡改等漏洞。

3. 这种的应用

在护网中，如果遇到只做了前端校验的登录框或支付接口，攻击者可以直接绕过前端，提交非法数据。这属于“逻辑漏洞”的一种，危害视业务场景而定，严重时可直接造成资金损失。

4. 如何抽象理解概念（大白话）

把客户端验证比作“超市门口的体重秤”：

  • 正常情况：门口放个体重秤，你自己称一下，觉得太胖就不进去买东西了（前端校验）。
  • 恶意情况：你完全可以无视这个秤，直接冲进超市拿东西（伪造请求）。超市保安（服务器）如果不检查，就会让你得逞。
  • 正确的防御是：保安在收银台再称一次（服务端校验）。

做一道题，就要往自己脑子里装点东西。
