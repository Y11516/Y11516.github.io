Pikachu XSS - DOM型XSS

2026年9月24日 Pikachu Web安全 XSS DOM型XSS

一、题目信息

  • 题目名称：DOM型XSS
  • 题目平台：Pikachu 漏洞练习平台（本地环境）
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 客户端漏洞
  • 靶场链接：http://localhost:8080/vul/xss/xss_dom.php（本地环境）
  • 涉及工具：Chrome浏览器、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是DOM型 XSS（Document Object Model Cross-Site Scripting）。与反射型和存储型 XSS 不同，DOM 型 XSS 的漏洞完全发生在浏览器端。服务器仅仅是发送了一个静态的 HTML 页面，页面的 JavaScript 代码通过 DOM 操作（如 innerHTML、document.write）将用户的输入直接当成了 HTML 代码渲染，从而触发了弹窗。

2. 怎么想（破题思路）

  • 页面提示“先到这里把什么是dom搞明白了再说”，说明这关不涉及服务器交互。
  • 按 F12 查看网页源码，找到 JavaScript 代码。发现类似 document.getElementById("dom").innerHTML = "> what do you see? " + str; 的代码。
  • 由于使用的是 innerHTML，HTML 的解析器会直接解析用户输入的标签。但是，**innerHTML 不会执行 <script> 标签**。因此，我们需要寻找其他能够执行 JavaScript 的 HTML 标签。
  • 利用 <img> 标签的 onerror 事件：当图片加载失败时，自动执行 JavaScript。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：直接输入 <script> 无效

踩坑情况：在输入框输入 <script>alert(1)</script>，点击按钮，页面没有任何反应。

原因分析：在 JavaScript 中，如果使用 innerHTML 插入一段 HTML 字符串，现代浏览器出于安全考虑，**不会执行**其中包含的 <script> 标签。

改进方式：换用其他能执行 JS 的标签，比如使用图片的 onerror 事件。

踩坑记录二：没有闭合原来的标签导致失效

踩坑情况：直接在输入框输入 <img src=1 onerror=alert(1)>，结果页面把它当作普通文本原样输出了。

原因分析：JavaScript 原代码中，可能有双引号或者单引号包裹了你的输入（比如 innerHTML = "> " + str）。如果不把这些引号闭合，我们的 Payload 就会被当成字符串的一部分，无法被解析为 HTML 标签。

改进方式：利用 "> 或者 '> 来闭合原代码的引号和标签。

详细实操步骤（逐字解析）

第一步：找到注入点

在输入框中输入以下 Payload 并点击 click me!：

'">

Payload 逐字深度解析：

  • '">：闭合原 JavaScript 代码中的单引号和双引号，跳出原有的 HTML 属性限制。
  • <img：声明插入一张图片。
  • src=1：指定图片地址为 1。这是一个不存在的地址，必定会加载失败。

4. 怎么迁移（跨领域联想）

  • 现代单页应用（SPA）开发：在 Vue、React 等框架中，如果开发者使用了 v-html 或 dangerouslySetInnerHTML 这类直接渲染 HTML 的 API，而没有对用户输入做过滤，同样会产生 DOM 型 XSS。
  • 浏览器插件与客户端：Electron 等基于 Web 技术开发的桌面应用，同样面临 DOM 型 XSS 的威胁。攻击者可能利用它读取本地文件甚至执行系统命令。
  • 安全开发（SDL）：防御 DOM 型 XSS 的核心在于：**永远不要信任用户输入，永远不要直接使用 innerHTML**。应该使用 textContent 或 innerText，它们会将输入作为纯文本处理，不会解析 HTML 标签。

三、名词大全与原理深度复盘

1. DOM（Document Object Model）

文档对象模型。它是浏览器把 HTML 代码解析后生成的一棵“树”。JavaScript 可以通过操作这棵树，来动态地修改页面的内容、结构和样式。document.getElementById、innerHTML 都是操作 DOM 的接口。

2. innerHTML 的特性

innerHTML 是获取或设置元素内部 HTML 的属性。当设置它时，浏览器会解析字符串中的 HTML 标签并渲染。但为了保证安全和性能，**它不会执行通过字符串插入的 <script> 标签**。

3. 为什么 <img onerror> 能执行 JS？

因为 onerror 是一个事件处理器（Event Handler）。当元素发生错误（如图片加载失败）时，浏览器会查找并执行这个属性里的 JavaScript 代码，这属于 HTML 事件模型的机制，不受 innerHTML 对脚本标签的限制。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型/存储型 XSS 的区别：反射型和存储型的漏洞点在**后端服务器**（服务器把用户输入直接输出到了页面）。而 DOM 型 XSS 的漏洞点在**前端 JavaScript**（服务器没有参与，只是 JavaScript 代码错误地处理了用户的输入）。
  • 与 SQL 注入的区别：SQL 注入攻击的是数据库，DOM 型 XSS 攻击的是前端的 DOM 树，属于两个完全不同的层面。

2. 这种题目的出现原因

这类漏洞源于前端开发者对 DOM 操作的安全隐患认知不足。开发者为了图方便，直接使用了 innerHTML 来动态渲染内容，却不知道这种写法等价于允许用户输入任意的 HTML 代码。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，DOM 型 XSS 常用于绕过 WAF。因为 Payload 根本没有发送给服务器（通常放在 URL 的 Fragment（锚点）部分），所以服务器端的 WAF 根本无法拦截。攻击者常利用它来窃取用户 Cookie，进行钓鱼或会话劫持。

4. 如何抽象理解概念（大白话理解）

把服务器和浏览器比作大楼的门卫和内部装修队：

  • 反射型/存储型 XSS：你把炸弹交给了大门的门卫（服务器），门卫把炸弹带进了大楼并引爆。
  • DOM型 XSS：门卫（服务器）根本不在，大楼里的装修队（JavaScript 代码）拿到了一张图纸（你的输入），图纸上写着“拆掉一面墙”，装修队不去核实，直接开着挖掘机（innerHTML）就执行了。这就是纯客户端的漏洞。
