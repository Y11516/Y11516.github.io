验证码绕过(on client) - Pikachu 靶场 Writeup

2026年9月17日 Pikachu 靶场 Web安全 暴力破解 前端绕过

这是老师留给我的额外任务，一开始我觉得 Pikachu 靶场很难，甚至不敢下手。但在经历了 CTFHub 的洗礼后，我鼓起勇气打开了这一关。结果发现，只要理解了原理，这不过是一只纸老虎。这篇 Writeup 记录了我的心路历程和通关过程。

一、题目分析

  • 靶场路径：暴力破解 -> 验证码绕过(on client)
  • 题目意图：考察前端 JavaScript 验证的安全缺陷。由于验证逻辑完全在浏览器端执行，攻击者可以通过修改前端代码或禁用 JS 来绕过验证。

二、核心原理：前端验证形同虚设

比喻： 前端验证就像是门口贴了一张纸条“请出示身份证”。但纸条本身是可以被撕掉或修改的。禁用 JavaScript 就相当于闭上了眼睛，纸条根本拦不住你。

缺陷所在： 后端没有验证验证码，而是把验证逻辑交给了浏览器的 JavaScript。攻击者打开 F12 把验证函数删掉，或者直接禁用 JS，就可以随意提交登录请求。

三、解题过程（详细步骤与踩坑记录）

1. 踩坑第一步：找不到代码标签

按照教程尝试在 F12 的 Elements 面板里寻找登录按钮的 onclick 事件。但页面 HTML 代码嵌套极深，全是 <div>，翻找了半天也没找到具体的 <button> 或 <input> 标签。

教训： 不要在一大堆压缩过的 HTML 里瞎找，使用浏览器左上角的“元素检查器”精准点击，比肉眼扫描高效百倍。

2. 破局：使用禁用 JavaScript 大法

既然前端验证全靠 JS，我们干脆把 JS 禁掉！

  • 在 Chrome 地址栏输入 chrome://settings/content/javascript 并回车。
  • 找到“网站可以使用 JavaScript”，将其开关关闭。
  • 刷新 Pikachu 页面。
  • 在用户名输入 admin，密码输入 123456（提示就在右上角），验证码框随便填（由于 JS 已禁用，前端已经拦不住我们了）。
  • 点击 Login，页面直接弹出了 login success！

通关后，我立刻把浏览器的 JavaScript 开关重新打开，恢复正常使用。

四、知识点总结与防御思考

💡 前端不可信原则： 这是 Web 安全的第一定律。任何在浏览器中运行的代码（包括 JavaScript 验证），攻击者都能修改甚至完全禁用。真正的安全验证必须在服务端完成。

💡 防御手段： 1. 前端验证码只作为用户体验优化；2. 关键验证逻辑（如验证码校验、权限判定）必须在后端 PHP、Java 等服务器代码中进行二次校验；3. 前端不要泄露任何敏感逻辑或密钥。

五、深度扩展：从 JavaScript 到服务端安全

问题一：JavaScript 到底在网页里干什么？

如果没有 JS，网页就像一张印在纸上的海报，你只能看，点哪里都不会有反应（早期的网页就是这样）。有了 JS，网页就有了“交互能力”：

  • 响应你的操作：你在登录框输入密码，密码框自动变成小黑点；你点一下按钮，弹出一个提示框。
  • 动态改变页面：你点了一下“下一页”，网页不刷新，内容直接就变了（这也是现在绝大多数网站的做法）。
  • 与后端说悄悄话（核心！）：你的鼠标刚移到搜索框，网页就瞬间弹出“最近热搜”。这其实是网页里的 JS 偷偷摸摸地在后台给服务器发了请求（API 接口），把数据拉回来展示给你看。

为什么在护网（黑客实战）中，JS 那么重要？

因为 JS 是在你的浏览器（客户端）里直接运行的。这意味着，任何人都可以右键“查看网页源代码”或者下载 JS 文件，把里面的代码看得清清楚楚。

  • 直接暴露后端接口：现代网站（如 Vue、React）都是“前后端分离”的。后端只给数据，而前端 JS 里写着所有的请求地址。黑客扒下 JS，就能知道这个网站有哪些隐藏的 API 接口（比如 /api/admin/delete_user）。
  • 可能藏着硬编码的密码：很多时候，开发人员图省事，会把服务器的密钥、数据库密码、甚至测试账号，直接写在 JS 文件里。扒 JS 就等于寻宝。
  • 发现 XSS 漏洞（跨站脚本攻击）：既然 JS 是浏览器能执行的代码，如果网站没过滤好用户输入，黑客就可以把一段恶意的 JS 代码藏在网页里。当受害者打开网页时，这段代码就会在受害者的浏览器里执行（盗取 Cookies、劫持账号等）。

问题二：什么叫做要在服务端完成？

一个生动的比喻：取钱

  • 前端（浏览器/你的手机）：就像是你手里拿着的取款单。你在单子上写：“我要取 100 万”。
  • 服务端（后台服务器）：就像坐在防弹玻璃后面的银行柜员。

什么是“前端验证”？

你填好取款单后，自己没有钱，于是你在单子上画了一个大大的红章：“审核通过”。这就是前端验证。因为你只能控制自己手里的这张单子，你可以在上面随便画、随便改，甚至把单子撕了说自己已经取过钱了，但这毫无意义。

什么是“必须在服务端完成”？

无论你在取款单上写了什么、画了什么，你都必须把单子递给柜台里的柜员。柜员拿到单子后，会亲自核对：

  1. 你的身份证是真的吗？
  2. 你的账户里真的有 100 万吗？
  3. 密码对不对？

柜员如果发现你账户里只有 100 块，哪怕你在单子上写“我有一百万”，柜员也会直接把你拒绝。这个“亲自核对”的过程，就是服务端验证。

回到 Web 安全：为什么前端不可信？

在网页里，前端代码（HTML、CSS、JavaScript）是在你的电脑（浏览器）里运行的。这意味着，你有绝对的权力控制你的浏览器。作为一个攻击者（或者你打 CTF 时），你可以做两件极其简单的事：

  1. 修改代码（按 F12 进入开发者工具）：网页上有个输入框限制你只能输入 3 个数字，你可以直接按 F12 把那个限制代码删掉，或者把按钮改个颜色。
  2. 截获并修改数据包（用 Burp Suite 抓包）：网页上的 JS 代码说“密码不能少于 8 位”，于是你输入了 8 位，但在网络传输过程中，你用抓包工具把数据拦截下来，硬生生把密码改成了 1 位，再发给服务器。

如果网站把安全校验做在了前端（浏览器里）：

比如，网页的 JS 代码里写着：“如果价格 > 1000，就不允许提交”。攻击者只需要按 F12 把这段 JS 代码删掉，或者用抓包工具直接把请求里的价格改成 -1 发给服务器。服务器如果连查都不查，直接照着做，那你就花 -1 元买到了东西，账户里还多了钱。

真正的“服务端完成”是什么样子的？

服务器（后端）是攻击者无法直接触碰的。你只能通过 HTTP 请求（数据包）给它发指令，它收到指令后，会在自己安全的机房里默默检查。如果验证放在了服务端，当你发送修改过的请求（比如金额改成了 -1）时：

  • 服务端逻辑：“等等，我查了一下数据库，这个商品原价是 1000 块，怎么他发来的数据里价格是 -1 块？肯定是攻击者改包了。直接拒绝！”
  • 服务端逻辑：“密码明明是 8 位，他只发了 1 位，肯定不对，直接报错。”
  • 服务端逻辑：“这个用户是普通用户，前端虽然藏着一个‘删除管理员’的按钮，但他发请求过来了，我得查查他的权限。一查，没权限，拦截！”

做一道题，就要往自己脑子里装点东西。
