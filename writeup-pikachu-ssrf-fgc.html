SSRF(file_get_content) - Pikachu Writeup

2026年9月20日 Pikachu Web安全 SSRF

一、题目信息

  • 题目名称：SSRF(file_get_content)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 服务端请求伪造（SSRF） / 环境配置限制
  • 靶场链接：http://localhost:8080/vul/ssrf/ssrf_fgc.php
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点依然是服务端请求伪造（SSRF），但这次后端使用的函数从 curl 换成了 PHP 内置的 file_get_contents()。file_get_contents() 与 curl 最大的区别在于，它受 PHP 配置文件 php.ini 中 allow_url_fopen 选项的限制。如果该选项为 Off，则无法通过该函数请求外部 URL 或读取 file:// 协议。

2. 怎么想（破题思路）

页面提示“又是一首诗”，和上关类似，没有明显的输入框。

  • 尝试直接在浏览器地址栏手动构造请求：?url=http://127.0.0.1/vul/ssrf/ssrf_info/info1.php。
  • 页面完全没有回显，尝试 file:///etc/passwd 也无法读取。
  • 确认后端可能存在环境配置限制，或前端未正确拼接参数。需要进一步测试 allow_url_fopen 是否开启。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：手动构造 URL 参数毫无反应

踩坑情况：在地址栏手动拼接 ?url=http://127.0.0.1/vul/ssrf/ssrf_info/info1.php 后，页面呈现空白，没有报错，也没有显示任何诗的内容。

原因分析：后端极大概率使用了 file_get_contents() 函数。该函数请求 URL 的能力受 PHP 配置项 allow_url_fopen 的限制。若该配置为 Off，则函数会直接返回 False，页面不输出任何内容。

改进方式：尝试测试 ?url=http://www.baidu.com。如果依旧空白，说明 allow_url_fopen 确实被关闭。这不是操作失误，而是靶场环境的安全防御机制。

踩坑记录二：尝试 file:///etc/passwd 读取本地文件失败

踩坑情况：输入 file:///etc/passwd，试图读取系统用户文件，页面同样毫无反应。

原因分析：除了 allow_url_fopen 限制外，PHP 可能还通过 disable_functions 禁用了相关文件读取函数，或者限制了 file:// 协议。

改进方式：在这种环境下，死磕并无意义。应当理解该函数与 curl 的底层差异。在真实环境中，如果 file_get_contents 受限，可以尝试寻找其他 curl 接口进行利用。

终极解法（理论）：利用 file_get_contents 触发 SSRF

如果环境支持，Payload 应为：

http://localhost:8080/vul/ssrf/ssrf_fgc.php?url=file:///etc/passwd

代码逐个符号深度解析：

  • ssrf_fgc.php?：触发漏洞的后端脚本（fgc 代表 file_get_contents）。
  • url=：后端用于接收目标地址的参数名。
  • file:///：本地文件传输协议。三个斜杠表示绝对路径。
  • etc/passwd：目标文件路径。

由于本靶场环境默认关闭了 allow_url_fopen，该漏洞在当前环境下无法回显。但已经掌握了其利用逻辑，属于环境限制导致的利用中断。

4. 怎么迁移（跨领域联想）

  • SSRF 与内网探测：无论是 curl 还是 file_get_contents，SSRF 的核心利用场景都是内网探测。攻击者可以尝试请求 http://192.168.1.1:80、http://10.0.0.1:6379 等地址，通过响应时间或状态码判断内网资产的存活情况。
  • gopher 协议攻击：如果 allow_url_fopen 被打开但限制了 HTTP 协议，可以尝试使用 gopher:// 协议构造原生 TCP 数据包，直接攻击内网的 Redis、FastCGI 等服务。
  • 代码审计：在审计 PHP 代码时，看到 file_get_contents($url) 或 curl_exec($ch) 时，必须检查目标 URL 是否可控，以及环境配置是否允许加载外部资源。

三、名词大全与原理深度复盘

1. file_get_contents() 函数

PHP 中的一个内置函数，用于将整个文件读入一个字符串。它不仅可以读取本地文件，也可以读取网络资源（如 HTTP、FTP）。当参数是 URL 时，它通常用于抓取网页内容。但它受 allow_url_fopen 配置的限制。

2. allow_url_fopen 配置项

PHP 配置文件中的一项。当设置为 On 时，允许 PHP 通过 URL 形式的封装协议（如 http://、ftp://）访问文件；当设置为 Off 时，禁止使用 URL 打开文件，从而大大提高了安全性，防止 SSRF 和 RFI 攻击。

3. curl 与 file_get_contents 的区别

curl 是一个功能强大的库，支持多种协议、自定义请求头、Cookie 管理、超时设置等，且不受 allow_url_fopen 限制。file_get_contents 简单轻量，但受限于该配置。在实战中，如果 file_get_contents 无法触发 SSRF，可以尝试寻找使用 curl 的接口。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 SSRF(curl) 相比：前者的请求依赖 curl 扩展，不受 PHP 配置限制，利用范围更广；后者的请求依赖 file_get_contents 函数，受 allow_url_fopen 限制，防御力度更高。
  • 与文件包含漏洞相比：文件包含是让服务器包含并执行文件；SSRF 是让服务器读取文件内容并返回（或者发起网络请求），两者虽然都涉及文件，但执行逻辑不同。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在处理图片下载、网页抓取等业务时，直接使用了 file_get_contents($_GET['url']) 等函数，而没有校验传入的 URL 是否属于内网或本地文件，导致服务器成了攻击者的“代理服务器”。

3. 这种应用在实际中如何体现？

在实际的渗透测试中，SSRF 是内网渗透的敲门砖。通过 SSRF，攻击者可以探测内网开放的端口、访问未授权的内网服务（如 Redis、Elasticsearch）、甚至可以读取云服务器的临时凭证（如 AWS 的 169.254.169.254 元数据接口），从而可能导致整个云环境被接管。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个快递员：

  • curl（上一关）：快递员有全套工具，无论你让他去隔壁房间（内网）还是去你家（本地文件）拿包裹，他都能做到。
  • file_get_contents（本关）：快递员的权限受限。公司规定（allow_url_fopen = Off），他不能随便去外面的房间拿包裹。你让他去拿，他只能两手一摊：“我做不到”。这就是环境配置导致的防御效果。
