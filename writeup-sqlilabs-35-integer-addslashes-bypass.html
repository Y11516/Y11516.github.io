SQLi-Labs Less-35

2026年9月28日 SQLi-Labs Web安全 SQL注入 数字型注入

一、题目信息

  • 题目名称：SQLi-Labs Less-35 (GET - Bypass Add Slashes (we dont need them) Integer based)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / 数字型注入 / 转义绕过
  • 靶场链接：http://localhost:8081/Less-35/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是数字型注入绕过 addslashes() 转义。因为 SQL 语句是 WHERE id=$id（没有引号包裹），所以 addslashes() 函数对数字参数完全无效。攻击者可以直接输入 SQL 语句，无需考虑单引号闭合。

2. 怎么想（破题思路）

  • 页面提示“Please input the ID as parameter with numeric value”，明确告知是数字型。
  • 直接输入 ?id=1，回显正常。
  • 输入 ?id=1 and 1=1，回显正常。
  • 输入 ?id=1 and 1=2，回显异常（无数据）。
  • 说明存在数字型注入。拼接报错注入 Payload 即可。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：习惯性加引号导致失败

踩坑情况：习惯性地输入 ?id=1'，被转义或没有回显。

原因分析：因为是数字型，没有引号需要闭合。加了单引号反而会被 addslashes 转义，导致 SQL 语法错误。

改进方式：直接使用 ?id=1 and ...，不加任何引号。

详细实操步骤（Payload逐字解释）

第一步：构造 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-35/?id=1%20and%20updatexml(1,concat(0x7e,(select%20database()),0x7e),1)--%20-

第二步：Payload 逐字解析

  • 1：数字型参数，无需闭合。
  • %20and%20：URL 编码的空格和逻辑与。
  • updatexml(...)：报错注入，获取当前数据库名。
  • --%20-：注释符，阻止后续 SQL 执行。

第三步：验证结果

页面回显 XPATH syntax error: '~security~'，注入成功。

4. 怎么迁移（跨领域联想）

  • 数字型与字符型的区别：数字型注入无需闭合引号，攻击面更广。在代码审计中，必须对所有输入进行严格类型转换。
  • 转义函数的局限性：addslashes() 只对特定字符有效。在数字型场景下完全无效，这警示我们安全防御不能只依赖单一的字符串转义。
  • 安全开发启示：使用参数化查询（Prepared Statements）是终极方案。

三、名词大全与原理深度复盘

1. 数字型注入 (Integer-based SQL Injection)

SQL 语句中的参数没有引号包裹，攻击者可以直接构造 SQL 片段，无需闭合引号。

2. addslashes() 函数

PHP 中用于转义单引号、双引号、反斜杠等特殊字符的函数。但它对数字和空格不进行转义。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-32/33/34 的区别：Less-32 到 34 是字符型宽字节注入，Less-35 是数字型注入，无需闭合引号，无需宽字节绕过。

2. 这种题目的出现原因（为什么存在）

开发者认为数字型参数不会被注入，或者直接使用了 addslashes() 就认为高枕无忧。这警示我们，任何输入都必须做类型和内容校验。

3. 这种应用在实际中如何体现？

在实战中，如果遇到 ID 参数、页码参数等数字型接口，可以直接测试注入，绕过所有字符串转义机制。

4. 如何抽象理解概念（大白话）

把靶场比作一个“检查站”：

  • 安检员（addslashes）只检查你带的是不是违禁品（引号、反斜杠）。
  • 但你手里拿的是纯数字（id=1），他根本不检查。
  • 你大大方方地在数字后面跟上了“炸弹代码”，直接进了门。
