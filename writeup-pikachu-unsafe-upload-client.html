一、题目信息

  • 题目名称：Unsafe Fileupload (client check)
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 文件上传漏洞 / 客户端校验绕过（前端绕过）
  • 靶场链接：http://localhost:8080/vul/unsafeupload/clientcheck.php
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12 Console/Elements）

二、解题步骤

1. 分析题目考什么

本题的核心考点是客户端（前端）文件上传校验绕过。后端服务器未对上传文件做任何安全过滤，仅依靠浏览器端的 JavaScript 代码来检查文件后缀。由于前端代码完全受控于用户浏览器，攻击者可以通过修改 DOM 元素或拦截数据包来轻易绕过这种防御，上传恶意的 PHP 木马文件（WebShell），从而获取服务器权限。

2. 怎么想（破题思路）

页面提示“这里只允许上传图片o”，右上角提示“一切在前端做的安全措施都是不靠谱的”。解题思路如下：

  • 准备一个恶意的 PHP 文件（如 shell.php）。
  • 尝试上传，触发前端 JS 拦截弹窗，确认防御机制为前端验证。
  • 通过 F12 的 Console 面板，直接禁用前端检查事件，或者删除 onchange 属性。
  • 再次上传 shell.php，成功后访问该文件路径，验证代码是否执行。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：在 Elements 面板中找不到 checkFile() 代码

踩坑情况：尝试在 F12 Elements 面板寻找并删除 onchange="checkFile()" 代码，但由于 DOM 结构复杂，鼠标难以准确选中真实的 <input> 标签，导致无法手动删除。

原因分析：现代前端页面常常对 input 标签进行了层叠样式和封装，在 Elements 面板中容易点错层级，导致修改失败。

改进方式：放弃鼠标寻找，直接在 F12 Console（控制台）中使用 JavaScript 选择器锁定 input 元素，强制将其 onchange 事件置空。

踩坑记录二：为什么传图片马（.jpg 包含 php 代码）无法执行？

踩坑情况：把 shell.php 改名成 shell.jpg 上传，虽然能上传成功，但访问时无法执行 PHP 代码。

原因分析：图片马通常用于后端会检查文件真实类型（如 getimagesize）的场景。而本题后端只认文件后缀，如果你的文件名是 .jpg，服务器就不会将其交给 PHP 引擎解析。

改进方式：本题直接上传纯 .php 后缀的文件即可。如果是后续更严格的关卡（如 getimagesize），才需要制作包含图片文件的“图片马”，并配合文件包含漏洞或解析漏洞来执行。

终极解法：利用 Console 绕过前端校验并上传

第一步：制作恶意文件

新建 shell.php，写入内容：

<?php phpinfo(); ?>

第二步：触发拦截（验证防御）

在页面点击选择文件，选中 shell.php，浏览器弹出弹窗拦截，证明前端 JS 在起作用。

第三步：利用 Console 解除防御

按 F12 打开控制台，输入以下 JavaScript 代码并回车：

document.querySelector('input[type="file"]').onchange = null;

代码逐个符号深度解析：

  • document：代表当前浏览器的文档对象模型（DOM）根节点。
  • querySelector()：一个强大的选择器方法，用于查找匹配指定 CSS 选择器的第一个元素。
  • 'input[type="file"]'：选择器字符串，精确定位类型为文件的 input 标签。
  • .onchange：代表该元素的“值改变”事件监听器。当用户选择文件后，这个事件会被触发，执行原本的 checkFile() 检查代码。
  • = null：将 onchange 赋值为空。这相当于直接卸除了按钮上的“检查机关”，之后选择任何文件都不会再触发拦截。

第四步：上传并验证

再次选择 shell.php，点击“开始上传”。页面提示上传成功，并返回路径。访问该路径，成功弹出紫色 phpinfo 页面，拿到服务器权限（GetShell）。

4. 怎么迁移（跨领域联想）

  • Burp Suite 抓包改包：除了前端删除 JS，另一种更通用的绕过方法是将文件改为 shell.jpg，在 Burp Suite 中拦截上传请求，将文件名改回 shell.php，绕过前端后缀检查的同时，服务器后端收到的是 PHP 文件。
  • Web 安全防御体系：该关卡印证了“前端验证不可靠”的铁律。在真正的开发中，必须在服务器端（后端）对上传文件的 MIME 类型、后缀白名单、文件头内容（Magic Number）进行严格校验，甚至需要重命名文件并剥离执行权限。
  • 黑帽攻击链：在真实渗透中，拿到 WebShell 只是第一步。攻击者会立即利用 WebShell 进行提权、留下后门、探测内网拓扑，进而控制整个内网域环境。

三、名词大全与原理深度复盘

1. 客户端校验（Client-side Validation）

在用户的浏览器中执行的校验（通常由 JavaScript 完成）。由于整个浏览器环境（包括 JS 代码、DOM 树）完全受用户控制，用户可以任意修改、跳过或禁用它。因此，客户端校验只能用于优化用户体验（减少无谓的服务器请求），绝不能作为安全防御手段。

2. WebShell（网页木马）

一个用 Web 语言（如 PHP、JSP、ASP）编写的脚本文件。攻击者通过上传漏洞将其放入 Web 服务器，之后就可以通过浏览器或工具向该文件发送指令，从而在服务器上执行系统命令、读取文件、篡改数据。

3. 为什么 是标准的探针？

phpinfo() 是 PHP 的内置环境探测函数，它会输出服务器的环境信息、PHP 版本、已安装模块、配置项（包括禁用函数）等，是安全测试中最标准的“探路”Payload。它能最直观地证明 PHP 代码已被成功解析执行。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 SQL 注入相比：SQL 注入是攻击数据库，属于数据层的渗透；文件上传是攻击服务器文件系统，是获取服务器权限（Getshell）最直接的途径。
  • 与 File Inclusion (RFI) 相比：RFI 是让服务器去远程下载并执行恶意代码，需要依赖 allow_url_include 配置；文件上传是直接把恶意代码传进服务器，不需要依赖外部网络，成功率更高。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者为了快速响应前端体验，只在前端做了文件格式检查（比如只允许选图片），却没有在后端再次进行校验。这是一种典型的“认为用户会按套路出牌”的防御盲区。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，文件上传漏洞是攻击者最喜欢利用的漏洞之一。一旦发现，通常能直接获取服务器控制权，被评为“高危”甚至“严重”级别。在 CTF 比赛中，文件上传也是常见的考点，常常与解析漏洞、文件包含漏洞、中间件漏洞相结合。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个夜总会：

  • 正常功能：你想带一个包（文件）进去，门口保安（前端 JS）检查你的包只能装衣服（图片），不能带武器（木马）。
  • 绕过验证：你把保安的检查规则手册撕了（Console 中把 onchange 置为 null），直接大摇大摆地拎着装有武器（PHP 木马）的包走进了夜总会。
  • 后端防御的真谛：夜总会真正的安全，不能只靠门口的保安，还必须有内部安检门（后端校验）。即便门口保安瞎了，内部安检门也能检测出武器并将其拦截。

做一道题，就要往自己脑子里装点东西。
