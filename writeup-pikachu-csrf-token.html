CSRF Token - Pikachu Writeup

2026年9月19日 Pikachu Web安全 CSRF

一、题目信息

  • 题目名称：CSRF Token（防御机制验证）
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站请求伪造（CSRF） / 防御机制
  • 靶场链接：http://localhost:8080/vul/csrf/csrftoken/csrf_token_login.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是CSRF Token 的防御机制。与前面两关不同，本题的服务器端不再仅仅依赖 Cookie 进行身份验证。每次页面加载时，服务器会生成一个随机且不可预测的 Token（令牌），将其嵌入在表单的隐藏字段中。提交表单时，服务器会校验这个 Token 是否正确。本题考察的是解题者能否识别 Token 的存在，并理解为什么传统的伪造请求会在此防御机制下失效。

2. 怎么想（破题思路）

在上一题中，我们可以通过构造自动提交的脚本发起攻击。但这一题，解题思路必须转变：

  • 点击“修改个人信息”，打开 F12 的 Elements 面板，查看表单源码。
  • 寻找是否存在 <input type="hidden" name="token" value="..."> 这样的隐藏字段。
  • 尝试刷新页面，观察该 value 值是否发生动态变化。如果发生变化，说明该 Token 由服务器随机生成。
  • 由于攻击者无法预测这个随机 Token，因此构造的伪造表单必然缺失或包含错误的 Token，服务器将直接拒绝请求。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：手动输入 URL 导致 404 Not Found

踩坑情况：在尝试手动构造请求 URL 时，直接在地址栏输入 .../csrftoken/csrf_token_edit.php，结果页面报错 404 Not Found。

原因分析：靶场的目录结构或文件命名在某些 Docker 镜像版本中可能存在差异。且 URL 路径中 csrf_token 与 csrftoken 容易混淆，手动输入容易引发路径解析错误。

改进方式：避免手动拼写 URL，应始终通过点击页面上的链接（如“修改个人信息”）进行页面跳转，确保路径正确。

踩坑记录二：环境文件缺失导致无法加载页面

踩坑情况：通过点击链接或正确输入 URL 仍然返回 404，说明当前本地 Docker 镜像中该页面文件缺失或损坏。

原因分析：部分 Pikachu 靶场镜像在打包时可能遗漏了 csrf_token_edit.php 文件，这是环境本身的 Bug，并非操作失误。

改进方式：若遇到环境故障，不必强行死磕，可基于已掌握的原理直接梳理该题的核心逻辑。本题的核心在于验证“Token 校验能阻止 CSRF 攻击”，而非真的去成功篡改邮箱。

终极解法：验证 Token 防御的拦截效果

假设能够正常进入修改页面，在 F12 Console 中执行以下代码，试图绕过 Token 直接提交：

var form = document.createElement("form");
form.action = "http://127.0.0.1:8080/vul/csrf/csrftoken/csrf_token_edit.php";
form.method = "POST";

var params = {
    sex: "boy",
    phonenum: "110",
    email: "hacker2@evil.com",
    add: "hacker",
    submit: "submit"
    // 故意不带 token 参数，模拟攻击者猜不到 token 的情况
};

for (var key in params) {
    var input = document.createElement("input");
    input.type = "hidden";
    input.name = key;
    input.value = params[key];
    form.appendChild(input);
}

document.body.appendChild(form);
HTMLFormElement.prototype.submit.call(form);

代码逐个符号深度解析：

  • form.action = "..."：指定目标接口地址。
  • params 对象：包含除了 token 之外的所有参数。由于没有 token，服务器端在执行 if ($_POST['token'] == $_SESSION['token']) 判断时会返回 False。
  • HTMLFormElement.prototype.submit.call(form)：强制提交表单，向服务器发起请求。

执行结果：页面刷新后，邮箱并不会被修改为 hacker2@evil.com。因为没有携带正确的 Token，服务器校验失败，防御机制生效，CSRF 攻击被成功拦截。这也是本题的正确验证结果。

4. 怎么迁移（跨领域联想）

  • Web 应用防火墙（WAF）：在现代企业级开发中，CSRF Token 通常以类似 WAF 的方式集成在框架层面。例如 Spring Security 默认开启 CSRF 防护，在请求头中携带 Token。理解这道题的底层逻辑，是后续配置企业级安全策略的基础。
  • JWT（JSON Web Token）：现代无状态鉴权常用 JWT。JWT 本质上也是一种 Token，但它在客户端存储签名信息，而 CSRF Token 是在服务端生成并校验的。理解 Token 的生成、下发和校验机制，对掌握 Web 鉴权技术至关重要。
  • 分布式系统的 Session 一致性：由于 Token 通常与用户 Session 绑定，在分布式环境中，如果 Session 不同步，可能导致 Token 校验失败。这是运维和架构设计中需要考虑的深层安全问题。

三、名词大全与原理深度复盘

1. CSRF Token（跨站请求伪造令牌）

一种服务端生成的、随机且不可预测的字符串。每次用户访问敏感页面时，服务器生成一个新的 Token，存储在用户的 Session 中，并将其作为隐藏字段（或自定义请求头）下发到前端。当用户提交请求时，服务器会对比请求中的 Token 与 Session 中存储的 Token 是否一致，若不一致则拒绝该请求，以此有效阻止 CSRF 攻击。

2. 为什么攻击者无法获得 Token？

根据浏览器的同源策略（Same-Origin Policy），攻击者搭建的恶意网站无法读取目标网站（如 Pikachu）页面中的 DOM 元素，自然也就无法获取隐藏在表单里的 Token 值。同时，Token 是随机生成的，攻击者无法通过猜测来伪造。

3. 浏览器同源策略（Same-Origin Policy）

浏览器最核心的安全功能，它限制了来自不同源（协议、域名、端口三者必须完全一致）的文档或脚本对当前文档的读取权限。正是由于同源策略的存在，攻击者的网页无法读取 Pikachu 页面的 Token。这也是为什么在上一题（CSRF POST）中，本地 HTML 文件无法发起攻击的原因——浏览器默认的 SameSite Cookie 策略进一步阻断了跨站的 Cookie 发送。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 CSRF(get) 相比：GET 型毫无防御，仅靠一个 URL 就能触发；CSRF Token 引入了服务端动态生成的随机令牌，请求的合法性不再仅依赖于 Cookie，而是需要额外验证 Token。
  • 与 CSRF(post) 相比：POST 型只是增加了参数在请求体中的隐蔽性，但依然无法阻止自动化脚本（如我们之前写的 JS 脚本）发起伪造请求。CSRF Token 则从逻辑上彻底阻断了这种伪造，因为脚本无法获得正确的随机参数。

2. 这种题目的出现原因（为什么存在）

这类题目出现的原因，是因为随着 Web 安全技术的发展，开发人员逐渐意识到仅靠 Referer 校验或 Cookie 校验不足以防御 CSRF。CSRF Token 作为一种更严谨、安全的防御手段被广泛采用。这道题就是为了让学习者从“攻击者”的角度思考：面对一个无法绕过的 Token 校验，我们应该如何应对（例如配合 XSS 漏洞来读取 Token，这属于高级组合攻击）。

3. 这种应用在实际中如何体现？

在实际的银行转账、密码修改、商品下单等敏感业务中，开发人员必须强制使用 CSRF Token。如果这些接口缺失 Token 校验，将直接导致用户的资金损失和隐私泄露。在安全审计中，审查 API 是否包含 CSRF Token 校验是评估一个系统是否安全的关键指标之一。

4. 如何抽象理解概念（大白话理解）

如果把服务器比作一个严格的银行柜员：

  • CSRF(get) 和 CSRF(post)：柜员只看你的脸（Cookie）。只要是你本人（或长得像你的人）递过来的条子，他都会照办。攻击者只要让你“路过”一下，你就把条子递过去了。
  • CSRF Token：柜员变聪明了。他会在你每次去办业务时，先发给你一张带有随机密码的“防伪纸条”（Token），并把这个密码记在银行的本子上。
  • 攻击失败：攻击者伪造的条子上，因为不知道那个随机密码，所以没有防伪信息。柜员核对本子后，直接拒绝办理。这就是 CSRF Token 防御机制生效的直观表现。
