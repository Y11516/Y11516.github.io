302跳转 - CTFHub Web 入门 Writeup

2026年9月16日 CTFHub Web安全 HTTP协议 302重定向

这道题考察的是 HTTP 协议中的“临时重定向（302）”。目标页面隐藏了 Flag，浏览器在访问时会自动跟随重定向跳转，导致常规手段无法直接看到隐藏信息。本篇 Writeup 记录了在浏览器中踩坑，并通过终端工具破局的过程。

一、题目信息

  • 题目名称：302跳转
  • 题目平台：CTFHub
  • 题目类型：Web / HTTP 协议 / 状态码
  • 题目提示：HTTP临时重定向
  • 涉及工具：浏览器开发者工具（Network 面板）、Mac 终端（curl 命令）
  • 最终Flag： ctfhub{...} （请填入实际获取的值）

二、解题过程

方式一：浏览器 F12 抓包（踩坑与分析）

进入靶场，页面显示 “No Flag here!” 和一个 “Give me Flag” 的链接。

1. 打开 F12 开发者工具，切换到 Network（网络）面板。

2. 为了捕捉跳转记录，必须勾选 Keep log（保留日志）。

3. 点击页面上的 “Give me Flag” 链接。此时 Network 列表出现了请求。

4. 发现第一个请求是 index.php，状态码为 302 Moved Temporarily。

5. 点击该请求，查看右侧的 Response headers（响应头），找到关键信息：

Location: /index.html

这说明服务器告诉浏览器：“去访问 /index.html 获取内容”。

6. 尝试查看 index.php 的 Response（响应体）来寻找 Flag，但浏览器提示：

Failed to load response data
No content available because this request was redirected

踩坑分析：现代浏览器为了性能优化，一旦遇到 302 重定向，会直接丢弃原请求的响应正文，迅速跳转去请求新的页面。因此，Flag 虽然写在 302 的响应体中，但被浏览器抛弃了，我们在 Network 面板里无法看到。

方式二：终端 curl 命令（成功破局）

既然浏览器会自作主张丢弃数据，我们可以在终端使用 curl 工具来强制抓取原始响应。执行以下命令：

curl -i "http://challenge-xxxx.sandbox.ctfhub.com:10800/index.php"

参数解释：

  • -i：显示响应头（Headers）和响应体（Body）。
  • 不加 -L：禁止 curl 自动跟随重定向，从而强制停在 302 这一步。

按下回车后，终端完整打印了 HTTP 通信内容。在响应头之后（空行之后的响应体部分），成功找到了隐藏的 Flag！

最终 Flag： ctfhub{...}

方式三（扩展）：Burp Suite 抓包

如果已经配置了 Burp Suite 代理，可以开启 Intercept 拦截。点击链接后，Burp 会拦截到 302 响应包。查看响应体（Body），同样可以原封不动地看到 Flag。这是专业渗透测试中最常用的方式。

三、知识点总结（往脑子里装的东西）

（一）HTTP 状态码全景图谱

HTTP 状态码是三位数字，第一位数字决定了它的“大类”。

  • 1xx（信息提示）：服务器收到请求了，正在处理。比如 101 Switching Protocols（升级协议，如 WebSocket）、103 Early Hints（提前返回资源提示）。
  • 2xx（成功）：请求成功。比如 200 OK（最常看到的成功）、202 Accepted（收到了，但还没处理完）。
  • 3xx（重定向）：你需要去另一个地方拿数据。比如 301 永久重定向、302 临时重定向、304 Not Modified（缓存没变）。
  • 4xx（客户端错误）：你的请求有问题。比如 400 Bad Request（语法错误，你之前发POST漏空行报的错）、401 Unauthorized（需要认证）、403 Forbidden（明确拒绝）、404 Not Found（页面不存在）、405 Method Not Allowed（方法用错了）。
  • 5xx（服务器错误）：服务器自己出问题了。比如 500 Internal Server Error（后端代码崩了）、502 Bad Gateway（网关错误）、503 Service Unavailable（服务不可用）。

（二）302 跳转的深度解析与拓展

  • 302 是什么？ 它是“临时重定向”。它是一个开发者自定义的“通知”，告诉浏览器去另一个地址（Location）。它不是随机生成的链接，而是后端逻辑写死的。
  • 302 与 202/103 的区别？
    • 302：浏览器会立刻“自动跟车”去新地址，并丢弃原响应体。
    • 202：浏览器不会跳转，停在原地渲染响应体。Flag 如果藏在响应体里，按 F12 就能直接看到。
    • 103：浏览器会直接忽略 103 的响应体，等待最终响应。这种藏 Flag 方式极其隐蔽，需用抓包工具甚至 Wireshark 抓底层 TCP 包。
    • 301 vs 307/308：301 是永久重定向；307/308 是严格保持原请求方法的跳转（比如 POST 过去还是 POST，不会变成 GET）。

（三）响应头（Headers）与响应体（Body）的区别

HTTP 响应就像快递包裹，分两层：

  • 响应头（Headers）：包裹外面的“快递单”。包含状态码、服务器信息、Location（跳转地址）等。浏览器只展示包裹里的东西，不展示快递单，所以 Flag 常藏在这里（比如自定义头 X-Flag: ctfhub{...}）。
  • 响应体（Body）：包裹里面的“实物”。就是 HTML 代码、JSON 数据等。浏览器会自动渲染它。Flag 常藏在 HTML 注释 <!-- flag --> 或隐藏的 DOM 标签中。
  • 为什么 curl -i 能破局？ -i 参数强制 curl 把快递单和实物全打印出来，不遗漏任何细节。

（四）抓包工具的选择与本质区别

  • curl -i（命令行工具）：轻量、快捷。它像“手动挡汽车”，不加 -L 就不会自动跑。适合单次快速验证，强制查看 302 响应内容，也极易写成 Python 自动化脚本。
  • Burp Suite（图形化工具）：专业强大。像“手术台”，能拦截浏览器发出的所有流量，不会丢弃数据。适合修改请求头、重放攻击、跑字典爆破等复杂操作。
  • 浏览器的本质：它是一个“自动挡汽车”。为了性能，它会自动执行 JS、自动跳转、自动丢弃 302 的原始数据。所以安全测试要突破“浏览器的自动化束缚”，去查看最原始的 HTTP 报文。

（五）CTF 与 真实渗透中的跳转拓展利用

  • SSRF 打内网（高级必考）：你之前在 SSRF 题目中见过“会跟随302跳转”的提示。攻击者可以自己搭建一个 VPS，返回 302 跳转。内网服务器（SSRF 点）跟随跳转后，就会把你的恶意数据（比如内网密码）带到你的 VPS 上，这叫“数据外带”。
  • WAF 欺骗：很多 WAF 拦截你时，会返回 200 状态码并显示“请求已被拦截”，让你误以为正常。所以不要只迷信状态码，永远要读响应体。
  • 隐藏 404 页面：出题人故意让你访问一个不存在的路径，返回 404 页面。但 404 页面的源码里可能藏着 Flag 或触发了隐藏逻辑，按 F12 查看源码往往有惊喜。

四、踩坑记录

1. 找错请求：分析时选中了跳转后的 index.html 请求，导致找不到 Flag。正确做法是选中状态码为 302 的 index.php 请求查看响应头。

2. 浏览器丢弃响应体：尝试查看 302 请求的 Response 时，浏览器提示 Failed to load response data... redirected。最终改用终端 curl -i 成功获取 Flag。

3. 混淆 302 与 202/103：曾以为把 302 改成 202 也能让浏览器自动跳转，实际上 202 只会让浏览器停在原地渲染响应体。要藏 Flag 需要根据状态码的特性来针对性设计。

4. 只看响应体不看响应头：一开始只在网页画面和响应体里找 Flag，忽略了浏览器隐藏了响应头。后来通过 F12 查看响应头里的 Location 才理解了跳转逻辑，并最终在 curl 打印的响应体/头中找到了 Flag。

做一道题，就要往自己脑子里装点东西。
