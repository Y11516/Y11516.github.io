CTFHub SSRF - 302跳转 Bypass

2026年9月23日 CTFHub Web安全 SSRF 302重定向

一、题目信息

  • 题目名称：SSRF - 302跳转 Bypass
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / SSRF（服务端请求伪造） / 白名单绕过
  • 靶场链接：http://challenge-0c23bf0975b53de9.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 302 重定向配合进制转换，绕过 WAF 对内网 IP 的过滤。后端代码（WAF）只会检查用户传入的初始 URL。如果初始 URL 是合法的外网地址，WAF 会放行。随后，该外网地址返回 302 重定向，指向内网 127.0.0.1。服务器底层的 cURL 会跟随跳转，从而绕过 WAF 访问到内网资源。

2. 怎么想（破题思路）

  • 题目提示“SSRF中有个很重要的一点是请求可能会跟随302跳转，尝试利用这个来绕过对IP的检测访问到位于127.0.0.1的flag.php”。
  • 直接输入 ?url=http://127.0.0.1/flag.php 会被 WAF 拦截，提示 hacker! Ban Intranet IP。
  • 我们需要找一个合法的外网服务，它能返回 302 跳转。比如 http://httpbin.org/redirect-to?url=...。
  • 关键所在：如果外网服务直接跳转到 127.0.0.1，WAF 依然会在初始 URL 字符串中检测到 127 并拦截。因此，必须把跳转目标改为 127.0.0.1 的十进制表示形式 2130706433，从而彻底绕开 WAF 的字符串匹配。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：302 跳转链接中包含 127 被拦截

踩坑情况：尝试输入 ?url=http://httpbin.org/redirect-to?url=http://127.0.0.1/flag.php，页面直接报错 hacker! Ban Intranet IP。

原因分析：WAF 检查了完整的 URL 字符串，发现里面包含了敏感词 127，于是拦截了初始请求。

改进方式：使用十进制 IP 2130706433 替代 127.0.0.1，并将整个 URL 进行 URL 编码。

详细实操步骤（逐字解析）

在浏览器地址栏输入以下 Payload（需完整 URL 编码）：

http://challenge-0c23bf0975b53de9.sandbox.ctfhub.com:10800/?url=http%3A%2F%2Fhttpbin.org%2Fredirect-to%3Furl%3Dhttp%3A%2F%2F2130706433%2Fflag.php

Payload 逐字深度解析：

  • ?url=：后端接收的参数名。
  • http%3A%2F%2Fhttpbin.org：外部合法服务（%3A 是 :，%2F 是 /）。WAF 看到的是合法的外网地址，予以放行。
  • %2Fredirect-to%3Furl%3D：httpbin 的重定向接口，后面的 url 参数指定要跳转的目标（%3F 是 ?，%3D 是 =）。
  • http%3A%2F%2F2130706433%2Fflag.php：重定向的目标地址。使用十进制 IP 2130706433（即 127.0.0.1），完全规避了 WAF 对 127 字符串的匹配。

4. 怎么迁移（跨领域联想）

  • WAF 绕过与重定向链：在真实渗透中，如果目标 WAF 严格过滤了内网 IP，攻击者会利用短链接、CDN、云函数或开放重定向漏洞作为跳板，将 WAF 的检测点与最终的请求目标分离。
  • DNS 重绑定（DNS Rebinding）：这是 302 跳转的高级变种。攻击者控制一个域名，让它第一次解析到合法外网 IP（通过 WAF），第二次解析到内网 IP（发起真实攻击）。
  • 安全开发（SDL）：防御 SSRF 绝不能靠单次请求的字符串过滤。必须对所有的重定向进行安全校验，并限制服务器请求内网 IP 的权限。

三、名词大全与原理深度复盘

1. 302 重定向与 SSRF 的化学反应

当后端使用 cURL 请求用户指定的 URL 时，如果对方返回 302 状态码，cURL 默认会自动跟随 Location 头部去请求新地址。WAF 往往只部署在“入口”，无法审查“出口”的第一次跳转。

2. 十进制 IP 与进制转换

127.0.0.1 本质上是 32 位整数。十进制表示为 2130706433，八进制为 0177.0.0.1，十六进制为 0x7f.0.0.1。底层函数 inet_aton() 会自动识别这些格式，而 WAF 只认识字符串。

3. URL 编码（Percent-encoding）

由于我们的 Payload 本身是一个 URL，里面包含了 ?、&、= 等特殊字符，必须对它们进行 URL 编码（如 ? 变成 %3F），防止浏览器将内层参数当作外层参数来解析。

四、题目思考

1. 这跟前面的数字IP Bypass有什么区别？

  • 与“数字IP Bypass”的区别：数字IP绕过是直接绕过 WAF 检测；而 302 跳转绕过是利用了“时间差”和“空间差”——先在 WAF 放行，再由外部服务器发起跳转请求内网。
  • 与“URL Bypass”的区别：URL Bypass 利用 @ 符号欺骗解析逻辑；302 跳转绕过则是利用 HTTP 协议的重定向特性，属于两个不同层面的逻辑缺陷。

2. 这种题目的出现原因

这类漏洞源于安全防护设计的“盲区”。开发人员以为在入口处做了校验就万事大吉，忽略了内部请求在跟随跳转时，会绕过所有的外部安全检查。这本质上是对“信任边界”的误解。

3. 这种应用在实际中如何体现？

在真实红蓝对抗中，SSRF 配合 302 跳转是绕过云厂商元数据保护、访问内网 Redis 和数据库的核心手法。攻击者常利用外部云函数或开源重定向服务作为跳板，让目标服务器自己打自己。

4. 如何抽象理解概念（大白话理解）

把服务器比作大楼的安检员：

  • WAF 安检：大楼门口的安检员对访客说：“不准去内部机密档案室（127.0.0.1）”。
  • 攻击者构造：你骗安检员说：“我不去内部，我只去门口那个问询处（httpbin.org）。”安检员放你进去了。
  • 底层请求（302跳转）：你到了问询处，告诉问询处的工作人员：“请你帮我送一份快递到内部机密档案室（十进制 IP）。”工作人员不知道那是禁区，老老实实帮你把快递送了进去。
  • 结论：安检员只防住了第一道门，没防住内部的“快递员”（cURL），从而被巧妙地绕过了。
