SQLi-Labs Less-49

2026年9月29日 SQLi-Labs Web安全 SQL注入 ORDER BY 时间盲注

一、题目信息

  • 题目名称：SQLi-Labs Less-49 (GET - Error based - String - Blind - ORDER BY CLAUSE)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / ORDER BY 注入 / 时间盲注
  • 靶场链接：http://localhost:8081/Less-49/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是ORDER BY 子句中的时间盲注。Less-49 是 Less-48 的字符型变体，需要闭合单引号 '。因为页面没有回显，且无法使用报错函数，攻击者必须利用 select sleep(3) 或 if(条件, sleep(3), 0) 来制造延迟，通过响应时间差判断注入是否成功。

2. 怎么想（破题思路）

  • 页面提示 "Please input parameter as SORT with numeric value"，但标签提示 "String"，说明实际是字符型（障眼法）。
  • 闭合单引号，构造时间盲注 Payload：1', (select sleep(3))-- -。
  • 如果页面卡顿 3 秒，说明时间盲注生效。
  • 如果卡顿不明显，改用布尔盲注：1' and if(1=1,id,username)-- -，观察页面排序结果的变化。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：页面卡顿时间远超 3 秒

踩坑情况：输入时间盲注 Payload 后，页面卡顿时间长达 20 秒，远超预期的 3 秒。

原因分析：在 ORDER BY 后面执行 sleep(3) 时，数据库需要逐行扫描并进行条件判断。如果表中有 20 行数据，每一行都卡 3 秒，累积下来总耗时就会达到 60 秒。这是 ORDER BY 注入的典型现象。

改进方式：只要页面有明显延迟，就证明时间盲注成功。无需关注具体延迟秒数。

详细实操步骤（Payload逐字解释）

第一步：时间盲注测试

在浏览器地址栏输入：

http://localhost:8081/Less-49/?sort=1',%20(select%20sleep(3))--%20-

预期结果：页面卡顿（可能长达 20 秒以上），证明注入点存在。

第二步：布尔盲注验证（更推荐，不卡顿）

分别输入以下两个 URL 对比排序结果：

http://localhost:8081/Less-49/?sort=1'%20and%20if(1=1,id,username)--%20-
http://localhost:8081/Less-49/?sort=1'%20and%20if(1=2,id,username)--%20-

预期结果：第一个 URL 按 ID 排序，第二个 URL 按 USERNAME 排序。

第三步：Payload 逐字解析

  • 1'：闭合原 SQL 中的单引号。
  • ,：因为 ORDER BY 后面可以接多个字段，这里用逗号分开。
  • (select sleep(3))：子查询，强制数据库停顿 3 秒。
  • -- -：注释掉后面的 SQL 语句。

4. 怎么迁移（跨领域联想）

  • 应用场景联想：ORDER BY 注入常见于电商系统或后台管理系统的“排序”按钮。用户在点击“按价格排序”、“按销量排序”时，底层就是在执行 ORDER BY 子句。
  • 防御策略联想：对于 ORDER BY 后面的参数，绝对不能接受用户直接输入的字符串。必须使用**白名单**机制（如只允许 "price", "time", "id"），或强制转换为数字类型。
  • 安全开发启示：使用参数化查询（Prepared Statements）是防御 SQL 注入的终极方案。

三、名词大全与原理深度复盘

1. 时间盲注 (Time-Based Blind SQL Injection)

当页面没有回显位，且过滤了报错信息时，攻击者通过构造 if(条件, sleep(N), 0) 或 sleep(N) 来制造延迟。如果条件成立，页面响应时间会显著增加。

2. ORDER BY 子句

SQL 中用于对结果集进行排序的语句，可指定一个或多个字段。在注入中，它的特殊之处在于不能直接使用 UNION 和逻辑运算符。

3. 优化器短路

当数据库可以通过索引快速返回结果时，查询优化器会跳过不必要的函数执行（如 sleep()），导致盲注延迟失效。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-48 的区别：Less-48 是数字型（无需闭合），Less-49 是字符型（需要闭合单引号）。
  • 与 Less-46/47 的区别：Less-46/47 是报错注入（有回显），Less-49 是盲注（无回显）。

2. 这种题目的出现原因（为什么存在）

开发者在编写排序功能时，为了图方便，直接将用户传来的字段名拼接到 SQL 后面，并且没有对参数进行白名单校验。他们认为“只是一个排序字段，没什么危害”，从而忽略了注入风险。

3. 这种应用在实际中如何体现？

在电商网站、论坛、后台管理系统中，用户可以点击“按价格排序”、“按销量排序”。如果后端没有对排序参数做白名单校验，攻击者就能利用 ORDER BY 注入获取数据库信息。

4. 如何抽象理解概念（大白话）

把靶场比作一个“整理书架的管理员”：

  • 你告诉他：“按 ID 排序（ORDER BY id）”，他就按顺序排好。
  • 你问他：“如果 1=1 成立，就按 ID 排；否则按名字排”。
  • 他按 ID 排了，你就知道 1=1 成立。你换成 1=2，他按名字排了，你就知道 1=2 不成立。
  • 这就是布尔盲注的核心：利用状态变化来推断真相。

做一道题，就要往自己脑子里装点东西。
