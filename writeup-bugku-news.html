一段新闻 - Bugku Crypto Writeup

2026年9月12日 Bugku CTF Crypto 零宽字符隐写

这道题名为“一段新闻”，分类为 Crypto。附件是一篇看似完全正常的新闻稿，没有任何错别字或藏头诗。这其实是一道极其经典的“零宽字符隐写”与“多重编码嵌套”的题目。

一、题目信息

  • 题目名称：一段新闻
  • 题目平台：Bugku CTF
  • 题目类型：Crypto / 零宽字符隐写 / 核心价值观编码
  • 题目提示：flag{}
  • 附件内容：一段新闻.zip（解压后为 一段新闻.txt）
  • 涉及工具：Mac 终端、Python 脚本、随波逐流 CTF 工具、在线文本加密工具

二、解题过程（极其曲折的踩坑记录）

1. 识别零宽字符隐写与初步尝试

打开附件，文本内容是一篇正常的新闻稿。结合题目分类 Crypto，我判断其中隐藏了肉眼不可见的“零宽字符”。

我首先尝试用 Mac 终端创建 Python 脚本来提取零宽字符：

cat > decode_zw.py << 'EOF'
with open('一段新闻.txt', 'r', encoding='utf-8') as f:
    content = f.read()

binary = ''
for char in content:
    if char == '\u200b':      # 零宽空格 = 0
        binary += '0'
    elif char == '\u200c':    # 零宽非连字符 = 1

if binary:
    flag = ''.join([chr(int(binary[i:i+8], 2)) for i in range(0, len(binary), 8)])
    print("提取成功，Flag为：", flag)
else:
    print("没有找到零宽字符。")
EOF

但在终端输入 python3 decode_zw.py 时，出现了 IndentationError 报错。原因是使用 cat 命令在终端里创建文件时，Python 代码的缩进（空格）被系统弄丢了。随后我尝试了 pbpaste 命令直接读取剪贴板，同样失败。

2. 遭遇多重陷阱：填充位与映射反转

我改用 VS Code 编写脚本，成功抓取到了 4675 个零宽字符。但脚本报错提示“没有找到零宽字符，或者位数不是 8 的倍数”。

我分析发现：4675 除以 8 等于 584 余 3。这意味着出题人在开头或结尾添加了 3 个填充位（Padding）。尝试切掉前 3 位或后 3 位后，依然全是乱码。此外，我尝试了标准映射（\u200b=0, \u200c=1）和反向映射（\u200b=1, \u200c=0），解出来的结果（如 ö*Lyïq&}）也全是乱码。

3. 发现终极真相：核心价值观编码

查阅题目评论区并深入分析后，我恍然大悟：原来这串二进制解码后得到的是“社会主义核心价值观编码”（即一串由“富强、民主、文明”等词组成的汉字），而不是直接的 Flag。由于我之前的代码用 chr() 转换 ASCII，而汉字在 UTF-8 中占多个字节，因此必然产生乱码。

4. 使用工具成功破解

我决定使用在线工具进行多层解码：

  • 访问 http://web.fly63.com/tool/txtencrypt/，导入 一段新闻.txt，成功提取出一大串隐藏的汉字（社会主义核心价值观）。
  • 复制这串汉字，访问 https://ctf.bugku.com/tool/cvecode（Bugku 核心价值观解码工具），粘贴并解码，瞬间解出了最终的 Flag。

最终 Flag： flag{why_d0nt_you_try_t0_understand_socia1ism?}

三、知识点总结（核心复习素材）

  • 1. 零宽字符隐写：利用 Unicode 中的不可见控制字符（如 U+200B、U+200C）隐藏数据。字符虽然不可见，但真实存在于文件中。
  • 2. 填充位（Padding）：出题人常在二进制流开头或结尾添加几位无意义的 0/1，导致总位数不能被 8 整除（如本题 4675 除以 8 余 3），从而破坏正常的 ASCII 解码。需要通过尝试偏移量（Offset）来修正。
  • 3. 映射反转与标准映射：0 和 1 的映射关系并非绝对的。当标准映射解出乱码时，必须尝试反向映射。
  • 4. 多层编码嵌套：出题人往往会把真正的答案隐藏在多层编码背后（如：零宽字符 -> 二进制 -> 核心价值观编码 -> Flag）。遇到乱码时，不要怀疑方向，而是要检查是否漏掉了某层解码。
  • 5. 工具的高效性：像“随波逐流”或在线文本加密工具，能够自动识别零宽字符并一键完成多层解码，在比赛中能极大节省时间。

四、额外问题（深度反思与解答）

1. 为什么一开始会出现那么多错误的尝试？

因为这道题不是单层加密，而是一个多层嵌套的“套娃”题。一开始的尝试，其实都在试图直接解开第一层“零宽字符”就拿到最终 flag，没有意识到后面还藏着第二层编码。所以才会在“填充位”、“映射反转”这些细节上反复折腾，因为方向从一开始就不完整。

2. 为什么用终端尝试不行？

终端（命令行）和图形化工具的本质区别在于集成度。终端/Python 脚本像一把精密的手术刀，它只做你让它做的事。我们写的脚本，功能是“提取零宽字符并转换为二进制”。当它把二进制转成文本时，用的是 chr()，这只能正确显示英文、数字等 ASCII 字符。而第二层编码是汉字（如“富强”、“民主”），每个汉字在 UTF-8 编码中占多个字节，用 chr() 处理就必然变成你看到的那些乱码（如 ö*Lyïq&}）。“随波逐流”等图形化工具像一个全能工具箱，它内置了“零宽字符检测器”功能，能自动识别并提取零宽字符，更重要的是，它内置了“社会主义核心价值观编码”的解码模块，能正确识别并处理那些 UTF-8 汉字，把它们直接翻译成最终的 flag。

3. 终端或者 Python 无法解开吗？为什么那条路不通了？

能解开，但路走“窄”了。之前的 Python 脚本失败，不是因为 Python 做不到，而是因为我们写的代码只实现了“解码零宽字符”这一半的功能。它输出的 ö*Lyïq&} 虽然看起来是乱码，但恰恰是“社会主义核心价值观编码”在错误解码方式下的表现形式。如果把代码完善一下，让它输出正确的 UTF-8 字符串，再对接一个“核心价值观解码”的库（比如 qsnctf-python 库就包含此功能），Python 脚本同样能一键出 flag。所以，不是路不通，是我们当时只修了前半段路，没修后半段。

4. 拿到题目是不是要观察判断它到底怎么弄？

完全正确。这就是 CTF 解题的核心方法论。一个有效的判断流程是：

  • 先观察，找“异常”：打开文件，先看有没有明显不合常理的地方。比如你看到的“列数有七千多列”，这就是“异常”，它强烈暗示了隐藏字符的存在。
  • 根据“异常”猜类型：发现“异常”后，就要联想它可能属于哪一类。列数异常 -> 隐藏字符 -> 可能是零宽字符隐写。
  • 用工具快速验证猜想：猜出大概方向后，直接用“随波逐流”这类工具去“一键解码”验证。如果解出来是一串汉字，说明猜对了第一层，并看到了第二层的线索。
  • 层层剥离，直到终点：接着上面的发现，再次判断“这串汉字是什么编码？”，然后选择对应的工具（如核心价值观解码器）继续解，直到拿到最终的 flag{}。

5. 什么是标准映射？什么是反向映射？

  • 标准映射（Standard Mapping）：约定俗成的规则，即 \u200b 代表 0，\u200c 代表 1。绝大多数 CTF 题、开源工具和 Python 库默认使用此规则。这就好比大家习惯用“红灯停、绿灯行”。
  • 反向映射（Reverse Mapping）：出题人故意反过来，即 \u200b 代表 1，\u200c 代表 0。出题人为了增加难度，或者为了防止有人直接用自动化工具秒杀，就会故意把 0 和 1 的角色对调。这就好比交通信号灯被人改成了“红灯行、绿灯停”。如果你用标准映射去解，就会完全错位。
  • 为什么要在题目里尝试这两种？因为出题人完全自由。当你用标准映射解出一堆乱码时，不要灰心，立刻怀疑：“出题人是不是把 0 和 1 对调了？”然后马上换成反向映射再试一次。

做一道题，就要往自己脑子里装点东西。
