一、题目信息

  • 题目名称：XSS之htmlspecialchars
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 实体编码绕过 / 伪协议
  • 靶场链接：http://localhost:8080/vul/xss/xss_htmlspecialchars.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）

二、解题步骤

1. 分析题目考什么

本题的核心考点是服务器端实体编码函数 htmlspecialchars 的局限性。许多初级开发者认为只要使用了 htmlspecialchars 过滤用户输入，XSS 就被彻底防御了。本题考察的是解题者能否理解不同的 HTML 输出上下文（例如在标签属性内执行），利用伪协议或属性闭合来绕过过滤。

2. 怎么想（破题思路）

页面提示“人生之所有苦短,是因为你的xss学习的还不够好”。解题思路：

  • 先输入最标准的 Payload（如 <script>alert(1)</script>），观察页面回显，确认转义规则。发现尖括号和双引号被转义，无法创建新的标签。
  • 思考输出上下文。如果输入的数据是被放在类似 <a href="..."> 的属性中，即使不能创建新标签，我们依然可以构造 URI 伪协议。
  • 尝试提交 javascript:alert(1)，并在页面上点击生成的链接，观察是否触发 JS。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：常规 Payload 被实体编码

踩坑情况：在输入框直接提交 <script>alert(1)</script>，页面没有弹窗，而是直接显示了被转义后的字符。

原因分析：服务器使用了 htmlspecialchars($input) 函数，将 < 转义为 &lt;，导致浏览器将其识别为普通文本，无法解析为脚本标签。

改进方式：不能创建新标签时，尝试利用已存在标签的属性。观察到页面回显是在 <a href="..."> 标签中，考虑使用 Javascript 伪协议。

踩坑记录二：属性闭合错误导致无效

踩坑情况：尝试输入 ' onclick='alert(1)，页面显示“你的输入已经被记录:”，并渲染为一个超链接，但点击后没有反应。

原因分析：该 Payload 试图闭合单引号属性，但页面渲染后的上下文可能被双引号包裹，或者 onclick 事件未正确绑定到生成的标签上。此外，手动点击被渲染出的文本并不等同于点击标签本身。

改进方式：放弃依赖事件属性，直接使用 javascript: 伪协议，点击链接必然触发 JS。

终极解法：利用 Javascript 伪协议

在输入框中输入以下 Payload：

javascript:alert(1)

代码逐个符号深度解析：

  • javascript:：这是一个 URI 伪协议。与常见的 http:// 或 https:// 不同，它会告诉浏览器，后面的内容是一段需要执行的 JavaScript 代码。当该字符串出现在链接的 href 属性中，点击链接就会执行。
  • alert(1)：JavaScript 的内置弹窗函数。

点击 submit 按钮后，页面会生成一个超链接。必须手动点击该链接，浏览器会执行 javascript: 后面的 JS 代码，成功弹窗。

4. 怎么迁移（跨领域联想）

  • 业务逻辑漏洞与上下文感知：XSS 的防御不能仅靠一个函数，必须考虑输出点所处的 HTML 上下文。在 HTML 标签属性内、JS 代码块内、CSS 样式内，对特殊字符的过滤要求完全不同，这是一种“上下文感知防御”思维。
  • 客户端安全与 CSP：如果网页部署了 CSP（内容安全策略），javascript: 伪协议通常会被拦截。作为防御者，配置 CSP 是防止此类绕过的重要手段；作为攻击者，则需要寻找允许的 CDN 资源进行 JSONP 劫持或外部脚本引入。
  • Web 爬虫与 URL 协议解析：在编写爬虫时，如果直接处理页面中的 href 属性，遇到 javascript: 伪协议会导致代码错误或安全风险。必须对这种协议进行过滤，这是常见的爬虫开发安全准则。

三、名词大全与原理深度复盘

1. htmlspecialchars 函数

PHP 语言中用于将特殊字符转换为 HTML 实体的函数。默认情况下（使用 ENT_COMPAT 参数），它只转义双引号 "，不转义单引号 '，并且会将 <、>、& 转义。这意味着它能够防止直接插入新的 HTML 标签，但无法防止在已经存在的标签属性内进行注入。

2. HTML 上下文 (HTML Context)

指用户输入最终被渲染在页面 HTML 代码中的位置。常见的有：HTML 标签之间（如 <div>输入</div>）、标签属性内（如 <input value="输入">）、JavaScript 代码中（如 <script>var a = '输入';</script>）等。不同上下文需要不同的编码策略。

3. 伪协议（Pseudo-protocol / URI Scheme）

浏览器中用于处理特定任务的协议，如 mailto:（发送邮件）、tel:（拨打电话）、javascript:（执行 JS 代码）。在 XSS 攻击中，javascript: 伪协议是绕过标签转义最常见的利用手段之一。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 XSS 之过滤相比：上一题是服务端直接删除了敏感关键字，属于“黑名单”防御；本题是服务端使用了编码函数进行转义，属于“白名单/编码”防御。
  • 与 DOM 型 XSS 相比：DOM 型是前端 JS 逻辑不当导致的，服务器完全无感知；本题是服务器端对输入进行了错误的处理，导致输出到前端时防范失效。

2. 这种题目的出现原因（为什么存在）

这种题目的出现，是因为很多开发者在安全防护上存在认知盲区，认为只要用了 htmlspecialchars 就能防御所有 XSS。这忽视了输出位置的多样性。例如，当用户输入被输出在 href 属性中时，虽然括号被转义，但依然可以使用 javascript: 协议执行脚本。

3. 这种应用在实际中如何体现？

在实际的渗透测试中，如果发现页面使用 htmlspecialchars 过滤了输入，测试人员会重点寻找输出点是否处于 HTML 属性（尤其是 href 或 src）中，并尝试使用伪协议（javascript:）或者闭合属性（" onmouseover=...）来绕过过滤。这是前端安全测试的基础技能之一。

4. 如何抽象理解概念（大白话理解）

如果把网站比作一个夜总会：

  • htmlspecialchars 过滤：门卫有一个清单，看到“枪”字（尖括号）就给你用胶带贴住嘴（转义成实体），让你发不出声音（无法创建新标签）。
  • XSS 之 htmlspecialchars 绕过：既然发不出声音，你就不发出声音，而是走到吧台（<a href> 标签）前，用手指了指墙上的“紧急按钮”（javascript: 伪协议）。一按下去，警报一样会响（执行 JS）。
  • 结论：堵住了一个漏洞（标签创建），不代表堵住了所有方法（属性执行）。
