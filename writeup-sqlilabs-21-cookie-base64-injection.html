SQLi-Labs Less-21

2026年9月28日 SQLi-Labs Web安全 SQL注入 Cookie Base64注入

一、题目信息

  • 题目名称：SQLi-Labs Less-21 (POST - Dump into outfile - String)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / Cookie注入 / Base64编码
  • 靶场链接：http://localhost:8081/Less-21/（本地环境）
  • 涉及工具：Chrome浏览器 (F12 开发者工具)

二、解题步骤

1. 分析题目考什么

本题的核心考点是Cookie 中的 Base64 编码注入。Less-21 和 Less-20 一样，通过 Cookie 的 uname 字段传递数据。但区别在于，后端会先对 Cookie 值进行 base64_decode()，再拼接到 SQL 语句中。攻击者必须将 Payload 进行 Base64 编码后，再通过 Cookie 发送。

2. 怎么想（破题思路）

  • 正常登录，抓取 Cookie，发现 uname 的值是 YWRtaW4=（即 admin 的 Base64 编码）。
  • 构造注入 Payload，进行 Base64 编码。
  • 使用 F12 开发者工具或 Burp Suite 替换 Cookie 中的 uname 值。
  • 刷新页面，观察报错回显，验证注入。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：Base64 尾部符号导致 Cookie 被截断

踩坑情况：使用 Python 脚本发送 Base64 编码的 Payload，服务器响应耗时仅 0.00 秒，未触发延迟。

原因分析：Base64 编码后往往以 = 或 == 结尾。HTTP Cookie 的键值对也用 = 分隔，导致 Python 的 requests 库或后端 PHP 解析 Cookie 时出现截断，Payload 不完整。

改进方式：放弃 Python 脚本，直接在浏览器 F12 的 Application 面板中修改 Cookie，或者使用 Burp Suite 抓包修改。

详细实操步骤（Payload逐字解释）

第一步：构造并 Base64 编码 Payload

使用报错注入读取数据库名：

') and updatexml(1,concat(0x7e,(select database()),0x7e),1)-- -

对该字符串进行 Base64 编码，得到结果：

第二步：修改 Cookie

按 F12 打开开发者工具 -> Application -> Cookies -> 找到 uname，将值替换为上面的 Base64 字符串。

第三步：验证

刷新页面，如果出现 XPATH syntax error: '~security~'，说明注入成功。

4. 怎么迁移（跨领域联想）

  • 编码与解码机制：遇到 Base64、URL 编码等，要意识到这是数据的“伪装”。后端解码后仍然会拼接 SQL，因此编码只是绕过 WAF 或特征匹配的手段。
  • Cookie 安全：再次印证了 Cookie 是用户完全可控的注入点。开发者常忽略对 Cookie 值的过滤和类型检查。
  • 环境差异：Docker 环境下 MySQL 版本正常，报错注入可正常回显。遇到环境问题时，应果断跳过或使用时间盲注（如 Less-19 的教训），不要在单一关卡死磕。

三、名词大全与原理深度复盘

1. Base64 编码

一种常见的二进制到文本的编码方式，常用于 HTTP 传输中携带复杂数据。在 Web 安全中，它常被用作混淆手段。Less-21 要求将 Payload 进行 Base64 编码后通过 Cookie 发送。

2. Cookie 注入

指后端将 Cookie 中的某个字段取出，不做过滤直接拼接到 SQL 语句中。Less-21 在 Less-20 基础上增加了 Base64 解码层，考验了攻击者的编码处理能力。

3. updatexml() 报错注入

在 MySQL 5.x 环境中，利用 updatexml() 函数解析非法 XPath 字符串时的报错，将查询结果拼接在报错信息中带出。回显长度上限为 32 字节。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-20 的区别：Less-20 直接注入 Cookie 原文；Less-21 增加了 Base64 编码/解码层，需要编码 Payload。
  • 与 Less-19 的区别：Less-19 注入 Referer，Less-21 注入 Cookie。Cookie 的传输机制更稳定，不容易被空格截断。

2. 这种题目的出现原因（为什么存在）

后端为了保证 Cookie 中的数据不被轻易篡改或为了方便传输，选择了 Base64 编码。然而，Base64 并非加密，只是编码，攻击者依然可以编码恶意的 Payload 并发送。这警示我们：编码不等于安全。

3. 这种应用在实际中如何体现？

在实战中，遇到带有 Base64 特征的 Cookie（如以 = 结尾的长字符串），应尝试解码，观察明文结构，再构造对应的注入 Payload 编码后发送。

4. 如何抽象理解概念（大白话）

把靶场比作一个“翻译门卫”：

  • Less-21 的门卫精通“火星文（Base64）”。
  • 你用火星文写了一句“炸弹代码”，让门卫翻译。
  • 门卫翻译成正常语言（解码），然后照着念（拼接到 SQL 语句）。
  • 结果门卫把自己炸了（报错注入）。
