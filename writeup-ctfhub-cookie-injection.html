Cookie注入 - CTFHub Web 入门 Writeup

2026年9月18日 CTFHub Web安全 SQL注入 SQLMap

这是我做过最曲折的一道 SQL 注入题。题目提示“输入点变了，尝试找找Cookie吧”。我从 Burp Suite 的 400 报错、Python 脚本的被拦截，一路折腾到环境超时，最后用 SQLMap 一键脱库。本篇 Writeup 详细记录了这个过程，并深入对比了“手写脚本”与“自动化工具”的本质区别。

一、核心概念：什么是 Cookie 注入？

大白话比喻： HTTP 协议没有记忆。Cookie 就是服务器发给你的一张“积分卡”。后端代码信任了 Cookie 中的 id 值，直接拿去拼接 SQL 语句，导致我们可以把注入 Payload 藏在 Cookie 里发送给服务器。

二、艰难踩坑全记录

1. 踩坑一：Burp Suite 的 400 Bad Request

在 Burp Repeater 里修改 Cookie 后，一直报错 400。原因是 HTTP 头部不能有未编码的空格，且手动添加的 Content-Length 干扰了 GET 请求的解析。

正确格式： 去掉多余的 Content-Length，将空格替换为 %20，逗号替换为 %2C，即：Cookie: id=-1%20union%20select%201,2。

2. 踩坑二：Python 脚本被单引号拦截

我用 Python 脚本成功注入了 -1 union select 1,2，并查出表名 roiapnjipo。但在查列名时，使用 table_name='roiapnjipo' 一直被 WAF 拦截，返回空白。

绕过方法： 使用十六进制代替单引号，即 table_name=0x726f6961706e6a69706f。但很遗憾，此时环境刚好过期了。

3. 踩坑三：环境过期与盲目猜测

CTFHub 环境只有半小时寿命。环境过期后，任何查询都返回空。我尝试手动猜测列名 flag、data，依然无果。此时我已经陷入了极度低效的盲猜阶段。

三、终极破局：使用 SQLMap 一键脱库

放弃手写脚本，直接使用自动化工具 SQLMap。只需一条命令，告诉它注入点在 Cookie 的 id 参数里（加星号 *）：

sqlmap -u "http://challenge-xxx.sandbox.ctfhub.com:10800/" --cookie="id=1*" --dump --batch

SQLMap 自动判断出注入类型，自动猜解数据库、表名、列名，并把所有数据全部打印出来。

最终 Flag： ctfhub{d788bb7f88066c33ec7abcde}

四、深度思考：VS Code 脚本 vs SQLMap 的区别

1. 定位不同（手动挡 vs 自动挡）

  • VS Code 写 Python 脚本（手动挡）： 你需要自己构思逻辑、自己处理 Cookie、自己转换 URL 编码。适合逻辑复杂、工具无法自动识别时的定制化攻击。
  • SQLMap（自动挡）： 这是一把“万能钥匙”。它内置了海量的 Payload 字典和绕过 WAF 的规则（Tamper 脚本）。你只需要告诉它“目标在哪”，它就能自动完成探测、注入、提权、脱库的全过程。

2. 效率与稳定性的取舍

  • 手写脚本耗时极长，遇到环境过期或 WAF 拦截容易崩溃，但好处是你能清楚每一行代码在干什么。
  • SQLMap 速度极快，能自动处理空格、逗号、单引号绕过等繁杂细节。但在 CTFHub 这类短生命周期环境中，也可能因为跑太久而中途断掉。

五、SQLMap 底层原理剖析

SQLMap 是怎么知道注入点在 Cookie 的？它的探测步骤非常严谨：

  1. 探测存活与 WAF： 发送无害请求，确认目标可访问，并检查是否被防火墙拦截。
  2. 判断注入类型： 发送 id=1 AND 1=1 和 id=1 AND 1=2，对比返回页面的长度、状态码、时间差。如果存在差异，说明存在布尔盲注或时间盲注。
  3. 确定回显位： 发送 id=1 UNION SELECT 1,2,3...，观察页面哪些数字被回显，从而判断出列数和回显位置。
  4. 自动化提取： 利用 information_schema 自动查询数据库名 -> 表名 -> 列名，最后读取数据。

做一道题，就要往自己脑子里装点东西。
