Pikachu XSS - DOM型xss-x

2026年9月24日 Pikachu Web安全 XSS DOM型XSS

一、题目信息

  • 题目名称：DOM型xss-x
  • 题目平台：Pikachu 漏洞练习平台（本地环境）
  • 题目类型：Web安全 / 跨站脚本攻击（XSS） / 客户端漏洞
  • 靶场链接：http://localhost:8080/vul/xss/xss_dom_x.php（本地环境）
  • 涉及工具：Chrome浏览器、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是DOM型 XSS 的进阶利用。与普通的 DOM 型 XSS 不同，本题的输入数据是通过 URL 的 GET 参数（?text=...）传递的。后端的 JavaScript 代码使用 decodeURIComponent 解码参数后，没有经过任何安全过滤，直接将其拼接到了 innerHTML 中一个 <a> 标签的 href 属性里。我们需要闭合原有的标签属性，并注入自动触发的事件，从而绕过 innerHTML 不能执行 <script> 标签的限制。

2. 怎么想（破题思路）

  • 页面有两个触发点：一个是输入框，另一个是下方写着“有些费尽心机想要忘记的事情”的超链接。
  • 查看源码（F12 或 View Source），找到核心 JavaScript 函数 domxss()。
  • 代码逻辑：获取 URL 中的 text 参数 -> decodeURIComponent 解码 -> 替换空格 -> 拼接到 innerHTML 的 <a href='...'> 中。
  • 突破口：由于是 innerHTML，<script> 会被忽略。因此，我们需要用 '> 提前闭合原有的 <a> 标签，然后注入一个 <img> 标签，利用其 onerror 事件自动执行弹窗。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：以为输入后会自动弹窗

踩坑情况：在输入框输入 Payload 并点击“请说出你的伤心往事”按钮后，页面只是刷新并显示了一句“有些费尽心机想要忘记的事情,后来真的就忘掉了”，没有弹窗。

原因分析：输入框仅仅触发了 GET 提交，把 text 参数放入了 URL。真正的 JS 执行函数 domxss() 是绑定在下方另一个超链接的 onclick 事件上的。我们需要再点一次那个超链接才会触发。

改进方式：输入 Payload 并提交后，必须点击页面下方那句“有些费尽心机想要忘记的事情...”。

踩坑记录二：直接输入 <script> 无效

踩坑情况：尝试输入 <script>alert(1)</script>，点击按钮后无任何反应。

原因分析：innerHTML 不会执行通过字符串插入的 <script> 标签，浏览器为了安全会直接忽略它。

改进方式：使用 <img src=1 onerror=alert(1)> 标签，利用图片加载失败的报错事件来自动执行 JS。

详细实操步骤（逐字解析）

第一步：分析漏洞源码

页面中有一段核心的 JavaScript 代码：

var str = window.location.search;
var txss = decodeURIComponent(str.split("text=")[1]);
var xss = txss.replace(/\+/g,' ');
document.getElementById("dom").innerHTML = "<a href='"+xss+"'>就让往事都随风,都随风吧</a>";

代码逐字深度解析：

  • window.location.search：获取 URL 中问号后面的部分（例如 ?text=payload）。
  • str.split("text=")[1]：以 “text=” 分割字符串，取后半部分，即获取用户输入。
  • decodeURIComponent：对 URL 编码进行解码，还原特殊字符（如 %20 变回空格）。
  • replace(/\+/g,' ')：将 URL 中的 `+` 替换成空格。
  • innerHTML = "<a href='" + xss + "'>...</a>"：将用户的输入直接拼接到 `href` 属性中，这里是漏洞的根源。

第二步：构造注入 Payload

在输入框中输入以下 Payload 并提交：

'">

Payload 逐字深度解析：

  • '">：单引号和双引号闭合原来的 `href` 属性，并提前闭合 `` 标签。
  • <img：声明一张图片。
  • src=1：图片地址填写 1，必定加载失败。
  • onerror=alert(1)：加载失败时，执行 `alert(1)` 弹窗。
  • >：闭合 img 标签。

第三步：手动触发 JS 执行

提交后，页面会刷新。此时你需要点击页面下方的文字：有些费尽心机想要忘记的事情,后来真的就忘掉了。这会触发 `domxss()` 函数，将包含 Payload 的 HTML 注入到 DOM 中，弹窗随即触发。

4. 怎么迁移（跨领域联想）

  • 现代前端框架安全：在 Vue 或 React 中，直接使用 v-html 或 dangerouslySetInnerHTML 等同于使用了 innerHTML。如果渲染的是用户输入，就会造成 DOM 型 XSS。正确的做法是使用 {{ }} 或 textContent 来渲染纯文本。
  • 客户端模板注入（CSTI）：前端框架在客户端渲染模板时，如果没有正确转义，同样可能导致 XSS，这是 DOM 型 XSS 在现代前端架构中的变种。
  • 安全开发（SDL）：永远不要信任 URL 参数、Cookie 等客户端可控数据。在进行 DOM 操作时，优先使用 textContent 而非 innerHTML，并配置合理的 CSP（内容安全策略）。

三、名词大全与原理深度复盘

1. innerHTML 与 XSS

使用 innerHTML 插入内容时，浏览器会将其作为 HTML 解析并渲染。这会导致用户输入如果包含 HTML 标签，就会被浏览器当成代码执行。虽然现代浏览器会屏蔽 <script>，但 <img onerror>、<svg onload> 等标签依然可以执行 JS。

2. decodeURIComponent 函数

它是 JavaScript 中用于解码 URL 编码的函数。在本题中，它被用来将 URL 中编码后的 Payload（如 %3C 还原为 <）还原成明文，由于开发者未进行任何过滤，导致 Payload 被成功注入。

3. 为什么点击两次才触发？

因为输入框是 GET 表单，它的作用是“把数据放到 URL 里”。而真正执行 DOM 操作的函数 `domxss()` 绑定在另一个超链接的 `onclick` 事件上。因此必须分两步：第一步提交数据，第二步手动点击那个链接来触发代码执行。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与反射型/存储型 XSS 的区别：反射型和存储型 XSS 的漏洞点都在**服务器端**（服务器把数据原样输出到 HTML）。而 DOM型xss-x 的漏洞点完全在**浏览器端**（JS 代码从 URL 读取数据并写入 DOM），服务器仅仅是发送了一个静态文件。
  • 与普通 DOM型xss 的区别：普通 DOM型xss 是从输入框读取数据；而本题是从 URL 的 GET 参数读取数据，然后通过 `innerHTML` 注入到 `href` 属性中，利用的是标签闭合和事件注入。

2. 这种题目的出现原因

这类漏洞源于前端开发者对 DOM 操作的安全认知不足。开发者为了方便，直接使用 `innerHTML` 来拼接 HTML 代码，且没有对从 URL 获取的参数进行任何过滤。这给了攻击者注入恶意标签的机会。

3. 这种应用在实际中如何体现？

在真实的红蓝对抗中，DOM型 XSS 常用于绕过 WAF。因为整个攻击过程（Payload 从 URL 到 DOM）完全发生在浏览器端，Payload 可能根本不会发送到服务器（或者在 URL 的 Fragment `#` 部分），服务器端的 WAF 无法拦截。攻击者常利用它来窃取用户 Cookie，进行会话劫持。

4. 如何抽象理解概念（大白话理解）

把服务器和浏览器比作大楼的门卫和内部装修队：

  • 反射型 XSS：你把炸弹交给了大门门卫（服务器），门卫把炸弹带进了大楼并引爆。
  • DOM型xss-x：门卫（服务器）根本不在，大楼里的装修队（JavaScript 代码）拿到了一张从门缝（URL参数）塞进来的图纸，图纸上写着“在这面墙上挂个炸弹（``）”。装修队看都不看，直接就把炸弹挂上去了（执行 `innerHTML`），导致爆炸。
