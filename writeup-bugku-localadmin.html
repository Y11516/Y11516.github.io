本地管理员 - Bugku WEB Writeup

2026年9月14日 Bugku CTF WEB 源码泄露 / IP伪造 curl实战

这道题名为“本地管理员”，分类为 WEB。它是一道极其经典的 Web 综合入门题，完美串联了信息搜集（源码泄露）、Base64 解码以及HTTP 头部伪造（X-Forwarded-For 绕过 IP 限制）三个核心知识点。这篇 Writeup 极其详细地记录了我如何通过 Mac 终端一步步拿下它的过程。

一、题目信息

  • 题目名称：本地管理员
  • 题目平台：Bugku CTF
  • 题目类型：WEB / 源码泄露 / 访问控制绕过
  • 靶场链接：http://靶场地址
  • 环境：macOS
  • 涉及工具：Mac 终端（curl、base64 命令）、浏览器（F12）

二、解题过程（详细步骤与原理剖析）

1. 第一步：信息搜集，寻找隐藏的密码（源码泄露）

打开靶场，看到一个普通的“管理员系统”登录界面。在 Web 安全中，第一步永远是信息搜集。

我按下 Fn + F12（或右键点击页面空白处 -> 查看网页源代码），滚动到页面最底部，发现了一段奇怪的代码：

<!-- 提示：密码在这里 -->
<!-- dGVzdDEyMw== -->

逻辑分析：这段以 == 结尾的字符串，明显是 Base64 编码。出题人把密码写在了 HTML 的注释里，这就是典型的源码泄露漏洞。

2. 第二步：Base64 解码，获取密码

我打开 Mac 终端，利用系统自带的 base64 工具进行解码：

echo "dGVzdDEyMw==" | base64 -d

命令解释：

  • echo "..."：把字符串输出到终端。
  • |：管道符，把左边命令的输出，直接传给右边命令处理。
  • base64 -d：-d 代表 decode（解码），把 Base64 还原成普通文本。

终端瞬间输出：test123。这就是登录密码。

3. 第三步：尝试登录，遭遇 IP 拦截

我回到网页，输入用户名 admin，密码 test123 并提交。然而页面提示“IP 不正确”或“只有本地管理员才能登录”。

原理剖析：服务器在验证账号密码的同时，也校验了请求的来源 IP。它要求只有 127.0.0.1（本机回环地址）才能登录。普通的浏览器请求带着我们真实的公网 IP，所以被拒绝了。

4. 第四步：使用 curl 伪造 X-Forwarded-For 头部（核心绕过）

为了绕过 IP 限制，我们需要伪造 HTTP 请求头。在 Mac 终端中，我使用了 curl 命令来手动构造 POST 请求：

curl -X POST -H "X-Forwarded-For:127.0.0.1" http://160.202.254.160:15659/ -d "user=admin&pass=test123"

命令参数拆解：

  • -X POST：告诉服务器，这是一个提交表单的 POST 请求。
  • -H "X-Forwarded-For:127.0.0.1"：最关键的一步！ 手动添加一个 HTTP 头部，伪装我们的 IP 为本地回环地址。服务器读取到这个头部，以为请求来自本机。
  • http://...：靶场的实际 IP 和端口。
  • -d "user=admin&pass=test123"：发送 POST 数据，携带用户名和密码。

按下回车，终端瞬间打印出服务器返回的 HTML 代码，里面成功包含了最终的 Flag！

最终 Flag： flag{9c7c99563fe711f5239b4cb68a8e9b11}

三、超详细名词解释与底层逻辑

1. 什么是源码泄露？

开发者将密码、测试数据、甚至后端逻辑写在了前端 HTML 代码里（比如注释 <!-- --> 中），用户按 F12 就能看到。这是最常见的安全漏洞之一。

2. 什么是 Base64？

一种将二进制数据转换为 64 个可打印字符的“编码”方式。它不是加密算法，不需要密码就能解开，常用于在网络中传输数据。以 `==` 结尾的字符串大概率就是它。

3. 什么是 HTTP 头部（HTTP Headers）？

浏览器和服务器之间通信时，除了数据本身，还会附带一堆“元数据”（如浏览器版本、Cookie、IP 等）。X-Forwarded-For 就是其中之一。

4. 什么是 X-Forwarded-For (XFF)？为什么能绕过？

当用户的请求经过代理（如 Nginx）时，代理会在请求头里加上 XFF 字段来记录用户的真实 IP。但是，很多开发者很粗心，直接使用 XFF 来判断用户 IP，而忽略了 XFF 是客户端可以随意伪造的。因此，我们通过 curl 伪造这个字段，就成功骗过了服务器。

四、现实防御思考

这道题也给开发人员敲响了警钟：

  • 前端不可信：绝不在前端 HTML/JS 中硬编码任何密码、密钥或敏感信息。
  • 不信任客户端头部：判断用户 IP 时，应优先使用服务器变量（如 PHP 中的 $_SERVER['REMOTE_ADDR']），它直接来自 TCP 连接，无法伪造。如果需要读取代理头部，必须使用受信任的白名单配置。
