SQLi-Labs Less-53

2026年9月30日 SQLi-Labs Web安全 SQL注入 ORDER BY 堆叠注入（字符型盲注）

一、题目信息

  • 题目名称：SQLi-Labs Less-53 (GET - Error based - ORDER BY CLAUSE - string - Stacked injection)
  • 题目平台：SQLi-Labs 本地靶场（Docker 环境）
  • 题目类型：Web安全 / SQL注入 / ORDER BY 注入 / 堆叠注入 / 字符型
  • 靶场链接：http://localhost:8081/Less-53/（本地环境）
  • 涉及工具：Chrome浏览器 (地址栏直接注入)

二、解题步骤

1. 分析题目考什么

本题的核心考点是字符型 ORDER BY 子句中的堆叠注入。Less-53 是 Less-52 的字符型变体，需要闭合单引号 '。由于是盲注环境（无回显），且不支持报错注入，攻击者直接利用分号 ; 在 ORDER BY 后堆叠执行 UPDATE 语句，修改数据库中用户的密码。

2. 怎么想（破题思路）

  • 页面提示 "numeric value"，但标签是 "String"，需要闭合单引号。
  • 因为没有报错回显，且标签有 "Stacked injection"，我们直接尝试篡改数据。
  • 构造堆叠 Payload：1'; update users set password='123456' where username='Dumb';-- -。
  • 提交后，观察页面回显的用户列表，如果密码全部变成 123456，即证明注入成功。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：寻找登录框无果

踩坑情况：成功执行 Payload 后，试图寻找登录框验证新密码，但发现页面没有登录入口。

原因分析：Less-53 是纯数据展示型靶场，不涉及登录逻辑。它的目的是展示堆叠注入直接篡改数据库的能力。

改进方式：观察页面下方的数据表，只要密码字段被成功修改，即视为通关。

详细实操步骤（Payload逐字解释）

第一步：构造并发送堆叠注入 Payload

在浏览器地址栏输入：

http://localhost:8081/Less-53/?sort=1'; update users set password='123456' where username='Dumb';-- -

第二步：Payload 逐字解析

  • 1'：闭合原 SQL 中的单引号。
  • ;：结束第一条查询语句。
  • update users set password='123456' where username='Dumb'：将 Dumb 用户密码修改为 123456。
  • -- -：注释掉后面的 SQL 语句。

第三步：验证结果

页面成功回显用户列表，且密码字段显示为 123456，证明堆叠注入成功执行。

4. 怎么迁移（跨领域联想）

  • 应用场景联想：ORDER BY 注入常见于电商系统或后台管理系统的“排序”按钮。用户在点击“按价格排序”、“按销量排序”时，底层就是在执行 ORDER BY 子句。
  • 防御策略联想：对于 ORDER BY 后面的参数，绝对不能接受用户直接输入的字符串。必须使用白名单机制（如只允许 "price", "time", "id"），或强制转换为数字类型。
  • 安全开发启示：使用参数化查询（Prepared Statements）是防御 SQL 注入的终极方案。

三、名词大全与原理深度复盘

1. 堆叠注入 (Stacked Query Injection)

利用分号 ; 在同一数据库连接中执行多条 SQL 语句。常见于后端使用 mysqli_multi_query() 的 PHP 应用。

2. 盲注 (Blind SQL Injection)

当页面没有回显位，且过滤了报错信息时，攻击者无法直接看到数据。需要依靠时间延迟或页面状态变化来推断数据。

3. ORDER BY 子句注入

当后端将用户可控的参数直接拼接到 ORDER BY 后面时产生的漏洞。其特殊性在于不能直接使用 UNION 和 AND，必须使用报错函数或盲注。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-52 的区别：Less-52 是数字型，Less-53 是字符型（需闭合单引号）。
  • 与 Less-51 的区别：Less-51 有报错回显，Less-53 是纯盲注。

2. 这种题目的出现原因（为什么存在）

开发者在编写排序功能时，为了图方便，直接将用户传来的字段名拼接到 SQL 后面，并且没有对参数进行白名单校验。他们认为“只是一个排序字段，没什么危害”，从而忽略了注入风险。

3. 这种应用在实际中如何体现？

在电商网站、论坛、后台管理系统中，用户可以点击“按价格排序”、“按销量排序”。如果后端没有对排序参数做白名单校验，攻击者就能利用 ORDER BY 注入获取数据库信息。

4. 如何抽象理解概念（大白话）

把靶场比作一个“整理书架的管理员”：

  • 你告诉他：“按 ID 排序（ORDER BY id）”，他就按顺序排好。
  • 你告诉他：“按 ID 排序（1）；然后，把《Dumb》这本书的密码改成 123456”。
  • 管理员先排好序，然后真的去执行了修改密码的动作。这就是堆叠注入在盲注环境下的威力。
