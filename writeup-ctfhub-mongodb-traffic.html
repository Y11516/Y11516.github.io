二、解题步骤

1. 分析题目考什么

本题的核心考点是网络流量分析与MongoDB 数据库底层协议（BSON）的识别。MongoDB 默认监听端口为 27017。与 Redis（明文文本协议）不同，MongoDB 的通信数据采用 BSON（Binary JSON）格式传输。这要求解题者不仅需要定位到特定流量，还要学会使用 Wireshark 解析二进制协议树，或通过命令行工具提取 BSON 字段。

2. 怎么想（破题思路）

拿到附件 mongodb.pcap 后，由于 MongoDB 使用二进制协议，直接在 Wireshark 最底层的 TCP 层或者使用 strings 命令暴力搜索，很容易看到乱码或误报的假字符串。

  • 首先，使用 Wireshark 过滤器过滤 mongo 或 tcp.port == 27017，定位到 MongoDB 的查询（Query）和返回（Reply）包。
  • 由于是二进制，必须利用 Wireshark 内建的 MongoDB 协议解析器，展开协议树（BSON），直接查看被解析好的键值对数据。
  • 如果图形界面受阻，可以使用 tshark 命令行工具直接提取特定字段。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：终端 strings 暴力搜索导致误报

踩坑情况：直接使用终端命令 strings mongodb.pcap | grep -i -E "flag|ctfhub|{"，输出结果包含大量类似 A{MMMMMMMM...f 的乱码。

原因分析：strings 命令无法识别 BSON 的二进制结构。由于二进制文件中存在大量十六进制字节，例如 0x4d 在 ASCII 码表中对应大写字母 M，0x41 对应 A，0x7b 对应 {。因此，strings 会将这些物理字节强行拼接在一起，生成毫无意义的“假 Flag”。

改进方式：对于二进制协议（如 MongoDB、MySQL），严禁直接使用 strings 盲搜。必须使用支持协议解析的工具（如 Wireshark 的协议树）或使用 tshark 按字段提取。

终极解法：Wireshark 协议树精准定位

在 Wireshark 中过滤 mongo 后，找到长度较大、且协议类型为 MONGO 且 Info 显示为 Response : Reply 或 Request : Query 的包（例如某包含有 Array(200) 信息的 Reply 包）。

左键点击该包，在下方“数据包详情”窗口中，逐层展开以下节点：

  • MongoDB 节点。
  • 展开其中的 Reply 或 Query 节点。
  • 继续展开 BSON 节点（Wireshark 会自动将二进制解析为类 JSON 的树状结构）。
  • 在展开的字段值中，即可肉眼看到明文的 Flag 字段。

最终提取到的 Flag 为：ctfhub{5f284ecc279d2cbd1af258bb53c7a5f6}。

踩坑记录二：Wireshark 搜索功能配置错误

踩坑情况：在主界面按下 Ctrl + F 搜索字符串时，一直无法搜到目标内容。

原因分析：搜索框左侧的下拉菜单未修改，默认选中了 Display filter（显示过滤器）。该模式仅用于过滤数据包列表，不能用于在数据包内部搜索文本。

改进方式：将下拉菜单修改为 String（字符串），并选择 Packet bytes（分组字节流），再输入 ctfhub 进行搜索。

命令行提取方案（tshark 进阶）

如果需要在无图形界面的服务器上解题，可使用 tshark 直接提取 MongoDB 的查询和回复字段，命令如下：

tshark -r mongodb.pcap -Y "mongo" -T fields -e mongo.query -e mongo.reply

命令逐字符解析：

  • tshark：Wireshark 的命令行版本。
  • -r mongodb.pcap：-r 代表 Read，指定读取名为 mongodb.pcap 的流量包文件。
  • -Y "mongo"：-Y 代表 Display Filter，此处只过滤出 MongoDB 协议的流量包。
  • -T fields：-T 代表 Output Format，fields 表示仅输出指定的字段内容，而非完整的数据包信息。
  • -e mongo.query -e mongo.reply：-e 代表 Extract Field，此处分别提取 mongo.query（查询请求）和 mongo.reply（服务端返回）字段的数据。

4. 怎么迁移（跨领域联想）

  • Web 渗透测试：在 API 接口测试中，前后端的数据交互大量采用 JSON 格式。掌握 BSON/JSON 的解析技巧，可以在抓包改包（如使用 Burp Suite）时，快速定位和篡改数据包中的参数。
  • 物联网与工控安全：许多工业协议也使用二进制帧结构，直接使用 strings 搜索无法提取有效信息，必须依赖特定的协议解析插件或自定义脚本进行解包。
  • 无线通信安全：蓝牙、Zigbee 等无线协议的数据包分析，同样需要将二进制抓包数据转换为结构化可读数据，思路完全一致。

三、名词大全与原理深度复盘

1. MongoDB（面向文档的 NoSQL 数据库）

MongoDB 是一种非关系型数据库（NoSQL），它不使用传统的关系型表结构，而是以类似 JSON 的文档形式存储数据。由于其灵活性和水平扩展能力，在大数据和现代 Web 应用中非常流行。默认端口为 27017。

2. BSON（Binary JSON）

BSON 是 MongoDB 用来存储和传输数据的二进制格式。它是 JSON 的一种二进制编码格式，具有以下特点：

  • 轻量级：相比 JSON 文本，BSON 在序列化和反序列化时性能更好。
  • 可遍历性：在 BSON 中，每个元素的长度信息都存储在头部，这使得数据库能够快速跳过不相关的字段，提高了遍历效率。
  • 数据类型丰富：支持 date 和 binary 等 JSON 不支持的数据类型。

由于是二进制格式，人工查看十六进制字节很难直接读懂，必须借助 Wireshark 的 BSON 解析器。

3. 为什么 MongoDB 的流量题难度高于 Redis？

Redis 采用的是 RESP（REdis Serialization Protocol），本质上是一个纯文本协议，所有命令和返回结果都是人类可读的字符串（例如 SET key value）。这意味着直接使用 strings 或 TCP 流追踪就能获取信息。而 MongoDB 的 BSON 协议是二进制的，数据中夹杂着大量的长度标识符、类型标识符和不可打印字符，必须经过解析器的解析才能变成可读的 JSON 数据。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Redis 流量相比：Redis 是明文文本协议，直接追踪 TCP 流或使用 strings 即可找到 Flag；MongoDB 是二进制 BSON 协议，直接 strings 会产生大量误报，必须依赖 Wireshark 的 BSON 协议树展开，或用 tshark 提取特定字段。
  • 与 ICMP 流量相比：ICMP 流量考的是“隐写术”，需要从协议头部、数据填充、包长度等非显性区域剥离出隐藏信息；MongoDB 则是直接获取数据库通信内容，属于“内容抓取”。

2. 这种题目的出现原因（为什么存在）

现实世界中，MongoDB 曾爆发过大规模的安全事件（如 MongoDB 勒索事件）。原因在于早期版本的 MongoDB 默认监听 0.0.0.0 且无密码认证，同时使用未加密的 HTTP/BSON 协议传输数据。攻击者只需扫描 27017 端口，即可连接数据库并窃取或删除数据。流量分析题正是还原了“未加密数据库流量被网络嗅探器截获”的真实攻击场景。

3. 这种应用在实际中如何体现？

在实际的安全运维与渗透测试中，安全工程师会使用抓包工具对数据库服务器进行旁路监听。通过分析 MongoDB 的 BSON 数据流，可以发现违规查询（如未授权访问敏感集合）或恶意注入攻击（如操作符注入 $where）。同时，开发人员通过分析这些流量，可以排查接口层面的性能瓶颈和异常调用。

4. 如何抽象理解概念（大白话理解）

如果把网络传输比喻成寄快递：

  • Redis（RESP）：就像寄了一张明信片，上面直接用签字笔写着“Flag在这里，快来拿”。
  • MongoDB（BSON）：就像寄了一个特殊的压缩文件袋（二进制格式），虽然里面确实有 Flag 的字样，但你没有对应的“解压软件”（Wireshark BSON解析器），直接把袋子撕开看到的只能是一团乱码（比如一堆字母 M 和 A 拼凑的假象）。想要拿到 Flag，就必须把文件袋放进解压软件里，才能看清里面的真实档案。
