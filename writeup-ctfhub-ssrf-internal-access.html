CTFHub SSRF - 内网访问

2026年9月22日 CTFHub Web安全 SSRF 内网探测

一、题目信息

  • 题目名称：内网访问（SSRF）
  • 题目平台：CTFHub 技能树
  • 题目类型：Web安全 / SSRF（服务端请求伪造）
  • 靶场链接：http://challenge-73fb72c67b2bb784.sandbox.ctfhub.com:10800（动态环境）
  • 涉及工具：Chrome浏览器

二、解题步骤

1. 分析题目考什么

本题的核心考点是SSRF（服务端请求伪造）漏洞。服务器提供了一项根据用户传入的 URL 获取内容的功能，但未对该 URL 进行严格校验。攻击者可以利用这一点，让服务器去请求内部资源（如 127.0.0.1 上的文件），从而绕过外网访问限制，获取内网敏感信息。

2. 怎么想（破题思路）

  • 页面直接白屏，但 URL 参数是 ?url=_，说明服务器会请求这个地址。
  • 题目提示明确：“尝试访问位于 127.0.0.1 的 flag.php 吧”。
  • 我们无法直接访问服务器内网的 127.0.0.1，但服务器自己可以。所以需要让服务器去访问 http://127.0.0.1/flag.php，并把结果返回给我们。
  • 构造 Payload：?url=http://127.0.0.1/flag.php。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：误认为环境没开或页面坏了

踩坑情况：刚打开页面，看到一片空白，以为服务挂了或环境报错。

原因分析：题目属于 SSRF 类型，参数 ?url=_ 是默认占位符，服务器请求失败自然没有回显。

改进方式：需要主动构造有效的 URL 参数，引导服务器去请求目标资源。

踩坑记录二：直接访问 http://127.0.0.1/flag.php 失败

踩坑情况：在自己的浏览器直接输入 http://127.0.0.1/flag.php，发现无法访问。

原因分析：127.0.0.1 是本地回环地址，指的是用户自己的电脑，而不是服务器。用户的电脑上没有这个文件。

改进方式：必须将 http://127.0.0.1/flag.php 作为参数值传递给服务器，由服务器代为访问。

详细实操步骤（逐字解析）

第一步：构造 Payload

在浏览器地址栏输入：

http://challenge-73fb72c67b2bb784.sandbox.ctfhub.com:10800/?url=http://127.0.0.1/flag.php

Payload 逐字深度解析：

  • ?url=：传递给服务器的参数，告诉服务器“请帮我请求这个地址”。
  • http://：指定协议为 HTTP。
  • 127.0.0.1：本地回环地址，指代服务器自身。
  • /flag.php：服务器内部存放 Flag 的文件路径。

第二步：获取回显

服务器收到请求后，会代替我们去访问 http://127.0.0.1/flag.php，并将获取到的内容原样返回。页面直接回显明文 Flag。

备选方案（当 127.0.0.1 被过滤时）：

  • 使用 localhost：?url=http://localhost/flag.php
  • 使用短地址 127.1：?url=http://127.1/flag.php
  • 使用内网网段 IP：?url=http://0.0.0.0/flag.php
  • 使用 file:// 伪协议：?url=file:///var/www/html/flag.php

4. 怎么迁移（跨领域联想）

  • 内网端口扫描：攻击者可以利用 SSRF 请求内网主机的不同端口（如 22、3306、6379），通过响应时间或报错信息判断端口是否开放。
  • 云环境元数据泄露：在云服务器（AWS、阿里云等）中，SSRF 可以用于访问 http://169.254.169.254/latest/meta-data/，窃取临时的云凭证（AK/SK），从而接管整个云账号。
  • 攻击内网应用：利用 SSRF 攻击内网中未授权的 Redis、Memcached、Jenkins 等服务，实现 RCE。

三、名词大全与原理深度复盘

1. SSRF（Server-Side Request Forgery）

服务端请求伪造。是一种由攻击者构造请求，由服务端发起请求的安全漏洞。攻击者利用服务器可以访问内网的优势，让服务器成为攻击内网的“跳板”。

2. 为什么服务器能访问 127.0.0.1 而我们不能？

127.0.0.1 是本地回环地址，指向机器自身。在 Web 服务部署中，许多内部服务（如管理后台、数据库）只监听在 127.0.0.1 上，外部用户无法直接访问。但 Web 服务器本身具有访问权限，SSRF 正是利用了这一信任关系。

3. SSRF 与 CSRF 的区别

CSRF（跨站请求伪造）是攻击者利用**用户**的浏览器发起恶意请求；SSRF 是攻击者利用**服务器**发起恶意请求。前者攻击的是用户，后者攻击的是服务器内网。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与文件包含（LFI/RFI）的区别：文件包含是直接引入文件并执行代码；SSRF 是让服务器发起 HTTP 请求，获取远程资源的内容，通常是读取，而非执行。
  • 与命令注入的区别：命令注入是直接执行系统命令；SSRF 是利用服务器的网络功能，构造网络请求，攻击面从“系统”转向了“网络”。

2. 这种题目的出现原因

开发人员在实现类似“图片加载”、“网页翻译”、“URL 预览”等功能时，直接使用了用户传入的 URL 发起请求，未对 URL 进行协议限制（如只允许 http/https）和黑名单过滤（如禁止访问 127.0.0.1、192.168 等内网网段）。

3. 这种应用在实际中如何体现？

在真实红蓝对抗中，SSRF 是突破边界、进入内网的利器。攻击者常利用 SSRF 探测内网拓扑、攻击内网应用、获取云环境凭证。企业防御需对 URL 进行白名单校验，并限制服务器访问内网资源的权限。

4. 如何抽象理解概念（大白话理解）

把服务器比作一个传令兵：

  • 正常流程：你站在大门外，想让传令兵去仓库（内网）拿一份文件。但你进不去仓库。
  • SSRF 漏洞：你骗传令兵：“帮我去外面那家店（你构造的恶意 URL）取个东西”，传令兵照做了，但其实你让它去的是“仓库”（127.0.0.1/flag.php）。
  • 结果：传令兵成功进入仓库，拿到了你想要的 Flag，并原路带回来交给了你。你成功利用传令兵的权限，越过了物理边界的限制。
