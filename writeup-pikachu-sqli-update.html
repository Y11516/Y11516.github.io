SQL-Inject insert/update注入 - Pikachu Writeup

2026年9月19日 Pikachu Web安全 SQL注入

一、题目信息

  • 题目名称：SQL-Inject insert/update注入
  • 题目平台：Pikachu 漏洞练习平台
  • 题目类型：Web安全 / SQL注入 / 数据篡改 / UPDATE语句注入
  • 靶场链接：http://localhost:8080/vul/sqli/sqli_iu/sqli_login.php（本地 Docker 环境）
  • 涉及工具：浏览器（Chrome/Firefox）、开发者工具（F12）

二、解题步骤

1. 分析题目考什么

本题的核心考点是利用 UPDATE 语句的 SQL 注入进行数据篡改（水平越权）。与之前 SELECT 查询获取数据的注入不同，本题的漏洞点隐藏在“修改个人信息”功能中。后端代码通常使用 update users set email='$email' where username='$username' 的结构，如果用户输入未经过滤，攻击者可以通过闭合单引号并追加新的 where 条件，从而修改其他用户（如管理员）的数据。

2. 怎么想（破题思路）

页面是一个登录页。解题思路如下：

  • 由于是 insert/update 注入，必须先注册一个普通账号（如 test / 123456）并登录。
  • 进入“修改个人信息”页面，找到可控的输入点（如邮箱框）。
  • 测试单引号 ' 是否引发报错，确认注入点。
  • 构造能闭合单引号、并在修改自己信息的同时，额外篡改管理员（admin）信息的 Payload。

3. 怎么解（详细步骤与踩坑记录）

踩坑记录一：尝试篡改密码字段引发 Unknown column 报错

踩坑情况：在邮箱框输入 test@123.com', password='123456' where username='admin'# 提交后，页面报错 Unknown column 'password' in 'field list'。

原因分析：本地 Docker 镜像的数据库中，用户表可能并未将密码字段命名为 password，或者该字段不在当前的 UPDATE 逻辑范围内。

改进方式：遇到未知字段名报错，应更换一个必定存在的字段（如 email）进行验证。这属于环境差异导致的常见报错，不必死磕，证明漏洞存在即可。

踩坑记录二：Payload 结构不完整无法越权

踩坑情况：只在邮箱框输入 test@123.com'，页面只会修改自己的信息，无法实现对 admin 的篡改。

原因分析：闭合单引号只是第一步，还需要构造合法的 SQL 语法，拼接 where 条件来绕过原有的用户限制（where username='test'）。

改进方式：构造完整的注入链：test@123.com', email='hacked@evil.com' where username='admin'#，将闭合、新赋值、越权条件与注释符拼接在一起。

终极解法：利用 UPDATE 注入篡改管理员信息

登录后，在“修改个人信息”页面的邮箱输入框中填入以下 Payload：

test@123.com', email='hacked@evil.com' where username='admin'#

代码逐个符号深度解析：

  • test@123.com：正常的邮箱输入，用于填补原有参数。
  • '：单引号，闭合后端 SQL 语句中的前引号，完成第一次逃逸。
  • ,：逗号，用于结束当前的赋值，准备追加新的赋值。
  • email='hacked@evil.com'：新追加的恶意赋值语句，意图将邮箱改为指定值。
  • where username='admin'：越权条件。原本后端代码末尾有 where username='$username'，加上这个条件后，SQL 引擎会被诱导修改 admin 的数据。
  • #：MySQL 注释符，将后端原代码末尾的 where username='test' 注释掉，保证前面的注入语句生效。

提交后，页面提示“修改成功”，证明你成功利用 UPDATE 注入篡改了 admin 用户的邮箱，完成了水平越权攻击。

4. 怎么迁移（跨领域联想）

  • IDOR（不安全的直接对象引用）与水平越权：本题本质上是利用 SQL 注入实现水平越权（修改同级用户的资料）。在开发中，不仅要防注入，还要在逻辑层严格校验“当前用户是否有权修改目标数据”。
  • 代码审计：白盒审计时，应重点关注所有执行 UPDATE 和 INSERT 语句的代码。如果这类语句直接拼接了未过滤的用户输入，且没有使用参数化查询，即为高危漏洞。
  • WAF 绕过：在真实攻防中，修改数据的注入往往拦截更严。可以尝试使用 /*!50000update*/ 内联注释、大小写混淆、或 URL 编码等方式绕过 WAF 对 update 和 where 的拦截。

三、名词大全与原理深度复盘

1. INSERT/UPDATE 注入与 SELECT 注入的区别

SELECT 注入是“读”数据，攻击者试图通过查询获取敏感信息；而 INSERT/UPDATE 注入是“写”数据，攻击者篡改数据库内容（如改密码、改余额、改权限）。从危害程度上讲，数据篡改往往比单纯的数据泄露更严重，可能导致业务瘫痪。

2. 为什么 UPDATE 注入无法直接回显数据？

UPDATE 语句通常没有查询结果集回显，因此不能使用 union select 来拖库。攻击者通常采用布尔盲注或时间盲注，或者像本题一样，利用 UPDATE 直接修改数据，通过登录验证来确认攻击是否成功。

3. 水平越权与垂直越权

水平越权是同级用户之间的越权（如用户 A 修改用户 B 的资料）；垂直越权是低权限用户获取高权限用户的功能（如普通用户修改管理员密码）。本题通过 SQL 注入修改 admin 的邮箱，属于利用注入漏洞实现的垂直越权尝试。

四、题目思考

1. 这跟前面的题有什么区别？

  • 与查询型注入相比：之前的字符型、数字型等均是在“查数据”，目的是获取信息；本题是在“改数据”，目的是篡改数据库内容，攻击的破坏力更直接。
  • 与 CSRF 相比：CSRF 是借用受害者的身份去改数据；本题是攻击者直接构造注入语句，通过数据库漏洞去改任意用户的数据，不需要受害者的配合（不需要点击链接）。

2. 这种题目的出现原因（为什么存在）

这类漏洞的出现，是因为开发者在编写修改信息的业务逻辑时，仅通过字符串拼接的方式构造 UPDATE 语句，且没有对修改的目标进行权限校验。使得用户不仅能修改自己的信息，还能通过注入追加 where 条件，越权修改他人的信息。

3. 这种应用在实际中如何体现？

在真实的渗透测试中，如果发现修改个人资料的接口存在注入，攻击者可以尝试通过构造 where username='admin' 来修改管理员的密码或邮箱。一旦成功，就能通过密码找回功能或直接登录接管管理员账号，从而拿下整个网站后台。

4. 如何抽象理解概念（大白话理解）

如果把数据库比作一个档案室的管理员：

  • 正常操作：你（test）去改自己的档案。你在申请表上填：“把邮箱改为 test@123.com”（update users set email='test@123.com' where username='test'）。
  • 攻击操作：你在填表时，偷偷在后面加了一行字：“把邮箱改为 test@123.com，顺便把管理员（admin）的邮箱改为 hacked@evil.com，至于我刚才说的“改我自己”那句话，不算数（#）”。
  • 死脑筋的管理员（有漏洞的代码）照本宣科，真的把管理员的邮箱也给改了。这就是 UPDATE 注入的威力——借自己的壳，改别人的档案。
